# 13장. 검색어 자동완성 시스템

> 📝 **Notion 원본**: https://app.notion.com/p/2dd1853e6fda423598f2b478574d6f05

> 🧩 **한 줄 요약** — DAU 1,000만, 입력한 접두어로 **인기순 상위 5개** 검색어를 100ms 안에 돌려주는 시스템. DB `LIKE` 조회는 데이터가 커지면 병목이라 **트라이(trie)** 를 쓰고, **접두어 길이 제한 + 노드마다 인기 검색어 캐시**로 조회를 O(1)로 낮춘다. 데이터 수집은 **로그 → 취합(주 1회) → 작업 서버가 트라이 생성 → 트라이 DB·트라이 캐시**로 비동기 처리, 질의는 **LB → API 서버 → 트라이 캐시(없으면 DB)**. 커지면 **과거 질의 패턴 기반 샤딩**.

## 1. 요구사항 & 규모

| 구분 | 내용 |
|---|---|
| **기능** | 입력 단어 = 검색어의 **첫 부분(접두어)** · 자동완성 **5개** · **인기 순위** 기준 · 영어 + 다국어 · 모두 소문자 가정 · DAU 1,000만 |
| **비기능** | 빠른 응답(**100ms 이내**) · 연관성 · 정렬(인기도 등 순위 모델) · 규모 확장성 · 고가용성 |

**개략적 규모 추정**
- 사용자당 하루 10건 검색, 질의당 평균 **20바이트**(ASCII, 4단어 × 5글자).
- 글자 입력마다 요청 → 1회 검색당 평균 **20건** 요청.
- QPS ≈ 10,000,000 × 10 × 20 / 24시간 / 3600초 ≈ **24,000**, 최대 QPS ≈ **48,000**.
- 질의 중 20%가 신규 검색어라 가정 → 매일 약 **0.4GB** 신규 데이터(400,000,000바이트).

## 3. 트라이 자료구조 ⭐

- 문자열을 간략하게 저장하는 **트리 형태** 자료구조. 루트 = 빈 문자열, 각 노드 = 글자 하나(자식 최대 26개), 각 노드는 하나의 단어 또는 접두어를 나타냄.

[🖼️ 원본 이미지: 트라이 자료구조]
[🖼️ 원본 이미지: 빈도 정보를 저장한 트라이 구조]

- 기호: **p** = 접두어 길이, **n** = 트라이 노드 수, **c** = 주어진 노드의 자식 노드 수.

| 단계 | 작업 | 시간 복잡도 |
|---|---|---|
| 1 | 접두어를 표현하는 노드 찾기 | O(p) |
| 2 | 그 노드의 하위 트리를 탐색해 모든 유효 노드 찾기 | O(c) |
| 3 | 유효 노드 정렬해 상위 k개 고르기 | O(c log c) |

[🖼️ 원본 이미지: k=2, 'be' 입력 시 알고리즘 동작]
- 예) k=2, `be` 입력 → 노드 `be` 찾기 → 유효 노드 beer, best, bet → 정렬 후 **best, bet**.
- 총 O(p) + O(c) + O(c log c), 최악엔 **전체 트라이 탐색**. 최적화 두 가지:

| 최적화 | 내용 | 장단점 |
|---|---|---|
| **접두어 최대 길이 제한** | 긴 검색어는 거의 없으니 p를 작은 정수로 가정 | 접두어 노드 찾기 → **O(1)** |
| **노드에 인기 검색어 캐시** | 각 노드에 상위 k개 저장 → 전체 탐색 방지 | 👍 조회 시간 크게 감소 / 👎 노드마다 저장 공간 많이 필요 · 최고 인기 검색 → **O(1)** |

## 4. 데이터 수집 서비스 (상세)

[🖼️ 원본 이미지: 데이터 분석 서비스의 수정된 설계안]

| 컴포넌트 | 역할 |
|---|---|
| **데이터 분석 서비스 로그** | 검색창 입력 질의의 원본 보관. **추가만** 되고 수정 없음 |
| **로그 취합 서버** | 시스템이 소비하기 쉽게 취합. 실시간성이 중요하면 주기 단축, 대부분 **주 1회**면 충분 |
| **취합된 데이터** | query · time(그 주 시작 날짜) · frequency(그 주 사용 횟수 합) |
| **작업 서버** | 주기적 비동기 작업. **트라이를 만들어 트라이 DB에 저장** |
| **트라이 캐시** | 분산 캐시로 트라이를 메모리에 유지 → 읽기 성능↑. **매주 트라이 DB 스냅샷**으로 갱신 |
| **트라이 DB** | 지속성 저장소. **문서 저장소**(트라이 직렬화 저장) 또는 **키-값 저장소**(키: 접두어, 값: 노드의 모든 데이터) |

매주 취합한 데이터 예:

| query | time | frequency |
|---|---|---|
| tree | 2023-10-01 | 12000 |
| tree | 2023-10-08 | 15000 |
| toy | 2023-10-01 | 850 |
| toy | 2023-10-09 | 6256 |

[🖼️ 원본 이미지: 트라이를 키-값 저장소(해시 테이블)로 변환]

> **요약** — 로그를 매주 취합 → 작업 서버가 비동기로 트라이 DB에 넣음 → 읽기가 많으니 트라이 캐시에 올려둠 → 트라이 DB로는 문서 혹은 키-값 DB가 좋다.

## 5. 질의 서비스 (상세)

[🖼️ 원본 이미지: 비효율성을 개선한 질의 서비스 설계안]

1. 검색 질의가 **로드밸런서**로 → 2. LB가 **API 서버**로 → 3. API 서버가 **트라이 캐시**에서 데이터를 가져와 응답 구성 → 4. 캐시에 없으면 **DB에서 가져와 캐시에 채움**.

| 최적화 | 내용 |
|---|---|
| **AJAX 요청** | 페이지 새로고침 없이 백그라운드로 **필요한 데이터(JSON)만** 받아옴 |
| **브라우저 캐싱** | 구글은 검색어를 **1시간** 캐시. `tw` → 백스페이스 → 다시 `tw` 시 두 번째는 바로 표시 → API 서버 트래픽 원천 차단 |
| **데이터 샘플링** | N개 요청 중 1개만 로깅 → 로깅 서버 디스크 I/O 병목·저장 비용 감소 |

## 6. 트라이 연산 & 저장소 확장

- **트라이 생성** — 작업 서버 담당. 분석 서비스 로그나 DB의 취합 데이터 이용.
- **트라이 갱신** — ① **매주 새 트라이로 교체** ② 노드 개별 갱신(성능은 나쁘지만 작은 트라이면 고려할 만).
- **검색어 삭제** — 트라이 캐시 앞에 **필터 계층**을 둬 부적절한 질의어 반환 차단, **물리적 삭제는 다음 업데이트 사이클에 비동기**로.

[🖼️ 원본 이미지: 트라이 캐시 앞의 필터 계층]

- **저장소 규모 확장** — 한 서버에 안 들어가면 샤딩. 영어만이면 **첫 글자 기준 샤딩**도 가능하지만, **과거 질의 패턴을 분석해 샤딩**하고 **검색어 대응 샤드 관리자**가 어떤 검색어가 어느 서버에 있는지 관리.

- 빈도 테이블에 기록된 수치를 사용해 상위 5개의 검색어를 반환한다.
  - `tw` 검색: twitter, twitch, twillight, twin peak, twitch prime

- 가장 인기있는 5개 질의문을 골라내는 방안으로 사용한다.

[🖼️ 원본 이미지: 트라이 자료구조]

트라이 자료구조
- 트라이는 트리 형태의 자료구조다.
- 이 트리의 루트 노드는 빈 문자열을 나타낸다.
- 각 노드는 글자 하나를 저장하며, 26개의 자식 노드를 가질 수 있다.
- 각 트리 노드는 하나의 단어, 또는 접두어 문자열을 나타낸다.

[🖼️ 원본 이미지: 빈도 정보를 저장한 트라이 구조]

빈도 정보를 저장한 트라이 구조
- p: 접주어의 길이
- n: 트라이 안에 있는 노드 개수
- c: 주어진 노드의 자식 노드 개수
- 가장 많이 사용된 질의어 k개는 다음과 같이 찾을 수 있다.
  - 해당 접두어를 표현하는 노드를 찾는다. (시간복잡도 O(p))
  - 해당 노드부터 시작하는 하위 트리를 탐색하여 모든 유효 노드를 찾는다. (시간복잡도 O(c))
  - 유효 노드들을 정렬하여 가장 인기 있는 검색어 k개를 찾는다. (시간복잡도 O(clogc))

[🖼️ 원본 이미지: k=2, be 입력 시 알고리즘 동작]

k=2이고 사용자가 검색창에 be을 입력했을 때, 알고리즘 동작
1. 접두어 노드 be를 찾는다.
2. 해당 노드부터 시작하는 하위 트리를 탐색하여 모든 유효 노드를 찾는다. (beer, best, bet)
3. 유효 노드를 정렬하여 2개만 골라낸다. (best, bet)

- 총 시간 복잡도: O(p) + O(c) + O(clogc)
- 최악의 경우 전체 트라이를 다 검색해야 한다. 최적화 방안은 다음과 같다.
  - 접두어의 최대 길이를 제한
  - 각 노드에 인기 검색어를 캐시

> ***접두어의 최대 길이 제한***

- 사용자가 검색창에 긴 검색어를 입력하는 일은 거의 없기 때문에, p값은 작은 정숫값으로 가정해도 안전하다.

> ***노드에 인기 검색어 캐시***

- 각 노드에 k개 인기 검색어를 저장해두면 전체 트라이를 검색하는 일을 방지할 수 있다.
- 👍 검색어를 질의하는 시간 복잡도를 엄청나게 낮출 수 있다.
- 👎 각 노드에 질의어를 저장할 공간이 많이 필요하게 된다.

최적회 기법을 적용하면?
- 접두어 노드 시간 복잡도 : O(1)
- 최고 인기 노드 시간 복잡도 : O(1)

[🖼️ 원본 이미지: 최적화 기법을 적용한 트라이]

*데이터 수집 서비스*

[🖼️ 원본 이미지: 데이터 분석 서비스의 수정된 설계안]

데이터 분석 서비스의 수정된 설계안

> ***데이터 분석 서비스 로그***

- 검색창에 입력된 질의에 관한 원본 데이터가 보관된다.
- 데이터는 추가만 되고, 수정은 일어나지 않는다.

> ***로그 취합 서버***

- 데이터를 잘 취합하여 시스템이 쉽게 소비할 수 있도록 한다.
- 결과를 빨리 보여주는 것이 중요할 경우, 데이터 취합 주기를 보다 짧게 가져간다.
- 대부분의 경우 일주일에 한 번 정도로 로그를 취합해도 충분하다.

> ***취합된 데이터***

| query | time | frequency |
|---|---|---|
| tree | 2023-10-01 | 12000 |
| tree | 2023-10-08 | 15000 |
| toy | 2023-10-01 | 850 |
| toy | 2023-10-09 | 6256 |

매주 취합한 데이터의 사례
- time 필드는 해당 주가 시작한 날짜를 나타낸다.
- frequency 필드는 해당 질의가 해당 주에 사용된 횟수의 합이다.

- 요약
  - 데이터를 취합하고
  - 그 로그들을 매주 마다 취합하고
  - 그걸 작업 서버에 넣어서 서버가 비동기적으로 트라이 DB에 넣을 수 있도록 하면되고
  - 읽기가 많으니까 트라이 DB 속 트라이 캐시에 취합한 로그 정보를 올려 놓는다는 거고
  - 트라이DB로는 문서 혹은 키-값 DB 가 좋다

> ***작업 서버***

- 주기적으로 비동기적 작업을 실행하는 서버 집합
- 트라이 자료구조를 만들고 트라이 데이터베이스에 저장하는 역할을 담당한다.

> ***트라이 캐시***

- 분산 캐시 시스템으로 트라이 데이터를 메모리에 유지하여 읽기 연산 성능을 높이는 구실을 한다.
- 매주 트라이 데이터베이스의 스냅샷을 떠서 갱신한다.

> ***트라이 데이터베이스***

- 지속성 저장소
- 사용할 수 있는 선택지는 2가지 있다.
  - 문서 저장소: 주기적으로 트라이를 직렬화하여 데이터베이스에 저장할 수 있다.
  - 키-값 저장소: 해시 테이블 형태로 변환 가능하다.(키: 접두어, 값: 노드에 보관된 모든 데이터)
    - [🖼️ 원본 이미지: 트라이를 해시 테이블로 변환]

*질의 서비스*

[🖼️ 원본 이미지: 비효율성을 개선한 새 설계안]

해당 설계안의 비효율성을 개선한 새 설계안
1. 검색 질의가 로드밸런서로 전송된다.
2. 로드밸런서는 해당 질의를 API 서버로 보낸다.
3. API 서버는 트라이 캐시에서 데이터를 가져와 해당 요청에 대한 자동완성 검색어 제안 응답을 구성한다.
4. 데이터가 트라이 캐시에 없는 경우에는 데이터를 데이터베이스에서 가져와 캐시에 채운다.

질의 서비스의 최적화 방안은 다음과 같다.
- AJAX 요청 (웹 새로고침 X)
  - 웹페이지 전체를 다시 불러오지 않고, 브라우저가 백그라운드에서 서버와 통신하여 **필요한 데이터(JSON)만 몰래 받아오는 기술**
- 브라우저 캐싱 (구글은 검색어를 1시간동안 캐시해 둠)
  - 서버가 응답을 줄 때 "이 데이터는 1시간 동안 안 변하니까, 다음에 또 필요하면 나한테 묻지 말고 네 브라우저 창고에서 꺼내 써
  - 'tw'를 쳤다가, 실수로 백스페이스를 누르고 다시 'tw'를 치는 경우 두 번째 요청은 바로 보여주기<br>API 서버로 향하는 트래픽 자체를 원천 차단
- 데이터 샘플링 (N개 요청 가운데 1개만 로깅)
  - 타이핑하는 모든 검색 기록 다 저장 안하기 로깅 서버의 디스크 I/O 병목과 저장 용량 비용 감소
