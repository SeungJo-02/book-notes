# 11장. 뉴스 피드 시스템 설계

> 📝 **Notion 원본**: https://app.notion.com/p/621cba1606f34ef3bf703b9965d41164

> 🧩 **한 줄 요약** — 인스타처럼 친구 포스팅을 **시간 역순**으로 모아 보여주는 피드. 시스템을 **발행(쓰기)**과 **읽기**로 나눠 설계하고, 핵심은 **팬아웃(fanout) — 쓰기 때 미리 뿌리는 push vs 읽을 때 모으는 pull**의 선택이다. 대부분 사용자는 **push**로 빠르게, 팔로워가 폭발하는 셀럽은 **pull**로(핫키 방지) → **하이브리드**. 팬아웃은 메시지 큐로 비동기 처리하고, 캐시는 **5계층**으로 쪼갠다.

| 컴포넌트 | 역할 |

## 4. 팬아웃 — push vs pull ⭐

**팬아웃** = 한 사용자의 새 포스팅을 그와 친구인 **모든 사용자에게 전달**하는 과정. 이 시스템의 심장.

| 기준 | **push (쓰기 때 팬아웃)** | **pull (읽기 때 팬아웃)** |
|---|---|---|
| 언제 갱신 | 포스팅하는 **순간** 친구 피드 캐시에 기록 | 사용자가 피드를 **열 때** 모아서 생성 |
| 읽기 속도 | **빠름**(이미 만들어둠) | 느림(그때 계산) |
| 단점 | 친구 많으면 갱신에 시간↑(**핫키**), 비활성 사용자 피드까지 갱신 → **자원 낭비** | 읽기 지연↑ |
| 유리한 대상 | 일반 사용자 | 비활성·거의 로그인 안 하는 사용자 |

> 🔑 **하이브리드가 정답** — 대부분은 **push**(빠른 조회). **친구/팔로워가 아주 많은 셀럽은 pull**(포스팅을 필요할 때만 가져가 시스템 과부하 방지). 요청·데이터는 **안정 해시**로 고르게 분산해 핫키를 줄인다.

## 5. 피드 발행 상세 흐름

[🖼️ 원본 이미지: 피드 발행 흐름 상세]

- **웹 서버** — 인증·**처리율 제한** 수행. 스팸·유해 콘텐츠 방지를 위해 **기간당 포스팅 수 제한**.
- **팬아웃 동작 과정**

[🖼️ 원본 이미지: 팬아웃 동작 과정]

1. **그래프 DB**에서 친구 ID 목록을 가져온다.
2. **사용자 정보 캐시**에서 친구 정보를 가져와 설정에 따라 일부를 걸러낸다(예: mute).
3. 친구 목록 + 새 포스팅 ID를 **메시지 큐**에 넣는다.
4. **팬아웃 작업 서버**가 큐에서 꺼내 **뉴스 피드 캐시**에 넣는다. (메모리 효율 위해 **포스팅/사용자 ID만** 저장, 크기 제한)

## 6. 피드 읽기 상세 흐름

[🖼️ 원본 이미지: 피드 읽기 흐름 상세]

1. 사용자가 피드 요청(`/v1/me/feed`)
2. 로드밸런서 → 웹 서버 하나로 전송
3. 웹 서버 → **뉴스 피드 서비스** 호출
4. 뉴스 피드 서비스 → **뉴스 피드 캐시**에서 **포스팅 ID 목록** 획득
5. 사용자 이름·사진·포스팅 내용·이미지 등을 **사용자 캐시·포스팅 캐시**에서 가져와 **완전한 피드** 생성
6. **JSON**으로 클라이언트에 전송 → 렌더링

<details>
<summary>상세 설명</summary>

뉴스 피드 서비스가 피드 캐시에서 **포스트 ID + 사용자 ID**를 받아, 그 ID로 사용자·포스트 정보 캐시(DB)를 조회해 단말기로 뿌린다. **정적 이미지는 브라우저에서 JS가 실행될 때 CDN에서** 가져온다.

</details>

## 7. 캐시 5계층

피드 시스템의 핵심. 용도별로 나눠 캐시한다.

| 계층 | 보관 내용 |
|---|---|
| **뉴스 피드** | 피드의 **ID** |
| **컨텐츠** | 포스팅 데이터(인기 콘텐츠는 별도) |
| **소셜 그래프** | 사용자 간 관계 |
| **행동** | 좋아요·답글 등 사용자 행위 |
| **횟수** | 좋아요 수·응답 수·팔로워/팔로잉 수 |

## 🔁 셀프 체크
1. 팬아웃 push 모델과 pull 모델의 갱신 시점과 트레이드오프는?
2. 팔로워가 아주 많은 셀럽에게는 왜 pull이 유리한가?
3. 뉴스 피드 캐시에 포스팅 전체가 아니라 **ID만** 저장하는 이유는?

<details>
<summary>답</summary>

1. **push**는 포스팅하는 순간 친구 피드를 갱신 → 읽기가 빠르지만 친구 많으면 갱신 부담(핫키)·비활성자까지 갱신해 낭비. **pull**은 읽을 때 모아 생성 → 자원은 아끼지만 읽기 지연↑.
2. push로 하면 셀럽이 한 번 올릴 때마다 **수백만 팔로워 피드를 전부 갱신**해야 해 핫키·과부하가 난다. pull이면 그 포스팅을 **필요할 때만** 가져가 부하를 분산한다.
3. 메모리 효율. 피드엔 **포스팅/사용자 ID만** 두고 실제 콘텐츠·사용자 정보는 읽을 때 각 캐시에서 채운다. 캐시 크기를 제한할 수 있다.

</details>

- 피드 발생 API : 새 스토리를 포스팅하기 위한 API. HTTP POST 형태로 요청. POST /v1/me/feed. 인자 - 바디(body): 포스팅 내용 / Authorization 헤더: API 호출 인증을 위해 사용

**피드 발생** (개략적 형태)
[🖼️ 원본 이미지: 피드 발생 개략]
- 사용자 : 모바일 앱이나 브라우저에서 새 포스팅을 올리는 주체 (POST)
- 로드밸런서 : 트래픽을 웹 서버들로 분산
- 웹 서버 : HTTP 요청을 내부 서비스로 중계하는 역할 담당
- 포스팅 저장 서비스 : 새 포스팅을 데이터베이스와 캐시에 저장
- 포스팅 전송 서비스 : 새 포스팅을 친구의 뉴스 피드에 푸시, 뉴스 피드 데이터는 캐시에 보관하여 빠르게 읽어갈 수 있도록 함
- 알림 서비스 : 친구들에게 새 포스팅이 올라왔음을 알리거나, 푸시 알림을 보내는 역할 담당

**뉴스 피드 생성** (개략적 설계)
[🖼️ 원본 이미지: 뉴스 피드 생성 개략]
- 사용자 : 뉴스 피드를 읽는 주체 (GET)
- 로드밸런서 : 트래픽을 웹 서버들로 분산
- 웹 서버 : 트래픽을 뉴스 피드 서비스로 전송
- 뉴스 피드 서비스 : 캐시에서 뉴스 피드를 가져오는 서비스
- 뉴스 피드 캐시 : 뉴스 피드를 렌더링할 때 필요한 피드 ID 보관

**상세 설계 — 피드 발행 흐름 상세 설계**
[🖼️ 원본 이미지: 피드 발행 흐름 상세]
- 웹 서버 : 인증이나 처리율 제한 등 기능 수행. 스팸 막기, 유해한 컨텐츠 방지를 위해 한 사용자가 특정 기간동안 올릴 수 있는 포스팅 수에 제한 두기
- 포스팅 전송(팬아웃) 서비스 : 어떤 사용자의 새 포스팅을 그 사용자와 친구 관계에 있는 모든 사용자에게 전달하는 과정. 2가지 모델 존재
	- 쓰기 시점에 팬아웃하는 모델 (push model)
		- 새로운 포스팅을 기록하는 시점에 뉴스 피드를 갱신
		- 포스팅이 완료되면 바로 해당 사용자의 캐시에 해당 포스팅을 기록
			- 장점 : 뉴스 피드가 실시간으로 갱신되며 친구 목록에 있는 사용자에게 즉시 전송됨 / 새 포스팅이 기록되는 순간에 뉴스 피드가 갱신되므로 뉴스 피드를 읽는 데 드는 시간이 짧아짐
			- 단점 : 친구가 많은 사용자의 경우 친구 목록을 가져오고 그 목록에 있는 사용자 모두의 뉴스 피드를 갱신하는 데 많은 시간이 소요될 수 있음 (hotkey 문제) / 서비스를 자주 이용하지 않는 사용자의 피드까지 갱신해야 하므로 자원 낭비
	- 읽기 시점에 팬아웃하는 모델 (pull model)
		- 피드를 읽어야 하는 시점에 뉴스 피드를 갱신. 요청 기반 모델. 사용자가 본인 홈페이지나 타임라인을 로딩하는 시점에 새로운 포스트를 호출
			- 장점 : 비활성화된 사용자, 또는 서비스에 거의 로그인하지 않는 사용자의 경우 유리함 (자원 낭비 최소화) / 데이터를 친구 각각에 푸시하는 작업이 필요 없으므로 핫키 문제 X
			- 단점 : 뉴스 피드를 읽는 데 많은 시간이 소요될 수 있음
- 대부분 사용자 : 푸시 모델 (뉴스 피드를 빠르게 가져올 수 있도록)
- 친구/팔로워가 아주 많은 사용자 : 풀 모델 (해당 사용자의 포스팅을 필요할 때 가져가게, 시스템 과부하 방지)
- 안정 해시를 통해 요청과 데이터를 고르게 분산 (핫키 문제 줄이기)

동작과정
[🖼️ 원본 이미지: 팬아웃 동작 과정]
1. 그래프 DB에서 친구 ID 목록을 가져온다.
2. 사용자 정보 캐시에서 친구들의 정보를 가져온다. 이후 사용자 설정에 따라 일부를 걸러낸다. (Ex. mute)
3. 친구 목록과 새 스토리의 포스팅 ID를 메시지 큐에 넣는다.
4. 팬아웃 작업 서버가 메시지 큐에서 데이터를 꺼내 뉴스 피드 데이터를 뉴스 피드 캐시에 넣는다. (메모리 효율을 위해 포스팅/사용자 ID만 저장, 크기에 제한)

**피드 읽기 흐름 상세 설계**
[🖼️ 원본 이미지: 피드 읽기 흐름 상세]
1. 사용자가 뉴스 피드를 읽으려는 요청 전송 (/v1/me/feed)
2. 로드밸런서가 요청을 웹 서버 가운데 하나로 전송
3. 웹 서버는 피드를 가져오기 위해 뉴스 피드 서비스 호출
4. 뉴스 피드 서비스는 뉴스 피드 캐시에서 포스팅 ID 목록을 가져옴
5. 뉴스 피드에 표시할 사용자 이름, 사용자 사진, 포스팅 컨텐츠, 이미지 등을 사용자 캐시와 포스팅 캐시에서 가져와 완전한 뉴스 피드를 생성
6. 생성된 뉴스 피드를 JSON 형태로 클라이언트에게 전송, 클라이언트는 해당 피드를 렌더링
- (상세 설명) 뉴스 피드 서비스가 뉴스 피드 캐시에서 포스트 ID랑 사용자 ID를 받아와서 이 ID 들 가지고 사용자정보 + 포스트 정보 캐시(DB)에서 조회한 뒤에 그걸 단말기로 뿌려주고 정적이미지는 브라우저에서 JS가 실행 되면 그 때 CDN에서 가져오는 거

**캐시 구조**
- 뉴스 피드 시스템의 핵심 컴포넌트. 본 설계안에서는 다섯 계층으로 나뉜다
[🖼️ 원본 이미지: 캐시 5계층]
- 뉴스 피드 : 뉴스 피드의 ID 보관
- 컨텐츠 : 포스팅 데이터 보관 (인기 컨텐츠는 따로 보관)
- 소셜 그래프 : 사용자 간 관계 정보 보관
- 행동 : 포스팅에 대한 사용자의 행위에 관한 정보 보관 (Ex. 좋아요, 답글 등등)
- 횟수 : 좋아요 횟수, 응답 수, 팔로워 수, 팔로잉 수 등의 정보 보관

**마무리** (추가로 논의해볼만한 사항)
- 데이터베이스 규모 확장 : 수직 vs 수평 / SQL vs NoSQL / 주-부(master-slave) 다중화 / 복제본(replica)에 대한 읽기 연산 / 일관성 모델 / 데이터베이스 샤딩
- 웹 계층을 무상태로 운영하기
- 가능한 한 많은 데이터를 캐시할 방법
- 여러 데이터 센터를 지원할 방법
- 메시지 큐를 사용하여 컴포넌트 사이의 결합도 낮추기
- 핵심 메트릭에 대한 모니터링 (예: 트래픽이 몰리는 시간대의 QPS, 사용자가 뉴스 피드를 새로고침할 때의 지연시간 등)
