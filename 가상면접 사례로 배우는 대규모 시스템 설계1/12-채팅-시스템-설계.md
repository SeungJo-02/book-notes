## 1. 요구사항 & 규모

- **기능** — 낮은 지연 **1:1 채팅** · 최대 **100명 그룹** · 접속상태 표시 · 메시지 **10만 자 이하** · **다단말 동시 접속** · **푸시 알림** · **영구 이력**.
- **규모** — DAU **5,000만**, QPS **500**(최대 1,000).
- 채팅 서비스가 하는 일: 메시지 수신 → 수신자 결정·전달 → **수신자 미접속 시 접속할 때까지 보관**.

## 2. 통신 기법 — 폴링·롱폴링·웹소켓 ⭐

메시지 **송신**은 HTTP로 충분하지만, **서버→클라 임의 시점 전송**이 문제. 세 기법 비교:

| 기법 | 방식 | 한계 |
|---|---|---|
| **폴링** | 클라가 주기적으로 "새 메시지?" 질의 | 자주 할수록 비용↑, 메시지 없으면 자원 낭비 |
| **롱 폴링** | 새 메시지/타임아웃까지 연결 유지, 받으면 재요청 | 송·수신자가 **같은 서버 아닐 수 있음**, 연결 해제 감지 불가, 여전히 비효율 |
| **웹소켓** ✅ | 한 번 맺으면 **항구·양방향** | 연결 관리 부담(아래) |

[🖼️ 원본 이미지: 폴링 / 롱폴링 / 웹소켓 동작 비교]

- **웹소켓 장점** — 송·수신 동일 프로토콜, 설계 단순, 방화벽 환경도 80/443 포트로 잘 동작.
- **웹소켓 단점(면접 포인트)**
  - **연결이 자주 끊김** — 모바일 네트워크 변화, LB·방화벽이 **유휴 커넥션 강제 종료** → **하트비트 + 재시도**로 해결.
  - **커넥션이 곧 메모리** — 동접 10만이면 소켓 10만 개를 메모리에 유지. H/W가 좋아도 **파일 디스크립터(FD) 제한**에 걸림. (FD = OS가 파일·소켓 자원에 붙이는 ID, 웹소켓 1개당 1개)
  - **Scale-out 시** 롱폴링과 같은 "같은 서버 아님" 문제 → **Redis Pub/Sub·카프카** 같은 분산 브로커 필수.
  - 파이프가 뚫리면 **날 것의 텍스트/바이트**만 오가 디버깅 어려움.

## 3. 개략 설계 — 3부분

[🖼️ 원본 이미지: 개략적 설계안 아키텍처]

| 구분 | 내용 |
|---|---|
| **무상태 서비스** | 로그인·회원가입·프로필 등 전통 요청/응답. 로드밸런서 뒤 API 서버 |
| **상태 유지 서비스** | 채팅 서버 — 각 클라가 **독립 웹소켓 연결** 유지 |
| **제3자 연동** | 가장 중요한 건 **푸시 알림** |

- **컴포넌트**: 채팅 서버(메시지 중계) · 접속상태 서버(접속 여부) · API 서버(그 외) · 알림 서버(푸시) · **키-값 저장소(채팅 이력)**.
- **규모** — 동접 1M × 접속당 10KB ≈ 10GB. 한 대로는 **SPOF** → 분산.

## 4. 저장소 & 데이터 모델

- 데이터 2종: **일반 데이터**(프로필·설정·친구목록 → 안정성 위해 **RDBMS**) / **채팅 이력**(양 방대, 최근 메시지 위주, 무작위 접근도 있음, 1:1은 읽기:쓰기 ≈ **1:1**).
- **채팅 이력 = 키-값 저장소 추천**
  - 수평 확장 쉬움 · 낮은 지연.
  - RDBMS는 **롱테일에 취약** — 오래된 메시지 검색 시 방대한 데이터가 Buffer Pool로 올라와 **핫 데이터가 밀려남**, 인덱스도 커져 성능↓, 샤딩도 어려움.

### 데이터 모델
| 1:1 메시지 | 그룹 메시지 |
|---|---|
| PK = `message_id`(bigint) | **PK = (channel_id, message_id) 복합키** |
| from·to·content·created_at | 클러스터링/커버링 인덱스 유리, 단건 조회는 비효율·세컨더리 인덱스 비대 |

- **메시지 ID** — 유일 + **시간순 정렬** 필요. `auto_increment`는 NoSQL 미지원 → **전역 64비트 순서 생성기**(스노플레이크류) 또는 지역 순서 생성기.

## 5. 서비스 탐색 (주키퍼)

- 역할: 클라에게 **가장 적합한 채팅 서버 추천**(클라 위치·서버 용량 기준). 가용 서버를 등록해 두고 기준에 맞는 서버 선택.
- **주키퍼** = 오케스트라 지휘자(분산 락·리더 선출·설정 공유·네임서비스).

[🖼️ 원본 이미지: 주키퍼 기반 서비스 탐색]

1. 사용자A 로그인 → 2. LB가 API 서버로 → 3. 인증 후 **서비스 탐색이 최적 채팅 서버 선정** → 4. A가 그 서버와 **웹소켓 연결**.

## 6. 메시지 흐름

### 6-1. 1:1 메시지 처리
[🖼️ 원본 이미지: 1:1 채팅 메시지 흐름]
1. A가 채팅 서버1로 전송 → 2. 서버1이 **ID 생성기로 message_id 결정**(정렬·멱등·동일 메시지 식별용) → 3. **메시지 동기화 큐**로 전송 → 4. **키-값 저장소**에 보관 → 5. (a) B 접속 중이면 B의 채팅 서버2로 전송, (b) 미접속이면 **푸시 알림 서버**로 → 6. 서버2가 웹소켓으로 B에게 전달.

### 6-2. 다단말 동기화
[🖼️ 원본 이미지: 여러 단말 간 메시지 동기화]
- 단말마다 **`cur_max_message_id`**(관측한 최신 메시지 ID) 유지. **새 메시지 = 수신자 ID가 나 + 그 메시지 ID > cur_max_message_id**.

### 6-3. 소규모 그룹 채팅
[🖼️ 원본 이미지: 소규모 그룹 채팅 메시지 흐름]
- A의 메시지를 **B·C의 메시지 동기화 큐에 각각 복사**. 새 메시지는 **자기 큐만 보면 됨**(플로 단순). 그룹이 작으면 복사 비용도 문제없음. 각 수신함 큐는 여러 발신자 메시지를 받을 수 있어야 함.

## 7. 접속상태 표시

접속상태 서버가 웹소켓으로 상태를 관리(실시간 서비스의 일부).

- **로그인** — 웹소켓 연결 후 상태 + `last_active_at`를 키-값 저장소에 기록 → 접속 중 표시.
- **로그아웃** — 상태를 online→offline으로.
- **접속 장애 — 박동(heartbeat)**: 클라가 매 5초 박동 전송, 마지막 이벤트 후 **x초(예 30초) 내 미수신이면 오프라인**. (연결이 잠깐 끊겼다 붙는 상황의 낭비를 방지)

[🖼️ 원본 이미지: 박동 이벤트로 오프라인 판정]

- **상태 전파 — 발행-구독**: 상태 변화를 친구들이 쉽게 통지받도록 pub/sub 사용. **그룹이 작을 때 효과적**.

## 정리

| 주제 | 핵심 |
|---|---|
| 실시간 전송 | 웹소켓(폴링·롱폴링 대비 항구·양방향) |
| 웹소켓 부담 | 연결 끊김(하트비트), FD 한계, scale-out엔 브로커 |
| 이력 저장 | 키-값 저장소(RDB는 롱테일 취약) |
| 메시지 ID | 시간순 64비트 생성기 |
| 다단말 | cur_max_message_id로 새 메시지 판정 |
| 그룹(소규모) | 수신자별 큐 복사 |
| 접속상태 | 박동 + 발행-구독 |

**문제 이해 및 설계 범위 확정**
- 채팅 시스템은 너무 다양하기 때문에 정확한 요구사항을 파악하는 것이 중요하다.
- [요구사항]
	- 응답지연이 낮은 일대일 채팅 기능
	- 최대 100명까지 참여할 수 있는 그룹 채팅 기능
	- 1:1 + 다:다 + 사용자의 접속상태 표시 기능
		- 메시지 길이는 10만자 이하
	- 다양한 단말 지원. 하나의 계정으로 여러 단말에 동시 접속 지원
	- 푸시 알림
	- 영원한 채팅이력
- [QPS] DAU : 5000만 / QPS : 500 / MAX QPS : 1000

**개략적 설계안 제시 및 동의 구하기**
- 채팅 서비스: 클라이언트로부터 메시지 수신 / 메시지 수신자 결정 및 전달 / 수신자가 접속 상태가 아닌 경우에는 접속할 때까지 해당 메시지 보관
[🖼️ 원본 이미지: 클라이언트와 채팅 서비스 관계]
- 채팅을 시작하려는 클라이언트는 네트워크 통신 프로토콜을 사용하여 서비스에 접속한다.
- 송신 클라이언트는 HTTP 프로토콜로 메시지를 채팅 서비스에 보낸다.
- 서버에서 클라이언트로 임의 시점에 메시지를 보내는 데는 폴링, 롱 폴링, 웹소켓 등의 기법들이 제안되어 왔다.

*폴링(polling)*
- 클라이언트가 주기적으로 서버에게 새 메시지가 있냐고 물어보는 방법이다.
	- 자주할수록 비용이 올라간다.
	- 메시지가 없을 경우 서버 자원이 불필요하게 낭비될 수도 있다.
[🖼️ 원본 이미지: 폴링]

*롱 폴링(long polling)*
- 폴링의 비효율을 보완하기 위해 등장한 기법
- 클라이언트는 새 메시지가 반환되거나 타임아웃 될 때까지 연결을 유지
- 클라이언트는 새 메시지를 받으면 기존 연결을 종료하고 서버에 새로운 요청을 보내 모든 절차를 다시 시작한다.
- 여전히 단점은 남아있다.
	- 전송 클라이언트와 수신 클라이언트가 같은 채팅 서버에 접속하지 않을 수 있다.
	- 서버 입장에서는 클라이언트의 연결 해제 여부를 알 방법이 없다.
	- 여전히 비효율적이다. (타임아웃 후 주기적으로 서버에 접속해야 함)
[🖼️ 원본 이미지: 롱 폴링]

*웹소켓(WebSocket)*
- 서버가 클라이언트에게 비동기(async) 메시지를 보낼 때 가장 널리 사용하는 기술이다.
- 한번 맺어진 연결은 항구적이며 양방향이다.
- 일반적으로 방화벽이 있는 환경에서도 잘 동작한다. 포트를 80, 443 등 기본 포트번호를 사용해서
[🖼️ 원본 이미지: 웹소켓]
[🖼️ 원본 이미지: 웹소켓 메시지 송수신]
- 메시지를 보낼 때나 받을 때나 동일한 프로토콜을 사용할 수 있다.
- 설계, 구현이 단순하고 직관적이다.
- 웹소켓 연결은 항구적으로 유지되어야 하기 때문에 서버 측에서 연결 관리를 효율적으로 해야 한다.
- 단점
	- 연결 자주 끊김: 네트워크 상태 / 모바일 네트워크 변수 / LB강제 종료(LB나 방화벽은 유휴 커넥션 발견 시 끊어 버린다)
		- 해결책: 하트비트 로직 + 재시도 로직 구현
	- 동접이 10만이라면 10만개의 네트워크 소켓 커넥션을 메모리에 띄워야함
		- 아무리 H/W가 좋아도 파일 디스크립터 제한에 걸려서 새로운 사용자를 못받음
			- 파일 디스크립터: OS에서 파일 자원 관리하기 위해 붙이는 ID / 일반 문서부터 네트워크 소켓까지 파일로 취급(웹소켓 1개당 ID 1개) / 시스템 자원 무한정 사용을 막기위해 최대 파일 디스크립터 제한 함
	- Scale-out 하면 롱폴링 문제였던 같은 채팅 서버 불가 문제 발생
		- Redis Pub/Sub이나 Kafka 같은 분산 메시지 브로커 필수
	- 한 번 파이프가 뚫리면 날 것의 텍스트나 바이트 덩어리만 왔다갔다 → 그러니 디버깅이 어렵다

*개략적 설계안* — 3부분(무상태 서비스 / 상태 유지 서비스 / 제3자 서비스 연동)
- 무상태 서비스
[🖼️ 원본 이미지: 무상태 서비스]
	- 로그인, 회원가입, 사용자 프로파일 표시 등을 처리하는 전통적인 요청/응답 서비스
	- 로드밸런서 뒤에 위치한다. (로드밸런서는 요청을 그 경로에 맞는 서비스로 정확하게 전달)
- 상태 유지 서비스
	- 채팅 서비스는 상태 유지가 필요하다. (각 클라이언트가 채팅 서버와 독립적인 네트워크 연결을 유지해야 함)
- 제3자 서비스 연동
	- 채팅 앱에서 가장 중요한 제3자 서비스는 푸시 알림이다.
- 규모 확장성
	- 동접자 1M이고, 접속당 10k 서버 메모리가 필요하면 10GB 필요. 근데 이걸 하나의 서버? → SPOF 등의 문제
[🖼️ 원본 이미지: 개략적 설계안]
	- 채팅 서버는 클라이언트 사이에 메시지를 중계하는 역할을 담당한다.
	- 접속상태 서버는 사용자의 접속 여부를 관리한다.
	- API 서버는 로그인, 회원가입, 프로파일 변경 등 그 외 나머지 전부를 처리한다.
	- 알림 서버는 푸시 알림을 보낸다.
	- 키-값 저장소에는 채팅 이력을 보관한다.

*저장소*
- 채팅 시스템이 다루는 데이터는 보통 2가지다.
	- 사용자 프로파일, 설정, 친구 목록과 같은 일반적인 데이터 (안정성 보장, RDBMS)
	- 채팅 시스템에 고유한 데이터인 채팅 이력
		- 채팅 이력 데이터의 양은 엄청나다.
		- 가장 빈번하게 사용되는 것은 주로 최근에 주고받은 메시지
		- 검색/언급/점프 등 무작위적인 데이터 접근도 가능
		- 1:1 채팅 앱의 경우 읽기:쓰기 비율은 대략 1:1 정도
- 본 설계안은 키-값 저장소를 추천할 것이다.
	- 수평적 규모확장이 쉽다.
	- 데이터 접근 지연시간이 낮다.
	- RDBMS는 long tail에 해당하는 부분을 잘 처리하지 못하는 경향이 있다.
		- RDBMS는 데이터를 메모리(Buffer Pool)에 올려두고 서비스한다. 롱테일 검색 쿼리 날리면 방대한 데이터들이 메모리로 올라간다 → HOT 데이터들이 메모리에서 나가게 된다 → 전체적으로 줴줴
		- 롱테일이 커질 수록 인덱스도 커져서 성능이 저하됨
		- 샤딩이 어렵고 80%정도의 안쓰는 데이터들까지 쌓아둬야하니 최악의 선택임
	- 이미 많은 안정적인 채팅 시스템이 키-값 저장소를 채택하고 있다.

*데이터 모델*
- 1:1 채팅을 위한 메시지 테이블
	- message_id (bigint): 기본 키, 메시지 순서를 쉽게 정할 수 있도록 하는 역할
	- message_from (bigint): 메시지 발송자 / message_to (bigint): 메시지 수신자 / content (text) / created_at (timestamp)
- 그룹 채팅을 위한 메시지 테이블
	- channel_id, message_id (bigint): 기본키=복합키
		- 클러스터링 인덱스 편함 / 완벽한 커버링 인덱스 / 단건 메시지 조회 시 비효율 / 세컨더리 인덱스 크기 비대화
	- message_to / content / created_at

*메시지 ID*
- message_id 값은 고유해야 한다.
- ID 값은 정렬 가능해야 하며 시간 순서와 일치해야 한다.
	- auto_increment (NoSQL은 지원X) / 전역적 64-bit 순서 번호 생성기 / 지역적 순서 번호 생성기

**상세 설계 — 서비스 탐색**
- 주된 역할은 클라이언트에게 가장 적합한 채팅 서버를 추천하는 것이다. (클라이언트의 위치 / 서버의 용량)
- 사용 가능한 모든 채팅 서버를 등록시켜두고, 클라이언트가 접속을 시도하면 사전에 정한 기준에 따라 최적의 채팅 서버를 골라준다.
- 주키퍼 : 오케스트라 지휘자 역할 (분산락, 리더선출, 설정 변경, NS 등등)
[🖼️ 원본 이미지: 주키퍼 서비스 탐색]
1. 사용자A가 시스템에 로그인을 시도한다.
2. 로드밸런서가 로그인 요청을 API 서버들 가운데 하나로 보낸다.
3. API 서버가 사용자 인증을 처리하고 나면 서비스 탐색 기능이 동작하여 해당 사용자를 서비스할 최적의 채팅 서버를 찾는다.
4. 사용자 A는 채팅 서버2(선택된 서버)와 웹소켓 연결을 맺는다.

**메시지 흐름**
*1:1 채팅 메시지의 처리 흐름*
[🖼️ 원본 이미지: 1:1 채팅 메시지 흐름]
1. 사용자 A가 채팅 서버1로 메시지 전송
2. 채팅 서버1은 ID 생성기를 사용해 해당 메시지의 ID 결정
	- NoSQL에는 auto_increment 기능 없다 + 분산 환경에서는 auto_increment 기능 의존 못함 + 메시지의 정확한 순서보장 때문에 사용
		- 스로우플레이크 같은 거 사용해서 미세한 오차 구분해서 정렬 / 카산드라나 다이나모 DB 같은 NoSQL에는 auto_increment 기능 없다 / ID를 보고 멱등성 보장하려고 / ID를 보고 나중에 여러 컴포넌트에서 발견되는 메시지가 같은 메시지임을 보여주려면 이걸 사용해야함
3. 채팅 서버1은 해당 메시지를 메시지 동기화 큐로 전송
4. 메시지가 키-값 저장소에 보관됨
5. (a) 사용자B가 접속 중인 경우 메시지는 사용자B가 접속 중인 채팅 서버(서버2)로 전송됨 (b) 사용자B가 접속 중이 아니라면 푸시 알림 메시지를 푸시 알림 서버로 보냄
6. 채팅 서버2는 메시지를 사용자B에게 전송. 사용자B와 채팅 서버2 사이에는 웹소켓 연결이 있는 상태이므로 그것을 이용

*여러 단말 사이의 메시지 동기화*
[🖼️ 원본 이미지: 다단말 동기화]
- 사용자A는 휴대전화와 랩톱 2개 단말을 이용하고 있다.
- 각 단말은 별도 웹소켓이 채팅 서버1에 연결되어 있다.
- 각 단말은 cur_max_message_id(해당 단말에서 관측된 가장 최신 메시지의 ID를 추적하는 용도)라는 변수를 유지한다.
- 2개 조건을 만족하면 새 메시지로 간주된다.
	- 수신자 ID가 현재 로그인한 사용자 ID와 같다.
	- 키-값 저장소에 보관된 메시지로서, 그 ID가 cur_max_message_id보다 크다.

*소규모 그룹 채팅에서의 메시지 흐름*
[🖼️ 원본 이미지: 소규모 그룹 채팅 흐름]
- 사용자A가 보낸 메시지가 사용자B와 C의 메시지 동기화 큐에 복사된다.
- 소규모 그룹 채팅에 적합하다.
	- 새로운 메시지가 왔는지 확인하려면 자기 큐만 보면 되니까 메시지 동기화 플로가 단순하다.
	- 그룹이 크지 않으면 메시지를 수신자별로 복사해서 큐에 넣는 작업의 비용이 문제가 되지 않는다.
[🖼️ 원본 이미지: 수신함 큐]
- 한 수신자는 여러 사용자로부터 오는 메시지를 수신할 수 있어야 한다.
- 각 사용자의 수신함, 즉 메시지 동기화 큐는 여러 사용자로부터 오는 메시지를 받을 수 있어야 한다.

**접속상태 표시**
- 접속상태 서버를 통해 사용자의 상태를 관리한다.
- 접속상태 서버는 클라이언트와 웹소켓으로 통신하는 실시간 서비스의 일부이다.
*사용자 로그인*
[🖼️ 원본 이미지: 로그인]
- 웹소켓 연결이 맺어지고 나면 접속상태 서버는 A의 상태와 last_active_at 타임스탬프 값을 키-값 저장소에 보관한다.
*로그아웃*
[🖼️ 원본 이미지: 로그아웃]
- 키-값 저장소에 보관된 사용자 상태가 online에서 offline으로 바뀐다.
*접속 장애*
- 장애가 발생하면 사용자를 오프라인 상태로 표시하고 연결이 복구되면 온라인 상태로 변경한다. (짧은 시간동안이면 비효율적)
- 박동 검사를 통해 문제를 해결할 수 있다.
	- 박동 이벤트를 접속상태 서버로 보내도록 하고, 마지막 이벤트를 받은 지 x초 이내에 또 다른 박동 이벤트 메시지를 받으면 온라인으로 유지한다. 그렇지 않을 경우 오프라인으로 바꾼다.
[🖼️ 원본 이미지: 박동 이벤트]
- 클라이언트는 박동 이벤트를 매 5초마다 서버로 보내고 있다.
- 이벤트를 3번 보낸 후, x=30초 동안 아무런 메시지를 보내지 않아 오프라인 상태로 변경되었다.
*상태 정보의 전송*
[🖼️ 원본 이미지: 상태 정보 전송]
- 상태정보 서버는 발행-구독 모델을 사용한다.
- 친구 관계에 있는 사용자가 상태정보 변화를 쉽게 통지 받을 수 있다.
- 클라이언트와 서버 사이의 통신에는 실시간 웹소켓을 사용한다.
- 그룹 크기가 작을 때 효과적이다.
