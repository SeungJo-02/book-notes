# 9장 웹 크롤러 설계

> 📝 **Notion 원본**: https://app.notion.com/p/adc158a537f44f4cb02f0c2977311b10

> 🧩 **한 줄 요약** — 웹 크롤러는 시작 URL에서 링크를 따라가며 페이지를 수집(**BFS**)하는 시스템. 핵심은 **미수집 URL 저장소**로 "예의·우선순위·신선도"를 관리하고, **중복 제거(해시)** · **robots.txt 준수** · **분산·안정 해시**로 10억 페이지 규모를 감당하는 것.

---

## 1. 웹 크롤러란

- 로봇·스파이더라고도 함. 링크를 따라 웹페이지·이미지·PDF 등을 수집.
- **용도** : 검색엔진 인덱싱(로컬 인덱스 생성) · 웹 아카이빙(장기 보관) · 웹 마이닝(지식 도출) · 웹 모니터링(저작권 감시)

---

## 2. 1단계 — 요구사항 · 규모 추정

**기본 알고리즘** : ① 시작 URL 페이지 다운로드 → ② 페이지에서 URL 추출 → ③ 추출 URL을 목록에 추가하고 반복.

| 구분 | 내용 |
|---|---|
| 기능 | 검색엔진 인덱싱용 · 10억 페이지 · 신규/수정 반영 · 5년 보관 · 중복 무시 |
| 비기능 | 규모확장성(병행성) · 안정성 · **예의**(과다 요청 금지) · 확장성 |

- **QPS** ≈ 400 (월 10억 ÷ 30일 ÷ 86,400초), **Peak** ≈ 800
- 페이지 평균 500KB → 월 **500TB**, 5년 **30PB**

---

## 3. 2단계 — 개략 설계: 핵심 컴포넌트

**다운로드 파이프라인**

| 컴포넌트 | 역할 |
|---|---|
| 시작 URL 집합 | 크롤링 출발점 (도메인 기반 / 주제별로 URL 공간 분할) |
| 미수집 URL 저장소 | 다운로드할 URL 큐(FIFO) — **설계의 심장** |
| HTML 다운로더 | URL이 가리키는 페이지를 인터넷에서 다운 |
| 도메인 이름 변환기 | URL → IP 주소 (DNS) |
| 컨텐츠 파서 | 파싱·검증 (느려지지 않게 **독립 컴포넌트**로) |

**저장 · 중복 · URL 관리**

| 컴포넌트 | 역할 |
|---|---|
| 중복 판별 | 페이지 **해시 값** 비교로 중복 제거 |
| 컨텐츠 저장소 | HTML 보관 (대부분 디스크 + 인기 콘텐츠는 메모리) |
| URL 추출기 | 링크 추출, 상대경로 → 절대경로 변환 |
| URL 필터 | 확장자·오류·제외목록 URL 배제 |
| 방문 URL 판별 | **블룸 필터 / 해시 테이블**로 재방문·무한루프 방지 |
| URL 저장소 | 이미 방문한 URL 보관 |

---

## 4. 작업 흐름 (요약)

1. 시작 URL → 미수집 URL 저장소
2. 다운로더가 URL을 꺼내 DNS로 IP를 얻어 페이지 다운
3. 파서가 형식 검증
4. 중복 확인 — 저장소에 있으면 버리고, 없으면 저장 후 URL 추출기로
5. 추출한 링크 → URL 필터 → 방문 URL 판별
6. 처음 보는 URL만 URL 저장소 + 미수집 URL 저장소에 추가

---

## 5. 3단계 — BFS와 미수집 URL 저장소

- 웹 = 유향 그래프(페이지=노드, 링크=에지), 크롤링 = 그래프 탐색.
- **BFS 사용** (DFS는 깊이를 예측하기 어려움). FIFO 큐로 구현.
- BFS의 두 문제 → **미수집 URL 저장소**로 해결:
  - ① 링크가 같은 서버로 몰려 **과부하** → *예의* 필요
  - ② URL에 **우선순위가 없음** → 품질 차등 필요

### 예의 (Politeness)
같은 사이트엔 한 번에 한 페이지, 시간차를 둔다. **호스트명 ↔ 작업 스레드**를 매핑.

```mermaid
flowchart LR
  QR["큐 라우터<br>같은 호스트→같은 큐"] --> MT["매핑 테이블<br>호스트↔큐"]
  MT --> Q["FIFO 큐 b1~bn"]
  Q --> QS["큐 선택기"]
  QS --> WT["작업 스레드<br>시간차 다운로드"]
```

### 우선순위 (Priority)
- 페이지랭크·트래픽·갱신 빈도로 순위 결정. **순위결정장치** → 우선순위별 큐, 높은 큐를 더 자주 선택.
- 전체 = **전면 큐**(우선순위 처리) + **후면 큐**(예의 보장)

### 신선도 (Freshness)
- 받은 페이지도 주기적 재수집. 최적화 : 변경 이력 활용 + 중요 페이지를 더 자주.

### 지속성 저장
- 대부분 디스크에 두되, I/O 병목을 피하려 **메모리 버퍼 큐**에 모았다가 배치로 디스크 기록.

---

## 6. HTML 다운로더 · 성능 최적화

- HTTP로 다운로드. **robots.txt**(로봇 제외 프로토콜)를 먼저 확인하고 캐시.
- 성능 : **분산 크롤링**(URL 공간 분할) · **DNS 결과 캐시**(크론잡 갱신) · **지역성**(서버 지역 분산) · **짧은 타임아웃**

---

## 7. 안정성 · 확장성 · 문제 컨텐츠

- **안정성** : 안정 해시(부하 분산) · 크롤링 상태 저장 · 예외 처리 · 데이터 검증
- **확장성** : 모듈 플러그인으로 새 콘텐츠 지원 (PNG 다운로더, 웹 모니터 등)
- **문제 컨텐츠** : 중복(해시·체크섬) · **거미 덫**(무한루프 유도 페이지) · 데이터 노이즈(광고·스팸)
- **4단계 마무리(추가 논의)** : 서버 측 렌더링(CSR이면 헤드리스 브라우저) · 스팸 필터링 · DB 다중화·샤딩 · 무상태 수평 확장 · 가용성/일관성/안정성 · 데이터 분석

---

## 8. 정리

| 개념 | 한 줄 정의 |
|---|---|
| 미수집 URL 저장소 | 다운로드할 URL 큐 — 예의·우선순위·신선도의 중심 |
| 예의(Politeness) | 호스트별 큐+전담 스레드로 한 번에 한 요청·시간차 |
| BFS | FIFO 큐 기반 그래프 탐색 (크롤러 기본 전략) |

| robots.txt | 사이트가 크롤러에 알리는 수집 허용 규칙 파일 |
| 거미 덫 | 크롤러를 무한 루프에 빠뜨리는 페이지 |

**1단계. 문제 이해 및 설계 범위 확정**

**웹 크롤러의 기본 알고리즘**
1. URL 집합이 입력으로 주어지면, 해당 URL들이 가리키는 모든 웹 페이지를 다운로드
2. 다운받은 웹 페이지에서 URL들을 추출
3. 추출된 URL들을 다운로드할 URL 목록에 추가하고 위의 과정을 처음부터 반복
- 즉, 페이지들어가서 해당 페이지에 있는 URL을 또 들어가고를 반복하는 거

기능요구사항
- 용도는 검색 엔진 인덱싱에 쓰일 것(아카이빙, 마이닝, 모니터링은 아님)
- 10억 개의 웹 페이지를 수집해야 합니다.
- 새로 만들어진 웹 페이지나 수정된 웹 페이지도 고려
- 수집한 웹 페이지는 5년 저장
- 중복된 컨텐츠를 갖는 페이지는 무시해도 됩니다.

비기능 요구사항
- **규모 확장성**: 병행성을 활용하면 보다 효과적일 것
- **안정성**: 비정상적 입력이나 환경에 잘 대응할 수 있어야 할 것
- **예절**: 짧은 시간 너무 많은 요청을 보내서는 안 될 것
- **확장성**: 새로운 형태의 컨텐츠를 지원하기 쉬울 것

**개략적 규모 추정**
- 매달 10억 개의 웹 페이지를 다운로드
- QPS = 10억 = (1,000,000,000/30일/24시간/3600초) = 대략 400페이지/초
- 최대(Peak) QPS = 2 * QPS = 800
- 웹 페이지의 크기 평균은 500k로 가정
- 10억 페이지 * 500k(1페이지 용량 가정) = 500TB/월
- 1개월치 데이터를 보관하는 데는 500TB, 5년간 보관하는 데는 500TB * 12개월 * 5년 = 30PB 저장용량이 필요

제시할 설계안 (웹 크롤러에 관한 선행연구 참고)

`[🖼️ 원본 이미지: 개략적 설계안 구조도]`

**시작 URL 집합**
- 웹 크롤러가 크롤링을 시작하는 출발점
- **전체 웹을 크롤링해야 할 경우** 가능한 많은 링크를 탐색하려면 해당 사이트의 도메인 이름이 붙은 URL을 시작 URL로 하는 것이 좋다 / 즉, **가능한 많은 링크를 탐색할 수 있도록 하는 URL**
- 보통 URL 공간을 작은 부분 집합으로 나누는 방법 혹은 주제별로 URL을 나누는 방법을 사용
  - URL 공간을 부분 집합으로 나누는 방법
    - 시작 URL: 한국 `https://www.naver.com`, `https://www.daum.net` / 일본 `https://www.yahoo.co.jp`
  - 주제별로 URL을 나누는 방법
    - 시작 URL: 다이닝코드로 모아둔 거 `https://www.diningcode.com/list.php?query=강남역` / 식품의약품안전처 토픽 `https://www.foodsafetykorea.go.kr/...`

**미수집 URL 저장소**
- 현대의 웹크롤러는 크롤링 상태를 `다운로드할 URL`과 `다운로드된 URL` 2가지로 나눠 관리
  - `다운로드할 URL` : 미수집 URL 저장소라고 부름 — FIFO : 방식(큐)

**HTML 다운로더**
- 인터넷에서 웹 페이지를 다운로드하는 컴포넌트
- `다운로드할 URL`은 미수집 URL 저장소가 제공해서 그 URL을 저장

**도메인 이름 변환기**
- 웹페이지 다운 시 URL을 IP로 바꿔야 하니까
- 도메인 이름 변환기를 사용하여 URL에 대응되는 IP 주소를 알아냄

**컨텐츠 파서 - 원본에서 필요한 데이터만 뽑기**
- 웹 페이지를 다운로드하면 파싱(parsing)과 검증(validation) 절차가 필수
- 이상한 웹 페이지면 문제가 되고 저장공간 낭비 되니까
- 크롤링 서버 내에 구현되면 느려지기 때문에, **독립된 컴포넌트**로 구현

**중복 컨텐츠인가?**
- 데이터 중복을 줄이고 데이터 처리에 소요되는 시간을 줄이는 것이 필요
- 웹 페이지의 **해시 값** 비교 — 두 개의 HTML을 비교하는 것은 시간이 너무오래 걸리기에

**컨텐츠 저장소**
- HTML 문서를 보관하는 시스템(역인덱스를 만들기위해)
- 구현 관련 기술을 고를 때 저장할 데이터의 유형, 크기, 저장소 접근 빈도, 데이터의 유효 기간 등을 종합적으로 고려해야 함
- 본 설계안에서는 디스크와 메모리를 동시에 사용하는 저장소를 택함
  - 데이터 양이 너무 많으므로 **대부분의 컨텐츠는 디스크**에 저장
  - **인기 있는 컨텐츠는 메모리**에 두어 접근 지연시간 감축

**URL 추출기**
- HTML 페이지를 파싱하여 링크들을 골라내는 역할
  - 상대 경로를 전부 절대 경로로 변환
    - 절대경로 `<a href="https://www.example.com/sports/baseball.html">야구 기사</a>`
    - 상대경로 `<a href="/sports/baseball.html">야구 기사</a>`

**URL 필터**
- 특정한 컨텐츠 타입이나 파일 확장자를 갖는 URL, 접속 시 오류가 발생하는 URL, 접근 제외 목록에 포함된 URL 등을 크롤링 대상에서 배제

**이미 방문한 URL?**
- 이미 방문한 URL, 미수집 URL 저장소에 보관된 URL을 추적할 수 있도록 하는 자료 구조 사용예정
- 서버 부하를 줄이고 시스템이 무한 루프에 빠지는 일을 방지
- 자료 구조로는 **블룸 필터(bloom filter)** 나 **해시 테이블**이 널리 사용됨

**URL 저장소**
- 이미 방문한 URL을 보관하는 저장소

**웹 크롤러 작업 흐름**

`[🖼️ 원본 이미지: 웹 크롤러 작업 흐름도]`

1. 시작 URL들을 미수집 URL 저장소에 저장
2. HTML 다운로더는 미수집 URL 저장소에서 URL 목록 호출
3. HTML 다운로더는 도메인 이름 변환기를 사용하여 URL의 IP 주소를 알아내고, 해당 IP 주소로 접속하여 웹 페이지 다운로드
4. 컨텐츠 파서는 다운된 HTML 페이지를 파싱하여 올바른 형식을 갖춘 페이지인지 검증
5. 컨텐츠 파싱과 검증이 끝나면 중복 컨텐츠인지 확인하는 절차 개시
6. 중복 컨텐츠인지 확인하기 위해, 해당 페이지가 이미 저장소에 있는지 확인
   - 이미 저장소에 있는 컨텐츠이면 처리하지 않고 버림
   - 없으면 저장소에 저장한 뒤 URL 추출기로 전달
7. URL 추출기는 해당 HTML 페이지에서 링크를 골라냄
8. 골라낸 링크를 URL 필터로 전달
9. 필터링이 끝나고 남은 URL만 중복 URL 판별 단계로 전달
10. 이미 처리한 URL인지 확인하기 위해, URL 저장소에 보관된 URL인지 확인 (이미 저장되어 있으면 버림)
11. 저장소에 없는 URL은 URL 저장소에 저장하고, 미수집 URL 저장소에도 전달

**3단계. 상세 설계**

**DFS를 쓸 것인가, BFS를 쓸 것인가**
- 웹은 유향 그래프(directed graph), 페이지는 노드(node), 하이퍼링크는 에지(edge)와 같다.
- 크롤링 프로세스는 유향 그래프를 edge를 따라 탐색하는 과정
- 웹 크롤러는 보통 BFS 사용 (DFS는 깊이가 어느 정도로 깊숙한지 예상하기 어렵기 때문)
  - FIFO(큐)를 사용하는 알고리즘 / 큐에 탐색할 URL을 넣고 다른 쪽으로는 꺼내기만 하기
- 👎 BFS 구현법의 문제점
  - 한 페이지에서 나오는 링크의 상당수는 같은 서버로 되돌아감 / 시작 URL의 하위 링크를 병렬로 처리하면 요청이 뒤로 갈 수록 기하급수적으로 늘어나서 과부하가 걸림
  - 표준적 BFS 알고리즘은 URL 간에 우선순위를 두지 않음 / 현실은 모든 웹페이지가 같은 수준의 품질이 아니기에 우선순위 생각하기
- 해결책 : **미수집 URL 저장소 사용**
  - 저장소를 잘 구현하면 예의를 갖춘 크롤러, URL 사이의 우선순위와 신선도를 구별하는 크롤러 구현이 가능함

***예의***
- 동일 웹 사이트에 대해서는 한 번에 한 페이지만 요청
- 같은 웹 사이트의 페이지를 다운받는 테스크는 시간차를 두고 실행하도록 할 것
- 이를 만족하기 위해 웹사이트의 호스트명(hostname)과 다운로드를 수행하는 작업 스레드 사이의 관계를 유지하면 됨
- 각 다운로드 스레드는 별도 FIFO 큐를 가지고 있어, 해당 큐에서 꺼낸 URL만 다운로드

  `[🖼️ 원본 이미지: 예의 — 호스트별 큐 구조도]`

- **큐 라우터(queue router)** : 같은 호스트에 속한 URL은 언제나 같은 큐로 가도록 보장하는 역할
- **매핑 테이블(mapping table)** : 호스트 이름과 큐 사이의 관계를 보관하는 테이블
- **FIFO 큐(b1~bn)** : 같은 호스트에 속한 URL은 언제나 같은 큐에 보관됨
- **큐 선택기(queue selector)** : 큐들을 순회하면서 큐에서 URL을 꺼내 해당 큐에서 나온 URL을 다운로드하도록 지정된 작업 스레드에 전달
- **작업 스레드(woker thread)** : 전달된 URL을 다운로드 하는 작업 수행 (URL 순차적 처리, 작업들 간 일정한 지연시간)
- 정리 : 큐 라우터가 맵핑 테이블을 보고 큐를 만들어두면 큐 선택기가 각각의 큐에 있는 데이터가 작업할 수 있도록 작업 스래드에 던저주는데 큐방식이니까 작업 스레드에 하나씩 업무를 처리

***우선순위***
- 유용성에 따라 URL의 우선순위를 나눌 때 고려할 사항
  - 페이지랭크(PageRank), 트래픽 양, 갱신 빈도(update frequency) 등 다양한 척도를 사용
- **순위결정장치(prioritizer)** : URL 우선순위를 정하는 컴포넌트 / URL을 입력 받고 우선순위를 계산

  `[🖼️ 원본 이미지: 우선순위 큐 구조도]`

- **큐** : 우선순위별로 큐가 하나씩 할당됨, 우선순위가 높으면 선택될 확률 증가
- **큐 선택기** : 임의 큐에서 처리할 URL을 꺼내는 역할 담당, 순위가 높은 큐에서 더 자주 꺼내도록 프로그램
- [전체설계]

  `[🖼️ 원본 이미지: 전체 설계도]`

- **전면 큐** : 우선순위 결정 과정 처리
- **후면 큐** : 크롤러가 예의 바르게 동작하도록 보증
- 정리 : 먼저 우선순위가 높은 URL을 필터링을 한 뒤 이후 BFS로 HTML을 다운로드할 URL을 탐색하는데 문제가 BFS를 사용하면 URL을 타면 탈수록 기하급수적으로 탐색하게 되니까 큐를 놔서(도메인 기준으로 )

***신선도***
- 데이터의 신선함을 유지하기 위해 이미 다운로드한 페이지라고 해도 주기적으로 재수집해야 한다.
- 모든 URL을 재수집하는 것은 많은 시간과 자원이 필요하기 때문에, **최적화 전략**이 필요하다.
  - 웹 페이지의 변경 이력 활용
  - 우선순위를 활용하여, 중요한 페이지는 좀 더 자주 재수집

***미수집 URL 저장소를 위한 지속성 저장장치***
- (본 설계안의 절충안) 대부분의 URL은 디스크에 두지만 IO 비용을 줄이기 위해 메모리 버퍼에 큐를 둠
- 버퍼에 있는 데이터는 주기적으로 디스크에 기록할 것
- 즉, 매번 I/O 작업하면 병목이 생기니까 메모리에 모았다가 배치 처리를 한다

**HTML 다운로더**
- HTTP 프로토콜을 통해 웹 페이지를 내려 받음

***Robots.txt***
- 로봇 제외 프로토콜
- 웹사이트가 크롤러와 소통하는 표준적 방법
- 크롤러가 수집해도 되는 페이지를 작성한 파일(일반 텍스트 파일(.txt))
  - 크롤러는 웹 사이트를 긁어 가기 전에 해당 파일에 나열된 규칙을 먼저 확인해야 함
- 주기적으로 다시 다운받아 캐시에 보관

***성능 최적화***
- **분산 크롤링** : 성능을 높이기 위해 크롤링 작업을 여러 서버에 분산, URL 공간은 작은 단위로 분할하여 각 서버가 그 중 일부의 다운로드 담당
- **도메인 이름 변환 결과 캐시** : DNS 조회 결과로 얻어진 도메인 이름과 IP 주소 사이의 관계를 캐시에 보관(매 요청마다 DNS 가면 시간이 오래 걸리니까), 크론잡을 사용해서 주기적으로 갱신(보통 사이트들이 동적 IP를 사용하니까)
- **지역성** : 크롤링 작업 수행 서버를 지역별로 분산
- **짧은 타임아웃** : 설정 시간동안 서버가 응답하지 않으면 크롤러는 다운로드 중단, 다음 페이지로 넘어감

***안정성***
- **안정 해시** : 다운로더 서버들에 부하를 분산할 때 적용 가능한 기술
- **크롤링 상태 및 수집 데이터 저장** : 장애가 발생한 경우에도 쉽게 복구할 수 있도록 크롤링 상태와 수집된 데이터를 지속적 저장장치에 기록
- **예외 처리** : 예외가 발생해도 전체 시스템이 중단되는 일 없이 작업을 이어나갈 수 있어야 함
- **데이터 검증** : 시스템 오류를 방지하기 위한 중요 수단 중 하나

***확장성***
- 새로운 형태의 컨텐츠를 쉽게 지원할 수 있도록 신경 써야 함
- 새로운 모듈을 끼워넣음으로써 새로운 형태의 컨텐츠를 지원할 수 있도록 설계할 수 있음

***문제 있는 컨텐츠 감지 및 회피***
- **중복 컨텐츠** : 해시나 체크섬을 사용하여 보다 쉽게 탐지
- **거미 덫** : 크롤러를 무한 루프에 빠뜨리도록 설계한 웹 페이지, 수작업으로 덫을 확인하고 찾아낸 후에 크롤러 탐색 대상에서 제외하거나 URL 필터 목록에 걸어둘 수 있음
- **데이터 노이즈** : 가치 없음, 광고, 스크립트 코드, 스팸 URL 등, 가능하면 제외

**4단계. 마무리**

추가로 논의해보면 좋을 사항
- **서버 측 렌더링** : 페이지 파싱 전 서버 측 렌더링 적용
  - 우리가 크롤링 할 페이지가 SSR을 사용한다면 베스트
  - CSR 이라면? HTML 다운로더에 헤드리스 브라우저를 탑제
    - 헤드리스 브라우저 : 브라우저의 화면 없는 버전
  - 크롤러 서버가 이 브라우저를 통해 자바스크립트를 끝까지 실행하고 DOM 트리가 완벽하게 생성되면 그때 완성된 HTML을 떠서 파서에게 넘겨준다
- **원치 않는 페이지 필터링** : 스팸 방지 컴포넌트를 통해 페이지 걸러내기
- **데이터베이스 다중화 및 샤딩** : 데이터 게층의 가용성, 규모 확장성, 안정성이 향상
- **수평적 규모 확장성** : 무상태 서버로 만드는 것
- **가용성, 일관성, 안정성** : 대형 시스템에서 필수적인 요소
- **데이터 분석 솔루션** : 데이터를 수집하고 분석, 시스템을 세밀히 조정하기 위함
