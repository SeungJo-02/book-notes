# 7장. 분산 시스템을 위한 유일 ID 생성기 설계

> 📝 **Notion 원본**: https://app.notion.com/p/9f9b934cd6f740429b41b9d7d0bef05b

> 🧩 **한 줄 요약** — 분산 환경에서 **64비트·숫자·시간순 정렬 가능**한 유일 ID를 **초당 1만 개** 만드는 설계. 후보 4가지(다중 마스터 복제·UUID·티켓 서버·**스노플레이크**) 중 요구사항을 모두 만족하는 건 **트위터 스노플레이크** — 64비트를 `사인1 + 타임스탬프41 + 데이터센터5 + 서버5 + 일련번호12`로 쪼개 **시간정렬·유일성·서버 독립 생성**을 동시에 얻는다.

## 1. 문제 & 요구사항

- DB의 `auto_increment`로 하면 되지 않을까? → **분산 환경에선 안 됨**, 여러 DB를 쓰면 지연 낮추기도 어렵다.
- **요구사항**
  - ID는 **유일**해야 한다
  - ID는 **숫자로만** 구성
  - ID는 **64비트**로 표현
  - ID는 **발급 날짜순 정렬** 가능
  - **초당 10,000개** 생성 가능

## 2. 후보 4가지 비교 ⭐

| 방법 | 핵심 | 장점 | 단점 |
|---|---|---|---|
| **다중 마스터 복제** | `auto_increment`를 서버 수 `k`만큼 증가 | DB 늘리면 처리량↑ | 데이터센터 확장 어려움, **시간순 정렬 X**, 서버 증감 어려움 |
| **UUID** | 128비트 난수, 서버마다 독립 생성 | 단순·조율 불필요·확장 쉬움 | **128비트**(요구는 64), **시간정렬 X**, 숫자 아닌 값 포함 |
| **티켓 서버** | 중앙 `auto_increment` DB 1대에서 번호표 발급(플리커) | 숫자 유일 ID 쉬움, 소규모 적합 | **SPOF**(다중화하면 동기화 문제 → 홀/짝 분할로 완화) |
| **스노플레이크** | 64비트를 절로 쪼갬 | **요구사항 전부 충족** | 시계 동기화 등 고려 필요 |

## 3. 스노플레이크 64비트 구조

[🖼️ 원본 이미지: 스노플레이크 64비트 ID 구조]

| 절 | 비트 | 역할 |
|---|---|---|
| **사인(sign)** | 1 | 음수/양수 구별용 (항상 0) |
| **타임스탬프** | 41 | 기원 시각 이후 경과 **밀리초** → **시간순 정렬**의 핵심 |
| **데이터센터 ID** | 5 | 최대 **32개** 데이터센터 |
| **서버 ID** | 5 | 데이터센터당 최대 **32개** 서버 |
| **일련번호** | 12 | 같은 ms 안에서 생성마다 +1, **1ms 지나면 0으로 리셋** |

## 4. 상세 — 타임스탬프·일련번호

- **데이터센터 ID·서버 ID**는 **시스템 시작 시 결정**, 운영 중 안 바뀜. 잘못 바꾸면 **ID 충돌** → 신중히.
- **타임스탬프·일련번호**는 ID 생성 중 실시간으로 만들어짐.

### 타임스탬프
[🖼️ 원본 이미지: 이진 표현에서 UTC 시각 추출 예제]
- 시간이 흐를수록 값이 커지므로 **ID가 시간순 정렬**된다. UTC ↔ 타임스탬프 상호 변환 가능.
- 41비트 최댓값 ≈ **69년**(2⁴¹−1 ms) → **69년만 정상 동작**. 이후엔 기원 시각을 바꾸거나 ID 체계 이전 필요.

### 일련번호
- 같은 밀리초에 **2개 이상** 만들 때만 0보다 커짐. 12비트 → **4096개**(2¹²).

---

## 5. 마무리 — 논의거리

- **시계 동기화** — 생성 서버들이 같은 시계를 쓴다고 가정했지만 실제론 어긋날 수 있음(NTP 등 필요).
- **각 절 길이 최적화** — 동시성 낮고 수명 긴 앱은 일련번호를 줄이고 타임스탬프를 늘리는 게 유리.
- **고가용성** — ID 생성기는 필수 컴포넌트라 아주 높은 가용성이 필요.

## 정리

| 축 | 스노플레이크가 푸는 법 |
|---|---|
| 유일성 | 타임스탬프+DC+서버+일련번호 조합이 겹치지 않음 |
| 64비트·숫자 | 전체를 64비트 정수로 구성 |
| 시간순 정렬 | 상위 비트가 타임스탬프라 값이 시간순 증가 |
| 처리량 | 서버마다 독립 생성 + ms당 4096개 |

## 🔁 셀프 체크
1. UUID는 왜 이 문제의 요구사항에 안 맞나?
2. 스노플레이크 ID가 **시간순 정렬**이 되는 이유는?
3. 타임스탬프에 41비트를 쓰면 생기는 수명 한계는?

<details>
<summary>답</summary>

1. UUID는 **128비트**라 64비트 요구를 넘고, **시간순 정렬이 안 되며**, 숫자가 아닌 값이 포함될 수 있다. (유일성·독립 생성은 좋지만 나머지 요구를 못 맞춤)
2. 64비트의 **상위(사인 다음) 41비트가 타임스탬프**라, 나중에 만든 ID일수록 이 부분이 커져 **정수 크기 자체가 시간순으로 증가**하기 때문.
3. 41비트로 표현 가능한 밀리초는 약 **69년**치라, 기원 시각으로부터 69년이 지나면 오버플로 → 기원 시각 변경이나 ID 체계 이전이 필요하다.

<details>
<summary>📄 원본 노트 (정리 전 원문)</summary>

- 분산 시스템에서 사용될 유일 ID 생성기를 설계해 볼 예정
- 보통 auto_increment 속성을 사용하면 되지 않을까… - 분산 환경에선 안됨 + 여러 DB를 쓰는 경우 지연 시간을 낮추기가 힘들다

**1단계. 문제 이해 및 설계 범위 확정** — 요구사항
- ID는 유일해야 한다.
- ID는 숫자로만 구성되어야 한다.
- ID는 64비트로 표현될 수 있는 값이어야 한다.
- ID는 발급 날짜에 따라 정렬 가능해야 한다.
- 초당 10,000개의 ID를 만들 수 있어야 한다.

**2단계. 개략적 설계안 제시 및 동의 구하기**
- 분산 시스템에서 유일성이 보장되는 ID를 만드는 방법은 여러 가지가 있다.

*다중 마스터 복제 (multi-master replication)*
[🖼️ 원본 이미지: 다중 마스터 복제]
- 데이터베이스의 auto_increment 기능을 활용. 다음 ID의 값을 구할 때 k만큼 증가시킨다. (k = DB 서버의 수)
- 장점
	- 규모 확장성 문제를 어느 정도 해결할 수 있다.
	- DB 수를 늘리면 초당 생산 가능 ID 수도 늘릴 수 있기 때문이다.
- 단점
	- 여러 데이터 센터에 걸쳐 규모를 늘리기 어렵다.
	- ID의 유일성은 보장되겠지만 그 값이 시간 흐름에 맞추어 커지도록 보장할 수는 없다.
	- 서버를 추가하거나 삭제할 때도 잘 동작하도록 만들기 어렵다.

*UUID (Universally Unique Identifier)*
- UUID: 컴퓨터 시스템에 저장되는 정보를 유일하게 식별하기 위한 128비트짜리 수
- 충돌 가능성이 지극히 낮다. ("중복 UUID가 1개 생길 확률을 50%로 끌어 올리려면 초당 10억 개의 UUID를 100년동안 계속해서 만들어야 한다.")
- 서버 간 조율 없이 독립적으로 생성 가능하다.
[🖼️ 원본 이미지: UUID 사용 시스템 구조]
- 각 웹 서버는 별도의 ID 생성기를 사용해 독립적으로 ID를 만들어낸다.
- 장점
	- UUID를 만드는 것은 단순
	- 서버 사이의 조율이 필요 없으므로 동기화 이슈도 없다.
	- 각 서버가 자기가 쓸 ID를 알아서 만드는 구조이므로 규모 확장도 쉽다.
- 단점
	- ID가 128비트로 같다. 이번 장에서 다루는 문제의 요구사항은 64비트이다.
	- ID를 시간순으로 정렬할 수 없다.
	- ID에 숫자(number)가 아닌 값이 포함될 수 있다.

*티켓 서버 (ticket server)*
- 분산 시스템 환경에서 고유한 식별자를 발급하기 위해 설계된 전담 데이터베이스 아키텍처
	- 여러 대의 웹 서버가 각자 알아서 ID를 만들면 겹칠 수도 있기에
	- 중앙에 서버를 하나 둬서 다른 웹 서버가 이곳에서 번호표를 받아 가도록 한 거
- 플리커(Flickr, 웹 사이트)는 분산 기본 키를 만들어 내기 위해 이 기술을 사용했다.
- auto_increment 기능을 갖춘 DB 서버, 즉 티켓 서버를 중앙 집중형으로 하나만 사용한다.
[🖼️ 원본 이미지: 티켓 서버 동작]
- 장점
	- 유일성이 보장되는 오직 숫자로만 구성된 ID를 쉽게 만들 수 있다.
	- 구현하기 쉽고, 중소 규모 애플리케이션에 적합하다.
- 단점
	- 티켓 서버가 SPFO가 된다. 해당 서버에 장애가 발생하면 모든 시스템이 영향을 받는다. (그렇다고 서버를 여러 대 사용하면 동기화 문제 발생 하니까 플리커라는 것으로 DB 설정을 틀어서 동기화 문제 해결 가능) (e.g. 티켓 서버 A는 홀수만 발급, 티켓 서버 B는 짝수만 발급)

*트위터 스노플레이크 (twitter snowflake) 접근법*
- 이번 장에서 풀어야 하는 문제의 요구사항을 만족시킬 수 있다.
[🖼️ 원본 이미지: 스노플레이크 64비트 구조]
- 생성할 64비트 ID의 구조 (생성해야 하는 ID의 구조를 여러 절로 분할)
- 사인(sign) 비트: 1비트를 할당한다. 음수와 양수를 구별하는 데 사용한다.
- 타임스탬프(timestamp): 41비트를 할당한다. 기원 시각 이후로 몇 밀리초가 경과했는지 나타내는 값이다. → 시간 순으로 정렬이 된다
- 데이터센터 ID: 5비트를 할당한다. (따라서 데이터센터당 32개 데이터센터 지원 가능)
- 서버 ID: 5비트를 할당한다. (따라서 데이터센터당 32개 서버 서버 사용 가능)
- 일련번호: 12비트를 할당한다. 각 서버에서 ID를 생성할 때마다 일련번호를 1만큼 증가시킨다. 1밀리초가 경과할 때마다 0으로 초기화된다.(1ms가 지나가면 0으로 리셋한다)

**3단계. 상세 설계**
- 트위터 스노플레이크 접근법을 사용하여 상세한 설계를 진행
- 데이터센터 ID와 서버 ID는 시스템이 시작할 때 결정 일반적으로 시스템 운영 중에는 바뀌지 않는다.
- 데이터센터 ID나 서버 ID를 잘못 변경하게 되면 ID 충돌이 발생할 수 있으므로, 신중해야 한다.
- 타임스탬프나 일련번호는 ID 생성기가 돌고 있는 중에 만들어지는 값이다.

*타임스탬프*
- 시간이 흐름에 따라 점점 큰 값을 갖게 되므로, 결국 ID는 시간 순으로 정렬 가능하게 된다.
[🖼️ 원본 이미지: 이진 표현에서 UTC 시각 추출 예제]
- 역으로 적용하면 어떤 UTC 시각도 상술한 타임스탬프 값으로 변환할 수 있다.
- 41비트로 표현할 수 있는 타임스탬프의 최댓값은 대략 69년(2^41 - 1 밀리초)이다. 즉, 해당 ID 생성기는 69년만 정상 동작한다.
- 유효 시간(69년)이 지나면 기원 시각을 바꾸거나 ID 체계를 다른 것으로 이전해야 한다.

*일련번호*
- 어떤 서버가 같은 밀리초 동안 하나 이상의 ID를 만들어 낸 경우에만 0보다 큰 값을 갖게 된다.
- 12비트를 할당했으므로, 4096(2^12)개의 값을 가질 수 있다.

**4단계. 마무리** — 추가로 논의할 수 있는 사항
- 시계 동기화: 이제까지 ID 생성 서버들이 전부 같은 시계를 사용한다고 가정했지만, 실제 상황에서 그렇지 않을 경우가 많다.
- 각 절의 길이 최적화: 동시성이 낮고 수명이 긴 애플리케이션의 경우, 일련번호 절의 길이를 줄이고 타임스탬프 절의 길이를 늘리는 것이 효과적일 수 있다.
- 고가용성: ID 생성기는 필수 불가결 컴포넌트이므로 아주 높은 가용성을 제공해야 한다.

</details>
