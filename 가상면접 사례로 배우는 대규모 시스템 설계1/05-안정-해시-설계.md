## 1. 왜 필요한가 — 해시 키 재배치 문제

- **기존 방식** : `해시(키) mod 서버수`로 담당 서버를 정한다.
- **문제** : 서버가 **추가/삭제되면 나눗셈의 분모(N)가 바뀌어** 대부분의 키가 다른 서버로 재배치된다.

> ⚠️ **연쇄 장애** — 재배치로 캐시가 엉뚱한 서버를 가리켜 **대규모 캐시 미스** → 요청이 원본 **DB로 와르르** → 서비스 전체 마비. 안정 해시가 막으려는 게 바로 이 시나리오.

---

## 2. 안정 해시란 — 해시 링

- **정의** : 해시 테이블(서버 클러스터) 크기가 조정돼도 **평균 `k/n`개**(k=전체 키, n=서버 수)의 키만 재배치되는 해시 방식.
- **해시 링** : 해시 공간의 **시작점과 끝점을 이어 붙여 원**으로 만든 것. 서버 IP와 데이터 키를 모두 이 원 위에 흩뿌린다. 공간이 넓어 서로 겹칠 확률은 사실상 0.

### 2-1. 해시 함수 선택

| 함수 | 공간 크기 | 특징 |
|---|---|---|
| SHA-1 | 0 ~ 2^160-1 | 160비트. 충돌 확률 사실상 0 |
| SHA-2 | 0 ~ 2^256-1 | 더 넓지만 **암호화 해시라 무겁다** → 분산용으론 과함 |
| **MurmurHash** | — | 비암호 해시, 빠름 → **실무 분산용 표준** |

> 분산 배치는 보안이 목적이 아니므로, 무거운 SHA-2보다 **빠른 비암호 해시(MurmurHash 등)**를 더 많이 쓴다.

## 3. 동작 방식 — 배치 · 조회 · 추가 · 제거

- **배치** : 해시 함수 `f(키 → 해시값)`로 서버와 데이터를 각각 링 위 좌표에 올린다.

| 연산 | 규칙 |
|---|---|
| **조회** | 키 위치에서 **시계방향으로 처음 만나는 서버**가 그 키를 담당 |
| **서버 추가** | 새 서버와 **반시계 방향 이웃 서버 사이 구간의 키**만 새 서버로 이동. 나머지는 그대로 |
| **서버 제거** | 제거된 서버의 키만 **시계방향 다음 서버**로 이동. 나머지는 그대로 |

→ 핵심은 "**변화의 영향이 링에서 인접한 한 구간에만 국한**된다"는 점. 그래서 재배치가 `k/n` 수준으로 작다.

---

## 4. 기본 안정 해시의 한계

서버를 링에 **한 번씩만** 올리면 두 가지 쏠림이 생긴다.

- **파티션 크기 불균등** — *파티션 = 인접한 두 서버 사이의 해시 공간*. 서버 위치가 랜덤이라 어떤 구간은 넓고 어떤 구간은 좁다.
- **키 분포 불균등** — 넓은 파티션을 맡은 서버에 키가 쏠려 **핫스팟**이 생긴다.

---

## 5. 해결책 — 가상 노드 (Virtual Nodes)

- 실제 서버 하나를 링 위 **여러 지점(가상 노드)**에 랜덤 배치한다. → 한 서버가 여러 작은 구간을 나눠 맡아 쏠림이 평준화된다.
- **가상 노드가 많을수록 키 분포의 표준편차가 작아진다** (편차↓ = 더 균등). 통상 가상 노드 100개면 표준편차 ≈ 10%, 200개면 ≈ 5% 수준.

### 5-1. 트레이드오프

| 대가 | 내용 |
|---|---|
| 메모리 사용량↑ | 가상 노드 정보를 모두 저장해야 함 |
| 재배치 오버헤드 | 서버 하나가 다운/추가되면 그에 딸린 **수백 개 가상 노드**를 갱신 |
| 디버깅 복잡 | 링 탐색으로 가상 노드를 찾은 뒤 "**이게 진짜 어느 서버 것인지**" 매핑 확인 단계가 추가 |

## 6. 정리 & 셀프 체크

### 개념 → 한 줄 정리

| 개념 | 한 줄 |
|---|---|
| 재배치 문제 | `mod N`은 서버 수 바뀌면 대부분 키 이동 → 캐시 미스·DB 폭격 |
| 안정 해시 | 해시 링으로 평균 **`k/n`개**의 키만 이동 |
| 시계방향 조회 | 키에서 시계방향 첫 서버가 담당 |
| 기본형 한계 | 파티션 크기·키 분포가 치우침(핫스팟) |
| 가상 노드 | 서버를 링에 여러 번 배치 → 편차↓ (대가: 메모리·재배치·디버깅) |
| 사용처 | DynamoDB · Cassandra 파티셔닝 |

### 🔁 셀프 체크
1. 안정 해시가 `mod N` 방식 대비 무엇을 해결하는가?
2. 가상 노드를 늘리면 좋은 점과 그 대가는?
3. 서버가 새로 추가될 때 실제로 이동하는 키는 어떤 키인가?

<details>
<summary>답</summary>

1. `mod N`은 서버 수가 바뀌면 대부분 키가 재배치돼 캐시 미스가 폭발하고 DB로 요청이 몰린다. 안정 해시는 평균 `k/n`개 키만 이동해 그 충격을 최소화한다.
2. 가상 노드↑ → 키 분포 표준편차↓(더 균등, 100개≈10%·200개≈5%). 대가는 메모리 증가, 서버 변동 시 수백 개 가상 노드 갱신, 가상 노드→실제 서버 매핑 디버깅 복잡성.
3. **새 서버와 그 반시계 방향 이웃 서버 사이 구간**의 키만 새 서버로 이동한다. 나머지 키는 그대로다.

</details>

<summary>📄 원본 노트 (정리 전 원문)</summary>

- 안정 해시 : 요청이나 데이터를 서버에 균등하게 나눌 때 사용하는 기술
- 해시 키 재배치 문제
  - 기존 : 각 행 데이터의 해시를 서버 수로 나눈 나머지 값으로 서버에 분산
  - 문제 : 서버 추가·삭제되면 대부분 데이터가 다른 서버로 이동 → 대규모 캐시미스 → 메인 DB 폭격 → 서비스 마비
- 해결책 : 안정해시 = 해시 테이블(서버 클러스터)이 조정되면 "총데이터 수 / 서버 대수"의 데이터만 재배치
  - 해시 공간과 해시 링 : SHA-1(시작·끝점을 이어붙여 서버 IP·데이터 ID를 트랙 위에 흩뿌림, 겹칠 확률 0, 크기 2^160-1) / SHA-2(2^256-1, 더 안전하지만 보안이 무거워 해시용으론 MurmurHash 같은 비암호 해시 사용)
  - 해시 서버 : 해시 함수 f(키→해시값)로 서버 수만큼 링 위에 배치
  - 해시 키 : 링 위에 데이터를 올려둔 것
  - 서버조회 : 키 위치로부터 오른쪽으로 갔을 때 나오는 서버에 저장
  - 서버 추가 : 서버 위치 왼쪽 데이터만 추가 서버로, 나머지는 그대로
  - 서버 제거 : 데이터 위치에서 가장 가까운 시계방향 서버로 이동
  - 문제점 2가지 : 파티션(인접 서버 사이 해시 공간) 크기가 균등하지 못함 / 키의 균등 분포 어려움
  - 해결책 가상노드 : 실제 서버를 가리키는 노드. 하나의 서버는 여러 가상노드를 가질 수 있고 랜덤 배치. 많을수록 편차 줄어듦. 트레이드오프(메모리 증가, 재배치 오버헤드-수백개 가상노드 업데이트, 디버깅·추적 복잡성)
  - 재배치할 키 결정 : 서버 추가 시 시계 반대쪽 데이터 전부, 삭제 시 가장 가까운 서버로
- 다이나모 DB나 카산드라에서 파티셔닝할 때 사용하는 개념

</details>
