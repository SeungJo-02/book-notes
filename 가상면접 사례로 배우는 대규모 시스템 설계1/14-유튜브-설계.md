## 2. 개략 설계 — 단말·CDN·API 서버

CDN과 BLOB 스토리지는 직접 만들지 않고 **기존 클라우드 서비스**를 쓴다.

[🖼️ 원본 이미지: 3개 컴포넌트로 구성된 개략적 설계]

| 컴포넌트 | 역할 |
|---|---|
| **단말(client)** | 컴퓨터, 모바일 폰, 스마트 TV |
| **CDN** | 비디오를 저장·캐시. 재생 버튼을 누르면 **CDN에서 스트리밍** |
| **API 서버** | 스트리밍을 뺀 **나머지 전부**: 피드 추천, 업로드 URL 생성, 메타데이터 DB·캐시 갱신, 가입 등 |

> 비유하면 CDN은 전국에 깔린 **편의점**이고, API 서버는 **본사 사무실**이다. 영상(무거운 물건)은 가까운 편의점에서 받고, 회원가입·추천 같은 서류 일은 본사가 처리한다.

## 3. 비디오 업로드 절차

[🖼️ 원본 이미지: 비디오 업로드 절차의 개략적 설계안]

| 컴포넌트 | 역할 |
|---|---|
| **로드밸런서** | API 서버 여러 대에 요청을 고르게 분산 |
| **API 서버** | 스트리밍 이외 모든 요청 처리 |
| **메타데이터 DB** | 비디오 제목·크기·포맷 등 메타데이터 보관. **샤딩/리플리케이션**으로 성능·가용성 확보 |
| **메타데이터 캐시** | 메타데이터와 사용자 객체 캐시 |
| **원본 저장소** | 원본 비디오를 담는 **BLOB**(대형 이진 파일) 저장소 |
| **트랜스코딩 서버** | 비디오 포맷(MPEG, HLS 등)을 단말·대역폭에 맞게 변환 |
| **트랜스코딩 비디오 저장소** | 변환 완료된 비디오를 담는 BLOB 저장소 |
| **CDN** | 변환된 비디오 캐시. 재생은 여기서 |
| **트랜스코딩 완료 큐** | 트랜스코딩 완료 이벤트를 담는 **메시지 큐** |
| **트랜스코딩 완료 핸들러** | 큐에서 이벤트를 꺼내 메타데이터 **캐시·DB를 갱신**하는 작업 서버 |

업로드는 두 프로세스가 **동시에** 돈다.

### 프로세스 a: 비디오 업로드

[🖼️ 원본 이미지: 프로세스 a 비디오 업로드 흐름]

1. 비디오를 **원본 저장소**에 업로드한다.
2. 트랜스코딩 서버가 원본 저장소에서 비디오를 가져와 **트랜스코딩**을 시작한다.
3. 트랜스코딩이 끝나면 아래 두 작업이 **병렬**로 진행된다.
   - 3a. 완료된 비디오를 **트랜스코딩 비디오 저장소**에 올린다 → 3a.1. 그 비디오를 **CDN**에 올린다.
   - 3b. 완료 이벤트를 **트랜스코딩 완료 큐**에 넣는다 → 3b.1. 완료 핸들러가 이벤트를 꺼낸다 → 3b.1.a. 메타데이터 **DB** 갱신, 3b.1.b. 메타데이터 **캐시** 갱신.
4. API 서버가 단말에게 "업로드 끝, 스트리밍 준비 완료"를 알린다.

### 프로세스 b: 메타데이터 갱신

[🖼️ 원본 이미지: 프로세스 b 메타데이터 갱신 흐름]

- 원본 저장소에 파일이 올라가는 **동안**, 단말은 **병렬로** 메타데이터 갱신 요청을 API 서버에 보낸다.
- 요청에는 파일 이름, 크기, 포맷 등이 들어 있고, API 서버는 이걸로 메타데이터 캐시와 DB를 갱신한다.

**두 프로세스를 시간순으로 붙이면**

| 시점 | 일어나는 일 | 사용자가 보는 것 |
|---|---|---|
| 업로드 시작 | (b) "이런 영상 올려요" 메타데이터 먼저 등록 → DB 상태 **처리 중(Processing)** / (a-1) 원본 업로드 | 업로드 진행 바 |
| 트랜스코딩 | (a-2) 화질별 인코딩 | "동영상 처리 중입니다" |
| 완료 핸들러 | (a-3) CDN 업로드 + 핸들러가 (b)에서 만든 레코드에 **CDN 주소 추가**, 상태 **준비 완료(Ready)** | 아직 처리 중 |
| 최종 알림 | (a-4) API 서버가 단말에 완료 알림 | "이제 공개돼요" |

> 핵심은 메타데이터를 **먼저** 등록해 두고, 트랜스코딩이 끝나면 핸들러가 그 레코드를 **갱신**한다는 것. 그래서 "처리 중" 상태를 사용자에게 보여줄 수 있다.

## 4. 비디오 스트리밍 절차

- **스트리밍 프로토콜**: 비디오 데이터를 보낼 때 쓰는 **표준화된 통신 방법**. 단말이 지원하는 프로토콜에 맞춰 인코딩해야 한다.

| 프로토콜 | 만든 곳 |
|---|---|
| **MPEG-DASH** (Dynamic Adaptive Streaming over HTTP) | MPEG 표준 |
| **HLS** (HTTP Live Streaming) | 애플 |
| 스무드(Smooth) 스트리밍 | 마이크로소프트 |
| HTTP 동적 스트리밍 | 어도비 |

> DASH·HLS 둘 다 이름에 **HTTP**가 들어간다. 영상을 몇 초짜리 조각으로 잘라 두고 일반 웹 요청으로 받아가기 때문에, 특별한 서버 없이 CDN을 그대로 쓸 수 있고 **중간에 화질을 바꾸기** 쉽다.

[🖼️ 원본 이미지: 비디오 스트리밍 개략적 설계]

- 사용자 단말에 **가장 가까운 CDN 에지(edge) 서버**가 비디오를 보내므로 전송 지연이 아주 낮다.

## 5. 비디오 트랜스코딩 ⭐

### 5-1. 왜 변환하나 (비트레이트)

- **비트레이트**: 1초 영상을 표현하는 데 쓰는 데이터 양. 높을수록 선명하지만 **더 센 컴퓨터와 더 빠른 회선**이 필요하다.

| 이유 | 설명 |
|---|---|
| 원본은 너무 크다 | 가공 안 한 원본은 저장 공간을 많이 차지 |
| 단말마다 지원 포맷이 다르다 | 상당수 단말·브라우저는 특정 포맷만 재생 |
| 끊김 없는 재생 | 대역폭이 좁은 사용자에겐 저화질, 넓은 사용자에겐 고화질 |
| 모바일은 네트워크가 수시로 바뀐다 | 품질을 **자동/수동으로 바꿀 수 있어야** 함 |

### 5-2. 인코딩 포맷

| 용어 | 뜻 | 비유 |
|---|---|---|
| **컨테이너(container)** | 비디오·오디오·메타데이터를 담는 그릇 (.mp4, .mov 등) | 도시락 **통** |
| **코덱(codec)** | 화질은 지키면서 파일 크기를 줄이는 **압축·해제 알고리즘** (H.264, VP9 등) | 도시락을 **꾹꾹 눌러 담는 방법** |

### 5-3. 유향 비순환 그래프(DAG) 모델

- 영상마다 필요한 처리가 다르다(어떤 건 워터마크, 어떤 건 섬네일만). 그래서 **각기 다른 처리 파이프라인**을 지원해야 한다.
- 병렬성을 높이려고 적절한 **추상화**를 두고, 클라이언트 프로그래머가 **실행할 작업(task)을 직접 정의**하게 한다.
- **DAG**: 화살표가 있고(유향) 돌아오는 길이 없는(비순환) 그래프. "A 끝나면 B·C 동시에, 둘 다 끝나면 D" 같은 **작업 순서도**다.

[🖼️ 원본 이미지: 비디오 트랜스코딩을 위해 채택한 DAG 모델]

| 작업 | 내용 |
|---|---|
| **검사** | 품질이 좋은지, 손상은 없는지 확인 |
| **비디오 인코딩** | 다양한 **해상도·코덱·비트레이트 조합**으로 인코딩 |
| **섬네일** | 사용자가 올린 이미지나 비디오에서 자동 추출한 이미지로 생성 |
| **워터마크** | 식별 정보를 이미지 위에 **오버레이** |

## 6. 트랜스코딩 아키텍처

[🖼️ 원본 이미지: 클라우드 서비스를 활용한 비디오 트랜스코딩 아키텍처]

5개 컴포넌트가 동작한 결과로 **인코딩된 비디오**가 나온다.

### 6-1. 전처리기

| 역할 | 내용 |
|---|---|
| **비디오 분할** | 비디오 스트림을 **GOP(Group of Pictures)** 단위로 쪼갠다. GOP는 특정 순서로 배열된 프레임 묶음으로 **독립 재생 가능**, 길이는 보통 몇 초 |
| **DAG 생성** | 클라이언트 프로그래머가 쓴 **설정 파일**에 따라 DAG를 만든다 |
| **데이터 캐시** | 분할된 비디오(GOP)와 메타데이터를 **임시 저장소**에 보관. 인코딩이 실패하면 보관된 데이터로 **재개** |

- 오래된 단말·브라우저는 GOP 단위 분할을 지원하지 않으므로 전처리기가 대신 쪼갠다.

### 6-2. DAG 스케줄러

- DAG를 **몇 개 단계(stage)** 로 나눈 뒤 각 단계를 자원 관리자의 **작업 큐**에 넣는다.

[🖼️ 원본 이미지: 하나의 DAG를 2개 작업 단계로 쪼갠 사례]

| 단계 | 작업 |
|---|---|
| 1단계 | 비디오·오디오·메타데이터 **분리** |
| 2단계 | 비디오 인코딩 + 섬네일 추출 + 오디오 인코딩 (**병렬**) |

### 6-3. 자원 관리자

- 자원을 효과적으로 **배분**한다. 큐 3개와 스케줄러 1개로 구성.

[🖼️ 원본 이미지: 3개 큐와 작업 스케줄러로 구성된 자원 관리자]

| 구성 | 내용 |
|---|---|
| **작업 큐** | 실행할 작업이 담긴 **우선순위 큐** |
| **작업 서버 큐** | 작업 서버의 가용 상태가 담긴 **우선순위 큐** |
| **실행 큐** | 현재 실행 중인 작업과 그 작업을 맡은 서버 정보 |
| **작업 스케줄러** | 최적의 **작업/서버 조합**을 골라 실행 지시 |

작업 스케줄러 동작 순서
1. 작업 큐에서 **가장 우선순위 높은 작업**을 꺼낸다.
2. 그 작업에 맞는 **작업 서버**를 고른다.
3. 서버에 실행을 지시한다.
4. 어떤 서버에 할당했는지 **실행 큐**에 기록한다.
5. 작업이 끝나면 실행 큐에서 **제거**한다.

### 6-4. 작업 서버

- DAG에 정의된 작업을 실제로 수행한다. **작업 종류별로 서버를 구분**해 관리(워터마크 서버, 인코딩 서버, 섬네일 서버, 병합 서버 …).

[🖼️ 원본 이미지: 작업 종류별 작업 서버]

### 6-5. 임시 저장소

- 데이터 **유형·크기·이용 빈도·유효기간**에 따라 저장소를 달리 쓴다.

| 데이터 | 저장소 | 이유 |
|---|---|---|
| 메타데이터 | **메모리 캐시** | 작업 서버가 자주 참조하고 크기가 작다 |
| 비디오/오디오 | **BLOB 저장소** | 크다 |

- 임시 저장소의 데이터는 비디오 프로세싱이 끝나면 **삭제**한다.

### 6-6. 인코딩된 비디오

- 인코딩 파이프라인의 **최종 결과물**(예: `funny_720p.mp4`).

## 7. 시스템 최적화 — 속도·안전성·비용

### 7-1. 속도

| 최적화 | 내용 |
|---|---|
| **비디오 병렬 업로드** | 비디오를 **GOP 단위로 쪼개** 병렬 업로드. 일부가 실패해도 그 조각만 다시 올리면 된다. GOP 경계로 쪼개는 일을 **단말이** 하면 더 빠르다 |
| **업로드 센터를 사용자 근거리에** | 미국 사용자는 북미, 중국 사용자는 아시아 업로드 센터로. 본 설계는 **CDN을 업로드 센터로** 활용 |
| **모든 절차를 병렬화** | 아래 참고 |

[🖼️ 원본 이미지: 병렬화 전, 각 단계가 앞 단계 결과를 기다리는 흐름]

- 원래 흐름은 **이전 단계의 결과물을 입력**으로 쓰므로(의존성) 앞 단계가 끝나기 전엔 다음 단계가 못 움직인다.
- **메시지 큐**를 중간에 끼워 **느슨하게 결합**한다.

[🖼️ 원본 이미지: 결합도를 낮추기 위한 메시지 큐 도입]

| 전 | 후 |
|---|---|
| 인코딩 모듈은 **다운로드 모듈이 끝나기를 기다려야** 했다 | 큐에 쌓인 이벤트 각각을 인코딩 모듈이 **병렬로** 처리한다 |

### 7-2. 안전성

**미리 서명된(pre-signed) 업로드 URL**
- 허가받은 사용자만 **올바른 위치**에 업로드하도록 보장한다.

[🖼️ 원본 이미지: 미리 사인된 업로드 URL 이용]

1. 클라이언트가 API 서버에 POST 요청으로 **미리 서명된 URL**을 달라고 한다. (그 URL이 가리키는 객체에 대한 접근 권한은 이미 부여된 상태)
2. API 서버가 미리 서명된 URL을 돌려준다.
3. 클라이언트는 그 URL이 가리키는 위치에 비디오를 **직접** 업로드한다.

> 비유: 택배 기사가 아파트 **공동현관 비밀번호**를 주민에게 1시간짜리 임시 번호로 받는 것. 번호가 있으면 그 시간 동안 그 동에만 들어갈 수 있고, 지나면 못 쓴다. 서버가 영상을 받아서 다시 저장소에 넣는 **중계 비용**도 없어진다.

**비디오 보호**

| 방법 | 내용 |
|---|---|
| **DRM** (디지털 저작권 관리) | 애플 페어플레이, 구글 와이드바인, MS 플레이레디 |
| **AES 암호화** | 허락된 사용자만 복호화해 시청 |
| **워터마크** | 소유자 정보(회사 로고·이름)를 비디오 위에 오버레이 |

### 7-3. 비용

CDN 비용(하루 $150,000)이 너무 크므로 **롱테일**(소수의 인기 영상이 대부분의 조회를 차지)을 이용한다.

1. **인기 비디오만 CDN**, 나머지는 비디오 서버에서 직접 재생.
2. 인기 없는 비디오는 **미리 인코딩하지 않는다**. 짧은 비디오라면 **요청 시 인코딩**.
3. 특정 지역에서만 인기인 비디오는 **다른 지역으로 옮기지 않는다**.
4. **CDN을 직접 구축**하고 ISP와 제휴 (넷플릭스 방식). 사용자 경험과 인터넷 비용 모두 개선.

## 8. 오류 처리

| 분류 | 처리 |
|---|---|
| **회복 가능 오류** | 재시도로 해결 시도. 안 되면 클라이언트에 적절한 오류 코드 |
| **회복 불가능 오류** | 관련 작업 중단, 클라이언트에 적절한 오류 코드 |

| 오류 | 해결 |
|---|---|
| 업로드 오류 | 몇 회 **재시도** |
| 비디오 분할 오류 | 단말이 못 쪼개면 **전체를 서버로 보내고 서버가 분할** |
| 트랜스코딩 오류 | 재시도 |
| 전처리 오류 | **DAG 재생성** |
| DAG 스케줄러 오류 | 작업 **재스케줄링** |
| 자원 관리자 큐 장애 | **사본(replica)** 이용 |
| 작업 서버 장애 | **다른 서버**에서 재시도 |
| API 서버 장애 | **무상태**라 신규 요청은 다른 API 서버로 |
| 메타데이터 캐시 서버 장애 | 데이터가 **다중화**되어 다른 노드에서 읽음. 죽은 서버는 교체 |
| 메타데이터 DB 서버 장애 | 주 서버 사망 → **부 서버 중 하나를 주로 승격** / 부 서버 사망 → 다른 부 서버로 읽기, 죽은 서버 교체 |

|---|---|

# **14장 유튜브 설계**
- 유튜브 시스템을 설계해보자.

## **문제 이해 및 설계 범위 확정**
- 빠른 비디오 업로드
- 원활한 비디오 재생
- 재생 품질 선택 기능
- 낮은 인프라 비용
- 높은 가용성과 규모 확장성, 그리고 안정성
- 지원 클라이언트: 모바일 앱, 웹 브라우저, 그리고 스마트 TV

### **개략적 규모 추정**
- 일간 능동 사용자(DAU) 수는 5백만
- 한 사용자는 하루에 평균 5개의 비디오를 시청
- 10%의 사용자가 하루에 1비디오 업로드
- 비디오 평균 크기는 300MB
- 비디오 저장을 위해 매일 새로 요구되는 저장 용량 = 5백만 \* 10% \* 300MB = 150TB
- CDN 비용
  - 클라우드 CDN을 통해 비디오를 서비스할 경우 CDN에서 나가는 데이터의 양에 따라 과금한다.
  - 아마존의 CloudFront를 CDN 솔루션으로 사용할 경우, 100% 트래픽이 미국에서 발생한다고 가정하면 1GB당 \$0.02의 요금이 발생한다.
  - 따라서 매일 발생하는 요금은 5백만 \* 5비디오 \* 0.3GB \* \$0.02 = \$150,000이다.

## **개략적 설계안 제시 및 동의 구하기**
- CDN과 BLOB 스토리지의 경우에는 기존 클라우드 서비스를 활용할 것이다.

[🖼️ 원본 이미지: 3개 컴포넌트로 구성된 개략적 설계]
🔼 3개 컴포넌트로 구성된 개략적 설계
- 단말(client): 컴퓨터, 모바일 폰, 스마트 TV를 통해서 유튜브를 시청할 수 있다.
- CDN: 비디오는 CDN에 저장한다. 재생 버튼을 누르면 CDN으로부터 스트리밍이 이루어진다.
- API 서버: 비디오 스트리밍을 제외한 모든 요청은 API 서버가 처리한다. 피드 추천, 비디오 업로드 URL 생성, 메타데이터 데이터베이스와 캐시 갱신, 사용자 가입 등등이 API 서버가 처리하는 과정이다.

### **비디오 업로드 절차**

[🖼️ 원본 이미지: 비디오 업로드 절차의 개략적 설계안]
🔼 비디오 업로드 절차의 개략적 설계안
- 사용자: 컴퓨터나 모바일 폰, 혹은 스마트 TV를 통해 유튜브를 시청하는 이용자
- 로드밸런서: API 서버 각각으로 고르게 요청을 분산하는 역할을 담당한다.
- API 서버: 비디오 스트리밍을 제외한 다른 모든 요청을 처리한다.
- 메타데이터 데이터베이스: 비디오의 메타데이터를 보관한다. (샤딩/리플리케이션을 적용하여 성능/가용성 요구사항 충족)
- 원본 저장소: 원본 비디오를 보관할 대형 이진 파일 저장소(BLOB) 시스템
- 트랜스코딩 서버(비디오 인코딩): 비디오 포맷(MPEG, HLS 등)을 변환하는 절차 (단말/대역폭 요구사항에 맞는 최적의 비디오 스트림 제공에 필요)
- 트랜스코딩 비디오 저장소: 트랜스코딩이 완료된 비디오를 저장하는 BLOB 저장소
- CDN: 비디오를 캐시하는 역할을 담당한다. 사용자가 재생 버튼을 누르면 비디오 스트리밍은 CDN을 통해 이루어진다.
- 트랜스코딩 완료 큐: 비디오 트랜스코딩 완료 이벤트들을 보관할 메시지 큐다.
- 트랜스코딩 완료 핸들러: 트랜스코딩 완료 큐에서 이벤트 데이터를 꺼내 메타데이터 캐시와 데이터베이스를 갱신할 작업 서버들이다.

> ***프로세스a : 비디오 업로드***

[🖼️ 원본 이미지: 프로세스 a 비디오 업로드]
1. 비디오를 원본 저장소에 업로드한다.
2. 트랜스코딩 서버는 원본 저장소에서 해당 비디오를 가져와 트랜스코딩을 시작한다.
3. 트랜스코딩이 완료되면 아래 두 절차가 병렬적으로 수행된다.
  - 완료된 비디오를 트랜스코딩 비디오 저장소로 업로드한다.
  - 트랜스코딩 완료 이벤트를 트랜스코딩 완료 큐에 넣는다.
    - 트랜스코딩이 끝난 비디오를 CDN에 올린다.
    - 완료 핸들러가 이벤트 데이터를 큐에서 꺼낸다.
      - 완료 핸들러가 메타데이터 데이터베이스를 갱신한다.
      - 완료 핸들러가 메타데이터 캐시를 갱신한다.
4. API 서버가 단말에게 비디오 업로드가 끝나서 스트리밍 준비가 되었음을 알린다.

> ***프로세스b : 메타데이터 갱신***

[🖼️ 원본 이미지: 프로세스 b 메타데이터 갱신]
- 원본 저장소에 파일이 업로드되는 동안, 단말은 병렬적으로 비디오 메타데이터 갱신 요청을 API 서버에 보낸다.
- 요청에 포함된 메타데이터는 파일 이름, 크기, 포맷 등의 정보가 들어 있다. API 서버는 이 정보로 메타데이터 캐시와 데이터베이스를 업데이트한다.

- **업로드 시작 (프로세스 B + 프로세스 A의 1번):**<br>사용자가 비디오 원본을 올리기 시작함과 동시에 "나 이런 영상(제목, 용량 등) 올려요"라고 API 서버에 메타데이터 갱신 요청을 보냅니다. 이때 DB에는 이 영상의 상태가 '처리 중(Processing)'으로 먼저 기록됩니다.
- **트랜스코딩 진행 (프로세스 A의 2번):**<br>원본 저장소에 파일이 다 올라가면 서버가 열심히 화질별로 인코딩을 시작합니다. 이때 사용자는 화면에서 '동영상 처리 중입니다' 같은 안내 메시지를 보게 됩니다.
- **작업 완료 및 핸들러의 갱신 (프로세스 A의 3번):**<br>인코딩이 끝나고 CDN에 파일이 다 올라가면, 완료 핸들러가 DB와 캐시를 찾아가서 아까 프로세스 B에서 만들어둔 기록에 'CDN 주소'들을 덧붙이고, 상태를 '서비스 준비 완료(Ready)'로 갱신(업데이트)합니다.
- **최종 알림 (프로세스 A의 4번):**<br>DB 갱신까지 모두 끝났으니, API 서버가 최종적으로 사용자의 단말(앱이나 웹 브라우저)에 "비디오 처리가 다 끝났어! 이제 시청자들에게 보여줘도 돼!"라고 완료 알림(푸시 알림이나 화면 갱신)을 전달합니다.

## **상세 설계**

### **비디오 트랜스코딩**
- 비트레이트가 높은 비디오 스트림을 정상 재생하려면 보다 높은 성능의 컴퓨팅 파워가 필요하고, 인터넷 회선 속도도 빨라야 한다.
- 비트레이트가 중요한 이유
  - 가공되지 않은 원본 비디오는 저장 공간을 많이 차지한다.
  - 상당수의 단말과 브라우저는 특정 종류의 비디오 포맷만 지원한다.
  - 끊김없는 비디오 재생 보장을 위해서, 네트워크 대역폭이 충분하지 않은 사용자에게는 저화질 비디오를, 충분한 사용자에게는 고화질 비디오를 보내야 한다.
  - 모바일 단말의 경우 네트워크 상황이 수시로 달라질 수 있다. (비디오 품질 자동/수동 변경이 가능하도록 해야 함)
- 인코딩 포맷
  - 컨테이너(container): 비디오 파일, 오디오, 메타데이터를 담는 바구니 같은 것
  - 코덱(codec): 비디오 화질은 보존하면서 파일 크기를 줄일 목적으로 고안된 압축 및 압축 해제 알고리즘

### **유향 비순환 그래프(DAG) 모델**
- 각기 다른 유형의 비디오 프로세싱 파이프라인을 지원한다.
- 처리 과정의 병렬성을 높이기 위해 적절한 수준의 추상화를 도입하여 클라이언트 프로그래머로 하여금 실행할 작업(task)을 손수 정의할 수 있도록 해야 한다.

[🖼️ 원본 이미지: 비디오 트랜스코딩을 위해 본 설계안이 채택한 DAG 모델]
🔼 비디오 트랜스코딩을 위해 본 설계안이 채택한 DAG 모델
- 검사: 좋은 품질의 비디오인지, 손상은 없는 지 확인하는 작업
- 비디오 인코딩: 비디오를 다양한 해상도, 코덱, 비트레이트 조합으로 인코딩하는 작업
- 섬네일: 사용자가 업로드한 이미지나 비디오에서 자동 추출된 이미지로 섬네일을 만드는 작업
- 워터마크: 비디오에 대한 식별정보를 이미지 위에 오버레이 형태로 띄워 표시하는 작업

### **비디오 트랜스코딩 아키텍처**

[🖼️ 원본 이미지: 본 설계안에서 정의한 클라우드 서비스를 활용한 비디오 트랜스코딩 아키텍처]
🔼 본 설계안에서 정의한 클라우드 서비스를 활용한 비디오 트랜스코딩 아키텍처
- 이 아키텍처가 동작한 결과로 인코딩된 비디오가 만들어진다.
- 5개의 주요 컴포넌트로 구성된다.
  - 전처리기
  - DAG 스케줄러
  - 자원 관리자
  - 작업 실행 서버
  - 임시 저장소

> ***전처리기***

1. 비디오 분할: 비디오 스트림을 GOP(Group of Pictures) 단위로 쪼갠다.
  - GOP는 특정 순서로 배열된 프레임 그룹이다.
  - 하나의 GOP는 독립적으로 재생 가능하며, 길이는 보통 몇 초 정도다.
  - 어떤 종류의 오래된 단말이나 브라우저는 GOP 단위의 비디오 분할을 지원하지 않는다. (전처리기가 대신 역할)
2. DAG 생성: 클라이언트 프로그래머가 작성한 설정 파일에 따라 DAG를 만들어낸다.
3. 데이터 캐시: 전처리기는 분할된 비디오의 캐시이기도 하다. 안정성을 높이기 위해 전처리기는 GOP와 메타데이터를 임시 저장소에 보관한다. 비디오 인코딩이 실패하면 시스템은 보관된 데이터를 활용해 인코딩을 재개한다.

> ***DAG 스케줄러***

- DAG 그래프를 몇 개 단계로 분할한 다음에 그 각각을 자원 관리자의 작업 큐에 집어넣는다.

[🖼️ 원본 이미지: 하나의 DAG 그래프를 2개 작업 단계로 쪼갠 사례]
🔼 하나의 DAG 그래프를 2개 작업 단계로 쪼갠 사례
- `1단계`: 비디오, 오디오, 메타데이터를 분리한다.
- `2단계`: 해당 비디오 파일을 인코딩하고 섬네일을 추출하며, 오디오 파일 또한 인코딩한다.

> ***자원 관리자***

- 자원 배분을 효과적으로 수행하는 역할을 담당한다.

[🖼️ 원본 이미지: 3개 큐와 작업 스케줄러로 구성된 자원 관리자]
🔼 3개와 큐와 작업 스케줄러로 구성된다.
- 작업 큐: 실행할 작업이 보관되어 있는 우선순위 큐
- 작업 서버 큐: 작업 서버의 가용 상태 정보가 보관되어 있는 우선순위 큐
- 실행 큐: 현재 실행 중인 작업 및 작업 서버 정보가 보관되어 있는 큐
- 작업 스케줄러: 최적의 작업/서버 조합을 골라, 해당 작업 서버가 작업을 수행하도록 지시하는 역할 담당

**작업 관리자**
- 작업 관리자는 작업 큐에서 가장 높은 우선순위의 작업을 꺼낸다.
- 작업 관리자는 해당 작업을 실행하기 적합한 작업 서버를 고른다.
- 작업 스케줄러는 해당 작업 서버에게 작업 실행을 지시한다.
- 작업 스케줄러는 해당 작업이 어떤 서버에게 할당되었는지에 관한 정보를 실행 큐에 넣는다.
- 작업 스케줄러는 작업이 완료되면 해당 작업을 실행 큐에서 제거한다.

> ***작업 서버***

- DAG에 정의된 작업을 수행한다.

[🖼️ 원본 이미지: 작업 종류별 작업 서버]
- 작업 종류에 따라 작업 서버도 구분하여 관리한다.

> ***임시 저장소***

- 여러 저장소 시스템을 활용할 수 있다.
- 저장할 데이터의 유형, 크기, 이용 빈도, 데이터 유효기간 등에 따라 달라진다.
- Ex1. 메타데이터는 작업 서버가 빈번이 참조하고 크기도 보통 작으므로, 메모리에 캐시해두면 좋다.
- Ex2. 비디오/오디오 데이터는 BLOB 저장소에 두는 것이 바람직하다.
- Ex3. 임시 저장소에 보관한 데이터는 비디오 프로세싱이 완료되면 삭제한다.

### **시스템 최적화**
- 속도, 안전성, 그리고 비용 측면에서 시스템을 최적화해보자.

> ***속도 최적화: 비디오 병렬 업로드***

- 하나의 비디오는 작은 GOP들로 분할할 수 있다.
- 분할한 GOP를 병렬적으로 업로드하면서 일부가 실패하더라도 빠르게 업로드 재개할 수 있다.
- 비디오를 GOP 경계에 맞춰 분할하는 작업을 단말이 수행하면 업로드 속도를 높일 수 있다.

> ***속도 최적화: 업로드 센터를 사용자 근거리에 지정***

- 업로드 센터를 여러 곳에 두는 것이다.
- 미국 거주자는 비디오를 북미 지역 업로드 센터로, 중국 사용자는 아시아 업로드 센터로 보내도록 한다.
- 본 설계안은 CDN을 업로드 센터로 이용한다.

> ***속도 최적화: 모든 절차를 병렬화***

[🖼️ 원본 이미지: 이전 단계의 결과물을 입력으로 쓰는 흐름]
- 위 그림은 이전 단계의 결과물을 입력으로 사용하여 만들어진다. (의존성)
- 느슨하게 결합된 시스템을 만들어서 병렬성을 높여보자.
- 결합도를 낮추기 위해 설계안을 변경해보자.

[🖼️ 원본 이미지: 결합도를 낮추기 위한 메시지 큐 도입]
🔼 결합도를 낮추기 위한 메시지 큐 도입
- 메시지 큐를 도입하기 전에 인코딩 모듈은 다운로드 모듈의 작업이 끝나기를 기다려야 했다.
- 메시지 큐를 도입한 뒤에, 메시지 큐에 보관된 이벤트 각각을 인코딩 모듈이 병렬적으로 처리할 수 있다.

> ***안전성 최적화: 미리 사인된 업로드 URL***

- 허가받은 사용자만이 올바른 장소에 비디오를 업로드할 수 있도록 한다.

[🖼️ 원본 이미지: 미리 사인된 업로드 URL 이용]
🔼 미리 사인된 업로드 URL 이용
1. 클라이언트는 HTTP 서버에 POST 요청을 하여 미리 사인된 URL을 받는다. (해당 URL이 가리키는 개체에 대한 접근 권한은 이미 주어진 상태)
2. API 서버는 미리 사인된 URL을 돌려준다.
3. 클라이언트는 해당 URL이 가리키는 위치에 비디오를 업로드한다.

> ***안전성 최적화: 비디오 보호***

- 디지털 저작권 관리(DRM) 시스템 도입: 애플의 페어플레이, 구글의 와이드바인, 마이크로소프트의 플레이레디 등
- AES 암호화: 허락된 사용자만 암호화된 비디오 시청 가능
- 워터마크: 비디오 위에 소유자 정보를 포함하는 이미지 오버레이 올리기 (회사 로고나 이름 등)

> ***비용 최적화***

1. 인기 비디오는 CDN을 통해 재생하되 다른 비디오는 비디오 서버를 통해 재생한다.
2. 인기가 별로 없는 비디오는 인코딩할 필요가 없을 수도 있다. 짧은 비디오라면 필요할 때 인코딩하여 재생할 수 있다.
3. 어떤 비디오는 특정 지역에서만 인기가 높다. 이런 비디오는 다른 지역에 옮길 필요가 없다.
4. CDN을 직접 구축하고 인터넷 서비스 제공자(ISP)와 제휴한다. (사용자 경험 향상과 인터넷 사용 비용 절감 가능)

> ***오류 처리***

- 회복 가능 오류: 재시도로 해결해보고, 어렵다면 클라이언트에게 적절한 오류 코드 반환
- 회복 불가능 오류: 관련 작업을 중단하고 클라이언트에게 적절한 오류 코드 반환

**몇 가지 유형의 해결 방안**
- 업로드 오류: 몇 회 재시도
- 비디오 분할 오류: 전체 비디오를 서버로 전송하고 서버가 해당 비디오 분할을 처리하도록 함
- 트랜스코딩 오류: 재시도
- 전처리 오류: DAG 그래프 재생성
- DAG 스케줄러 오류: 작업을 다시 스케줄링
- 자원 관리자 큐에 장애 발생: 사본(replica) 이용
- 작업 서버 장애: 다른 서버에서 해당 작업을 재시도
- API 서버 장애: API 서버는 무상태 서버이므로 신규 요청은 다른 API 서버로 우회될 것
- 메타데이터 캐시 서버 장애: 데이터는 다중화되어 있으므로 다른 노드에서 데이터를 여전히 가져올 수 있을 것 (장애 캐시 서버는 새로 교체)
