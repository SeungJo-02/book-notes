### 1.1 도메인이란?
- S/W로 해결하려는 문제 영역 (예: 온라인 서점)
- 도메인은 여러 하위 도메인으로 나뉨: 회원, 결제, 재고, 배송 등
- 하위 도메인은 직접 구현할 수도, 외부 시스템을 쓸 수도 있음 (예: 결제는 PG사, 배송은 택배사 시스템)
- 도메인마다 하위 도메인 구성이 다름 (소규모 쇼핑몰은 정산을 외부 서비스에 맡기기도 함)

### 1.2 도메인 전문가와 개발자 간 지식 공유
- 도메인 전문가(현업 담당자)가 원하는 기능을 개발자가 구현
- 제일 중요한 건 요구사항 이해: 처음에 잘못 이해하면 되돌리는 비용이 큼 (Garbage in, Garbage out)
- 해결: 개발자가 전문가와 직접 대화해서 요청 뒤의 진짜 목적까지 파악

### 1.3 도메인 모델
- 도메인을 이해하기 위한 개념 모델 (객체 다이어그램, 상태 다이어그램 등 표현 방식은 자유)
- 개념 모델 ≠ 구현 모델: 구현 모델은 DB·프레임워크 같은 구현 기술을 반영함
- 처음부터 완벽한 개념 모델은 없음 → 개념 모델을 최대한 따르는 구현 모델을 고르고 계속 다듬음

### 1.4 도메인 모델 패턴

| 영역 | 역할 | 예시 |
|---|---|---|
| 표현(UI) | 사용자 요청 받기, 결과 보여주기 | 컨트롤러 |
| 응용(Application) | 요청 처리 흐름 조율, 규칙은 도메인에 맡김 | OrderService |
| 도메인 | 도메인 규칙 구현 | Order, OrderState |
| 인프라스트럭처 | DB·메시징 등 외부 시스템 연동 | JPA 리포지터리 |

> ✏️ **정정** — 원래 "도메인 영역 예: service 코드"라고 적었는데 반대. service는 응용 영역이고, 도메인 규칙은 엔티티·밸류 안에 둔다. 또 UI 영역은 UI/UX 디자인이 아니라 요청·응답을 다루는 코드 계층(컨트롤러 등)이다.

- 예: "출고 전에만 배송지 변경 가능" 규칙은 Order 안에 있음

```java
public class Order {
    private OrderState state;
    private ShippingInfo shippingInfo;

    public void changeShippingInfo(ShippingInfo newInfo) {
        if (!state.isShippingChangeable()) {
            throw new IllegalStateException("can't change shipping in " + state);
        }
        this.shippingInfo = newInfo;
    }
}
```

### 1.5 도메인 모델 도출
- 요구사항에서 핵심 구성요소·규칙·기능을 찾는 과정
- 기능을 먼저 찾아 메서드로: 주문 취소 → `cancel()`, 배송지 변경 → `changeShippingInfo()`, 결제 완료 → `completePayment()`
- 구성 예시
  - Order: 주문 상태, OrderLine 목록, ShippingInfo, 총 금액
  - OrderLine: 상품, 가격, 수량, 금액(가격 × 수량)
  - ShippingInfo: 받는 사람, 주소
- 규칙도 모델에 넣음: "최소 1종류 이상 상품 주문", "총 주문 금액 = 각 OrderLine 금액의 합"
- 모델 초안은 문서로 남겨 전문가·개발자가 공유 (전체 구조 → 세부 순서로)

### 1.6 엔티티와 밸류
- 도출한 모델은 크게 엔티티와 밸류로 나뉨

### 1.6.1 엔티티
- 식별자를 가짐: 객체마다 고유하고, 상태가 바뀌어도 식별자는 그대로 (예: 주문번호)
- 두 엔티티가 같은지는 식별자로 판단 → `equals()`·`hashCode()`를 식별자 기준으로 구현

### 1.6.2 엔티티의 식별자 생성
- 특정 규칙: 회사 규칙대로 생성 (예: 날짜 + 시간 + 일련번호)
- UUID·Nano ID 같은 고유 식별자 생성기 사용
- 값 직접 입력: 회원 아이디, 이메일 (중복 검사 필요)
- 일련번호: DB 자동 증가 컬럼 (저장한 뒤에야 식별자를 알 수 있음)

### 1.6.3 밸류 타입
- 개념적으로 완전한 하나를 표현하는 타입 (예: Address = 도시 + 우편번호 + 주소, Money)
- 장점: 코드 의미가 분명해지고, 밸류 전용 기능을 넣을 수 있음 (`Money.add()`, `multiply()`)
- 보통 불변으로 만듦 → 값 변경 = 새 객체로 교체
- 불변이 아니면 참조를 공유하는 다른 객체 값까지 바뀔 수 있음 → 넘길 때 복사본을 만들어야 함 (방어적 복사)
- 두 밸류가 같은지는 모든 속성 값으로 비교

```java
public class Money {
    private final int value;

    public Money add(Money other) {
        return new Money(this.value + other.value); // 자기 값은 안 바꾸고 새 객체 반환
    }
}
```

### 1.6.4 엔티티 식별자와 밸류 타입
- 식별자도 밸류 타입으로 만들 수 있음: `String` 대신 `OrderNo`
- 필드 이름이 id여도 타입만 보고 "주문번호"임을 알 수 있음

### 1.6.5 도메인 모델에 set 메서드 넣지 않기
- set은 필드 값만 바꿀 뿐 도메인 의미가 안 드러남 → `setState()` 대신 `completePayment()`
- 빈 객체 생성 후 set으로 채우면 중간에 불완전한 객체가 생김 → 필요한 값은 생성자로 받고 생성자에서 검사
- 클래스 내부에서만 쓰는 변경용이면 private set은 허용
- 불변 밸류 타입은 set 자체를 두지 않음
- 객체는 참조로 공유돼서 set 하나로 다른 객체 값까지 바뀔 수 있음

### 1.7 도메인 용어와 유비쿼터스 언어
- 코드에 도메인 용어를 그대로 씀: 이해가 쉽고, 전문가와 대화할 때 번역 과정이 없음
- 예: 주문 상태 `STEP1`, `STEP2` 대신 `PAYMENT_WAITING`, `PREPARING`, `SHIPPED`
- 유비쿼터스 언어: 전문가·관계자·개발자가 공통 언어를 정하고 대화·문서·도메인 모델·코드·테스트에 같은 용어를 사용
- 한국어 용어에 맞는 영단어 고르기가 중요 → 용어 사전으로 관리

- 각 종 도메인에는 전문가들이 있고 그들이 원하는 기능을 개발자가 만들다
- 가장 중요한 건 요구사항
  - 처음 잘못 만들면 돌이키기가 힘들다
- 해결책 : 직접 대화 

**도메인 모델**
- 도메인을 이해하기 위한 개념 모델 
- 구현 모델과 개념모델은 다르지만 개념모델에 최대한 맞도록 구현 모델 선택 해야한다 

**도메인 모델 패턴**
- 아키텍처 구성
  - UI : UI/UX
  - APP : 요청을 실행
  - 도메인 : 도메인 규칙 구현
    - e.g. service 코드 
  - 인프라 : 외부 시스템과 연동

**도메인 모델 도출**
- 도메인 하나에 핵심이 뭔 지
  - Order
    - 배송, 주문, 취소 등 + OrderLine + ShippingInfo
  - OrderLine
    - 상품, 가격, 수량 등 
  - ShippingInfo
    - 각종 주소

**엔티티와 밸류**
- 엔티티
  - 식별자를 가진다 e.g. ID(주문번호) 값 : UUID, 회사마다 규칙 등등
- 밸류
  - 식별자가 없고 코드의 의미를 더 잘 이해할 수 있도록 class를 추가하는 것
    - 보통 불변(데이터 변경 기능이 없다 ) 안전한 코드 작성이 가능해서 
    - 만약 불변 객체가 아니면 데이터를 복사한 새로운 객체 생성이 필요 
    - 엔티티 식별자를 위한 밸류 타입을 만들 수 있다
- get/set 사용 지양 특히 set
  - set은 필드 값만 바뀌는 거지 도메인 지식을 구현하는 것이 아님 
  - 그리고 도메인 객체 생성 시 온전하지 않을 수 있다 
    - 그래서 생성자로 받아야 한다
  - 그리고 prive으로 클래스 내부에서 데이터를 변경할 목적이라면 사용하기
  - 불변 밸류라면 set 사용 하지 않기 
  - 객체는 주소를 가리키기에 set 사용하면 다른 객체도 변할 수 있다
  - 밸류 타입 클래스에서는 SET을 무조건 안쓴다 

**도메인 용어와 유비쿼터스 용어**
- 도메인 용어 사용하기
  - 이해도 쉽고 코드 작성할 때도 쉽다
  - 한국인은 영단어 선택 잘해야한다
