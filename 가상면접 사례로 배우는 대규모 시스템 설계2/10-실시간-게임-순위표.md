# 10장. 실시간 게임 순위표

> 📝 **Notion 원본**: https://app.notion.com/p/f6435cd511a748a483242c055943c27b

> 🧩 **한 줄 요약** — DAU 500만(점수 갱신 최대 QPS 2,500) 게임의 월간 순위표. 점수는 클라이언트가 아니라 **게임 서버가 정해서** 순위표 서비스로 넘기고, 순위 계산은 관계형 DB 대신 **레디스 정렬 집합(sorted set)** 으로 처리한다(갱신·순위 조회 모두 O(log n)). 레디스는 읽기 사본과 **MySQL 점수 기록**으로 장애에 대비하고, 5억 DAU까지 커지면 **고정 파티션(점수 구간) 또는 해시 파티션(레디스 클러스터)** 으로 샤딩한다. 대안으로 NoSQL(DynamoDB)도 살펴본다.

### 1-1. 기능 요구사항

| 항목 | 내용 |
|---|---|
| 전체 표시 | 순위표에 모든 플레이어가 나온다 |
| 기간 | **매달 새로운 순위표** |
| 조회 | 상위 10명 + 특정 사용자의 순위 |
| 보너스 | 어떤 사용자의 **위아래 4순위** 사용자 표시 |

| 항목 | 내용 |

### 1-3. 규모 추정

| 항목 | 계산 | 결과 |
|---|---|---|
| DAU / MAU | 가정 | **500만 / 2,500만** |
| 평균 동시 플레이 | 500만 ÷ 10⁵초 (하루에 고르게 분포) | 초당 **50명** |
| 최대 동시 플레이 | 평균 × 5 | 초당 **250명** |
| 점수 갱신 QPS | 50명 × 하루 10게임 | **500** |
| 최대 점수 갱신 QPS | 500 × 5 | **2,500** |
| 상위 10명 조회 QPS | 하루 한 번 게임을 열 때만 표시 | 약 **50** |

- 하루는 약 10⁵초(86,400초)로 어림잡는다.
- 쓰기(점수 갱신)가 읽기(상위 10명 조회)보다 훨씬 많은 시스템이다.

## 2. API & 개략적 설계

### 2-1. API

| API | 하는 일 | 누가 부르나 |
|---|---|---|
| `POST /v1/scores` | 게임에서 이긴 사용자의 점수를 갱신 | **게임 서버만** (내부 API) |
| `GET /v1/scores` | 상위 10명 조회 | 클라이언트 |
| `GET /v1/scores/{:user_id}` | 특정 사용자 순위 조회 | 클라이언트 |

### 2-2. 구성

[🖼️ 원본 이미지: 개략적 설계안 (클라이언트 → 게임 서비스 → 순위표 서비스 → 순위표 저장소)]

- **게임 서비스** : 사용자가 게임을 플레이하게 하고, 이기면 점수를 확정한다.
- **순위표 서비스** : 순위표를 만들고 보여준다.

### 2-3. 생각해 본 것

**클라이언트가 순위표 서비스에 점수를 직접 보내면 안 될까?**

[🖼️ 원본 이미지: 클라이언트가 점수를 직접 설정하는 구조]

- 그러면 점수를 **클라이언트가 정하게** 된다.
- 👎 중간자 공격(요청을 가로채 점수를 조작)이 가능해서 안전하지 않다.
- 그래서 **점수는 서버(게임 서비스)가 정하고**, 순위표 서비스에는 서버끼리만 넘긴다.

**게임 서비스와 순위표 서비스 사이에 메시지 큐가 필요할까?**

[🖼️ 원본 이미지: 카프카를 거쳐 순위표 · 분석 · 푸시 알림 서비스가 점수를 받는 구조]

- 점수 데이터를 **다른 곳에서도 쓴다면**(분석, 푸시 알림 등) 카프카에 넣고 여러 소비자가 나눠 읽는 게 합리적이다.
- 순위표만 쓴다면 굳이 넣지 않아도 된다. 이 장에서는 쓰지 않는 쪽으로 간다.

## 3. 데이터 모델 — RDB vs 레디스 ⭐

### 3-1. 관계형 데이터베이스

규모가 작고 사용자가 많지 않을 때는 충분하다.

| 동작 | 방법 |
|---|---|
| 점수 획득 | 이번 달 순위표에 그 사용자 레코드가 없으면 새로 넣고, 있으면 점수를 더한다 |
| 상위 10명 | 점수로 정렬해서 위에서 10개 |
| 특정 사용자 순위 | 점수로 정렬한 뒤 **그 사용자가 몇 번째인지** 센다 |

```sql
-- 점수 획득
INSERT INTO leaderboard (user_id, score) VALUES ('mary1934', 1)
  ON DUPLICATE KEY UPDATE score = score + 1;

-- 특정 사용자 순위: 나보다 점수가 높은 사람 수 + 1
SELECT COUNT(*) + 1 FROM leaderboard
WHERE score > (SELECT score FROM leaderboard WHERE user_id = 'mary1934');
```

**왜 이 시스템에서는 RDB가 힘든가?**

핵심은 **"특정 사용자의 순위"** 다. 순위는 "나보다 위에 있는 사람 수"라서, 사용자가 수백만 명이면 매번 그만큼의 행을 세야 한다(O(n)). 점수는 계속 바뀌니 순위를 미리 계산해 캐시해 두기도 어렵다.

| 원인 | 설명 |
|---|---|
| 순위 계산 비용 | 순위 = 나보다 점수 높은 행 수 → 인덱스가 있어도 그 범위를 다 세야 함 |
| MVCC 오버헤드 | 읽을 때마다 각 행이 내 트랜잭션에 보이는 버전인지 확인 |
| 랜덤 디스크 I/O | 버퍼 풀에 없으면 디스크 여기저기 흩어진 페이지를 읽음 |
| 커넥션 · 스레드 한계 | 읽기가 몰리면 커넥션 풀 고갈, 컨텍스트 스위치 비용 |
| 쓰기 부하 | 점수가 바뀔 때마다 점수 인덱스(B+Tree)도 고쳐야 함 → 쓰기가 몰리면 페이지 분할·잠금 경합 |

> 💡 보강 — `ORDER BY score DESC LIMIT 10` 자체는 점수에 **인덱스가 있으면** 인덱스 앞쪽 10개만 읽어서 빠르다(풀스캔 X). 인덱스가 없을 때만 전체를 정렬한다. 진짜 문제는 상위 10명이 아니라 **임의 사용자의 순위**다.

### 3-2. 레디스

- **메모리**에서 동작해서 읽기·쓰기가 빠르다.
- 순위표에 딱 맞는 **정렬 집합(sorted set)** 자료형이 있다.

**정렬 집합 = 해시 테이블 + 스킵 리스트를 동시에 유지**

| 구조 | 저장하는 것 | 쓰임 | 시간 |
|---|---|---|---|
| 해시 테이블 | 사용자 → 점수 | "이 사용자 점수가 몇 점?" | O(1) |
| 스킵 리스트 | 점수 순으로 정렬된 사용자 | 순위 · 범위 조회 | O(log n) |

**해시 테이블**
- Key와 Value를 짝지어 저장한다. 해시 함수가 키를 숫자(배열 인덱스)로 바꿔서 그 자리에 바로 저장·조회한다 → 이론상 O(1).
- 두 키가 같은 자리에 걸리면(충돌) **체이닝**으로 기존 데이터 뒤에 연결 리스트로 이어 붙인다.

[🖼️ 원본 이미지: 해시 테이블 체이닝 구조]

**스킵 리스트**
- 정렬된 연결 리스트는 찾을 때 처음부터 따라가야 해서 O(n)이다. 이걸 줄이려고 나왔다.
- 맨 아래에 전체 리스트를 두고, 그 위에 **일부 노드만 뽑은 리스트(인덱스 층)** 를 여러 겹 올린다. 위층에서 크게 건너뛰다가 아래층으로 내려오며 찾는다 → 평균 O(log n).
- B-Tree보다 구현이 단순해서 인메모리 정렬 구조로 자주 쓴다.
- 레디스는 각 층의 건너뛰는 거리(span)도 같이 저장해서, 내려오면서 거리를 더하면 **순위가 바로 계산**된다. 그래서 순위 조회도 O(log n)이다.

> 💡 비유 — 지하철 급행과 완행. 급행(위층)으로 멀리 간 뒤 완행(아래층)으로 갈아타서 목적지 역을 찾는다.

## 4. 레디스 정렬 집합 명령어

랭킹 키는 월별로 `leaderboard_2026_10`처럼 두는 게 책의 방식이다. 아래 예시는 `game:rank`로 쓴다.

| 명령 | 하는 일 | 시간 |
|---|---|---|
| `ZADD` | 사용자 삽입(이미 있으면 점수 덮어씀) | O(log n) |
| `ZINCRBY` | 점수를 지정한 만큼 증가(없으면 새로 만듦) | O(log n) |
| `ZRANGE` / `ZREVRANGE` | 점수 순 정렬에서 특정 범위의 사용자 조회 | O(log n + m) |
| `ZRANK` / `ZREVRANK` | 오름차순/내림차순 기준 특정 사용자의 위치(0부터) | O(log n) |

```bash
# userA(100점), userB(85점), userC(120점) 삽입
> ZADD game:rank 100 "userA" 85 "userB" 120 "userC"
(integer) 3

# userB의 점수를 50점 증가
> ZINCRBY game:rank 50 "userB"
"135"   # 85 + 50

# 1등부터 3등까지 점수와 함께 내림차순 조회 (상위 10명이면 0 9)
> ZREVRANGE game:rank 0 2 WITHSCORES
1) "userB"
2) "135"
3) "userC"
4) "120"
5) "userA"
6) "100"

# userA의 내림차순 등수 (0부터 시작 → 2 = 3등)
> ZREVRANK game:rank "userA"
(integer) 2
```

**보너스 — 위아래 4순위 사용자**
`ZREVRANK`로 내 순위 r을 구한 뒤 `ZREVRANGE game:rank (r-4) (r+4)`로 가져온다.

## 5. 저장소 요구사항 & 장애 복구

| 항목 | 내용 |
|---|---|
| 저장할 것 | 최소한 **사용자 ID와 점수** |
| 한 항목 크기 | 26바이트 (ID 24바이트 + 점수 2바이트) |
| 최악의 경우 | MAU 2,500만 명 모두 순위표에 있음 → 26B × 2,500만 ≈ **650MB** |
| 결론 | 레디스 서버 **한 대로 충분**, 피크 2,500 QPS도 감당 가능 |

- 레디스가 죽을 때를 대비해 **읽기 사본(replica)** 을 둔다.
- 관계형 DB에는 **사용자 테이블**과 **점수 테이블**(사용자 ID · 점수 · 획득 시각) 두 개를 둔다.
  - 경연 기록, "최근 10번의 게임 기록과 획득 점수" 같은 다른 기능은 레디스가 아니라 RDB에서 조회한다.
  - **레디스 복구용**으로도 쓴다. 레디스가 날아가면 점수 테이블에서 `SUM(점수) GROUP BY 사용자`로 사용자별 점수를 다시 계산해 빈 레디스에 `ZADD`로 넣으면 순위표가 복구된다.
- 가장 자주 조회되는 **상위 10명의 사용자 정보(이름 · 프로필 사진)** 는 따로 캐시한다.

## 6. 자체 서비스 vs 클라우드(람다)

### 6-1. 자체 서비스

[🖼️ 원본 이미지: 자체 서비스 구성 (API 서버 · 레디스 · MySQL)]

- 매달 새 정렬 집합을 만들어 그 달의 순위표로 쓴다.
- 순위표를 보여줄 때 API 서버는 레디스의 순위와 함께 **DB의 사용자 이름 · 프로필 이미지**도 가져온다(자주 보는 건 캐시).

### 6-2. 클라우드 — API 게이트웨이 + AWS 람다

[🖼️ 원본 이미지: API 게이트웨이 → 람다 → 레디스/DB 구성]

- **AWS 람다** : 서버를 직접 준비·관리하지 않고 코드만 올려서 실행한다(서버리스).
- 클라이언트가 API 게이트웨이를 호출하면, 게이트웨이가 경로에 맞는 람다 함수를 부른다.
- DAU가 늘어나면 람다가 **자동으로 개수를 늘려** 규모를 맞춘다.

요청 한 번의 흐름:

| 순서 | 누가 | 하는 일 |
|---|---|---|
| 1 | 클라이언트 | `GET /api/data` HTTP 요청 |
| 2 | API 게이트웨이 | HTTP 요청을 **Event JSON**으로 바꿔 지정된 람다 호출 |
| 3 | AWS 인프라 | 대기 중인 람다가 없으면 **Firecracker 마이크로 VM**을 띄우고 코드를 올림 (콜드 스타트) |
| 4 | 람다 | Event JSON을 입력으로 받아 서비스 코드 실행 |
| 5 | 람다 | 결과를 게이트웨이 규격의 **Response JSON**으로 반환 |
| 6 | API 게이트웨이 | Response JSON을 HTTP 응답으로 바꿔 클라이언트에 전달 |

> 💡 보강 — 3번의 콜드 스타트 때문에 첫 요청이 느릴 수 있다. 한 번 뜬 실행 환경은 한동안 재사용(웜 스타트)되어 그다음부터는 빠르다.

## 7. 레디스 규모 확장 — 샤딩 ⭐

DAU가 **5억**(100배)으로 늘면 → 점수 갱신 최대 QPS 250,000, 저장 65GB. 레디스 한 대로는 부족하니 **샤딩**이 필요하다.

### 7-1. 고정 파티션 (점수 구간으로 나누기)

[예시] 점수 1~100은 샤드1, 101~200은 샤드2, … 처럼 **점수 범위별로** 샤드를 나눈다.

| 동작 | 방법 |
|---|---|
| 점수 갱신 | 사용자가 지금 어느 샤드에 있는지 알아야 함 → **사용자 ID → 점수**를 MySQL이나 **보조 캐시**에서 조회 |
| 샤드 이동 | 점수가 올라 구간을 넘으면 기존 샤드에서 지우고 새 샤드에 넣음 |
| 상위 10명 | **점수가 가장 높은 샤드**에서만 가져오면 끝 |
| 특정 사용자 순위 | (내 샤드 안 순위) + (나보다 높은 구간 샤드들의 사용자 수) |

- 높은 샤드의 사용자 수는 `INFO KEYSPACE`로 바로 얻는다. 노드에 키가 몇 개 있는지, 만료가 설정된 키는 몇 개인지 같은 요약 정보를 즉시 돌려주는 명령이다.
- **점수가 고르게 퍼져 있어야** 한다. 한 구간에 사람이 몰리면 그 샤드만 바빠진다(핫스팟) → 구간을 조정해야 한다.

> 💡 보강 — 노트의 **쿼리 캐시와 2차 캐시**는 "보조 캐시"를 이해하려고 비교해 본 개념이다.
> - **쿼리 캐시** : 특정 조건의 결과로 **ID 목록만** 저장. 예) 1000점 이상 유저 = `[1번, 2번, 3번]`
> - **2차 캐시** : ID를 키로 **행 하나의 상세 정보**를 저장. 예) `1번 = {이름: 철수, 점수: 1050}`
>
> 고정 파티션에서 필요한 건 2차 캐시처럼 **ID로 점수를 바로 찾는** 쪽이다. 점수를 알아야 어느 샤드에 있는지 알 수 있기 때문이다.

### 7-2. 해시 파티션 (레디스 클러스터)

[예시] 사용자 ID를 해시해서 샤드를 정한다. 점수가 특정 구간에 몰려 있어도 **고르게 나뉜다.**

- 레디스 클러스터는 **해시 슬롯 16,384개**를 만들고 여러 노드가 나눠 맡는다.
- 키가 들어오면 `CRC16(key) % 16384`로 슬롯 번호를 정하고, 그 슬롯을 맡은 노드로 보낸다.
- 노드를 늘리거나 줄일 때는 슬롯만 옮기면 되어서 재배치가 쉽다.

| 동작 | 방법 |
|---|---|
| 점수 갱신 | 사용자 ID의 슬롯이 있는 샤드에서 `ZINCRBY` |
| 상위 10명 | **모든 샤드에서 각자 상위 10명**을 받아 애플리케이션에서 다시 정렬 (scatter-gather) |
| 특정 사용자 순위 | **어렵다** — 모든 샤드에 "이 점수보다 높은 사람 몇 명?"을 물어 합쳐야 함 |

- **scatter-gather 문제** : 모든 노드에 요청을 뿌리고, 가장 느린 노드까지 응답해야 결과를 낼 수 있다.
- 즉, **저장 용량은 자동으로 분산되지만**, 전체 순위를 볼 때 네트워크 비용 + 재정렬 때문에 지연이 늘어난다. 상위 k가 커지면(예: 상위 1000) 더 느려진다.

**고정 vs 해시 비교**

| | 고정 파티션 | 해시 파티션 |
|---|---|---|
| 나누는 기준 | 점수 구간 | 사용자 ID 해시 |
| 상위 10명 | 최상위 샤드 하나만 | 모든 샤드 조회 후 병합 |
| 특정 사용자 순위 | 쉬움 | 어려움 |
| 데이터 균형 | 점수 분포에 좌우 | 고르게 나뉨 |
| 운영 | 샤드 이동·구간 조정을 직접 | 클러스터가 자동 |

→ 책은 **고정 파티션**을 고른다. 순위 조회가 핵심 기능이기 때문이다.

### 7-3. 레디스 노드 크기

- 쓰기가 많으면 데이터 크기의 **2배 메모리**를 잡는다.
- 장애 대비 **스냅숏**을 만들 때 레디스는 fork로 자식 프로세스를 띄우는데, 그동안 바뀐 페이지는 복사(copy-on-write)되어 메모리를 더 쓰기 때문이다.
- 성능 측정은 `redis-benchmark`로 한다.

## 8. NoSQL을 대안으로

DynamoDB, 카산드라, MongoDB 같은 NoSQL도 쓸 수 있다.

- **쓰기에 최적화**되어 있다.
- **같은 파티션 안의 항목을 점수(정렬 키)로 효율적으로 정렬**할 수 있다.
- 레코드가 많아지면 상위 점수를 찾으려고 테이블 전체를 뒤져야 해서 느려진다.
  - → `game_name#{year-month}`를 **파티션 키**, **점수를 정렬 키**로 두면 그 달의 데이터 안에서 점수 순으로 바로 읽을 수 있다.

> 💡 보강 — 그런데 한 달치가 파티션 하나에 몰리면 그 파티션만 뜨거워진다(**핫 파티션**). 책은 그래서 `game_name#{year-month}#p{파티션번호}`처럼 **쓰기를 여러 파티션으로 나누고(write sharding)**, 상위 10명은 각 파티션에서 받아 합치는(scatter-gather) 방식을 쓴다. 이 경우 정확한 순위 대신 "상위 10%" 같은 **백분위**로 보여주는 타협을 한다.

| 요구사항 | DAU 500만 · 점수 갱신 최대 QPS 2,500 · 월간 순위표 · 상위 10명 + 내 순위 · 실시간 반영 |

| 레디스 | **정렬 집합 = 해시 테이블(점수 O(1)) + 스킵 리스트(순위 O(log n))** · `ZADD` `ZINCRBY` `ZREVRANGE` `ZREVRANK` |
| 저장 · 복구 | 26B × 2,500만 ≈ 650MB → 한 대로 충분 · 읽기 사본 · MySQL 점수 테이블로 재계산 복구 · 상위 10명 정보 캐시 |
| 배포 | 자체 서버 또는 API 게이트웨이 + 람다(자동 확장, 콜드 스타트 주의) |
| 샤딩 (5억 DAU) | **고정 파티션**(점수 구간, 순위 계산 쉬움, 보조 캐시 필요) vs **해시 파티션**(클러스터 16,384 슬롯, scatter-gather) · 쓰기 많으면 메모리 2배 |
| NoSQL | 파티션 키 `game#월` + 정렬 키 점수 · 핫 파티션은 write sharding · 백분위로 타협 |
| 마무리 | 동점자는 레디스 해시에 **처음 그 점수를 딴 시각**을 저장해 먼저 딴 사람을 위로 · 장애 시 MySQL 승리 기록으로 레코드마다 `ZINCRBY` 재실행 |

2. 점수를 클라이언트가 순위표 서비스에 직접 보내면 안 되는 이유는?
3. 고정 파티션과 해시 파티션에서 "상위 10명"과 "특정 사용자 순위"를 각각 어떻게 구하나? 책이 고정 파티션을 고른 이유는?

<details>
<summary>답</summary>

1. 순위는 "나보다 점수가 높은 사람 수 + 1"이라서 RDB는 사용자가 수백만 명이면 매번 그만큼의 행을 세야 한다(O(n)). 점수가 계속 바뀌니 미리 계산해 둘 수도 없다. 레디스 정렬 집합은 **해시 테이블로 사용자의 점수를 O(1)에 찾고**, 점수 순으로 정렬된 **스킵 리스트에서 위층부터 건너뛰며 내려오면서 거리를 더해** 순위를 O(log n)에 구한다. 점수 갱신(`ZINCRBY`)도 O(log n)이다.
2. 클라이언트가 점수를 정하면 요청을 가로채서 점수를 바꾸는 **중간자 공격**이 가능하다. 그래서 점수는 게임 결과를 아는 **게임 서버가 정하고**, `POST /v1/scores`는 서버끼리만 부르는 내부 API로 둔다.
3. 고정 파티션은 점수 구간별로 나누므로 상위 10명은 **최상위 샤드에서만** 가져오면 되고, 특정 사용자 순위는 **내 샤드 안 순위 + 위쪽 샤드들의 사용자 수**(`INFO KEYSPACE`)로 구한다. 해시 파티션은 사용자가 아무 샤드에나 흩어져 있어서 상위 10명은 **모든 샤드의 상위 10명을 받아 다시 정렬**해야 하고, 특정 사용자 순위는 모든 샤드에 물어봐야 해서 어렵다. 순위 조회가 핵심 기능이라 책은 **고정 파티션**을 고른다(대신 점수가 몰리는 구간은 직접 조정해야 한다).

### **데이터 모델**

#### **관계형 데이터베이스**

- 규모 확장성이 크게 중요하지 않고 사용자 수가 많지 않은 경우에 좋다.
- 사용자가 점수를 딴 경우
  - 해당 월의 순위표에 해당 사용자의 레코드가 없다면 새로운 레코드를 만들어 넣는다.
  - 이미 레코드가 있는 경우 점수 데이터를 갱신한다.
- 특정 사용자 순위 검색
  - 순위표 테이블을 점수 기준으로 정렬한 다음 순위를 매긴다.
- 관계형 데이터베이스는 본 시스템에 요구되는 다량의 읽기 부하를 처리하기 어렵다.
  - Join 연산
  - MVCC 오버헤드 : MVCC에서 바뀌는 지 아닌지 계속 확인 하는 작업 땜시
  - 랜덤 디스크 I/O : Buffer Pool에서 히트가 안되면 디스크의 흩어진 데이터를 여기저기 찾음
  - 커넥션 병목과 스레드 한계 : 읽기가 너무 몰리면 풀고갈 혹은 컨텍스트 스위치 비용 때문에
  - Limit 사용할 때도 풀스캔을 돌리고 메모리에 올려주기에 별로
  - 쓰기가 막 몰리는 경우에는 RDBMS가 B+Tree 구조라 포화가 온다

#### **레디스**

- 메모리에서 동작하므로 빠른 읽기 및 쓰기가 가능하다.
- 순위표 시스템 설계 문제를 해결하는 데 이상적인 정렬 집합(sorted set) 자료형을 제공한다.
  - 정렬집합 : **해시테이블**과 **스킵 리스트 동시 유지**
    - 점수를 찾을 때 해시 테이블로 찾고 랭킹을 가져올 때는 스킵 리스트로 범위 스캔을 한다
  - 해시테이블
    - Key와 Value를 짝지어 저장하는 구조, 검색속도 이론상 O(1)
      - 유저가 Key 값을 넣으면 내부의 해시함수가 키를 숫자로 바꾸고 배열의 인덱스가 되어 해당 위치에 Value를 저장하거나 즉시 찾아낸다
      - 충돌이 나면 Chaining을 써서 기존 데이터 뒤에 링크드 리스트로 줄을 이어 매달아 놓는다
        [🖼️ 원본 이미지: 해시 테이블 체이닝]
  - 스킵 리스트
    - 링크드 리스트의 단점인 순차 검색(O(N)) 극복하기 위해 나옴
      B-Tree를 대신해 인메모리에서 주로 사용
    - 가장 밑에 리스트가 있으면 그 위에 몇 개의 리스트만 올려 놓고 검색할 땐 위에서 검색
- 레디스 정렬 집합을 사용한 구현
  - 현재 서비스 중인 게임의 랭킹 키(Key)를 `game:rank`라고 가정
  - ZADD: 기존에 없던 사용자를 집합에 삽입한다.
    ```
    # userA(100점), userB(85점), userC(120점) 삽입
    > ZADD game:rank 100 "userA" 85 "userB" 120 "userC"
    (integer) 3
    ```
  - ZINCRBY: 사용자 점수를 지정된 값만큼 증가시킨다.
    ```
    # userB의 점수를 50점 증가시킴
    > ZINCRBY game:rank 50 "userB"
    "135"  # (85 + 50 = 135점이 반환됨)
    ```
  - ZRANGE/ZREVRANGE: 점수에 따라 정렬된 사용자 중에 특정 범위에 드는 사용자들을 가져온다.
    ```
    # 0번(1등)부터 2번(3등)까지 점수와 함께 내림차순 조회
    > ZREVRANGE game:rank 0 2 WITHSCORES
    1) "userB"
    2) "135"
    3) "userC"
    4) "120"
    5) "userA"
    6) "100"
    ```
  - ZRANK/ZREVRANK: 오름차순/내림차순 정렬하였을 때 특정 사용자의 위치를 가져온다.
    ```
    # userA의 내림차순 기준 등수 조회
    > ZREVRANK game:rank "userA"
    (integer) 2
    ```

#### **저장소 요구사항**

- 최소한 사용자 ID와 점수는 저장해야 한다.
- 최악의 시나리오를 가정하면 약 650MB의 저장공간이 레디스 캐시에 필요하다. (26바이트 * 2,500만)
  - 순위표 한 항목당 26바이트가 필요
- 보통 레디스에 읽기 사본을 두는 식으로 구성한다.
- 관계형 테이블을 사용할 경우 2개의 테이블(사용자 및 점수)이 필요하다.
  - 경연 기록과 같은 다른 게임 기능 구현에 활용할 수 있다.
  - 인프라 장애 발생 시 레디스 순위표를 복구하는 데에도 활용할 수 있다.
    - 최근 10번의 게임 기록과 획득 점수"를 볼 때는 레디스가 아닌 RDBMS
    - 레디스가 날아가면 RDBMS에 남아있는 점수 테이블에서 `SUM(점수) GROUP BY 사용자` 쿼리를 실행해 유저별 최종 점수를 재계산한 뒤, 비어있는 새 레디스에 `ZADD`로 밀어 넣으면 랭킹보드를 완벽하게 복구
- 최적의 방안은 가장 자주 검색되는 상위 10명의 사용자 정보를 캐시하는 것이다.

#### **클라우드 서비스를 이용하는 방안**

- 아마존 API 게이트웨이, AWS 람다를 사용한다.
  - `AWS 람다`: 서버를 직접 준비하거나 관리할 필요 없이 코드를 실행할 수 있다.
- API 게이트웨이를 호출하고, 게이트웨이는 적절한 람다 함수를 호출한다.
- 람다를 사용하면 DAU 성장세에 맞춰 자동으로 서비스 규모를 확장할 수 있다.
  - 클라 : `GET /api/data` HTTP 요청 발송
  - API Gateway : HTTP 요청을 가로채서 `Event JSON`으로 변환 후 지정된 람다 호출
  - AWS 인프라 : 대기 중인 람다가 없다면, Firecracker VM을 띄우고 이미지를 로드
  - Lambda : `Event JSON`을 입력값으로 받아 서비스 코드를 실행
  - Lambda : 실행 결과를 API Gateway가 요구하는 규격에 맞춰 `Response JSON`으로 반환
  - API Gateway : `Response JSON`을 다시 완벽한 HTTP 응답으로 변환하여 클라이언트에게 전달

#### **데이터 샤딩 방안**

- 고정 파티션
  - 점수의 범위에 따라 파티션을 나누는 방안이다.
  - 점수가 고르게 분포되어야 한다.
  - 사용자의 점수가 높아져 다른 샤드로 옮겨야 할 때는 기존 샤드에서 해당 사용자를 제거한 후 다음 새 샤드로 옮겨야 한다.
  - 쿼리캐시 : 특정 쿼리 조건에 해당하는 (**결과 식별자(ID) 리스트**만 저장
    - 1000점 이상 유저 =  `[1번, 2번, 3번]`
  - 2차캐시 : 데이터베이스의 특정 행 하나하나 **전체 상세 정보**를 식별자(ID)를 기준으로 저장
    - `1번 = {이름: 철수, 점수: 1050}`, `2번 = {이름: 영희, 점수: 1200}`
  - 즉, 점수가 고르게 퍼져있는 경우에 사용
    - info keyspace : 해당 Redis 노드(샤드)에 총 몇 개의 Key가 저장되어 있는지, 만료 시간이 설정된 Key는 몇 개인지 등의 요약 정보를 즉시 반환
- 해시 파티션
  - 레디스 클러스터를 사용하는 것으로, 사용자들의 점수가 특정 대역에 과도하게 모여 있는 경우 효과적이다.
  - 여러 노드에 데이터를 자동으로 샤딩하는 방법을 제공한다.
  - 각각의 키가 특정한 해시 슬롯에 속하도록 하는 샤딩 기법을 사용한다.
  - 레디스 클러스터는 가상의 방 16,384개를 만들어서 여러 노드(서버)가 나누어서 관리
  - 데이터가 들어와서 해시 함수를 거쳐서 번호를 받고 그 번호에 해당하는 노드로 이동
    - 문제 (Scatter-Gather 문제)
      - 전체 노드에 요청을 보내고 가장 느린 노드가 응답을 해야 결과를 반환할 수 있다
  - 즉, 저장 용량의 한계는 자동으로 분산되지만 전체 순위 조회 시 네트워크 비용 + 재정렬 연산으로 인해서 지연시간이 늘어난다
- Redis 노드 크기 조정
  - 쓰기작업이 많은 경우에는 메모리 2배더 할당하기
    - 장애대비를 위한 스냅숏을 생성할 때 쓰기를 감당하기 위해서
