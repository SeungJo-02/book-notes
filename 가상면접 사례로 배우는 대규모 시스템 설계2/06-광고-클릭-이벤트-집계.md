# 6장. 광고 클릭 이벤트 집계

> 📝 **Notion 원본**: https://app.notion.com/p/78541293a1b24876ab3735bab95b6500

> 🧩 **한 줄 요약** — 페이스북·구글 규모의 광고 클릭 로그를 **매분 집계**해 "지난 M분간 ad_id별 클릭 수 / 상위 N개 광고"를 돌려주는 시스템. 돈(RTB·과금)이 걸려 **정확성**이 최우선이라 **원시+집계 데이터를 둘 다** 저장하고, **카프카+맵리듀스형 집계 서비스**로 비동기 처리하며, **정확히 한 번(exactly-once)·조정(reconciliation)**으로 정합성을 보증한다.

## 1. 무엇을 만드나 & 규모

[🖼️ 원본 이미지: RTB 디지털 광고 동작 절차]

- **RTB**(Real-Time Bidding, 실시간 입찰)는 디지털 광고의 핵심. **속도와 정확성**이 생명 — 돈이 걸려 있기 때문. 지표로 **CTR**(클릭률)·**CVR**(전환율)이 중요.
- **기능 요구사항**
  - 입력 데이터: 서버에 분산된 **로그 파일**
  - 지난 **M분** 동안의 `ad_id`별 클릭 수 집계
  - 매분 가장 많이 클릭된 **상위 100개** 광고 반환
  - 다양한 속성에 따른 **필터링** 집계 지원
  - 데이터 양은 **페이스북·구글 규모**
- **비기능 요구사항**
  - **정확성**(RTB·과금에 쓰이므로) · 지연/중복 이벤트 적절 처리 · 부분 장애 감내(견고성) · 전체 처리 지연 **수 분 이내**
- **개략적 추정**
  - DAU 10억 × 인당 1클릭 → **광고 클릭 QPS ≈ 10,000**, 최대 QPS는 평균의 **5배**
  - 이벤트 하나당 0.1KB → **월 저장량 ≈ 3TB**, 이벤트 수는 매년 30% 증가

## 2. 질의 API 설계

### 2-1. 지난 M분간 각 ad_id 클릭 수
```
GET /v1/ads/{:ad_id}/aggregated_count
```
| 구분 | 필드 | 뜻 | 자료형 |
|---|---|---|---|
| Request | from / to | 집계 시작·종료 시각 | long |
| Request | filter | 필터링 전략 식별자 | long |
| Response | ad_id | 광고 식별자 | string |
| Response | count | 집계된 클릭 횟수 | long |

### 2-2. 지난 M분간 상위 N개 ad_id
```
GET /v1/ads/popular_ads
```
| 구분 | 필드 | 뜻 | 자료형 |
|---|---|---|---|
| Request | count | 반환할 광고 개수 | integer |
| Request | window | 집계 윈도 크기(분) | integer |
| Request | filter | 필터링 전략 식별자 | long |
| Response | ad_ids | 광고 식별자 목록 | array |

## 3. 데이터 모델 — 원시 vs 집계

집계 결과 테이블은 `ad_id · click_minute · filter_id · count` 형태(필터별로 나눠 집계).

| | 원시 데이터만 보관 | 집계 결과만 보관 |
|---|---|---|
| 장점 | 원본 무손실 · 필터링·재계산 자유 | 용량 절감 · 빠른 질의 |
| 단점 | 막대한 용량 · 느린 질의 | 데이터 손실 |

> 🔑 **결론: 둘 다 저장한다.** 문제가 생기면 **원시 데이터로 디버깅**하고, 평상시엔 **집계 데이터로 빠르게 질의**한다.

- **DB 선택**: 원시 데이터는 쓰기·시간범위 질의에 최적인 **카산드라·InfluxDB**. 집계 데이터도 같은 유형의 DB를 쓸 수 있다.

## 4. 개략 설계 — 카프카 비동기 파이프라인

- **카프카** 같은 메시지 큐로 생산자·소비자를 **분리(디커플링)**하면 전체가 비동기로 동작하고, 양쪽 규모를 **독립적으로 확장**할 수 있다.

[🖼️ 원본 이미지: 개략적 설계안]

[🖼️ 원본 이미지: 정확하게 한 번 처리하기 위한 메커니즘]

- **집계 서비스(맵리듀스 형태)**
  - **맵 노드**: 데이터 출처에서 읽은 데이터를 **필터링·변환**
  - **집계 노드 → 리듀스 노드**: 각 집계 노드 결과를 **최종 결과로 축약**
  - 주요 사용 사례: 클릭 수 집계 / 상위 N개 광고 / 데이터 필터링

## 5. 스트리밍 vs 일괄 (람다 아키텍처)

일괄+스트리밍 경로를 **동시에 지원**하는 아키텍처를 **람다(Lambda)**라 한다.

| | 서비스(온라인) | 일괄(오프라인) | 스트리밍(실시간 근접) |
|---|---|---|---|
| 응답성 | 빠르게 응답 | 응답 불필요 | 응답 불필요 |
| 입력 | 사용자 요청 | 유연한 크기 | 경계 없음 |
| 출력 | 응답 | 구체화 뷰·지표 | 구체화 뷰·지표 |
| 성능 기준 | 가용성·지연 | 처리량 | 처리량·지연 |
| 사례 | 온라인 쇼핑 | 맵리듀스 | 플링크 |

- **데이터 재계산(이력 데이터 재처리)**: 이미 집계한 데이터를 다시 계산해야 할 때. 집계 서비스는 **재사용**하되 처리 대상 데이터는 **다른 곳(원시 저장소)**에서 읽는다.

## 6. 시간 · 윈도 · 전달 보장

### 6-1. 어느 시각을 기준으로?
| 기준 | 장점 | 단점 |
|---|---|---|
| **이벤트 시각**(클릭 발생) | 집계가 더 정확 | 타임스탬프 오류·조작에 취약 |
| **처리 시각**(서버가 처리) | 서버 타임스탬프라 안정적 | 집계가 부정확할 수 있음 |

### 6-2. 집계 윈도
- **텀블링 윈도**: 겹치지 않는 같은 크기 구간 → **매 분 클릭 집계**에 적합
- **슬라이딩 윈도**: 구간을 미끄러뜨리며 집계 → **M분간 상위 N개 광고**에 적합

### 6-3. 전달 보장 — 정확히 한 번(exactly-once)
- 중복 처리 방지 + 모든 이벤트 처리 보장이 목표. 본 설계는 **정확히 한 번**을 권장.
- 데이터 손실을 막으려면 **다운스트림에서 집계 결과 수신 확인(ACK)을 받은 뒤 오프셋을 저장**한다.

## 7. 규모 확장 · 핫스팟 · 결함 내성

- **메시지 큐 확장** — 생산자: 쉬움(인스턴스 제한 X). 소비자: 노드 추가/삭제로 조정(트래픽 적은 시간대에).
- **브로커** — 해시 키로 같은 id 이벤트를 같은 파티션에서 구독 / 파티션 수는 사전 충분히 확보 / 토픽 물리 샤딩은 대역폭↑이나 유지비↑.
- **집계 서비스·DB 확장** — 노드 추가/삭제로 수평 확장. DB는 **안정 해시**류로 수평 확장 기본 지원.
- **핫스팟** — 특정 서비스·샤드에 데이터가 몰리는 것. 과부하 유발 → **집계 노드를 더 할당**해 해결.
- **결함 내성 — 스냅숏** — 노드 장애 시 새 노드로 교체 후 **마지막 스냅숏에서 복구**. 스냅숏 이후 도착한 이벤트는 새 노드가 **카프카에서 다시 읽어** 처리.

---

## 8. 정확성 — 모니터링과 조정

- **지속 모니터링**
  - **지연 시간**: 기록된 시각들의 차이를 시간 지표로 변환해 추적
  - **메시지 큐 크기**: 카프카면 레코드 처리 지연 지표를 대신 추적
  - **집계 노드 자원**: CPU·디스크·JVM 등
- **조정(reconciliation)** — 데이터 무결성을 보증하는 기법. 매일 각 파티션의 클릭 이벤트를 **이벤트 발생 시각으로 정렬한 일괄 결과**를 만들어 **실시간 집계 결과와 비교**한다.

## 정리

| 주제 | 핵심 |
|---|---|
| 무엇 | M분 클릭 집계 + 상위 N개 광고, 페이스북·구글 규모 |
| 저장 | 원시+집계 **둘 다**(디버깅용·질의용) |
| 처리 | 카프카로 비동기 디커플링 + 맵리듀스형 집계 |
| 정확성 | exactly-once(ACK 후 오프셋 저장) + 조정 |
| 시간/윈도 | 이벤트 vs 처리 시각 / 텀블링·슬라이딩 |
| 안정성 | 스냅숏 복구 · 핫스팟은 노드 추가 |

## 🔁 셀프 체크
1. 원시 데이터와 집계 데이터를 굳이 **둘 다** 저장하는 이유는?
2. 이벤트 시각과 처리 시각 중 무엇을 기준으로 집계하며, 각 트레이드오프는?
3. '정확히 한 번' 전달을 보장할 때, 데이터 손실을 막기 위한 오프셋 저장 순서는?

<details>
<summary>답</summary>

1. 문제 시 **원시 데이터로 디버깅·재계산**하고 평상시엔 **집계 데이터로 빠르게 질의**하기 위해. 원시만 두면 질의가 느리고, 집계만 두면 손실·재계산 불가.
2. **이벤트 시각**은 집계가 정확하나 타임스탬프 오류·조작에 취약, **처리 시각**은 안정적이나 부정확할 수 있다. 정확성이 중요하면 이벤트 시각을 우선한다.
3. 다운스트림이 **집계 결과를 확실히 받았다는 ACK를 확인한 뒤에 오프셋을 저장**한다. 그래야 중간에 죽어도 다시 읽어 재처리할 수 있다.

**질의 API 설계 — 지난 M분간 각 ad_id에 발생한 클릭 수 집계**
`GET /v1/ads/{:ad_id}/aggregated_count`
- 주어진 ad_id에 발생한 이벤트 수를 집계하여 반환
- Request: from(집계 시작 시간, long) / to(집계 종료 시간, long) / filter(필터링 전략 식별자, long)

`GET /v1/ads/popular_ads`
- 지난 M분간 가장 많은 클릭이 발생한 상위 N개 광고 목록 반환
- Request: count(상위 몇 개, integer) / window(분 단위 집계 윈도 크기, integer) / filter(필터링 전략 식별자, long)
- Response: ad_ids(광고 식별자 목록, array)

**데이터 모델 — 집계 결과 데이터**
- 컬럼: ad_id / click_minute / filter_id / count
- 🔼 필터를 사용해 집계한 데이터

**비교**
- 원시 데이터만 보관하는 방안 — 장점: 원본 데이터를 손실 없이 보관 / 데이터 필터링 및 재계산 지원. 단점: 막대한 데이터 용량 / 낮은 질의 성능
- 집계 결과 데이터만 보관하는 방안 — 장점: 데이터 용량 절감 / 빠른 질의 성능. 단점: 데이터 손실
- 결론: 둘 다 저장하는 것이 좋다.
	- 문제가 발생하면 원시 데이터로 디버깅 가능하다.
	- 집계 결과 데이터로 빠르게 질의할 수 있다.

**올바른 데이터베이스의 선택**
- (원시 데이터) 쓰기 및 시간 범위 질의에 최적화된 카산드라나 InfluxDB를 사용하는 것이 좀 더 바람직하다.
- (집계 데이터) 원시 데이터와 같은 유형의 데이터베이스를 활용하는 것이 가능하다.

**개략적 설계안 — 비동기 처리**
- 카프카 같은 메시지 큐를 도입하여 생산자와 소비자의 결합을 끊으면, 그 결과로 전체 프로세스는 비동기 방식으로 동작하게 되고, 생산자와 소비자의 규모를 독립적으로 확장해 나갈 수 있게 된다.

**집계 서비스**
- 맵 노드: 데이터 출처에서 읽은 데이터를 필터링하고 변환하는 역할

**집계 노드**
- 리듀스 노드: 모든 `집계` 노드가 산출한 결과를 최종 결과로 축약
- 주요 사용 사례: 클릭 이벤트 수 집계 / 가장 많이 클릭된 상위 N개 광고 반환 / 데이터 필터링

**상세 설계 — 스트리밍 vs 일괄 처리**
- 일괄 및 스트리밍 처리 경로를 동시에 지원하는 시스템의 아키텍처를 람다라고 부른다.
- 서비스(온라인 시스템): 응답성=클라에게 빠르게 응답 / 입력=사용자의 요청 / 출력=클라에 대한 응답 / 성능기준=가용성·지연 시간 / 사례=온라인 쇼핑
- 일괄 처리 시스템(오프라인): 응답성=응답 필요 없음 / 입력=유연한 크기 입력 / 출력=구체화 뷰·집계 결과 지표 / 성능기준=처리량 / 사례=맵리듀스
- 스트리밍 시스템(실시간에 가깝게): 응답성=응답 필요 없음 / 입력=입력에 경계 없음 / 출력=구체화 뷰·집계 결과 지표 / 성능기준=처리량·지연 / 사례=플링크

**데이터 재계산**
- 이미 집계한 데이터를 다시 계산해야 하는 경우가 있는데, 이를 이력 데이터 재처리라고 한다.
- 재계산 프로세스는 데이터 집계 서비스를 재사용하기는 하지만 처리 대상 데이터는 다른 곳에서 읽는다.

**시간**
- 이벤트 시각: 광고 클릭이 발생한 시각
	- 👍 집계 결과가 보다 정확하다.
	- 👎 타임스탬프에 의존하므로 설정 시각 오류 또는 의도적인 조작 문제에서 자유로울 수 없다.
- 처리 시각: 집계 서버가 클릭 이벤트를 처리한 시스템 시각
	- 👍 서버 타임스탬프가 보다 안정적이다.
	- 👎 집계 결과가 보다 부정확할 수 있다.

**집계 윈도**
- 텀블링 윈도는 시간을 같은 크기의 겹치지 않는 구간으로 분할한다. (매 분 발생한 클릭 이벤트 집계에 적합함)
- 슬라이딩 윈도는 데이터 스트림을 미끄러져 나아가면서 같은 구간 안에 있는 이벤트를 집계한다. (M분간 가장 많이 클릭된 상위 N개 광고를 알아내기에 적합함)

**전달 보장**
- 이벤트의 중복 처리를 어떻게 피할 수 있는가?
- 모든 이벤트의 처리를 어떻게 보장할 수 있는가?
- 본 설계안에서는 `정확히 한 번` 방식을 권장한다.
	- 데이터 손실을 막으려면 다운스트림에서 집계 결과 수신 확인 응답을 받은 후 오프셋을 저장해야 한다.

**시스템 규모 확장**
- 메시지 큐의 규모 확장
	- 생산자: 쉬움 (인스턴스 수 제한 X)
	- 소비자: 노드 추가/삭제를 통해 쉽게 조정 가능 (트래픽 적은 시간대에)
- 브로커
	- 해시 키: 같은 id를 갖는 이벤트를 전부 같은 파티션에서 구독 가능
	- 파티션의 수: 사전에 충분한 수만큼 확보 필요
	- 토픽의 물리적 샤딩: 여러 토픽을 두면 처리 대역폭을 높일 수 있지만, 유지 관리 비용도 커짐
- 집계 서비스의 규모 확장
	- 노드의 추가/삭제를 통해 수평적으로 조정이 가능하다.
- 데이터베이스의 규모 확장
	- 안정 해시와 유사한 방식으로 수평적인 규모 확장을 기본적으로 지원하고 있다.

**핫스팟 문제**
- 다른 서비스나 샤드보다 더 많은 데이터를 수신하는 서비스나 샤드를 핫스팟이라고 한다.
- 서버 과부하 문제가 발생할 수 있다.
- 더 많은 집계 서비스 노드를 할당하여 해결할 수 있다.

**결함 내성**
- 스냅숏을 이용하면 집계 서비스의 복구 절차가 단순해진다.
- 어떤 집계 서비스 노드 하나에 장애가 발생하면 해당 노드를 새 것으로 대체한 다음 마지막 스냅숏에서 데이터를 복구하면 된다.
- 스냅숏을 마지막으로 찍은 후에 도착한 새로운 이벤트는, 새 집계 서비스 노드가 카프카 브로커에서 읽어가 다시 처리할 것이다.

**데이터 모니터링 및 정확성**
- 지속적 모니터링
	- 지연 시간: 추적이 가능하도록 기록된 시각 사이의 차이를 시간 지표로 변환해서 모니터링하면 됨
	- 메시지 큐 크기: 카프카를 사용할 경우 레코드 처리 지연 지표를 대신 추적하면 됨
	- 집계 노드의 시스템 자원: CPU, 디스크, JVM 등 관련

**조정**
- 다양한 데이터를 비교하여 데이터 무결성을 보증하는 기법을 말한다.
- 매일 각 파티션에 기록된 클릭 이벤트를 이벤트 발생 시각에 따라 정렬한 결과를 일괄 처리하여 만들어 낸 다음, 실시간 집계 결과와 비교해볼 수 있다.
