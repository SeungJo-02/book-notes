## 1. 무슨 서비스인가 / 요구사항 (1단계)

현재 위치에서 가까운 시설을 찾는 서비스.

### 기능 요구사항
- 고객은 사업장 **상세정보**를 볼 수 있어야 한다.
- 고객의 **위치 + 검색 반경**에 매치되는 사업장 목록을 **반환**한다.
- 사업장 정보는 사업자가 CRUD, **다음날까지 반영**(실시간 아님).
- 사용자 이동에 따른 실시간 결과 변경은 고려하지 않음. 반경 조절값: 0.5 / 1 / 2 / 5 / 20 km.

### 비기능 요구사항
- **낮은 응답 지연** · **데이터 보호**(LBS·GDPR·CCPA) · **고가용성/규모 확장성**.

### 개략적 규모 추정
- DAU 1억 · 사업장 2억 · 고객당 하루 5회 검색 가정.
- `QPS = (1억 × 5) ÷ 86,400초 ≈ 5,000`

## 2. API & 데이터 모델 (2단계)

### 검색 API — `GET /v1/search/nearby`

검색 기준에 맞는 사업장 목록 반환 (페이지 분할 언급하면 가점).

| 필드 | 설명 | 자료형 |
|---|---|---|
| latitude | 검색할 위도 | decimal |
| longitude | 검색할 경도 | decimal |
| radius | optional, 기본 5000m | int |

- **decimal** — Float/Double의 미세 연산 오차를 막는 정밀 수치형. 정밀도는 완벽하지만 느리고 저장공간을 더 쓴다.
- 응답: `{ "total": 10, "business": [ {business object} ] }` — 목록엔 검색결과용 정보만, 상세는 별도 API.

### 데이터 모델 — 읽기/쓰기 비율이 설계를 지배
- 검색·상세조회(읽기)는 폭주, 추가/편집/삭제(쓰기)는 드묾.
- → **MySQL이 유리**(MVCC·레플리카·커버링 인덱스·멀티스레드). 읽기는 사본 DB로 분산.
- 테이블: `business`(PK `business_id`) + **지리 위치 색인 테이블**(지오해시 기반, §4에서).

## 3. 개략적 설계안

- **로드밸런서** — 단일 DNS 진입점, URL 경로로 어느 서비스에 보낼지 결정.
- **위치 기반 서비스(LBS)** — 읽기 전용, QPS 높음(피크·인구밀집 심함), **무상태 → 수평 확장 쉬움**.
- **사업장 서비스** — 소유주의 쓰기(QPS 낮음) + 고객의 상세 조회(피크에 높음).
- **DB 클러스터** — 주-부(primary-secondary). 주=쓰기, 부=읽기. 다음날 반영이라 복제 지연 무방.
- **규모 확장** — 피크엔 서버 자동 증설/유휴엔 감축. 여러 **리전·AZ** 배치로 가용성↑(AZ 장애→다른 AZ, 리전 장애→다른 리전).

## 4. 주변 사업장 검색 알고리즘 ⭐

핵심 질문: **2차원(위·경도) 위치를 어떻게 색인해 반경 검색을 빠르게 하나?**

| 방안 | 핵심 아이디어 | 평가 |
|---|---|---|
| **2차원 검색** | `lat/long BETWEEN` 범위 쿼리 | 전체 스캔 · 색인은 1차원만 개선 → **비효율** |
| **균등 격자** | 지도를 같은 크기 격자로 분할 | 사업장 분포 불균등 · 인접 격자 탐색 까다로움 |
| **지오해시** | 2D 좌표 → **1D 문자열** | 구현 쉬움 · 반경 검색 지원 → **실무 표준** |
| **쿼드트리** | 재귀 사분면 분할(메모리) | 밀도별 동적 격자 · k-NN, **구현 복잡** |
| **구글 S2** | 힐베르트 곡선으로 1D화 | 영역 지정 유연, 구글맵·틴더 |

> 색인 방안은 크게 **해시 기반**(균등격자·지오해시) vs **트리 기반**(쿼드트리·S2·R트리)로 나뉜다.

### 4-1. 지오해시 (Geohash)
- 위·경도 공간을 **사분면으로 재귀 분할**하고 각 분할을 비트로 → base32 문자열로 인코딩.
- **접두어가 같을수록 물리적으로 가깝다.** 문자열이 길수록 격자가 작아짐(정밀도↑).
- 예: 구글 `9q9hvu` · 페이스북 `9q9jhr` → 앞자리 공통 = 인접.
- **정밀도 선택** — "사용자 반경으로 그린 원을 덮는 **최소 격자**"가 되는 지오해시 길이를 고른다. 너무 크면 무관한 사업장이 딸려오고, 너무 작으면 반경을 못 덮는다.

> ⚠️ **지오해시 경계 문제 (면접 단골)** — ① 물리적으로 아주 가까운데 격자가 갈리면 접두어가 안 겹쳐 **누락**된다. ② 접두어는 겹치는데 다른 격자에 있을 수도. → 해결: **내 격자 + 인접 8개 격자를 모두 조회**한다. 그래도 사업장 수가 모자라면 반경을 넓히거나 조건을 완화.

### 4-2. 쿼드트리 (Quadtree)
- 한 격자 안 사업장이 **기준(예: 100개)을 넘으면 사분면으로 분할** → 밀집지역은 작은 격자, 한산하면 큰 격자.
- **메모리 자료구조**(DB 아님). 각 LBS 서버가 **시작 시점에 구축**.
- 장점: 밀도별 동적 격자 · **k번째 가까운 사업장**까지 가능. 단점: 구현·색인 갱신 복잡(O(log n) + 락), 배포 시 시작 느림.

<details>
<summary>쿼드트리 메모리·구축 계산 (2억 사업장)</summary>

- 말단 노드 832B(좌표 32B + ID 8B×100), 내부 노드 64B.
- 총 ≈ 2백만 × 832B + 0.67백만 × 64B ≈ **1.71GB**, 구축 "몇 분".

```java
public void buildQuadtree(TreeNode node) {
  if (countBusiness(node) > 100) {
    node.subdivide();
    for (TreeNode child : node.getChildren()) buildQuadtree(child);
  }
}
```

</details>

### 4-3. 구글 S2 & 기업 채택
- **S2** — 힐베르트 곡선으로 지구를 1D 색인화하되 인접성 유지, 영역 지정이 유연. 구글맵·틴더.
- 채택: 지오해시(빙지도·Redis·MongoDB·리프트) · 쿼드트리(Yext) · 지오해시+쿼드트리(Elasticsearch) · S2(구글맵·틴더).

> 🎤 **면접 한 줄** — 대부분은 **지오해시로 충분**(구현·색인 갱신 쉬움). 인구 밀도 편차가 크거나 **k-NN**이 필요하면 쿼드트리/S2를 고려한다.

## 5. 상세 설계 (3단계)

### 5-1. 지리 정보 색인 테이블
- **방안1** — `geohash | business_ids(JSON 배열)` : 갱신 시 배열 통째로 잠가야 함 ✗
- **방안2(권장)** — `(geohash, business_id)` **복합키로 행마다 저장** : 추가/삭제 쉽고 **락 불필요** ✔
- `business` 테이블은 `business_id`로 **샤딩**(부하 고른 분산). 색인 테이블은 읽기 폭주라 사본 DB 증설.

| geohash | business_id |
|---|---|
| 32feac | 343 |
| 32feac | 347 |
| f3lcad | 112 |

### 5-2. 캐시 전략

> 🗝️ **캐시 키는 사용자 위치가 아니라 지오해시로** — 위치는 조금만 움직여도 계속 바뀌어 적중률이 낮지만, 같은 격자면 지오해시가 동일해 **적중률이 크게 오른다**.

| 키 | 값 | 용도 |
|---|---|---|
| 지오해시 | 격자 내 사업장 ID 목록 | 검색 결과 |
| 사업장 ID | 사업장 상세 객체 | 상세 정보 |

- 조회 로직: Redis miss면 아래 SQL을 실행하고 **1일 TTL**로 캐싱.

```sql
SELECT business_id FROM geohash_index WHERE geohash LIKE '{:geohash}%'
```


### 5-3. 배치 · 갱신 · 최종 흐름
- **지역/AZ 배치** — 물리적 거리↓, 트래픽 고른 분산, 가용성↑, **지역 개인정보법 준수**.
- **쓰기 흐름** — 주 DB 기록 → 부 DB 복제 → **밤사이 배치로 캐시 갱신**(다음날 반영, 실시간 불필요 합의).
- **검색 흐름** — LB → LBS(반경 덮는 지오해시 길이 계산 → 내 격자 + 인접 8개) → **지오해시 Redis**로 ID 목록 → **사업장 Redis**로 상세 → 결과 반환.

## 6. 정리 & 셀프 체크

### 개념 → 한 줄 정리

| 개념 | 한 줄 |
|---|---|
| 지오해시 | 2D 좌표를 1D 문자열로 — 접두어 같으면 가깝다. 반경 덮는 최소 길이 선택 |
| 경계 문제 | 격자 경계로 가까운데 누락 → **인접 8격자까지 조회** |
| 쿼드트리 | 밀도별 동적 격자 · k-NN, 메모리 구조, 구현·갱신 복잡 |
| 색인 테이블 | `(geohash, business_id)` 복합키 행 방식 — 추가/삭제 락 불필요 |
| 캐시 키 | 위치 대신 지오해시 — 적중률↑, 1일 TTL |
| 읽기·쓰기 | 읽기 폭주·쓰기 희소 → 주-부 복제 · 다음날 반영 |

### 🔁 셀프 체크
1. 지오해시가 무엇이고, 왜 **검색 반경에 따라 지오해시 길이**를 바꾸는가?
2. 지오해시 대신 **쿼드트리**를 쓰는 건 언제인가?
3. 두 위치가 물리적으로 아주 가까운데 검색 결과에 안 잡히는 이유와 해법은?

<details>
<summary>답</summary>

1. 위·경도 2D를 사분면 재귀분할로 만든 1D 문자열. 반경을 덮는 **최소 격자**가 되는 길이를 골라야 — 격자가 너무 크면 무관한 사업장이 딸려오고, 너무 작으면 반경을 못 덮는다.
2. 인구 밀도 편차가 크거나(밀집=작은 격자) **k번째 가까운 사업장**이 필요할 때. 대신 구현·색인 갱신이 복잡(락)하다.
3. 지오해시 **격자 경계** 때문. 서로 다른 격자에 놓이면 접두어가 안 겹쳐 누락된다. → 내 격자뿐 아니라 **인접 8개 격자를 함께 조회**한다.

</details>

> ✅ **이 장의 뼈대** — ① 읽기 폭주·쓰기 희소 성격 파악 → ② 2D를 1D로 바꾸는 지오해시 색인 → ③ 경계 문제를 인접 격자로 해결 → ④ 지오해시 키 캐시 + 주-부 복제 + 지역/AZ 배치.
