## 1. 요구사항 & 규모 추정

- **기능 요구사항** — 사용자 위치 갱신 · 경로 안내(ETA 포함) · 지도 표시 · 다양한 이동 방법(운전·도보·대중교통 등) 지원.
- **규모** — DAU **10억**, 도로 데이터는 **수 TB의 가공되지 않은 원본**.
- **비기능 요구사항** — **정확한 도착 시간** · 부드러운 경로 표시(확대·이동이 매끄러움) · **데이터·배터리 사용량 최소화** · 일반적인 수준의 가용성·확장성.

### 1-1. 저장소 추정

| 항목 | 계산 | 값 |
|---|---|---|
| 최대 확대(21단계) 타일 수 | 확대할 때마다 1장 → 4장, 4²¹ | 약 **4.4조 장** |
| 전부 저장 | 4.4조 × 100KB(압축 PNG) | 약 **440PB** |
| 사람이 없는 지역 제외 | 지구 표면 약 90%는 바다·사막 등 → 압축률 높음 | 44~88PB, 어림잡아 **50PB** |
| 모든 확대 수준 합계 | 50 + 50/4 + 50/16 + … (등비급수) | 약 **67PB → 넉넉히 100PB** |
| 메타데이터 | | 무시해도 될 만큼 작음 |
| 도로 데이터 | 요구사항 | 수 TB |

> 💡 한 단계 낮은 확대 수준은 타일 수가 1/4이라, 모든 수준을 더해도 최대 수준의 약 4/3배밖에 안 된다. 그래서 50PB에 여유를 더해 100PB로 잡는다.

### 1-2. 서버 대역폭 (위치 갱신 QPS)

| 단계 | 계산 | 값 |
|---|---|---|
| 하루 사용량 | 10억 명 × 주 35분 ÷ 7 = 인당 하루 5분 | **50억 분/일** |
| 매초 위치를 보내면 | 50억 분 × 60초 | 3,000억 요청/일 |
| QPS | 3,000억 ÷ 10⁵초 | **300만 QPS** |
| 15초마다 모아 보내면 | 300만 ÷ 15 | 평균 **20만 QPS** |
| 최대치 | 평균 × 5 | 최대 **100만 QPS** |

> ⚠️ 20만/100만 QPS는 **위치 갱신 요청**의 평균/최대치다. 경로 안내 요청 QPS가 아니다. (원본 노트에서 라벨이 바뀌어 있어 바로잡음)

## 2. 지도 101 — 먼저 알아야 할 개념

| 개념 | 뜻 | 핵심 |
|---|---|---|
| **측위 시스템** | 구 표면 위 위치를 표현하는 체계 | **위도**(북/남) · **경도**(동/서) |
| **지도 투영법(도법)** | 3차원 구 위의 위치를 2차원 평면에 대응 | 모든 투영법은 형태를 조금씩 왜곡한다. 구글 맵은 **웹 메르카토르** |
| **지오코딩** | 주소 → 위도·경도 변환 (반대는 역지오코딩) | **인터폴레이션**: GIS 등 여러 시스템의 도로망 데이터를 결합해 주소 위치를 추정 |
| **지오해싱** | 지도 영역을 영문자·숫자로 된 짧은 문자열로 인코딩 | 격자를 재귀적으로 4등분. **앞자리(접두사)가 같으면 가까운 영역** |
| **지도 타일** | 지도를 한 장이 아니라 작은 이미지 조각으로 | 클라이언트가 **확대 수준에 맞는 타일만** 받아 이어 붙임 |
| **도로 그래프** | 교차로 = 노드, 도로 = 엣지 | 모든 경로 탐색 알고리즘(다익스트라, A* 등)의 전제 |

> 💡 **웹 메르카토르를 쓰는 이유** — 세계 지도를 **정사각형**으로 만들 수 있어서 타일을 4등분해 나가기 좋고, 좁은 영역에서는 모양(각도)이 유지된다. 대신 극지방으로 갈수록 면적이 크게 부풀려진다(그린란드가 아프리카만 해 보이는 이유).

### 2-1. 경로 안내 타일 — 도로망을 쪼개기
- 전 세계 도로망을 하나의 그래프로 두면 메모리에 올릴 수도 없고 탐색도 느리다.
- 그래서 지오해싱과 비슷하게 **격자로 쪼갠 작은 그래프(= 경로 안내 타일)** 단위로 관리한다. 타일마다 인접 타일로 이어지는 엣지 정보도 가진다.
- 👍 필요한 타일만 불러오니 **메모리 요구량↓** · 한 번에 처리할 경로 양↓ · **탐색 성능↑**.

### 2-2. 계층적 경로 안내 타일
| 구체성 | 타일 크기 | 담는 도로 |
|---|---|---|
| **상** | 가장 작음 | 지방도(골목까지 세밀하게) |
| **중** | 더 넓음 | 관할구를 잇는 간선 도로 |
| **하** | 가장 넓음 | 도시·주를 잇는 주요 고속도로 |

- 서울→부산처럼 먼 길은 출발지 근처는 **상** 타일, 중간은 **하**(고속도로) 타일로 탐색한다. 모든 골목을 다 뒤지지 않아도 된다.

## 3. 개략적 설계

[🖼️ 원본 이미지: 개략적 설계안 — 위치 서비스 · 경로 안내 서비스 · 지도 표시(CDN)]

### 3-1. 위치 서비스
- 클라이언트가 **t초마다** 자기 위치를 보낸다. 이 데이터 스트림으로 **ETA 정확도 향상 · 교통 상황 파악 · 우회 경로 안내** 등 시스템을 점점 개선할 수 있다.
- **일괄 요청** — 위치 이력을 클라이언트에 모아 두었다가(예: 15초치) 한 번에 보낸다 → 전송 빈도↓, 배터리·데이터 절약.
- 그래도 쓰기가 매우 많으므로 **쓰기에 최적화되고 수평 확장이 쉬운 DB(카산드라)**, 다른 서비스에도 쓰려면 **카프카** 같은 스트림으로 로깅.
- 프로토콜은 **HTTP + keep-alive**(연결 재사용).

```http
POST /v1/locations
locs: JSON으로 인코딩한 (위도, 경도, 시각) 순서쌍 배열
```

### 3-2. 경로 안내 서비스
- 출발지~목적지의 **적당히 빠른 경로**를 찾는다. 최단 시간일 필요는 없지만 **정확도는 보장**돼야 한다.
- 요청은 로드밸런서를 거쳐 서비스에 도달한다.

```http
GET /v1/nav?origin=1355+market+street,SF&destination=Disneyland
```

| 응답 필드 | 뜻 |
|---|---|
| `distance` / `duration` | 거리·소요 시간 (`text`는 표시용, `value`는 m·초) |
| `start_location` / `end_location` | 시작·끝 좌표 (`lat`, `lng`) |
| `html_instructions` | 안내 문구 (예: "Brandon St에서 북동쪽으로") |
| `polyline` | 경로 선을 압축 인코딩한 점 목록 |
| `geocoded_waypoints` | 출발·도착지를 지오코딩한 결과 |
| `travel_mode` | 이동 방법 (`DRIVING` 등) |

### 3-3. 지도 표시
- 클라이언트가 타일을 새로 받는 순간: ① 사용자가 **확대·이동**할 때 ② 안내 중 사용자가 **현재 타일을 벗어나 인접 타일로** 갈 때.

| 방법 | 장단점 |
|---|---|
| 요청마다 **즉석에서 타일 생성** | 👎 서버 부하 심각 · 👎 캐시 활용 어려움 |
| 확대 수준별로 **미리 만든 타일 전달** ✅ | 👍 확장 쉽고 빠름 · 👍 타일은 **정적**이라 **CDN 캐시**에 딱 맞음 |

- **데이터 사용량** — 30km/h 이동, 타일 1장 = 200m×200m(100KB)라면 1km×1km에 25장 = **2.5MB** → 시간당 30km = **75MB**.
- **CDN 트래픽** — 하루 50억 분 × 분당 1.25MB(75MB ÷ 60) = **6.25PB/일** → 초당 약 **62.5GB**(6.25PB ÷ 10⁵).

[🖼️ 원본 이미지: CDN 기반 서비스 구조]

**지도 표시 흐름**
1. 모바일 클라이언트가 **타일 URL**을 받으려고 지도 타일 서비스를 호출한다(로드밸런서 경유).
2. 로드밸런서가 요청을 지도 타일 서비스로 전달한다.
3. 지도 타일 서비스가 위치·확대 수준으로 **타일 URL 9개**(보려는 타일 1 + 주변 8)를 계산해 돌려준다.
4. 클라이언트가 그 타일들을 **CDN에서** 내려받는다.

> 💡 URL 계산은 지오해시만 알면 클라이언트도 할 수 있다. 서버에 두는 이유는 **타일 인코딩 방식을 바꿔도 앱을 업데이트하지 않아도 되기** 때문이다.

## 4. 상세 설계 — 데이터 모델

| 데이터 | 저장소 | 이유 |
|---|---|---|
| **경로 안내 타일** | **객체 저장소(S3)** + 서비스 메모리 캐시 | 미리 계산된 정적 파일. DB에 넣을 이유가 없음 |
| **사용자 위치** | **카산드라** | 초당 100만 쓰기 · 수평 확장 |
| **지오코딩 DB** | **키-값 저장소(Redis)** | 읽기가 잦고 빨라야 함, 변경은 드묾 |
| **미리 만든 지도 이미지** | 객체 저장소 + **CDN** | 계산 비용이 크고 같은 이미지 요청이 반복됨 → 한 번 만들어 캐시 |

### 4-1. 경로 안내 타일
- 원본 도로 데이터는 가공이 안 돼 있어서, **경로 안내 타일 처리 서비스**라는 **오프라인 가공 파이프라인**이 타일로 만든다.
- 탐색할 때는 그래프를 메모리의 **인접 리스트**로 올린다. 인접 리스트는 노드마다 연결된 이웃과 가중치를 묶어 둔 목록이다. 예: `A → [(B, 50m), (C, 120m)]`
- **노드·엣지를 DB 행으로 넣지 않는 이유**
  - 길 찾기는 "다음 노드"를 계속 따라가야 해서, DB면 **매 단계 I/O + 조인**이 생긴다.
  - 미리 만든 **읽기 전용 파일**이라 트랜잭션·락·ACID가 필요 없다.
- 그래서 **S3에 파일로 보관**하고 경로 안내 서비스가 **적극적으로 캐시**한다. 파일은 **지오해시 기준으로 분류**해 두면, 위도·경도만으로 해당 타일 파일을 바로 찾을 수 있다.

<details>
<summary>❓ 정적 파일을 왜 DB가 아니라 S3에 두나?</summary>

- **비용** — DB 스토리지는 용량이 커질수록 매우 비싸다. 객체 저장소는 훨씬 싸다.
- **커넥션** — 수십 MB짜리 데이터를 DB에서 읽는 동안 커넥션이 오래 잡혀 **커넥션 부족**이 생길 수 있다.
- **캐시 오염** — DB는 읽을 때 버퍼 풀(메모리)에 올리므로, 큰 정적 파일이 **핵심 데이터를 캐시에서 밀어낸다**.
- **CDN 연동** — S3 객체는 고유한 **HTTP URL**이 있어서 앞단에 CDN을 붙이기 쉽다.

</details>

### 4-2. 사용자 위치 데이터
- 도로 데이터·경로 안내 타일 갱신, 실시간 교통량 DB, 교통 이력 DB 구축에 쓰인다.

| user_id | timestamp | user_mode | driving_mode | location |
|---|---|---|---|---|
| 101 | 1635740977 | active | driving | (20.0, 30.5) |

## 5. 상세 설계 — 서비스

### 5-1. 위치 서비스

[🖼️ 원본 이미지: 사용자 위치 데이터베이스]

- 초당 100만 건 쓰기 → **NoSQL 키-값 DB 또는 열 중심 DB**.
- 사용자 위치는 계속 새 값으로 바뀌므로 **일관성보다 가용성**이 중요하다. CAP 중 **AP**(가용성 + 분할 내성)를 택한다.
  - 분할 내성: 네트워크가 끊겨 노드가 나뉘어도 시스템이 계속 동작하는 능력.
- → **카산드라**가 가장 적합하다.
- 키는 **`(user_id, timestamp)`**, 값은 위도·경도.
  - `user_id` = **파티션 키**: 한 사용자의 데이터를 한 파티션에 모아 **최근 위치를 빨리** 읽는다.
  - `timestamp` = **클러스터링 키**: 파티션 안에서 시간순으로 정렬한다.

| key(user_id) | timestamp | lat | long | user_mode | navigation_mode |
|---|---|---|---|---|---|
| 51 | 132053000 | 21.9 | 89.8 | active | driving |

**사용자 위치 데이터의 쓰임**
- 새로 생기거나 폐쇄된 도로 감지 · 지도 정확도 개선 · 실시간 교통 현황 파악.
- 그래서 DB 저장과 별도로 **카프카에 로깅**하고, 여러 서비스가 각자 구독한다. **데이터 하나를 여러 서비스가 나눠 쓰는 구조**다.
  - **실시간 교통 상황 서비스** → 실시간 교통량 DB 갱신
  - **경로 안내 타일 처리 서비스** → 새 도로·폐쇄 도로를 찾아 S3의 경로 안내 타일에 반영
  - 그 밖에 교통 이력·분석 서비스 등

### 5-2. 지도 표시

**지도 타일 사전 계산**
| 확대 수준 | 타일 수 | 전체 해상도 |
|---|---|---|
| 0 | 1장 | 256×256 |
| 1 | 2×2 | 512×512 |
| 2 | 4×4 | 1024×1024 |
| n | 2ⁿ×2ⁿ | (256·2ⁿ)² |

- 한 단계 올릴 때마다 동서·남북으로 2배씩, 전체 타일 수는 4배가 된다.
- 클라이언트는 **자기 확대 수준에 맞는 타일만** 받으므로, 대역폭을 크게 쓰지 않고도 적절한 해상도의 지도를 보여준다.

**최적화: 벡터 타일**
- 이미지 대신 **경로·다각형 같은 벡터 정보**를 보내고, 클라이언트(WebGL 등)가 직접 그린다.
- 👍 이미지보다 **압축률이 월등** → 대역폭 절약.
- 👍 확대할 때 요소 크기를 부드럽게 조절할 수 있다(래스터는 확대하면 깨지고 레벨이 바뀔 때 뚝뚝 끊김).

### 5-3. 경로 안내 서비스

[🖼️ 원본 이미지: 경로 안내 서비스 구성]

| 구성 요소 | 하는 일 |
|---|---|
| **지오코딩 서비스** | 출발지·목적지 주소를 위도·경도로 변환. 장소 이름·지번 등 **주소 형식이 다양**하니 주의 |
| **경로 계획 서비스** | 아래 3개 서비스를 조율해 최적 경로를 만든다 |
| └ **최단 경로 서비스** | 위도·경도를 받아 **k개 최단 경로** 반환(교통 상황 고려 X). S3의 경로 안내 타일에 **A* 변형**을 실행하며, 출발지 타일부터 필요한 타일만 불러가며 탐색 |
| └ **ETA 서비스** | 현재 교통 상황 + 과거 이력으로 **머신러닝**을 이용해 도착 시간 예측 |
| └ **순위 결정 서비스** | 사용자 필터(유료 도로·고속도로 제외 등) 적용 후 **소요 시간 순으로 상위 k개** 반환 |
| **중요 정보 갱신 서비스들** | 카프카 위치 스트림을 구독해 **비동기로** 최신 상태 유지 |
| └ 경로 안내 타일 처리 | 새 도로·폐쇄 도로를 반영해 타일 갱신 |
| └ 실시간 교통 상황 | 활성 사용자의 위치 스트림에서 교통 정보를 추출해 교통량 DB 갱신 → ETA 서비스가 사용 |

> 💡 **A***는 다익스트라에 "목적지까지 남은 거리 추정값(휴리스틱)"을 더해, 목적지 쪽 노드를 먼저 탐색하게 만든 알고리즘이다. 탐색 범위가 크게 줄어든다.

## 6. 적응형 ETA와 전송 프로토콜

- 현 설계는 안내 도중 교통이 바뀌어도 **ETA 변경·경로 재탐색을 하지 않는다**. 해결하려면 서버가 **안내 중인 모든 사용자를 추적**해야 한다.
- 핵심 질문: ① 안내 중인 사용자를 어떻게 추적하나? ② 수백만 경로 중 **교통 변화에 영향받는 사용자를 어떻게 빨리 찾나?**

### 6-1. 영향받는 사용자 찾기
| 방법 | 저장 방식 | 탐색 비용 |
|---|---|---|
| 단순 방식 | `user_1: r_1, r_2, r_3, …, r_k` (경로가 지나는 타일 목록) | `r_2`에 사고가 나면 모든 레코드를 전수 조사 → **O(n × m)** (n = 레코드 수, m = 평균 경로 길이) |
| **재귀적 상위 타일** ✅ | 현재 타일 + 그 **상위 타일 + 그 상위…**를 **출발지·목적지를 모두 포함하는 타일**이 나올 때까지 저장 | 각 레코드의 **마지막(가장 큰) 타일**에 변화가 난 타일이 속하는지만 보면 됨 → **O(n)** |

[🖼️ 원본 이미지: 재귀적인 경로 타일 수집]

- ⚠️ 한계: **교통 상황이 좋아졌을 때**(더 빠른 길이 생겼을 때)의 처리는 해결하지 못한다.

### 6-2. 전송 프로토콜 (서버 → 클라이언트 알림)
| 방식 | 평가 |
|---|---|
| 모바일 푸시 알림 | 👎 메시지 크기가 매우 제한적(iOS 4KB 등), 웹 앱 지원 X |
| 롱 폴링 | 👎 서버 부담이 큼 |
| **웹소켓** ✅ | 👍 서버 부담이 적고 **양방향 통신** 지원 |
| SSE | 단방향이지만 이 용도에는 충분. 웹소켓과 함께 후보 |

| 규모 | DAU 10억, 위치 갱신 평균 20만·최대 100만 QPS, 타일 저장 ≈100PB |

2. 지도 타일을 요청마다 만들지 않고 **미리 만들어 CDN으로** 주는 이유는?
3. 경로 안내 타일(도로 그래프)을 DB 행이 아니라 **S3 파일 + 메모리 인접 리스트**로 다루는 이유는?

<details>
<summary>답</summary>

1. 초당 최대 100만 건의 **쓰기**를 감당해야 하고 **수평 확장**이 쉬워야 한다. 위치는 계속 새 값으로 바뀌니 **일관성보다 가용성**(AP)이 중요한데, 카산드라가 이 조건에 맞는다. `user_id`를 파티션 키로 두면 한 사용자의 위치가 한 파티션에 모여 **최근 위치를 빨리** 읽을 수 있고, `timestamp` 클러스터링 키로 시간순 정렬이 된다.
2. 즉석 생성은 **서버 부하가 크고 캐시하기 어렵다**. 타일은 확대 수준과 위치만 같으면 누구에게나 같은 **정적 데이터**라서 미리 만들어 두면 **CDN 캐시**로 전 세계에 싸고 빠르게 뿌릴 수 있고 확장도 쉽다.
3. 길 찾기는 "다음 노드"를 계속 따라가는 작업이라, DB에 두면 매 단계 **I/O와 조인**이 생겨 느리다. 타일은 미리 만든 **읽기 전용 파일**이라 트랜잭션·락도 필요 없다. 그래서 싼 **S3**에 지오해시 기준으로 보관하고, 필요한 타일만 **메모리 인접 리스트**로 올려 탐색하고 캐시한다.

> **3차원 위치의 2차원 변환**

[🖼️ 원본 이미지: 지도 투영법 사이의 차이점]

  - e.g. 주소 → 위도 x도, 경도 y도
  - 인터폴레이션이라는 방식을 쓴다
    - 다양한 시스템이 제공하는 데이터를 결합한다는 뜻
      e.g. GIS(도로망을 지리적 좌표공간에 대응 시키는 방법 제공 서비스)

> **경로 안내 알고리즘을 위한 도로 데이터 처리**

[🖼️ 원본 이미지: 그래프로 표현한 지도]
- 모든 경로 탐색 알고리즘은 교차로를 노드(node)로, 도로는 노드를 잇는 선(edge)으로 표현하는 그래프 자료 구조를 가정한다.
- 좋은 성능을 위해 그래프를 관리 기능 단위로 분할할 필요가 있다. (각 격자는 경로 안내 타일이라 부름)
- 도로망을 언제든 불러올 수 있는 경로 안내 타일로 분할해 놓으면 경로 탐색 알고리즘이 동작하는 데 필요한 메모리 요구량을 낮출 수 있고, 한번에 처리해야 하는 경로의 양이 줄어들며, 필요한만큼만 불러오면 되기 때문에 탐색 성능도 좋아진다.

> **계층적 경로 안내 타일 (길 찾기 연산을 어떻게 할 건가)**

- 구체성 정도를 상, 중, 하로 구분하여 3가지 종류의 경로 안내 타일을 준비한다.
  - 가장 구체성이 높은 타일의 경우(**상**), 그 크기는 아주 작으며, 이런 타일에는 지방도 데이터만 둔다.
  - **중**은 더 넓은 지역을 커버하며, 규모가 비교적 큰 관할구를 잇는 간선 도로 데이터만 둔다.
  - 구체성이 가장 낮은 타일(**하**)은 그보다 더 큰 영역을 커버하며, 그런 타일에는 도시와 주를 연결하는 주요 고속 도로 데이터만 둔다.

- 카프카 같은 스트림 엔진을 활용하여 위치 데이터를 로깅해야 할 수도 있다.
- 통신 프로토콜은 HTTP를 keep-alive 옵션과 함께 사용하면 효율을 높일 수 있을 것이다.

  - 사용자가 지도를 확대 또는 이동시키며 주변을 탐색한다.
  - 경로 안내가 진행되는 동안 사용자의 위치가 현재 지도 타일을 벗어나 인접한 타일로 이동한다.
- 다량의 지도 타일 데이터를 서버에서 효과적으로 가져오는 방법은 다음과 같다.
  - 클라이언트의 위치, 현재 클라이언트가 보는 지도의 확대 수준에 근거하여 필요한 지도 타일을 즉석에서 만든다.
    - 👎 심각한 부하가 걸릴 수 있다.
    - 👎 캐시를 활용하기 어렵다.
  - 확대 수준별로 미리 만들어 둔 지도 타일을 클라이언트에 전달하기만 한다.
    - 👍 규모 확장이 용이하고, 성능 측면에서도 유리하다.
    - 👍 지도 타일은 정적이므로 캐시를 통해 서비스하기 적합하다.

**경로 안내 타일**
- 데이터가 가공되지 않는 도로데이터라 데이터 가공이 필요 (가공 파이프 라인 필요)
- 한 타일의 노드와 엣지로 만들어져 있는 타일을 여럿 묶는다
- 보통은 메모리에 인접 리스트에 올릴텐데 데이터 양이 방대하다.
  - 인접 리스트 : 그래프 데이터를 메모리에서 탐색하기 위한 자료구조
    노드 A에서 연결된 다른 교차로들과 가중치를 리스트로 묶음
    e.g. A -> [(B, 50m), (C, 120m)]
- 그렇다고 노드 및 엣지를 DB에 넣으면 비용이 비싸고 필요없다
  - 길 찾기 알고리즘은 다음 노드 탐색이 필요하다
    - I/O 지연 + Join 한계 + 무거운 기능(Lock, ACID)
  - 심지어 쓸 때 없음
    - 미리 만들어주는 방식이니까 즉 정적 파일이라 트랜잭션이 필요없고 S3을 이용해서 통째로 서버 메모리에 인접리스트로 올리는 게 더 좋음
- 객체 저장소(ex. S3)에 파일을 보관하고 그 파일을 이용할 경로 안내 서비스에서 적극적으로 캐싱한다.
  - 저장할 때는 지오해시 기준으로 분류해서 집어 넣기 그러면 위도랑 경도가 주어지면 그 위치에 있는
    파일을 기준으로 찾기가 편하니까

DB와 스토리지 (토글)
  - 이미 계산이 끝난 정적파일을 저장할 때 왜 DB에 저장을 안하나?
    - DB에서 사용하는 저장소는 유지비용이 매우 비싸다(용량이 커질수록 비싸진다)
    - 수십MB데이터를 가져오면 커넥션이 계속 잡히고 있으니까 커넥션 부족으로 이슈 생길 수 O
    - DB는 데이터 읽을 때 트랜젝션로그도 확인하고 Buffer Pool(메모리)에 올리는 과정을 거친다
      정적파일 때문에 핵심데이터가 쫓겨 나면 캐시오염도 생긴다
    - S3같은 경우 파일로 저장되고 고유한 HTTP URL을 갖기 때문에 앞단에 CDN을 붙이기가 쉽다

**지도 표시**

> **지도 타일 사전 계산**

- 확대 수준 0은 세계 전부를 256*256픽셀짜리 타일 하나로 표현한다.
- 확대 수준을 1단계 올릴 때마다 해당 수준을 위한 전체 타일 수는 동서 방향으로 2배, 남북 방향으로 2배 늘어난다.
  - 확대 수준 1: 필요한 타일 `2*2`장, 해당도 `512*512` 픽셀
  - 확대 수준 2: 필요한 타일 `4*4`장, 해상도 `1024*1024` 픽셀
- 클라이언트는 해당 정보를 제공하기 위한 타일을 다운 받는 데 많은 네트워크 대역폭을 소진하지 않고도 클라이언트에 설정된 확대 수준에 최적인 크기의 지도를 표시할 수 있다.

> **최적화: 벡터 사용**

- 이미지 대신 경로와 다각형 등의 벡터 정보를 보낸다.
- 클라이언트는 수신된 경로와 다각형 정보를 통해 지도를 그려낸다.
- 이미지에 비해 월등한 압축률을 가지므로, 네트워크 대역폭을 많이 아낄 수 있다.
- 벡터화 된 이미지를 사용하면 클라이언트는 각 요소 크기를 적절하게 조정할 수 있어 훨씬 매끄러운 확대 경험을 제공할 수 있다.

> **경로 계획 서비스**

- 최단 경로 서비스
  - 출발지와 목적지 위도/경도를 입력으로 받아 k개 최단 경로를 반환한다. (교통, 도로 상황 고려 X)
  - 객체 저장소에 저장된 경로 안내 타일에 대해 A* 경로 탐색 알고리즘의 한 형태를 실행한다.
    - 입력으로 출발지와 목적지의 위도/경도를 받는다.
    - 출발지 타일에서 시작하여 그래프 자료 구조를 탐색해 나간다.
- 예상 도착 시간 서비스
  - AI를 활용해 현재 교통 상황 및 과거 이력에 근거하여 예상 도착 시간을 계산한다.
- 순위 결정 서비스
  - 경로 계획 서비스는 ETA 예상치를 구하고 나면 순위 결정 서비스에 관련 정보를 모두 전달하여 사용자가 정의한 필터링 조건을 적용한다.
    - Ex. 유료 도로 제외, 고속도로 제외 등
  - 필터링이 끝나고 남은 경로를 소요 시간 순으로 정렬하여 최단 시간 경로 k개를 구한 다음 경로 안내 서비스에 결과를 반환한다.

> **중요 정보 갱신 서비스들**

- 카프카 위치 데이터 스트림을 구독하고 있다가 중요 데이터를 비동기적으로 업데이트하여 그 상태를 항상 최신으로 유지하는 역할을 담당한다.
- **경로 안내 타일 처리 서비스**는 도로 데이터에 새로 발견된 도로, 폐쇄되었음이 확인된 도로 정보를 반영하여 경로 안내 타일을 지속적으로 갱신한다.
- **실시간 교통 상황 서비스**는 활성화 상태 사용자가 보내는 위치 데이터 스트림에서 교통 상황 정보를 추출한다.

  - 레코드를 전수 조사해서 어떤 사용자가 해당 타일을 가지고 있는지 알아내야 한다.
  - 테이블에 보관된 레코드 수가 n이고 안내되는 경로의 평균 길이가 m이라면 교통 상황 변화에 영향 받는 모든 사용자 검색의 시간 복잡도는 O(n*m)이 된다.

[🖼️ 원본 이미지: 재귀적인 경로 타일 수집]
- 경로 안내를 받는 사용자 각각의 현재 경로 안내 타일, 그 타일을 포함하는 상위 타일, 그 상위 타일의 상위 타일을 **출발지와 목적지가 모두 포함된 타일**을 찾을 때까지 재귀적으로 더하여 보관하는 것이다.
- 어떤 타일의 교통 상황이 변했을 때 경로 안내 ETA가 달라지는 사용자는, 해당 사용자의 데이터베이스 레코드 마지막 타일에 그 타일이 속하는 사용자다.
- 검색 시간 복잡도가 O(n)으로 줄어든다.
- 교통 상황이 개선되었을 때 해야 하는 일까지 해결해 주지 않는다.
