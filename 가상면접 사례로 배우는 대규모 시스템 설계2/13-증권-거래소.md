# 13장. 증권 거래소

> 📝 **Notion 원본**: https://app.notion.com/p/a189e207480e4918b06521065889abd7

> 🧩 **한 줄 요약** — 하루 10억 건 주문(QPS 43,000, 최대 215,000)을 **밀리초 지연(P99)** 으로 체결하는 거래소. 주문은 **게이트웨이 → 주문 관리자(위험·자금 점검) → 시퀀서 → 체결 엔진** 을 지나고, 이 **중요 경로를 한 서버 안에** 몰아넣어 네트워크·디스크 왕복을 없앤다(**mmap + 애플리케이션 루프 + CPU 코어 고정**). 상태는 DB에 쓰지 않고 **이벤트 소싱**으로 로그만 쌓아 **같은 순서로 재생하면 같은 결과**(결정론)를 보장하고, 장애는 **메인/서브 복제 + Raft 리더 선출**로 넘긴다.

## 1. 요구사항 & 규모

### 1-1. 기능 요구사항

| 항목 | 내용 |
|---|---|
| 거래 대상 | **주식만** |
| 주문 | **새 주문 · 주문 취소 · 지정가 주문**만 지원 (시장가·조건부는 범위 밖) |
| 시간 | **거래 시간 내**에만 |
| 실시간성 | 주문이 체결되면 **실시간으로** 알려야 함 · **호가 창(오더북)** 은 실시간 갱신 |
| 규모 | **수만 명 동시 거래** · 하루 **수십억 건** 주문 |
| 위험 점검 | 하루 거래 한도 같은 규칙이 지켜지는지 확인 |
| 자금 점검 | 주문 전에 **자금 확인**. 체결 안 된 주문에 묶인 돈은 **다른 주문에 못 씀** |

**주문 종류 (용어 정리)**

| 종류 | 뜻 | 비유 |
|---|---|---|
| **새 주문** | 매수/매도 요청을 등록. 돈이 있는지 확인하고 **대기열에 줄 세움** | 번호표 뽑기 |
| **주문 취소** | 오더북에 대기 중인 주문 삭제 (100개 중 30개만 받고 나머지 70개 취소 같은 경우) | 번호표 반납 |
| **주문 교체** | 기존 주문서를 찢고 새 주문서로 | 번호표 다시 뽑기 |
| **지정가 주문** | **정확한 목표 가격**을 지정. "50,000원 이하로만 산다", "55,000원 이상으로만 판다" | 가격표 붙여서 줄 서기 |
| **시장가 주문** | 가격을 안 정하고 **지금 가장 유리한 상대 물량을 즉시** 가져감 | 지금 있는 것 중 제일 싼 거 |
| **조건부 주문** | Stop Loss: 5만 원 주식이 4만 5천 원(감시 가격)에 닿으면 **자동 매도** | 안전핀 |

- **오더북**: 매수/매도 주문 목록이 표시되는 곳. 증권 거래소의 **체결 엔진**이 관리하는 주문 장부.
- 시간 조건 주문: **IOC**(Immediate Or Cancel, 원하는 양이 없으면 **있는 만큼만** 사고 나머지 취소) · **FOK**(Fill Or Kill, 100개 원하는데 99개뿐이면 **아예 안 삼**).

### 1-2. 비기능 요구사항

| 항목 | 내용 |
|---|---|
| **지연 시간** | 밀리초 수준. 평균보다 **P99**(느린 쪽 1%)가 중요 |
| **처리량 + 안정성** | 수십억 건을 흔들림 없이 |
| **가용성** | 최소 **99.99%** (연간 약 52분 다운 허용) |
| **결함 내성** | 장애 파급을 줄이고 **빠르게 복구** |
| **보안** | **KYC**(사용자 신원 확인) + 공격 방지 장치 |

### 1-3. 규모 추정

- 주식 **100가지**, 하루 **10억 건** 주문.
- 뉴욕증권거래소 영업시간 09:30~16:00 = **6.5시간**.
- QPS = 10억 ÷ (6.5 × 3,600) ≈ **43,000**.
- 최대 QPS = 평균의 5배 ≈ **215,000** (장 시작·마감 직후 몰림).

## 2. 증권 거래 101

| 용어 | 뜻 |
|---|---|
| **브로커** | 개인이 증권을 거래하고 시장 데이터를 보게 해 주는 UI. 토스증권, 키움증권(영웅문), 로빈후드 |
| **기관 고객** | 수백억~수천억을 굴리는 기업형 투자자. **전문 소프트웨어로 대량 거래**, **낮은 응답 시간** 필요 |
| **지정가 주문** | 가격 고정. **즉시 체결 안 될 수 있고 부분 체결**도 발생 |
| **시장가 주문** | 가격 지정 없음. **시장가로 즉시 체결** |

**시장 데이터 수준**

| 수준 | 보여주는 것 |
|---|---|
| **L1** | 최고 매수 호가, 최저 매도 호가 및 수량 |
| **L2** | L1보다 **더 깊은 호가**(체결 대기 물량을 어느 가격까지 보여줄지) |
| **L3** | L2 + 각 가격에 **체결을 기다리는 개별 주문 물량** |

- **봉 차트**: 특정 기간의 주가(시가·고가·저가·종가). 1분, 5분, 1시간, 1일, 1주일, 1개월 단위.
- **FIX**(Financial Information Exchange Protocol): 증권 거래 정보를 교환하는 **기업 중립적 통신 프로토콜**. 외부(브로커)에서 거래소로 들어올 때 쓴다.

## 3. 개략 설계 — 거래·시장 데이터·보고 흐름

[🖼️ 원본 이미지: 증권 거래소 개략적 설계안]

### 3-1. 거래 흐름 (1~14)

| 단계 | 내용 |
|---|---|
| (1) | 고객이 브로커의 웹/모바일 앱으로 주문 |
| (2) | 브로커가 주문을 거래소로 전송 |
| (3) | 주문이 **클라이언트 게이트웨이**를 통과. 속도 제한, 인증, 정규화 같은 **기본 문지기** 역할 |
| (4)~(5) | **주문 관리자**가 **위험 관리자**의 규칙에 따라 위험성 점검 |
| (6) | 점검을 통과한 주문에 대해 **지갑**에 자금이 충분한지 확인 |
| (7)~(9) | 주문이 **시퀀서**를 거쳐 **체결 엔진**으로. 체결 가능한 주문이 있으면 **매도·매수 측에 하나씩 두 개의 집행 기록** 생성. 나중에 재생해도 같은 결과가 나오도록 **시퀀서가 주문·집행 기록을 일정 순서로 정렬** |
| (10)~(14) | 집행 사실을 거꾸로 거슬러 클라이언트에 전송 |

### 3-2. 시장 데이터 흐름 (M1~M3)

| 단계 | 내용 |
|---|---|
| M1 | 체결 엔진이 주문 체결 시 **집행 기록 스트림** 생성 |
| M2 | **시장 데이터 게시 서비스**가 집행 기록·주문 스트림으로 **봉 차트와 호가 창** 구성 |
| M3 | 시장 데이터는 **실시간 분석 전용 스토리지**에 저장. 브로커(앱 화면)로도 전달 |

> 거래가 나면 체결 엔진이 매도/매수 집행 기록을 **줄줄이 스트림으로** 흘려보내고, 게시 서비스가 그걸 보고 **전광판(봉 차트·호가 창)** 을 그린다. 알고리즘 봇은 그 데이터로 분석한다.

### 3-3. 보고 흐름 (R1~R2)

- **보고 서비스**가 주문·집행 기록에서 보고에 필요한 모든 필드를 모아 종합한 레코드를 **DB에 기록**한다. 거래 이력, 세금 보고, 규정 준수 보고, 결산용.

> M은 **스트림을 보고 화면을 그리는** 쪽, R은 **스트림을 모아 DB에 넣는** 쪽.

## 4. 핵심 컴포넌트 ⭐

### 4-1. 체결 엔진 (매칭 엔진)

- 각 주식 **심볼**마다 주문서(호가 창)를 유지·관리한다.
  - 한국 주식은 숫자 코드: 삼성전자 `005930`, 카카오 `035720`
  - 미국 주식은 알파벳: 애플 `AAPL`, 테슬라 `TSLA`, 구글 `GOOGL`
- **매수 주문과 매도 주문을 연결**한다.
- 집행 기록 스트림을 **시장 데이터로 배포**한다.

### 4-2. 시퀀서

- 체결 엔진을 **결정론적**으로 만드는 핵심. **입력 시퀀서**와 **출력 시퀀서** 두 개가 각자 고유한 순서를 유지한다.
- 순서는 **순서 ID(일련번호)** 를 찍어 보장한다.
- 입력·출력 **메시지 큐 역할**도 한다: 체결 엔진에 수신 주문을 전달, 주문 관리자에게 집행 기록을 회신.
- 흐름: 접수 주문 → **입력 시퀀서** → 체결 엔진 → **출력 시퀀서**

| 왜 순서 ID를 찍나 | 설명 |
|---|---|
| 공정성 | 수많은 투자자가 **동시에** 매수 버튼을 누르면 순서 보장이 어렵다. ID를 부여해 **도착 순서대로** 줄 세운다(돈이 많든 적든 같은 규칙) |
| 시의성 | 먼저 온 주문이 먼저 처리 |
| 복구·재생 | 출력 시퀀서가 결과에 ID를 찍어 두면 **빠른 복구 + 재생**, **정확히 한 번 실행** 보장 |

> 면접 Q. 순서를 구분 가능하게 하려고 어떤 것을 고민해 봤나요?
> → 분산 환경에서 **스노우플레이크** 같은 시간 기반 유일 ID 생성기 (설계1 7장).

### 4-3. 주문 관리자

- 한쪽에서는 **주문**을 받고 다른 쪽에서는 **집행 기록**을 받는다.
- 클라이언트 게이트웨이로 받은 주문에 대해
  1. **위험 점검** 컴포넌트에 보내 위험성 검토
  2. 사용자 **지갑**에 거래 자금이 충분한지 확인
  3. 주문을 **시퀀서**에 전달 (필요한 속성만)
- 시퀀서가 돌려주는 체결 엔진의 집행 기록을 **게이트웨이를 통해 브로커에 반환**한다.

> 면접 Q. 주문 관리자에서 가장 신경 써야 하는 부분은?
> → **빠르고, 효율적이고, 정확**해야 한다. 다양한 상태 변화를 관리해야 해서 복잡하지만, **이벤트 소싱**이 좋은 방법이다.

> 면접 Q. 이벤트 소싱(CQRS)은 결국 비동기 처리인데, 쓰기 속도 대비 **조회 시차(불일치)** 는 어떻게 해결하나?

| 방법 | 내용 | 주의 |
|---|---|---|
| **FE 낙관적 업데이트** | 화면만 먼저 결과를 보여줌 | 서버에서 실패하면 되돌려야 함 |
| **Cache-Aside** | 이벤트 발행 때 **캐시에도 쓰고**, 읽기는 Redis에서 | 캐시 무효화 관리 |
| **클라이언트 폴링 + 버전 번호** | 이벤트 일련번호를 화면에 주고, 앱이 **처리 끝났는지 폴링**(로딩 뱅글뱅글) → 끝나면 완료 표시 | 폴링 부하 |

### 4-4. 클라이언트 게이트웨이

- 클라이언트 주문을 받아 **주문 관리자**로 보낸다. **인증, 정규화, 유효성 검사, 처리율 제한** 담당.
- **지연 시간에 민감하고 가벼워야** 한다. 가능한 한 빨리 목적지로 던져야 하므로 **필요한 기능만** 넣는다.
- 고객 유형별(개인/기관)로 **다른 게이트웨이**를 둔다.

> 면접 Q. 개인용·기관용 게이트웨이로 무엇을 쓸 건가요? 이유는?
> → 지연 시간, 거래량, 보안 요구가 다르다.

| 대상 | 선택 | 이유 |
|---|---|---|
| **개인 고객** | AWS API Gateway | 인증(OAuth 등)과 트래픽 조절에 강함 |
| | ALB | HTTP(7계층) 트래픽을 안전하게 분산 |
| **기관 고객** | NLB | HTTP가 아닌 **TCP(4계층)** 수준에서 가로채 초고속 분산 |
| | 커스텀 EC2 + ENA | AWS의 가장 빠른 네트워크 인터페이스. **커널(OS)을 거치지 않고** 랜카드에서 앱으로 직행 |

**코로케이션 엔진**
- 기관 투자자의 서버를 거래소 **체결 엔진이 있는 데이터 센터 건물 안으로 이사**시키는 물리적 서비스.
- 인터넷 망을 타지 않고 초저지연 게이트웨이(DPDK 등)로 체결 엔진과 **직결**. 물리적 거리 단축 + 소프트웨어 최적화가 합쳐져야 **고빈도 매매(HFT)** 가 가능하다.
- 모든 코로케이션 서버의 **광케이블 길이를 mm 단위까지 똑같이** 맞춰 둘둘 말아 두어 **물리적 공정성**을 보장한다.

### 4-5. 시장 데이터 게시 서비스 · 보고 서비스

| 서비스 | 역할 | 핵심 |
|---|---|---|
| 시장 데이터 게시 | 체결 엔진에서 집행 기록을 받아 **호가 창과 봉 차트** 생성 | 실시간 |
| 보고 | 거래 이력, 세금 보고, 규정 준수 보고, 결산 | **정확성과 규정 준수** |

## 5. API & 데이터 모델

### 5-1. API

| API | 용도 |
|---|---|
| `POST /v1/order` | 주문 처리. 인증 필요 |
| `GET /v1/execution?symbol=&orderId=&startTime=&endTime=` | 집행(체결) 정보 질의 |
| `GET /v1/marketdata/orderBook/L2?symbol=&depth=` | 심볼·깊이에 대한 **L2 호가 창** |
| `GET /v1/marketdata/candles?symbol=&resolution=&startTime=&endTime=` | 시간 범위·해상도·심볼에 대한 **봉 차트** |

### 5-2. 상품 · 주문 · 집행

| 모델 | 내용 | 저장 |
|---|---|---|
| **상품** | 거래 대상 주식의 속성: 유형, 거래 심벌, UI 표시 심벌, 결산 통화, 매매 수량 단위, 호가 가격 단위 | 주로 UI용. **아무 DB + 캐시** 적합 |
| **주문** | 매수/매도를 실행하라는 **명령** | **중요 거래 경로에서는 DB에 안 넣음**. 메모리에서 체결 |
| **집행 기록** | 체결이 이루어진 **결과**. 가장 중요한 데이터 | 보고 서비스가 조정·세금 보고용으로 DB 저장. 호가 창·봉 차트 **재구성**에도 사용 |

### 5-3. 호가 창

자료구조가 만족해야 할 것: **일정한 조회 시간** · 빠른 **추가/취소/실행** · 빠른 업데이트 · 최고 매수 호가/최저 매도 호가 질의 · 가격 수준 순회

### 5-4. 봉 차트

- 시장 데이터 프로세서가 호가 창과 더불어 쓰는 핵심 자료구조.
- 종목별·시간 간격별 가격 이력을 추적하면 **메모리가 많이 필요** → 최적화 필요.

| 최적화 | 내용 |
|---|---|
| **링 버퍼** | 미리 메모리를 할당해 둔 링 버퍼에 봉을 보관 → **새 객체 할당 횟수 감소** |
| 메모리 상한 | 메모리에 두는 봉 개수를 제한하고 나머지는 **디스크** |
| DB | 실시간 분석용 **컬럼형 DB**, 장 마감 후 **이력 전용 DB** |

## 6. 상세 설계 — 성능(중요 경로 단일 서버화)

지연 시간을 줄이는 길은 두 가지.

| 방법 | 내용 |
|---|---|
| **중요 경로에서 실행할 작업 수 줄이기** | 중요 매매 경로 = **게이트웨이 → 주문 관리자 → 시퀀서 → 체결 엔진**. 여기엔 꼭 필요한 것만 (**로깅도 뺀다**) |
| **각 작업의 소요 시간 줄이기** | 네트워크·디스크 사용량을 줄인다 |

**왜 수십 ms가 나오나**
- 핵심 경로 컴포넌트가 각각 **다른 서버**에서 돌면 왕복 네트워크 지연이 **약 500µs**. 컴포넌트가 많아지면 **한 자릿수 ms**까지 늘어난다.
- 시퀀서는 이벤트를 **디스크에 저장**하는 이벤트 저장소(카프카처럼). 순차 쓰기라도 **수십 ms**.
- 다 합치면 **수십 ms**. 목표(밀리초)에 못 미친다.

**해결: 전부 한 서버에**

[🖼️ 원본 이미지: 모든 구성 요소를 단일 서버에 배치한 낮은 지연 시간 설계안]

- 모든 컴포넌트를 **같은 서버**에 두어 네트워크 구간을 없앤다.
- 같은 서버 안 컴포넌트 간 통신은 이벤트 저장소인 **mmap**으로.

| 기법 | 내용 | 효과 |
|---|---|---|
| **애플리케이션 루프** | `while` 로 작업을 **계속 폴링**. 각 컴포넌트는 서버의 **프로세스** 하나 | 실행 시간이 **예측 가능** |
| **단일 스레드 + CPU 코어 고정** | 컴포넌트를 단일 스레드로 구현하고 **특정 CPU 코어에 고정** | **컨텍스트 스위치 없음**, **잠금(락) 경합 없음** → P99 감소. 단점: 코딩이 복잡 |
| **mmap** | 파일을 메모리에 매핑하는 유닉스 시스템 콜. 프로세스 간 **고성능 메모리 공유** | 공유 메모리에 접근해도 **디스크 I/O 없음**. 이걸로 컴포넌트 간 **메시지 버스**를 만들면 네트워크·디스크를 안 거친다 |

> 비유: 부서가 건물마다 흩어져 있으면 서류 하나 넘길 때마다 택배(네트워크)를 보내야 한다. 한 사무실 **같은 책상**에 앉히고 서류를 **책상 위 공용 트레이(mmap)** 에 올려 두면 걸어갈 필요도 없다.

- 여기에 **이벤트 소싱**을 결합하면 아주 빠른 MSA가 된다.

## 7. 이벤트 소싱 ⭐

| 기존 | 이벤트 소싱 |
|---|---|
| **현재 상태**를 DB에 유지 | 상태를 바꾸는 **모든 이벤트의 변경 불가능한 로그**를 유지 |
| 문제가 생기면 **원인 추적이 어렵다**(현재 상태만 있고 "왜"가 없다) | **모든 이벤트를 순서대로 재생**하면 주문 상태를 복구할 수 있다 |

> 비유: 통장 잔액(상태)만 적어 두면 왜 그 돈이 됐는지 모른다. **입출금 내역(이벤트)** 을 전부 남기면 처음부터 더하기만 해도 잔액이 나오고, 어디서 잘못됐는지도 보인다.

[🖼️ 원본 이미지: 이벤트 소싱 기반 거래 흐름]

**흐름**
1. 외부 도메인 → 거래 도메인으로 들어올 때 **FIX** 사용.
2. 게이트웨이가 FIX → **SBE**(Simple Binary Encoding)로 변환. 빠르고 간결한 인코딩이 목적.
3. 각 주문을 이벤트 저장소 클라이언트로 **NewOrderEvent** 형태로 전송.
4. 체결 엔진에 **내장된 주문 관리자**가 NewOrderEvent를 받으면 **유효성 검사 → 내부 주문 상태에 추가** → 담당 CPU 코어로 전송.
5. 주문이 체결되면 **OrderFilledEvent** 를 만들어 이벤트 저장소로.
6. 다른 서비스들은 이벤트 저장소를 **구독**해서 이벤트가 올 때마다 처리.

**더 효율적으로**

| 변경 | 이유 |
|---|---|
| 주문 관리자를 **재사용 가능 라이브러리**로 각 컴포넌트에 내장 | 중앙화된 주문 관리자를 **중요 경로 밖 컴포넌트**(보고 서비스 등)가 질의하면 지연 시간이 늘어난다 |
| 시퀀서는 **이벤트 저장소에 쓰기 전 순서를 정하는 유일한 쓰기 주체**로만 | 시퀀서가 여럿이면 쓰기 권한을 두고 경쟁, 바쁜 시스템에선 **락 경합** |
| **백업 시퀀서** | 다운 대비 |

**링 버퍼**
- 시퀀서는 각 컴포넌트의 **링 버퍼**에서 이벤트를 가져와 순서 ID를 찍고 이벤트 저장소로 보낸다.
- 체결 엔진·주문 관리자가 데이터를 빠르게 읽을 때 쓰는 자료구조. **메모리 위에 원형 배열을 미리 만들어** 둔다.

| 동작 | 내용 |
|---|---|
| 시퀀서(쓰기) | 새 주문을 넣고 다음 빈칸으로 이동 |
| 컴포넌트(읽기) | 배열을 보다가 주문을 발견하면 복사 |
| 재사용 | 읽힌 칸을 시퀀서가 다시 만나면 **새 데이터를 덮어쓴다** → 메모리를 새로 받고 버리는 일이 없어 **GC가 없다** |

> 비유: **회전 초밥**. 접시(칸)는 정해진 수만큼만 돌고, 손님이 먹은 빈 접시는 요리사가 새 초밥을 올려 다시 돌린다. 접시를 매번 새로 사고 버리지 않는다.

## 8. 고가용성 & 결함 내성

### 8-1. 고가용성

- 다운되면 **즉각 복구**해야 한다. **SPOF**(단일 장애점)를 찾아 주 인스턴스를 **다중화**한다. 장애 감지와 백업 전환 결정이 **빨라야** 한다.
- 무상태 서비스는 **수평 확장**. 하지만 **상태가 있는** 주문 관리자·체결 엔진은 **사본 간 상태 복사**가 필요하다.

| 구성 | 역할 | 다운되면 |
|---|---|---|
| **메인** | 이벤트를 받고 → 체결 → 이벤트 저장소에 기록까지 | **서브가 대체** |
| **서브** | 이벤트를 **받기만** 하며 상태를 따라감 | 재시작 → 이벤트 재생으로 **모든 상태 복구** |

- 메인 장애 감지: **모니터링 + 헬스 체크**.
- 위 방식은 **단일 서버 안**에서만 가능. 서버 자체가 죽으면 **메인/서브 서버 클러스터**가 필요하고, 이벤트 저장소 데이터를 부 서버로 복제해야 한다 (**UDP** 사용).

### 8-2. 결함 내성

- 핵심 데이터를 **여러 데이터 센터**에 복제한다.

**주 서버 다운 시 언제, 어떻게 부 서버로 전환하나?**

| 어려움 | 내용 |
|---|---|
| 오보 | 경보가 **오보**인데 부 시스템으로 넘어갈 수 있다 |
| 코드 버그 | 버그가 원인이면 부 서버로 넘어가도 **같은 문제**. 시스템을 더 이상 쓸 수 없게 된다 |

- 그래서 처음 출시 땐 **수동으로** 장애 복구, 운영 경험이 쌓이면 자동 프로세스 도입.
- **카오스 엔지니어링**: 일부러 장애를 일으켜 까다로운 사례를 수면 위로 끌어내고 **운영 경험을 빠르게 축적**.

**새 리더는 어떻게 뽑나? → Raft**

| 규칙 | 내용 |
|---|---|
| 최소 투표 수 | **전체/2 + 1** 이상 받아야 리더 |
| 평소 | 리더가 팔로워들에게 **하트비트** 전송. 팔로워는 각자 **타임아웃**(인내심)을 가짐 |
| 리더 사망 | 타임아웃이 **가장 먼저 끝난** 팔로워가 "나 리더 할래" 선언 + 투표 요청 |
| 선출 | 나머지가 투표 → 규칙대로 받으면 리더가 되어 하트비트 전송 시작 |

**복구 목표**

| 용어 | 뜻 | 거래소 |
|---|---|---|
| **RTO** (목표 복구 시간) | 다운돼도 사업에 심각한 피해가 없는 **시간의 최댓값** | 우선순위에 따른 **성능 저하 전략** 필요 |
| **RPO** (목표 복구 시점) | 심각한 피해 전에 **잃어도 되는 데이터 양**(손실 범위) | **0을 지향**. Raft 복제로 해결 |

## 9. 체결 알고리즘 & 결정론

### 9-1. 체결 알고리즘

- **FIFO**: 특정 가격 수준에서 **먼저 들어온 주문이 먼저 체결**, 마지막 주문이 가장 나중.
- **LMM**(주도 시장 조성자): "당장 팔고 싶은데 살 사람이 없네?"가 안 생기도록 매수·매도 주문을 **호가 창에 깔아 두는 의무**를 진 기관. CME 사이트에 각종 체결 알고리즘이 있고, **다크 풀**도 대표 사례.

### 9-2. 결정론

| 종류 | 내용 | 측정 |
|---|---|---|
| **기능적 결정론** | 시퀀서·이벤트 소싱으로 **이벤트를 같은 순서로 재생하면 항상 같은 결과**. 이벤트 **순서**가 중요 | |
| **지연 시간 결정론** | 각 거래의 처리 시간이 **거의 같다**. 거의 모든 거래에 안정적 성능 | **P99, P99.99** 측정. **HdrHistogram** 활용 |

- 원인 조사: 자바라면 **안전 지점(safepoint)** 과 **Stop-The-World**(GC로 모든 스레드 정지)가 원인인 경우가 많다.

## 10. 시장 데이터 배포 · 코로케이션 · 보안

### 10-1. 시장 데이터 게시 서비스 최적화

- 체결 엔진의 체결 결과로 **호가 창과 봉 차트를 재구축**한 뒤 구독자에게 게시한다.
- **공정한 배포**: 모든 수신자가 **동시에** 받아야 한다. **안정적 UDP 멀티캐스트**가 한 번에 많은 참가자에게 뿌리기 좋다.

| 전송 방식 | 뜻 |
|---|---|
| **유니캐스트** | 하나 → 하나 |
| **브로드캐스트** | 하나 → 전체 하위 네트워크 |
| **멀티캐스트** | 하나 → 여러 하위 네트워크의 **선택된** 호스트들 |

### 10-2. 코로케이션

- 헤지 펀드·브로커 서버를 **거래소와 같은 데이터 센터**에 두게 한다 (§4-4 참고).

### 10-3. 네트워크 보안

- 공개 서비스·데이터를 **비공개 서비스와 분리**해 DDoS가 가장 중요한 클라이언트에 영향을 못 주게 한다.
- 자주 안 바뀌는 데이터는 **캐싱**.
- DDoS에 대비해 **URL 강화**.
- 효과적인 **허용/차단 리스트**.
- **처리율 제한**.

## 11. 마무리

- 대형 거래소의 이상적 배포 모델은 **모든 것을 하나의 거대한 서버 또는 단일 프로세스에** 두는 것이다.
- 암호화폐 거래소는 **클라우드 인프라**로 배포하는 곳이 많다.
- 일부 탈중앙화 금융(DeFi)은 **AMM**(자동 시장 조성자) 기반이라 **호가 창 자체가 없다**.

    - 인증, 정규화, 유효성 검사, 처리율 제한 등의 역할을 맡는다
  - 지연 시간에 민감하고, 가벼워야 한다.
    - 가능한 빨리 목적지로 주문을 던져줘야 하기 때문이다
    - 게이트웨이의 역할들도 신속하게 처리가 필요 (필요한 기능만 넣기)
  - 고객유형별(개인고객/기관고객)로 다양한 게이트웨이 존재

  Q. 고객별 기관용으로 사용할 클라이언트 게이트웨이 어떤 것을 사용하실 건가요? 선택한 이유는요?

    - 지연시간, 거래량, 보안 요구사항등이 고려사항이다
      - 고객 거
        - AWS API Gateway : 인증(OAuth 등)과 트래픽 조절에 탁월
        - ALB : HTTP 트래픽을 안전하게 분산
      - 기관용
        - NLB : HTTP(7계층)가 아닌 TCP(4계층) 수준에서 트래픽을 가로채어 초고속으로 분산
        - 커스텀 EC2 + ENA : AWS가 제공하는 가장 빠른 네트워크 인터페이스를 달아 커널(OS)을 거치지 않고 랜카드에서 앱으로 데이터를 직행
  - 코로케이션 엔진
    - 기관 투자자들의 서버를 거래소(한국거래소, 나스닥 등)의 메인 매칭 엔진(체결 서버)이 있는 데이터 센터 건물 안으로 이사시켜 버리는 물리적인 서비스
    - 거래엔진 S/W - 사용하면 빠른 성능 보장 가능<br>이 코로케이션 구역 안에 있는 기관 서버는 인터넷 망을 타지 않고, 앞서 말한 초저지연 게이트웨이(DPDK 등)를 통해 체결 엔진과 직결됩니다. 이 물리적 거리 단축과 소프트웨어 최적화가 결합되어야만 진정한 고빈도 매매(HFT)가 가능해집니다.
      - 모든 코로케이션 서버의 광케이블 선 길이를 mm 단위까지 똑같이 맞춰서 둘둘 말아놓아서 진정한 물리적 공정성을 보장
- 시장 데이터 흐름
  - 시장 데이터 게시 서비스는 체결 엔진에서 집행 기록을 수신하고 집행 기록 스트림에서 호가 창과 봉 차트를 만들어낸다.
- 보고 흐름
  - 거래 이력, 세금 보고, 규정 준수 여부 보고, 결산 등의 기능을 제공한다.
  - 정확성과 규정 준수가 핵심이다.

### **데이터 모델**

### 상품, 주문, 집행
- 상품은 거래 대상 주식이 가진 속성으로 정의된다.<br>상품 유형, 거래에 쓰이는 심벌, UI에 표시될 심벌, 결산에 이용되는 통화단위, 매매 수량 단위, 호가 가격 단위 등등
- 주로 UI를 위한 데이터 모델 - 아무 DB에 저장 가능 + 캐시 적용하기 좋다
- 주문은 매수/매도를 실행하라는 명령이다.
- 집행 기록은 체결이 이루어진 결과다.
- 주문 집행 기록은 가장 주요한 데이터
  - 중요 거래경로는 주문+집행 기록을 DB에 안 넣는다
  - 메모리에서 거래를 채결 등
  - 보고 서비스는 조정이나 세금 보고 등을 위해 DB에 주문 및 집행기록 저장
  - 집행 기록은 호가 창/ 주문서와 봉차트 데이터 재구성에 쓰인다

  - 메모리에 두는 봉의 개수를 제한하고 나머지는 디스크에 보관한다.
- DB

  - 시장 마감 이후에는 데이터를 이력 유지 전용 DB에 저장

## **상세 설계**

### **성능**
- 지연 시간을 줄이는 방법은 2가지 있다.
  - 중요 경로에서 실행할 작업 수를 줄인다.
  - 각 작업의 소요 시간을 줄인다.
    - 네트워크 및 디스크 사용량 줄이기
      - 중요 매매 경로
        - 게이트웨이-주문관리자-시퀀서-체결엔진
        - 여기에 꼭 필요한 것만 넣기(로깅도 빼기)
    - 각 작업의 실행시간 경감
      - 핵심경로의 구성요소가 네트워크를 통해 개별 서버에서 실행한다 가정했을 때 왕복 네트워크 지연시간이 500mcs인데 컴포넌트가 많아지면 한자리수 ms(밀리초)단위 까지 늘어날 수 있다
      - 시퀀서
        - 이벤트를 디스크에 저장하는 이벤트 저장소다(like 카프카)
        - 순차 쓰기한다해도 수십 ms단위
      - 모두 고려하면 수십 ms 나올 거다
  - 네트워크 및 디스크 엑세스 지연 시간을 줄이거나 없애는 방향으로 실제로 많이 줄임
  - 모든 것을 동일한 서버에 배치해서 네트워크를 통하는 구간을 없애버림 <br>같은 서버 내 컴포넌트 간 통신은 이벤트 저장소인 mmap사용
  - 모든 구성 요소를 단일서버에 배치 + 낮은 지연시간 달성 설계안(471p)
    - 애플리케이션 루프
      - while로 작업을 계속 폴링
        - 각 구성요소의 실행시간을 줄여 전체적인 실행 시간이 예측 가능하도록 보장
        - 컴포넌트는 서버의 프로세스
          - CPU 성능을 위해서 단일 스레드로 구현 특정 CPU 코어에 고정(472p)
            - 컨텍스트 스위치 없음
            - 잠금 결합도 없음
            - 위 두가지가 P99를 줄인다
          - 단점
            - CPU를 고정하면 코딩이 복잡
    - mmap
      - 파일을 메모리에 맵핑하는 유닉스 시스템 콜
      - 프로세스 간 고성능 메모리 공유 메커니즘을 제공
        - 공유 메모리에 접근해도 디스크 I/O가 없다
      - 그래서 서버에서 이걸 이용해서 경로의 구성요소가 서로 통신할 때 이용할 메시지 버스를 구현한다
        - 그러면 네트워크, 디스크에 접근 안함
      - 여기에 이벤트 소싱 설계 페러다임을 결합하면 레전드 MSA 제작 가능

### **이벤트 소싱**
- **기존 : 상태를 DB에 유지 + 문제 발생 시 원인 추적이 어렵 + 현재 상태에 대한 원인이 없음**
- **현재 상태를 저장하는 대신 상태를 변경하는 모든 이벤트의 변경 불가능한 로그를 유지한다.**
- **모든 이벤트를 순서대로 재생하면 주문 상태를 복구할 수 있다.**
- 외부 도메인 → 거래 도메인 들어올 때 FIX 사용
  - 게이트웨이는 FIX → SBE로 변환 (빠르고 간결한 인코딩 목적)
  - 각 주문을 이벤트 저장소 클라를 사용해서 NewOrderEvent형태로 전송
  - 체결엔진에 내장된 주문 관리자가 NewOrderEvent를 수신하면 유효성 검사를 한 다음에 내부 주문 상태에 추가 이후 해당 주문은 담당 CPU 코어로 전송
  - 주문이 체결이 되면 OrderFilledEvent 생성되어 이벤트 저장소로 전송
  - 다른 서비스 들은 이벤트 저장소를 구독해서 이벤트 받을 때마다 적절히 처리
- 더 효율적으로 한다면?
  - 주문관리자 : 재사용 가능 라이브러리(컴포넌트에 내장되는)
    - 주문 상태는 중요하니까 위 처럼 설계 해도 된다
    - 근데 주요 거래 경로에 없는 컴포넌트들이 질의를 중앙화된 주문관리자를 이용하면 지연시간이 늘어난다 (보고서비스 같이)
  - 시퀀서도 없다
    - 시퀀서가 여러개면 이벤트 저장소에 쓰는권한을 두고 경쟁하기에 안좋고
    - 거래소 같이 바쁜 시스템이라면 락 경합 가능성도 있다
    - 그저 이벤트 저장소에 넣기 전 이벤트의 순서를 정해주는 유일한 쓰기 연산 주체로 사용하기
    - 시퀀서는 각 컴포넌트에서 링 버퍼에서 이벤트를 가져온다
      - 이벤트에 순서 ID를 찍고 다음 이벤트 저장소로 보냄
      - 백업 시퀀서 두기 다운의 경우 대비
    - 링버퍼
      - 체결 엔진이나 주문 관리자가 그 데이터를 빠르게 읽을 때 사용하는 자료구조
      - 메모리 위에 원형 배열을 미리 만드는 방식
      - 동작원리
        - 시퀀서 : 새주문을 넣고 다은 빈칸으로 이동
        - 컴포넌트 : 배열을 보다가 주문을 발견하면 그 걸 복사한다
        - 재사용 : 데이터 읽힌 접시가 시퀀서를 만나면 요리사는 새로운 데이터를 덮어 씌운다 → GC가 없다 <br>보통 프로그램은 쓰고 지울 때마다 매모리를 새로 받고 GC를 하는데…
        - 즉, 회전 초밥

### **고가용성**
- 서비스가 다운되면 즉각 복구해야 한다.
- SPOF를 식별해야 한다. 주 인스턴스를 다중화해야 한다.
- 장애 감지 및 백업 인스턴스로서의 장애 조치 결정이 빨라야 한다.
- 무상태 서비스면 수평적확장 가능 but, 상태를 저장하는 경우(주문 관리자, 체결엔진) 사본 간 상태 데이터를 복사할 수 있어야 한다
- 복사 사례
  - 메인과 서브로 나눔
    - 메인은 이벤트 받고 이벤트 저장소에 체결 까지
      - 다운되면 서브가 대체
    - 서브는 이벤트 받는 거만
      - 다운되면 재시작 → 모든 상태 복구
  - 메인 장애감지 방식
    - 모니터링, 헬스체크
  - 위 방식은 단인 서버에서만 가능
    - 메인/서브 서버 클러스터 구성이 필요
    - 이벤트 저장소 데이터를 부 서버로 복제해야하는데
      - UDP 사용

### **결함 내성**
- 일단 핵심 데이터를 여러 데이터 센터에 복제해서 문제 해결
- 주 서버가 다운되면 언제, 어떻게 부 서버로 자동 전환하는 결정을 내리나?
  - 다운이란
    - 경보 오보가 뜨면 부 시스템으로 전환 가능성존재
    - 코드 버그라면 부서버로 전환되어도 같은 문제 직면 가능 <br>이러면 시스템을 더 이상 사용할 수 없어
  - 그래서?
    - 처음 출시 때는 수동으로 장애복구 시도
    - 짬이 차면 그때 프로세스 도입
    - 카오스 엔지니어링 : 까다로운 사례를 수면으로 이끌어내고 운영경험을 빠르게 축적
- 부 서버 가운데 새로운 리더는 어떻게 선출하는가?
  - 레프트 사용 : 리더 선출 알고리즘
    - 규칙 : 최소 투표수 : 전체/2 +1 이상의 투표를 받아야 리더 선정
    - 평소 : 리더가 하트비트를 팔로워들에게 전달<br>팔로워들은 각자만의 인내심(타임아웃)을 갖고 있다
    - 리더가 죽으면 팔로워들의 인내심 중 가장 인내심이 없는 팔로워가 나 리더할래 선언 및 다른 팔로워들에게 투표해줘라고 함
    - 나머지 팔로워가 투푤 함
    - 규칙대로 투표를 받으면 그 때부터 걔가 리더가 되어 다른 팔로워들에게 하트비터 준다
- 복구 시간 목표는 얼마인가?(RTO : 목표 복구 시간)
  - 다운되어도 사업에 심각한 피해가 없는 시간의 최댓값
  - 우선순위에 따른 성능 저하 전략이 필요
- 어떤 기능을 복구해야 하는가? 시스템이 성능 저하 상태로도 동작할 수 있는가?
  - RPO : 목표 복구 시점 즉, 심각한 피해가 발생하기 전 손실 될 수 있는 데이터의 양(즉 손실 범위)
  - 증권거래소는 0을 지향
  - 앞서 설명한 레프트방싱르 사용하면 해결가능

### **체결 알고리즘**

### **시장 데이터 게시 서비스 최적화**
- 시장 데이터 게시 서비스는 체결 엔진의 체결 결과를 받아 이를 기반으로 호가 창과 봉 차트를 재구축한 다음 구독자에게 데이터를 게시한다.

### **시장 데이터의 공정한 배포**
- 모든 수신자가 동시에 시장 데이터를 받을 수 있도록 보장하는 것이 중요하다.
- 안정적 UDP를 사용하는 멀티캐스트는 한 번에 많은 참가자에게 업데이트를 브로드캐스트하기 좋다.

### **멀티캐스트**
- 유니캐스트: 하나의 출처에서 하나의 목적지로만 보내는 전송 프로토콜
- 브로드캐스트: 하나의 출처에서 전체 하위 네트워크로 보내는 방식
- 멀티캐스트: 하나의 출처에서 다양한 하위 네트워크상의 호스트들로 보내는 방식<br>즉 하나에서 선택적으로 보내는 방식

### **코로케이션**
- 헤지 펀드 또는 브로커의 서버를 거래소와 같은 데이터 센터에 둘 수 있도록 한다.

### **네트워크 보안**
- 공개 서비스와 데이터를 비공개 서비스에서 분리하여 DDoS 공격이 가장 중요한 클라이언트에게 영향을 미치지 않도록 한다.
- 자주 업데이트되지 않는 데이터는 캐싱한다.
- 디도스 공격에 대비해 URL을 강화한다.
- 효과적인 허용/차단 리스트 매커니즘을 사용한다.
- 처리율 제한 기능을 활용한다.

## **마무리**
- 대형 거래소를 위한 이상적인 배포 모델은 모든 것을 하나의 거대한 서버 또는 단일 프로세스에 배치하는 것이라는 결론에 도달한다.
- 최근 암호화폐 산업이 발전함에 따라 많은 암호화폐 거래소가 클라우드 인프라를 사용하여 서비스를 배포한다.
- 일부 탈중앙화 금융 프로젝트는 AMM 개념을 기반으로 하며, 심지어 호가 창도 없다.
