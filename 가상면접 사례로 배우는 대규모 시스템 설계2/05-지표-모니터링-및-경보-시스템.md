## 1. 무엇을 만드나 & 규모

- 인프라 상태를 확인해 **가용성·안정성**을 지키는 것이 주목적. (로그 모니터링·분산 추적은 이번 범위 밖)
- 규모 추정: DAU 1억 · 서버 풀 1,000개 × 풀당 100대 × 대당 100지표 = **약 천만 개 지표**.
- 보관 정책(다운샘플링 계단): **원본 1주 → 1분 단위 30일 → 1시간 단위 1년**.
- 비기능: 규모 확장성 · 낮은 응답 지연 · 안정성(경보 놓치지 않기) · 유연한 파이프라인.

## 2. 먼저 알 용어

| 용어 | 뜻 |
|---|---|
| **다운샘플링** | 시간이 지난 데이터의 수집 간격(해상도)을 낮춰 저장량을 줄이는 최적화. 예) 10초 간격 → 1분 간격 |
| **롤업** | 다운샘플링을 위해 자잘한 값들을 **하나의 대표값으로 요약하는 연산**. 예) 60초 CPU를 평균(AVG)으로 1분 값 1개로 |
| **웹훅** | 폴링(내가 계속 물어봄)의 반대 — 이벤트가 나면 **상대 서버가 내 URL로 먼저 연락**. 받을 URL을 미리 등록해 둠 |
| **서버 풀** | 서버들의 모음 |

<details>
<summary>로그의 종류 (참고)</summary>

- **액세스 로그** — 웹서버 출입구 기록(누가·언제·어떤 IP로 무슨 페이지를 요청). 예) Nginx·Apache
- **에러 로그** — 에러 메시지 + 스택 트레이스(요청→에러 지점을 역순으로 보여줌)
- **일반 로그** — 개발자가 코드에 심은 비즈니스 흐름 기록

</details>

> ⚠️ **롤업의 두 함정 (면접 포인트)** — ① **스파이크 증발**: CPU가 순간 peak를 쳐도 평균으로 롤업하면 평온해 보인다 → **평균과 최댓값을 별도로** 저장해야 함. ② **경보 지연**: 롤업된 과거 데이터 기준으로 경보하면 알림이 늦다 → **치명적 경보는 원본 데이터를 보도록** 아키텍처를 구성.

### 2-1. 이동 평균 — SMA vs EMA

| 구분 | 단순 이동 평균(SMA) | 지수 이동 평균(EMA) |
|---|---|---|
| 가중치 | 모든 구간에 **동일**(예: 5일 각 20%) | **최근일수록 큰** 가중치 |
| 반응 | 최고·최저가 희석돼 **느림** | 최근 변화에 **빠르게** 반응 |

## 3. 개략 설계 — 5개 컴포넌트

```
지표 출처 → [수집기] → [시계열 DB] → [질의 서비스] → 시각화 / 경보
```

| 컴포넌트 | 역할 |
|---|---|
| 지표 출처 | 앱 서버·DB·메시지 큐 등 지표가 생기는 곳 |
| 지표 수집기 | 지표를 모아 시계열 데이터로 기록 |
| 시계열 DB(TSDB) | 지표를 시계열 형태로 저장 |
| 질의 서비스 | TSDB 조회를 대신 받아주는 API 계층 |
| 경보 / 시각화 | 임계값 위반 알림 / 그래프·차트 제공 |

---

## 4. 데이터 모델 — 시계열

- 지표는 **시계열 데이터**(타임스탬프 + 값)로 기록. 각 시계열엔 **고유 이름 + 선택적 레이블(label)**.
  - 예) `metric=cpu.load`, `label={host:i631, env:prod}` → 특정 시각의 값
  - 레이블로 필터·집계 가능. 예) `region=us-west`인 모든 웹서버의 10분 평균 CPU
- **접근 패턴**: **쓰기 부하는 막대**, **읽기 부하는 스파이크**(대시보드 열 때 순간 치솟음) → 이 성격이 **TSDB 선택**을 정당화.
- 대표 TSDB: **Prometheus · InfluxDB** (메모리 캐시 + 디스크, 빠른 실시간 분석).

## 5. 지표 수집 — 풀 vs 푸시 ⭐

| 기준 | 풀(Pull) | 푸시(Push) |
|---|---|---|
| 방식 | 수집기가 주기적으로 **가져감** | 대상 서버의 에이전트가 **보냄** |
| 사례 | Prometheus | CloudWatch · Graphite |
| 디버깅·헬스체크 | **쉬움**(엔드포인트 직접 확인) | 상대적으로 어려움 |
| 짧은 수명 프로세스 | 다 못 끌어가고 죽을 수 있음(→ Push Gateway로 보완) | **유리** |
| 복잡한 방화벽 | 불리 | **유리** |
| 전송/성능 | 보통 TCP(오버헤드 낮음) | 보통 UDP(지연 낮음) |
| 신뢰성 | 가져올 지표가 이미 정의됨 | 아무나 보낼 수 있어 **인증 강제** |

### 5-1. 풀 모델과 서비스 탐색(SDS)
- 수집기에 모든 서버 IP를 파일로 박아두면 서버가 뜨고 죽을 때마다 수정해야 해 비효율.
- **SDS**(Service Discovery Service) = 컨테이너처럼 IP가 수시로 바뀌는 환경에서 "누가 살아있나"를 관리. 서버가 켜지면 자기 IP를 등록. 예) **etcd**(쿠버 핵심 저장소), **ZooKeeper**(카프카·하둡).
- 수집기는 SDS에 **변경 이벤트 콜백(구독)**을 걸어, 엔드포인트가 바뀔 때만 통보받는다(계속 폴링 안 함).

> 🔑 **중복 수집 방지 = 안정 해시** — 수집기 서버가 여럿이면 같은 지표를 중복으로 끌어올 수 있다. 해시 링 구간마다 담당 수집기를 지정하면 **한 서버의 지표는 항상 하나의 수집기가** 처리하도록 보장된다.

<details>
<summary>푸시 모델의 함정과 대비</summary>

- 대상 서버에 **수집 에이전트**(Telegraf·Datadog) 설치 → 주기 전송.
- 수집기가 밀리면 에이전트 **버퍼에 잠깐 보관 후 재전송**.
- 에이전트 클러스터가 오토스케일링으로 줄면 **버퍼째 소실** 위험 → 수집기도 오토스케일 + **앞에 로드밸런서**를 둬 분산.

</details>

## 6. 전송 파이프라인 규모 확장 — 카프카 완충

- 문제: TSDB에 장애가 나면 **데이터 소실**. → 수집기와 TSDB 사이에 **카프카**를 둔다.
- 카프카 이점: 고가용·확장성, 수집·처리 **결합도↓**, **DB 장애에도 데이터 보존**(카프카는 소비 후에도 디스크에 보관, 소비자는 오프셋만 저장).

### 6-1. 스트림 처리 엔진 (카프카 → TSDB 사이)

| 엔진 | 처리 방식 | 특징 |
|---|---|---|
| **Spark** | 마이크로 배치(짧은 구간씩 모아 한 번에) | 정확성↑, 지연 다소↑ |
| **Storm** | 1건씩 즉시 처리 | 초저지연 |
| **Flink** | 1건씩 즉시 + 앞뒤 상태 기억 | 정확성+저지연+복구력 |

<details>
<summary>카프카 규모 확장 & 대안</summary>

- **파티션 수 늘리기**(BPS에 맞춰, 되돌릴 수 없음)
- **지표 이름으로 파티션 배치** → 소비자가 이름별 집계 가능
- **태그/레이블로 더 잘게** → 한 지표가 파티션을 독점하는 핫스팟 완화
- **중요 지표는 별도 토픽**으로 우선순위 부여
- 대안: **Gorilla**(페이스북 메모리 기반 TSDB) — 일부 네트워크 장애에도 높은 쓰기 가용성

</details>

## 7. 데이터 집계 지점

| 지점 | 장점 | 단점 |
|---|---|---|
| 수집 에이전트(클라이언트) | 간단 | 복잡한 집계 로직 어려움 |
| 수집 파이프라인(스트림 처리) | DB 기록량↓ | 지연 도착 데이터·원본 미보관 → 정밀도 낮음 |
| 질의 시(원본 보관 후) | 데이터 손실 없음 | 질의 속도 느림 |

## 8. 질의 · 저장소 · 경보 · 시각화

### 8-1. 질의 서비스
- 시각화·경보가 **TSDB를 직접 뒤지지 않게** 대신 받는 API 서버 클러스터(결합도↓).
- **캐시 계층**으로 TSDB 질의 부하↓·성능↑. 단, 플러그인이 이미 있거나 캐시가 불필요한 규모면 **굳이 안 만드는 게 깔끔**.
- TSDB는 SQL이 까다로워 **독자 질의어**(예: InfluxDB의 **Flux**) 제공.

### 8-2. 저장소 계층
- **TSDB 선택이 성능을 좌우** — 질의의 85%는 최근 26시간 데이터 대상.
- 절감: **인코딩·압축**(첫 타임스탬프는 32비트, 이후는 **차이값**만), **다운샘플링**, **냉동 저장소**(비활성 데이터를 싼 곳에 — 직접 만들기보단 가져다 씀).

### 8-3. 경보 시스템
1. 설정을 캐시에 로드 → 경보 관리자가 읽음
2. 주기적으로 질의 서비스 호출 → **임계값 비교** → 위반 시 이벤트 생성(필터·병합·중복제거, 접근 제어, 재시도)
3. 경보 저장소(**Cassandra** 등 키-값, 최소 1회 전달 보장) → 카프카 → 소비자가 **이메일·SMS·페이저듀티·웹훅**으로 발송
- **밑바닥부터 구현은 비현실적** — 사서 쓰는 게 실무.

### 8-4. 시각화
- 데이터 계층 위에 얹는 대시보드(지표·경보). **Grafana** 같은 상용품 구입이 바람직.

## 정리

| 주제 | 핵심 |
|---|---|
| 데이터 성격 | 쓰기 폭주·읽기 스파이크 → 시계열 DB |
| 수집 | 풀(Prometheus) vs 푸시(CloudWatch), SDS·안정해시로 보완 |
| 안정성 | 카프카로 완충(DB 장애에도 보존) + 스트림 처리 |
| 저장 절감 | 다운샘플링·차이값 압축·냉동 저장소 |
| 롤업 함정 | 스파이크 증발(평균+최댓값 별도), 경보 지연(원본 참조) |
| 경보·시각화 | 만들기보다 구매(Grafana 등) |

<details>
<summary>📄 원본 노트 (정리 전 원문)</summary>

- 무슨 서비스인가?
  - 서비스 인프라의 상태를 확인하고 가용성과 안정성을 달성하는데 main역할을 하는 서비스
- 용어 정리
  - 로그 : 서비스에서 발생한 사건들을 시간순으로 적어둔 거
    - 종류
      - 엑세스 로그 : 웹서버의 출입구 기록 (누가, 언제, 어떤 IP로, 무슨 웹페이지를 요청했는가. e.g. Nginx, Apache)
      - 에러 로그 : 에러가 났을 때 에러 메시지와 스택 트레이스 기록 (스택 트레이스: 에러 발생 시 요청부터 에러난 부분을 역순으로 보여주는 기록)
      - 일반 로그 : 개발자가 코드에 넣은 비즈니스 흐름 기록
  - 서버 풀 : 서버들의 모음
  - 다운 샘플링 : 시간이 지남에 따라 데이터의 수집 간격(해상도)을 의도적으로 깎아내는 전체적인 최적화 과정. e.g. 10초마다 데이터 수집 → 1분마다 데이터 수집(지난 6번의 데이터를 평균으로 롤업)
  - 롤업 : 다운샘플링을 실행하기 위해, 여러 개의 자잘한 데이터를 하나의 대표값으로 요약하는 수학적 연산 방식. e.g. CPU 사용률 지표 : 60초 동안의 데이터를 '평균(AVG)' 연산으로 롤업하여 1분짜리 데이터로 변환
  - 웹훅 : 기존 폴링은 내 서버가 다른 서버에 계속 물어보는 방식인데 이건 서버에서 이벤트 발생하면 서버가 내 서버에 연락을 주는
    - 원리 : url 등록(데이터를 보내줄 서버에 웹훅 URL 주소를 미리 등록) → 이벤트 발생 → 데이터 전송
- 모니터링 관련 주의 사항
  - 스파이크(Spike) 증발 현상 : CPU가 pick을 찍었는데 이걸 평균으로 롤업하면 평온해 보일 수 있다. 그러면 안되니까 평균 이랑 최댓값 롤업을 별도로 저장해야한다
  - 경보 지연 : 롤업된 과거 데이터 기준으로 경보 설정 시 알림이 딜레이 발생함. 그래서 치명적인 경보는 원본 데이터를 바라보도록 아키텍처를 구성해야 한다
- 단순 이동 평균(SMA) : 5일 치 데이터를 각각 20%씩 비중을 두고 더해서 나누기 5. 최저와 최고가 희석되어 느리게 반응
- 지수 이동 평균(EMA) : 과거 데이터 보다 최근 데이터에 높은 가중치를 부여 → 최근 변화에 더 빠르게 반응

**문제 이해 및 설계 범위 확정 — 개략적 요구사항 및 가정**
- 회사 내부에서 사용할 시스템 → 그럼 SaaS 제품을 설계한다면?
- 측정 할 거 : 시스템 운영 지표, rps, 서버 프로세스 개수 등등. DAU : 1억
- 서버 풀 1,000개, 풀당 서버 수 100개. 서버당 100개의 운영 지표를 수집한다고 치면 모니터링해야 하는 지표의 수는 천만 개 수준
- 수집한 그대로 데이터를 보관하는 기간은 일주일. 그 뒤에는 1분 단위 데이터로 변환한 후에 30일간 보관. 그 뒤에는 1시간 단위 데이터로 변환한 뒤에 1년간 보관.
- 경보는 이메일, 전화, 페이저 듀티, 웹훅 등등. 에러로그, 액세스 로그, 분산 시스템 트레이싱은 필요 없다 → 만약 필요하다면?
- 모니터링할 지표 예 : CPU 사용률, 요청 수, 메모리 사용량, 메시지 큐 내의 메시지 수
- 비기능 요구사항 : 규모 확장성 / 낮은 응답 지연 / 안정성(중요 경보 놓치지 않기) / 유연성(미래 신기술을 쉽게 통합할 수 있는 파이프라인)
- 안고려 요구사항 : 로그 모니터링(ELK - ES, 로그스태시, 키바나) / 분산 시스템 추적(요청이 한 서비스에서 다른 서비스로 이동할 때마다 데이터 수집)

**개략적 설계안**
- 기본적 사항 : 데이터 수집 / 데이터 전송 / 데이터 저장소 / 경보 / 시각화
- 데이터 모델 : 지표 데이터는 통상 시계열 데이터 형태로 기록(타임스탬프). 시계열 각각에는 고유한 이름 + 선택적 레이블(label)
  - 사례1 : production 서버 인스턴스의 특정 시간대 CPU 부하 → 지표 이름 + 레이블(host:i631, env:prod) + 특정 시각의 데이터
  - 사례2 : 지난 10분간 us-west의 모든 웹 서버 CPU 부하 평균 → 지표 이름 CPU.load, 레이블 지역 us-west 데이터를 저장소에서 가져와 평균
  - 데이터 접근 패턴 : 쓰기 부하는 막대, 읽기 부하는 spiky(일시적으로 치솟았다 사라짐)
- 데이터 저장소 시스템 : 인기 시계열 DB는 InfluxDB, 프로메테우스(Prometheus). 다량의 시계열 데이터를 저장하고 빠른 실시간 분석 지원. 메모리 캐시와 디스크 저장소를 함께 사용
- 개략 컴포넌트 : 지표 출처 / 지표 수집기 / 시계열 데이터베이스 / 질의 서비스 / 경보 시스템 / 시각화 시스템

**상세 설계 — 지표 수집**
- 지표 데이터 소실은 심각한 문제가 아님 (지표를 보내는 쪽은 데이터가 갔든 안갔든 상관이 없다)
- 풀 모델 : 지표 수집기가 실행 중인 애플리케이션에서 주기적으로 지표 데이터를 가져온다(pull)
  - 수집기 안에 모든 서비스의 DNS/IP 정보 파일 넣으면 가장 간단. 대신 서버가 추가/삭제되는 환경에서는 파일 수정이 계속 들어가니까 별로임
  - 해결책 : SDS 사용. 각 서비스는 자신의 가용성 정보를 서비스 탐색 서비스(SDS)에 기록, SDS는 엔드포인트 목록에 변화가 생길 때마다 지표 수집기에 통보
    - SDS : 수시로 서버(IP)가 새로 생겼다 죽기를 반복하는 컨테이너 환경에서 통신하기 위한 서비스. 서버가 켜지면 SDS에게 IP 등록, 다른 서버는 이걸 보고 통신 상대를 찾음. etcd(쿠버의 핵심 저장소), ZooKeeper(하둡이나 카프카에서 쓰는 구형 모델)
  - 서비스 탐색 기반 풀 흐름 : ① 지표 수집기는 SDS에서 서비스 엔드포인트 설정 메타데이터 목록을 가져온다(서버/오케스트레이터가 데이터 변경 시 SDS에 꽂음 + 주기적 하트비트로 생존 확인) ② 사전 합의된 HTTP 엔드포인트에서 지표 데이터를 가져온다(엔드포인트를 노출하기 위해 서비스에 특정 클라이언트 라이브러리 추가) ③ 엔드포인트 목록 변화(IP 추가/삭제)를 통지받기 위한 변경 이벤트 알림 콜백(알람구독)을 SDS에 등록(안하면 계속 수집기가 SDS한테 폴링)
  - 여러 서버가 중복되는 데이터를 가져올 수 있음 → 해결책 안정해시(해시 링 구간마다 그 구간 서버의 지표 수집을 담당하는 수집기를 지정, 특정 서버의 지표는 항상 하나의 수집 서버가 처리함을 보장)
- 푸시 모델 : 웹 서버/DB 서버 같은 서버가 직접 지표를 수집기에 전송(push)
  - 모니터링 대상 서버에 수집 에이전트(Telegraf, Datadog) 설치. 자기 서버의 CPU·메모리 상태를 모아 수집기에 주기적으로 전송
  - 전송할 트래픽이 많아 수집기가 일시적으로 처리 못하고 오류를 뱉으면 에이전트 버퍼에 잠깐 보관 후 재전송
  - 에이전트 클러스터가 오토스케일링 되면 데이터 소실 가능(버퍼에 데이터가 있는데 웹 서버가 삭제되면 서버와 지표가 함께 증발)
  - 그래서 지표 수집기 서버들도 트래픽에 맞춰 오토스케일링 + 앞에 로드밸런서를 두는 것이 좋다(수천 대 에이전트가 쏘는 데이터를 로드밸런서가 여러 수집기에 골고루 분배)
- 풀 vs 푸시 : pull(Prometheus) / push(CloudWatch, Graphite)
  - 손쉬운 디버깅 : 풀 모델이 낫다 / 상태 진단(health check) : 풀 쪽이 쉽다
  - 생존 기간이 짧은 프로세스 : 지표를 다 끌어가기 전에 중단될 수 있어 푸시가 낫다(풀도 push Gateway로 해결 가능)
  - 방화벽 등 복잡한 네트워크 구성 : 푸시가 낫다
  - 성능 : 풀은 일반적으로 TCP(오버헤드 낮음), 푸시는 보통 UDP(지연 전송 낮음)
  - 데이터 신빙성 : 풀은 가져올 지표가 이미 정의됨, 푸시는 아무나 수집기에 보낼 수 있으므로 인증(authentication) 강제

**지표 전송 파이프라인 규모 확장**
- 풀/푸시 상관없이 자료수집기는 많은 데이터 수집을 위한 서버 필요. TSDB에 문제 생기면 데이터 손실 → 메시지 큐(카프카)로 해결
  - 대규모 메시지 큐 : 카프카
  - 컨슈머 : 아파치 스파크(쏟아지는 데이터를 1초·0.5초 등 짧은 시간 단위 '바구니'에 모아 한꺼번에 처리) / 아파치 스톰(데이터 1개 툭 떨어지면 즉시 처리) / 아파치 플링크(들어오는 즉시 1개씩 처리 + 앞뒤 상태 기억, 스파크의 정확성 + 스톰의 초지연 속도, 복구 능력도 있음)
  - 스트림 처리가 카프카와 시계열 DB 중간에 위치 시 장점 : 카프카는 고도로 안정·확장성 뛰어난 분산 메시지 플랫폼 / 데이터 수집·처리 컴포넌트 사이 결합도↓ / DB 장애에도 데이터 소실 없음(카프카는 서버 HDD에 기록·보관, 보관 기간 동안 원본을 절대 안 지움, 소비자는 오프셋 위치만 저장)
- 카프카를 통한 규모 확장 : 대역폭(BPS)에 따라 파티션 수 늘리기(되돌릴 수 없음) / 지표 이름에 따라 파티션 배치(소비자가 이름별 집계 가능) / 태그·레이블로 더 세분화(지표 하나가 한 파티션을 잡는 핫스팟 시 더 잘게 쪼개기) / 중요 지표 우선순위(중요 지표 토픽 따로 파기)
- 카프카의 대안 : 고릴라(Gorilla) — 페이스북의 메모리 기반 시계열 DB. 일부 네트워크 장애에도 높은 수준의 쓰기 가용성 유지

**데이터 집계 지점**
- 수집 에이전트가 집계(클라이언트 측) : 복잡한 집계 로직 지원 어려움
- 데이터 수집 파이프라인에서 집계 : 보통 스트림 프로세싱 엔진 필요(플링크). DB에는 결과만 기록해 기록량 많이 줄어듦. 대신 늦게 도착하는 지표 처리 어렵고 원본 미보관이라 정밀도·유연성 안좋음
- 질의 시 집계 : 데이터를 날것 그대로 보관 후 질의 시 필요한 시간 구간에 맞게 집계. 데이터 손실은 없으나 속도 느림

**질의 서비스**
- 질의 서버 클러스터. 시각화·경보 시스템이 직접 TSDB에 들어가 뒤지지 않도록 요청을 대신 받아주는 API 서버 클러스터. 클라이언트와 TSDB 사이 결합도↓
- 캐시 계층 : 질의 결과 캐시 서버 도입으로 TSDB 질의 부하↓·질의 서비스 성능↑
- 질의 서비스를 두면 곤란한 경우 : 관련 플러그인을 이미 갖춤 / 별도 캐시 불필요. 즉 대규모가 아니면 질의 서비스를 직접 개발해 덧붙일 필요 없이 플러그인 사용이 깔끔
- 시계열 DB 질의어 : SQL이 아닌 독자 질의어 제공(SQL로 시계열 DB 처리는 까다로움). 플럭스(Flux)로 작성하면 간단한 질의문

**저장소 계층**
- 시계열 DB는 신중하게 선택 : 운영 데이터 질의의 85%는 지난 26시간 내 데이터 대상. 적절히 고르면 성능 큰 이득
- 저장 용량 최적화
  - 데이터 인코딩·압축 : 첫 타임스탬프는 32비트(1610087371), 이후로는 차이만큼만(4비트: 10)
  - 다운샘플링 : 데이터 해상도를 낮춰 저장소 요구량 줄임(1분·1시간 해상도, 평균도 좋지만 최대·최솟값도 고려)
  - 냉동 저장소 : 잘 사용되지 않는 비활성 데이터 보관(보통 더 쌈, 직접 만들기보단 가져와 사용)

**경보 시스템**
1. 설정 파일을 가져와 캐시 서버에 보관
2. 경보 관리자는 경보 설정 내역을 캐시에서 가져옴
3. 설정된 규칙에 근거해 지정된 시간마다 질의 서비스 호출 → 질의 결과와 임계값 비교 → 위반 시 이벤트 생성 / 정보 필터링·병합·중복제거(짧은 시간 동안 같은 인스턴스 경보 병합) / 접근 제어(관리 작업은 개인만) / 재시도(최소 한 번 전달 보장)
4. 경보 저장소는 카산드라 같은 키-값 저장소(서버가 꺼져도 최소 한 번 알림 전달 보장)
5. 경보 이벤트를 카프카에 전달 6. 경보 소비자가 카프카에서 읽음 7. 이메일·단문 메시지·페이저듀티·HTTP 서비스 엔드포인트 등 다양한 채널로 알림 전송
- 만들 것인가 구매할 것인가 : 실무에서 밑바닥부터 구현은 수용 어려움

**시각화 시스템**
- 데이터 계층 위에 구축. 지표 대시보드(다양한 시간 범위)·경보 대시보드(경보 상태). 상용품 구입 바람직(Grafana)

**마무리** : 풀 vs 푸시 / 카프카 활용 규모 확장 / 최적 시계열 DB 선정 / 다운샘플링 데이터 크기 절감 / 경보·시각화 구현 vs 구입
