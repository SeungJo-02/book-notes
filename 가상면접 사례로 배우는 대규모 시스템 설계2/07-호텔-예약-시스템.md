## 1. 요구사항 & 규모 추정

- **기능 요구사항** — 웹/앱 예약·취소 · 호텔/객실 정보 페이지 · 객실 예약 · 관리자(호텔 직원) 페이지 · **초과 예약 10%** 지원 · 가격 변동.
- **비기능 요구사항** — 성수기 대비 **높은 동시성** · 적절한 지연(최대 몇 초 허용).
- **규모 추정** — 5,000 호텔 · 100만 객실 · 가동률 70% · 평균 투숙 3일.

| 항목 | 계산 | 값 |
|---|---|---|
| 일일 예약 | (100만 × 0.7) / 3 | 약 240,000 |
| 예약 **TPS** | 240,000 / 10만 초 | **약 3** |
| 상세 페이지 QPS | (90% 이탈 가정) | 약 300 |
| 예약 상세 QPS | | 약 30 |
| 객실 예약 QPS | | 약 3 |

> 🔑 예약 자체는 **초당 몇 건**밖에 안 된다 → 이 낮은 경쟁도가 뒤의 **락 전략 선택**을 좌우한다.

## 2. API 설계

REST, 관리자 API는 호텔 직원 전용.

| 분류 | API | 설명 |
|---|---|---|
| 호텔 | `GET /v1/hotels/{id}` | 호텔 상세 |
| 호텔 | `POST/PUT/DELETE /v1/hotels...` | 추가·갱신·삭제(직원용) |
| 객실 | `GET /v1/hotels/{id}/rooms/{id}` | 객실 상세 |
| 객실 | `POST/PUT/DELETE .../rooms...` | 추가·갱신·삭제(직원용) |
| 예약 | `GET /v1/reservations` | 내 예약 이력 |
| 예약 | `GET /v1/reservations/{id}` | 특정 예약 상세 |
| 예약 | **`POST /v1/reservations`** | 신규 예약 |
| 예약 | `DELETE /v1/reservations/{id}` | 예약 취소 |

> ⭐ 가장 중요한 `POST /v1/reservations` — 인자로 받는 **reservation_id를 멱등 키**로 쓴다. (같은 날 같은 객실에 **중복 예약**이 생기는 것을 막기 위해)

## 4. 개선된 데이터 모델 — 객실 유형·재고

- 실제로는 **특정 객실**이 아니라 **객실 유형(room type)**을 예약한다 → `roomID` → **`roomTypeID`**로 변경.
- 주요 테이블

| 테이블 | 담는 것 |
|---|---|
| `room` | 객실 정보 |
| `room_type_rate` | 특정 객실 유형의 **특정 일자 요금** |
| `reservation` | 투숙객 예약 정보 |
| `room_type_inventory` | 호텔의 모든 객실 유형 **재고**(hotel_id·room_type_id·date·total_inventory·total_reserved) |

- `total_inventory` = 총 객실 수 − 일시 제외 객실 수, `total_reserved` = 예약된 객실 수.

### 4-1. 재고 저장 방식 — 날짜당 레코드 ✅
| 방식 | 특징 |
|---|---|
| 시작일~종료일 범위 | 겹치는 기간을 **부등호 조건**으로 찾아야 함 → 쿼리 성능↓ |
| **날짜당 1행** | 매일 재고를 하루치(행)로 미리 쪼개 저장 → **로직 단순** |

- 저장량 추정: 5,000 호텔 × 20 객실 유형 × 2년 ≈ **7,300만 행**. → **SPOF·고가용성**을 함께 고려해야 함.

## 5. 동시성 문제 ⭐

### 5-1. 같은 사용자가 예약 버튼을 여러 번 누름
| 방법 | 평가 |
|---|---|
| 클라이언트에서 버튼 비활성화 | 불안정(JS 끄면 우회 가능) |
| **멱등 API**(reservation_id를 멱등 키) | ✅ 확실 |

### 5-2. 여러 사용자가 같은 객실을 동시에 예약
| 방법 | 장점 | 단점 |
|---|---|---|
| 비관적 락 | 즉시 락으로 충돌 방지·구현 쉬움 | **데드락** 위험 · 확장성↓ |
| **낙관적 락**(버전 번호) | 락 불필요 · 경쟁 약할 때 적합 | 경쟁 치열하면 성능↓ |
| **DB 제약**(`total_inventory - total_reserved >= 0`) | 구현 매우 쉬움 | 경쟁 심하면 실패 급증 · 버전 관리 어려움 |

> 🔑 **예약 QPS가 낮으므로**(경쟁이 심하지 않음) → **낙관적 락**이나 **DB 제약 조건**이 이 시스템에 적합하다. 비관적 락은 확장성 문제로 부적합.

## 6. 규모 확장 — 샤딩·캐시·일관성

### 6-1. DB 샤딩
- 여러 DB에 데이터를 쪼개 보관. **`hotel_id`를 샤딩 키**로(대부분 질의가 hotel_id로 필터링).

### 6-2. Redis 캐시
- 낡은 데이터는 **TTL**로 자동 소멸. 잔여 객실 정보를 **미리 캐시**에 올려두고, 요청 일부만 DB가·나머지는 캐시가 처리.
- 👍 DB 부하↓ · 성능↑  👎 DB↔캐시 **일관성 100% 유지 어려움**.

### 6-3. 서비스 간 데이터 일관성
| 방식 | 특징 |
|---|---|
| **2PC(2단계 커밋)** | 여러 노드의 원자적 트랜잭션 보증(모두 성공 or 실패), 강한 일관성. 한 노드 장애 시 복구까지 **진행 중단** |
| **Saga** | 국지 트랜잭션을 엮고, 실패 시 이전 것들을 **보상 트랜잭션**으로 되돌림. **결과적 일관성** |

## 정리

| 주제 | 핵심 |
|---|---|
| 규모 | 예약 TPS≈3(낮음) → 경쟁도 낮음 |
| 저장소 | RDB(ACID), 재고는 날짜당 1행 |
| 예약 단위 | 객실이 아니라 **객실 유형** |
| 중복 클릭 | 멱등 키(reservation_id) |
| 동시 예약 | 낙관적 락 / DB 제약(경쟁 약해서) |
| 확장 | hotel_id 샤딩 + Redis(TTL) |
| 서비스 일관성 | 2PC(강함) vs Saga(결과적) |

**동시성 문제**
1. 같은 사용자가 예약 버튼을 여러 번 누를 수 있다.
	- 클라이언트 측 구현: 클라이언트 요청 전송 후 예약 버튼을 비활성화시킨다. (안정적이진 않다. JS비활성화 하면 우회 가능)
	- 멱등 API: 예약 API 요청에 멱등 키를 추가한다. (ex. reservation_id)
2. 여러 사용자가 같은 객실을 동시에 예약하려 할 수 있다.
	- 비관적 락: 사용자가 레코드를 갱신하려고 하는 순간 즉시 락을 걸어 동시 업데이트를 방지한다.
		- 👍 변경 중이거나 변경이 끝난 데이터를 갱신하는 일을 막을 수 있다.
		- 👍 구현이 쉽고 모든 갱신 연산을 직렬화하여 충돌을 막는다.
		- 👎 여러 레코드에 락을 걸면 교착 상태(데드락)가 발생할 수 있다.
		- 👎 확장성이 낮다. (성능적 문제)
	- 낙관적 락: 여러 사용자가 동시에 같은 자원을 갱신하려 시도하는 것을 허용한다. (버전 번호 사용)
		- 👍 애플리케이션이 유효하지 않은 데이터를 편집하는 일을 막는다.
		- 👍 데이터베이스 자원에 락을 걸 필요가 없다. (버전 번호를 통해 데이터 일관성 유지)
		- 👍 데이터에 대한 경쟁이 치열하지 않은 상황에 적합하다.
		- 👎 데이터에 대한 경쟁이 치열한 상황에서는 성능이 좋지 않다.
		- 예약 QPS가 일반적으로 높지 않기 때문에 호텔 예약 시스템에서 적합하다.
	- 데이터베이스 제약 조건 (total_inventroy - total_reserved >= 0)
		- 👍 구현이 쉽다.
		- 👍 데이터에 대한 경쟁이 심하지 않을 때 잘 동작한다.
		- 👎 데이터에 대한 경쟁이 심하면 실패하는 연산 수가 급격히 늘어난다.
		- 👎 데이터베이스 제약 조건은 애플리케이션 코드와 달라서 버전을 통제하기 어렵다.
		- 👎 제약 조건을 허용하지 않는 데이터베이스도 있다.
		- 데이터에 대한 경쟁이 심하지 않은 호텔 예약 시스템에서 적합하다.

**시스템 규모 확장 — 데이터베이스 샤딩**
- 데이터베이스를 여러 대 두고, 각각에 데이터의 일부만 보관하도록 한다.
- hotel_id를 샤딩 조건으로 쓰면 좋다. (대부분 질의는 hotel_id를 필터링 조건으로 사용함)

**캐시**
- 데이터를 보관할 때 낡은 데이터는 자동적으로 소멸되도록 TTL을 설정하는 것이 바람직하다.
- 레디스(Redis)는 해당 상황에 적합하다.
- 요청 가운데 일부만 잔여 객실 데이터베이스가 처리하고 나머지는 캐시가 담당한다.
	- 예약 서비스: API 제공
	- 잔여 객실 캐시: 사전에 잔여 객실 정보를 캐시에 미리 저장해둔다.
	- 잔여 객실 데이터베이스: 잔여 객실 수에 대한 가장 신뢰성 있는 정보가 보관된다.
	- 👍 데이터베이스 부하가 크게 감소한다.
	- 👍 높은 성능을 보장한다.
	- 👎 데이터베이스와 캐시 사이의 데이터 일관성을 100% 유지하기는 어렵다.

**서비스 간 데이터 일관성**
- 데이터 일관성 문제를 해결하기 위해
	- 2단계 커밋(2PC): 여러 노드에 걸친 원자적 트랜잭션 실행을 보증하는 데이터베이스 프로토콜
		- 모든 노드가 성공하든 실패하든 둘 중 하나로 트랜잭션이 마무리되도록 보증한다.
		- 한 노드에 장애가 발생하면 복구될 때까지 진행이 중단된다.
		- 하나의 트랜잭션을 통해 ACID 속성을 만족시킨다.
	- 사가(Saga): 각 노드에 국지적으로 발생하는 트랜잭션을 하나로 엮은 것
		- 어느 한 트랜잭션이라도 실패하면 그 이전 트랜잭션의 결과를 전부 되돌리는 트랜잭션들을 순차적으로 실행한다.
		- 결과적 일관성에 의존한다.
