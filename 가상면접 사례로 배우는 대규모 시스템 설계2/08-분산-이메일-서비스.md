# 8장. 분산 이메일 서비스

> 📝 **Notion 원본**: https://app.notion.com/p/5262b56728a44d92a9c348063848686c

> 🧩 **한 줄 요약** — 사용자 10억 명(전송 QPS 100,000, 1년 저장 수천 PB)을 감당하는 지메일급 메일 서비스. 서버 한 대에 파일로 쌓던 **전통적 메일 서버**를 **웹 서버 · 실시간 서버(웹소켓) · 메타데이터 DB · 첨부 파일 저장소(S3) · 캐시 · 검색 저장소**로 나누고, 보내기와 받기를 모두 **메시지 큐로 비동기 처리**한다. 메타데이터 DB는 일관성을 위해 가용성을 일부 내주고, 스팸으로 분류되지 않도록 **IP 평판 관리와 이메일 인증**을 챙긴다.

## 1. 요구사항 & 규모

### 1-1. 기능 요구사항

| 항목 | 내용 |
|---|---|
| 인증 | 로그인한 사용자만 자기 메일함 접근 |
| 발송 / 수신 | 메일 보내기 · 받기 |
| 조회 | 모든 이메일 가져오기, **읽음 여부로 필터링** |
| 검색 | 제목 · 발신일 · 본문으로 검색 |
| 보호 | 스팸 · 바이러스 방지 |
| 첨부 | 첨부 파일 지원 |

### 1-2. 비기능 요구사항

| 항목 | 내용 |
|---|---|
| **안정성** | 데이터가 사라지면 안 됨 |
| **가용성** | 데이터를 여러 노드에 복제해서 일부가 죽어도 동작 |
| **확장성** | 사용자와 용량이 늘어도 성능 유지 |
| **유연성 · 확장성** | 기능 추가와 성능 개선이 쉬워야 함 |

### 1-3. 규모 추정

| 항목 | 계산 | 결과 |
|---|---|---|
| 사용자 | | **10억 명** |
| 전송 QPS | 10⁹ × 하루 10건 ÷ 10⁵초 | **100,000** |
| 메타데이터 저장 (1년) | 10억 명 × 하루 40건 수신 × 365일 × 50KB | **730PB** |
| 첨부 파일 저장 (1년) | 10억 명 × 하루 40건 × 365일 × 20%(첨부 비율) × 500KB | **1,460PB** |

- 가정 : 한 사람이 하루에 10건 보내고 40건 받음, 메일 한 통의 메타데이터 평균 50KB, 첨부 파일이 있는 메일 20%, 첨부 평균 500KB.
- 하루는 약 10⁵초(86,400초)로 어림잡는다.
- 숫자가 PB 단위라서 **서버 한 대로는 불가능 → 분산 저장소가 필수**라는 결론이 나온다.

## 2. 이메일 101

### 2-1. 이메일 프로토콜

| 프로토콜 | 용도 | 방식 | 특징 |
|---|---|---|---|
| **SMTP** | **보낼 때** (표준) | 클라이언트 → 메일 서버, 메일 서버 → 메일 서버로 PUSH | 네이버 메일 서버가 구글 메일 서버로 보낼 때도 SMTP |
| **POP** | 받을 때 (옛날 방식) | 서버에 도착한 메일을 **몽땅 내려받고 서버 원본은 지움** | 내려받은 뒤엔 인터넷이 끊겨도 읽을 수 있음. 큰 메일은 오래 걸리고 **여러 기기 동기화 불가** |
| **IMAP** | 받을 때 (요즘 방식) | **원본은 서버에 두고** 기기에서 조작·확인 | 클릭하기 전엔 본문을 안 받고 헤더만 받아서 느린 인터넷에서도 괜찮음. **다중 기기 동기화** 완벽, 대신 서버 용량을 많이 씀 |
| **HTTPS** | 웹메일 | 브라우저로 메일함 접속 | 엄밀히 메일 프로토콜은 아니지만 웹 기반 메일 시스템이 사용 |

### 2-2. DNS와 MX 레코드
- 메일을 보내는 서버는 DNS에서 **수신자 도메인의 MX(메일 교환기) 레코드**를 조회해서 받을 서버 주소를 찾는다.
- MX 레코드는 **우선순위 + 메일 서버 목록**으로 되어 있다.
  - 우선순위 숫자가 **낮을수록 먼저** 시도한다.
  - 높은 우선순위 서버에 연결이 실패하면 **다음 우선순위 서버**로 연결한다.

### 2-3. 첨부 파일
- 메일 메시지와 함께 보내며 보통 **Base64**로 인코딩한다.
- **MIME**(다목적 인터넷 메일 확장) 규격으로 첨부 파일을 인터넷으로 보낼 수 있게 한다. 메일 서비스는 보통 첨부 파일 크기 상한을 둔다.

## 3. 전통적 메일 서버

- 보통 **서버 한 대**로 운영하고, 사용자가 많지 않을 때 잘 동작한다.

### 3-1. 아키텍처

[🖼️ 원본 이미지: 전통적 메일 서버 아키텍처 (아웃룩 → SMTP → DNS 조회 → 지메일 → IMAP/POP)]

1. 앨리스가 아웃룩에서 메일을 쓰고 `보내기`를 누르면 아웃룩 메일 서버로 전송된다 (**SMTP**).
2. 아웃룩 메일 서버가 **DNS 질의**로 수신자의 SMTP 서버 주소를 찾아 그쪽으로 보낸다 (서버 간도 **SMTP**).
3. 지메일 서버가 메일을 저장하고 밥이 읽어 갈 수 있게 한다.
4. 밥이 지메일에 로그인하면 클라이언트가 **IMAP/POP** 서버를 통해 새 메일을 가져온다.

### 3-2. 저장소 — 파일 시스템

| 방식 | 구조 | 문제 / 장점 |
|---|---|---|
| **mbox** (구형) | 모든 메일을 **거대한 텍스트 파일 하나**에 이어 붙임 | 여러 작업이 동시에 지우거나 쓰면 파일이 깨질 수 있어 **Lock이 필요 → 병목** |
| **Maildir** (현대) | **메일 1통 = 파일 1개** | 파일이 서로 달라 Lock이 필요 없고 파일이 깨질 위험도 거의 없음 |

- Maildir 폴더 구조
  - `tmp` : 메일 데이터를 아직 받고 있는 중
  - `new` : 다 받았지만 아직 안 읽은 메일
  - `cur` : `new`의 메일을 열면 이동. 읽음·답장함 같은 플래그가 파일 이름에 붙어 상태를 기억
- 한계 : 사용자가 수십억 명이 되면 디스크 I/O가 병목이 되고, 서버 한 대라 **가용성·안정성**도 못 맞춘다 → **분산 저장소 계층**이 필요해졌다.

## 4. 분산 메일 서버

- 현대적 사용 패턴(웹메일, 여러 기기)을 지원하고 확장성과 안정성 문제를 해결한다.

### 4-1. 이메일 API

| 메서드 | 엔드포인트 | 역할 |
|---|---|---|
| POST | `/v1/messages` | 수신자에게 메시지 전송 |
| GET | `/v1/folders` | 계정의 모든 폴더 반환 |
| GET | `/v1/folders/{:folder_id}/messages` | 폴더 아래 모든 메시지 반환 |
| GET | `/v1/messages/{:message_id}` | 특정 메시지의 모든 정보 반환 |

### 4-2. 아키텍처

[🖼️ 원본 이미지: 분산 메일 서버 아키텍처]

| 컴포넌트 | 역할 |
|---|---|
| **웹메일** | 사용자가 브라우저로 메일을 받고 보냄 |
| **웹 서버** | 로그인 · 메일 보내기 · 폴더/메일 조회 같은 요청/응답 처리 |
| **실시간 서버** | 새 메일을 클라이언트에 실시간으로 밀어 줌 (웹소켓, 상태 유지 서버) |
| **메타데이터 DB** | 제목 · 본문 · 발신자 · 수신자 등 메일 메타데이터 저장 |
| **첨부 파일 저장소** | 객체 저장소(아마존 S3) |
| **분산 캐시** | 최근 받은 메일을 캐싱 (클라이언트가 최신 메일을 자주 읽기 때문) |
| **검색 저장소** | 분산 문서 저장소 (역색인으로 전문 검색) |

**첨부 파일을 DB가 아니라 S3에 두는 이유**
- DB에 BLOB으로 넣으면 조회할 때마다 무거운 데이터를 통째로 옮겨야 한다.
- S3에 파일을 두고 **DB에는 파일 주소만** 저장하면, 브라우저가 그 주소로 S3에서 직접 받아 간다.
- DB 용량과 전송량 모두 줄어든다.

## 5. 이메일 전송 · 수신 절차 ⭐

### 5-1. 전송 절차

[🖼️ 원본 이미지: 이메일 전송 절차]

1. 사용자가 웹메일에서 메일을 쓰고 전송을 누른다.
2. **로드밸런서**가 처리율 제한 한도 안에서 요청을 웹 서버로 넘긴다.
3. **웹 서버**
   - 기본 검증 (메일 크기 한도 등)
   - 수신자 도메인이 송신자 도메인과 같으면 (같은 서비스 안이면) 스팸·바이러스 검사 후 바로 저장소에 넣고 끝
   - 아니면 메시지를 저장소와 분리해서, 무거운 것은 저장소에 두고 가벼운 것만 **외부 전송 큐**로 보냄
4. **메시지 큐**
   - 4-a. 기본 검증 실패 → **에러 큐**
   - 4-b. 통과 → **외부 전송 큐** (첨부가 크면 큐에는 S3 참조만 넣음)
5. **외부 전송 담당 SMTP 작업 프로세스**가 큐에서 꺼내 스팸·바이러스 여부를 확인한다.
6. 통과한 메일은 저장소의 `보낸 편지함`에 저장된다.
7. SMTP 작업 프로세스가 **수신자의 메일 서버**로 보낸다.

- 큐에 메일이 오래 쌓이면 원인을 나눠서 본다.
  - 수신자 서버가 문제 → **지수적 백오프**로 재시도
  - 소비자가 느림 → **소비자(작업 프로세스)를 더 추가**

### 5-2. 수신 절차

[🖼️ 원본 이미지: 이메일 수신 절차]

1. 메일이 **SMTP 로드밸런서**에 도착한다.
2. 로드밸런서가 여러 **SMTP 서버**로 트래픽을 나눈다 (SMTP 단계에서 유효하지 않은 메일은 바로 반송할 수 있음).
3. 첨부 파일이 너무 커서 큐에 못 넣으면 **첨부 파일 저장소(S3)**에 먼저 둔다.
4. 메일을 **수신 이메일 큐**에 넣는다.
5. **메일 처리 작업 프로세스**가 스팸 필터링, 바이러스 차단 등을 한다.
6. 메일을 메일 저장소 · 캐시 · 객체 저장소에 보관한다.
7. 수신자가 **온라인**이면 실시간 서버로 넘긴다.
8. 실시간 서버(**웹소켓**)가 클라이언트에 새 메일을 실시간으로 보낸다.
9. **오프라인** 사용자의 메일은 저장소에만 둔다.
10. 사용자가 접속하면 웹 서버가 저장소에서 새 메일을 가져와 돌려준다.

### 5-3. 생각해 본 것 — 왜 SMTP 서버와 메일 처리를 나눌까?

| 질문 | 답 |
|---|---|
| SMTP 서버와 메일 처리를 하나로 합치면? | 스팸·바이러스 검사는 오래 걸린다. 합치면 SMTP 서버가 검사하는 동안 다음 메일을 못 받는다. **큐로 나눠 비동기**로 처리하면 SMTP는 빨리 받고 검사는 뒤에서 따로 확장할 수 있다 |
| 검사 전 메일을 저장소에 넣으면 바이러스가 들어가지 않나? | 저장만 해서는 괜찮다. 바이러스 코드는 **실행되지 않으면** 피해가 없다. 메일 처리 단계에서 문제를 찾으면 저장소에서 지운다 |

## 6. 메타데이터 데이터베이스

### 6-1. 메일 메타데이터의 특성
- 메일 **헤더는 작고 자주** 쓰인다.
- 메일 **본문은 크기가 제각각이고 자주 읽히지 않는다** (보통 한 번 읽고 끝).
- 메일은 **그 사용자만** 읽을 수 있어야 한다 → 같은 사용자의 데이터는 한곳에 모아 두면 좋다.
- **최신 메일일수록 많이 읽힌다** (데이터 신선도가 사용 패턴을 정함).
- 데이터 유실이 절대 안 되므로 **높은 안정성**이 필요하다.

### 6-2. 어떤 DB를 쓸까

| 후보 | 판단 |
|---|---|
| **관계형 DB** | 작은 데이터를 효율적으로 검색하기엔 좋다. 하지만 메일 본문은 크고, BLOB으로 넣으면 검색 성능이 나쁘고 디스크 I/O가 너무 많다 → **부적격** |
| **분산 객체 저장소 (S3)** | 백업 보관엔 좋지만, 읽음 표시 · 키워드 검색 · 스레드 묶기 같은 기능을 구현하기 어렵다 |
| **NoSQL** | 지메일은 구글 Bigtable을 쓰지만 내부 구현이 공개돼 있지 않다. 카산드라를 고려해 볼 수는 있다 |
| **결론** | 대형 메일 서비스는 보통 **자체 저장소 시스템**을 만들어 쓴다 |

- 자체 시스템이 꼭 갖춰야 할 것
  - **강한 일관성**
  - **디스크 I/O 최소화**
  - **매우 높은 가용성 · 결함 내성**
  - **증분 백업** (최근 백업 이후 바뀐 부분만 저장)

### 6-3. 데이터 모델
- **파티션 키** : 데이터를 여러 노드에 나누는 기준 (예: `user_id` → 한 사용자의 메일은 한 파티션에)
- **클러스터 키** : 같은 파티션 안에서 정렬 기준 (예: 시간 기반 `email_id` → 최신순)
- 지원해야 하는 질의
  - 특정 사용자의 모든 폴더
  - 특정 폴더의 모든 메일
  - 메일 생성 · 삭제 · 수신
  - 읽은 메일 / 안 읽은 메일 전체
- 읽음 여부 필터는 NoSQL에서 `WHERE is_read = false`처럼 하기 어려워서, 책은 **읽은 메일 테이블과 안 읽은 메일 테이블을 따로 두는 비정규화**로 푼다 (읽으면 한쪽에서 지우고 다른 쪽에 넣음).

### 6-4. 일관성 문제
- 한 메일함은 **주 사본 하나**가 담당한다.
- 주 사본에 장애가 나면, 복원될 때까지 클라이언트는 다른 사본으로 동기화·갱신을 끝낼 수 없다.
- 즉 **일관성을 위해 가용성을 희생**한다 (CAP).
  - 네트워크 분할(P)은 분산 시스템에서 피할 수 없어서, 실제 선택지는 **C냐 A냐** 두 가지다. 메일은 C를 고른다.

## 7. 이메일 전송 가능성(스팸으로 안 가게)

- 새로 만든 메일 서버는 **평판이 없어서** 다른 서비스가 스팸으로 분류하기 쉽다. 그래서 아래 방법으로 평판을 쌓는다.

| 방법 | 내용 |
|---|---|
| **전용 IP** | 메일 발송에 전용 IP를 쓴다. 이력이 없는 IP는 신뢰받지 못한다 |
| **범주화** | 마케팅 메일과 중요 메일처럼 범주가 다르면 **다른 IP**로 보낸다 |
| **발신인 평판 (IP 워밍업)** | 새 IP는 발송량을 **서서히** 늘린다 |
| **스팸 발송자 신속 차단** | 스팸을 뿌리는 사용자를 빨리 막아 서버 평판을 지킨다 |
| **피드백 처리** | ISP의 피드백을 쉽게 받아 처리할 경로를 만든다 |
| **이메일 인증** | SPF · DKIM · DMARC로 "진짜 이 도메인이 보낸 메일"임을 증명한다 |

- 피드백 종류

| 종류 | 뜻 | 대응 |
|---|---|---|
| **경성 반송** (hard bounce) | 수신 주소가 잘못돼서 ISP가 거부 | 그 주소로 다시 보내지 않음 |
| **연성 반송** (soft bounce) | ISP 쪽 사정으로 일시적으로 실패 | 나중에 재시도 |
| **불만 신고** | 수신자가 "스팸" 버튼을 누름 | 발송 대상·내용 점검 |

- 이메일 인증 용어 (책 보강)
  - **SPF** : 이 도메인으로 메일을 보내도 되는 서버 IP 목록을 DNS TXT 레코드에 공개
  - **DKIM** : 메일에 전자 서명을 붙이고, 공개 키를 DNS에 올려 위조·변조 여부를 확인
  - **DMARC** : SPF·DKIM 검사에 실패한 메일을 어떻게 처리할지(무시·격리·거부) 정하는 정책

## 8. 검색 · 규모 확장성 · 가용성

### 8-1. 검색
- 메일 검색은 **쓰기가 읽기보다 훨씬 많다**. 메일을 받고 보내고 지울 때마다 색인을 고쳐야 하지만, 검색은 가끔 한다.

| | **방안 1 : Elasticsearch** | **방안 2 : 맞춤형 검색 솔루션** |
|---|---|---|
| 방식 | 사용자는 검색 결과가 올 때까지 기다림 (**동기**). 색인 작업은 Kafka 같은 큐로 **비동기** 처리 | 대형 메일 사업자는 자기 요구사항에 맞춘 검색 엔진을 **직접 개발** |
| 장점 | 텍스트 기반 검색을 잘 지원, 구현이 쉬움 | 쓰기가 많은 패턴에 맞게 최적화 가능 (예: 디스크 I/O를 줄이는 LSM 트리 기반 색인) |
| 단점 | **주 메일 저장소와 동기화**를 맞추기 까다로움 | 만들기 어렵고 비용이 큼 |

- 규모가 작으면 Elasticsearch로 시작하고, 아주 커지면 메일 저장소 안에 검색을 내장한 자체 솔루션을 고민한다.

### 8-2. 규모 확장성 · 가용성
- 대부분의 컴포넌트는 **수평 확장**이 가능하다.
- 가용성을 높이려면 데이터를 **여러 데이터센터에 복제**한다. 네트워크가 분할되면 사용자는 다른 데이터센터의 메일 서버로 접속할 수 있다.

## 🔁 셀프 체크
1. POP와 IMAP의 차이를 "원본이 어디 있느냐"로 설명하면? 요즘 IMAP을 쓰는 이유는?
2. 메일을 받을 때 SMTP 서버가 스팸·바이러스 검사를 직접 하지 않고 큐에 넘기는 이유는?
3. 메타데이터 DB로 관계형 DB를 쓰지 않는 이유와, 장애 때 가용성보다 일관성을 고르는 이유는?

<details>
<summary>답</summary>

1. POP는 메일을 **기기로 내려받고 서버 원본을 지운다**. 그래서 내려받은 기기에서만 읽을 수 있고 여러 기기 동기화가 안 된다. IMAP은 **원본을 서버에 두고** 기기는 헤더만 받아 보다가 클릭할 때 본문을 받는다. 폰·PC·웹 어디서 봐도 같은 상태(읽음, 폴더)가 유지돼서 요즘은 IMAP을 쓴다.
2. 스팸·바이러스 검사는 오래 걸린다. SMTP 서버가 직접 하면 검사하는 동안 다음 메일을 받지 못해 수신이 막힌다. **수신 큐에 넣고 메일 처리 작업 프로세스가 비동기로 검사**하면 SMTP는 빨리 받고, 검사 쪽은 따로 늘릴 수 있다. 검사 전에 저장해도 바이러스는 실행되지 않으면 피해가 없고, 문제가 발견되면 지운다.
3. 메일 본문은 크기가 크고 제각각이라 BLOB으로 넣으면 검색이 느리고 디스크 I/O가 많아진다. 그래서 대형 서비스는 강한 일관성 · I/O 최소화 · 높은 가용성 · 증분 백업을 갖춘 **자체 저장소**를 만든다. 메일함은 주 사본 하나가 맡는데, 장애 때 다른 사본에 쓰게 하면 읽음 표시나 삭제 같은 상태가 어긋날 수 있다. 메일은 데이터가 틀리거나 사라지면 안 되므로 **잠시 못 쓰더라도 일관성**을 지킨다.

</details>

- 이메일 전송 QPS = 100,000 (10^9 * 10 / 10^5)
  - 한 사람이 하루에 보내는 평균 이메일 수는 10건으로 가정
- 1년간 스토리지 요구사항 = 730PB (10억 명 * 하루 40건 * 365일 * 50KB)
  - 한 사람이 하루에 수신하는 이메일 수는 평균 40건으로 가정
  - 이메일 하나의 메타데이터는 평균 50KB로 가정
- 1년간 필요한 저장 용량 = 1,460PB (10억 명 * 하루 40건 * 365일 * 20% * 500KB)
  - 첨부 파일을 포함하는 이메일의 비율은 20%로 가정
  - 첨부 파일의 평균 크기는 500KB로 가정

## **개략적 설계안 제시 및 동의 구하기**

### **이메일 101**

#### **이메일 프로토콜**

<details>
<summary>레거시 프로토콜 종류(공부용)</summary>

- SMTP : 메일을 **보낼 때** 사용하는 표준 프로토콜(국룰)
  - 언제 사용?
    - 유저의 이메일을 구글 등의 메일 서버로 PUSH
    - 네이버 메일 서버에서 구글 메일 서버로 PUSH
- POP : 메일을 **받을 때** 사용하는 옛날 프로토콜
  - 메일 서버에 도착한 내 이메일을 몽땅 다운로드하고 서버에 있는 원본을 지우는 방식
    - 용량 문제, 인터넷이 끊겨도 다운한 상태라서 괜찮음
    - 용량이 큰 메일은 오래걸린다
    - 여러기기 간 연동은 안됨
- IMAP : 메일을 **받을 때** 사용하는 요즘 프로토콜
  - 메일 서버에 원본을 두고 내 기기에서 조작하고 확인하는 방식
    - 완벽한 다중 기기 동기화
    - 서버용량을 많이 차지
    - 인터넷이 약해도 헤더만 다운로드 하기에 문제 없다

</details>

- SMTP: 이메일을 한 서버에서 다른 서버로 보내는 표준 프로토콜
- POP, IMAP: 이메일을 가져오는 목적으로 가장 널리 사용되는 프로토콜
  - POP: 이메일을 읽으려면 파일 전부를 다운로드 받아야 함
  - IMAP: 클릭하지 않으면 메시지는 다운로드 되지 않음
- HTTPS: 웹 기반 이메일 시스템의 메일함 접속에 이용

### **전통적 메일 서버**

- 보통 서버 한 대로 운용된다.
- 사용자가 많지 않을 때 잘 동작한다.

#### **전통적 메일 서버 아키텍처**

[🖼️ 원본 이미지: 전통적 메일 서버 아키텍처]

1. 앨리스는 아웃룩 클라이언트에 로그인하여 이메일을 작성하고 `보내기` 버튼을 누른다. 이메일은 아웃룩 메일 서버로 전송된다. 아웃룩 클라이언트와 메일 서버 사이의 통신 프로토콜은 SMTP이다.
2. 아웃룩 메일 서버는 DNS 질의를 통해 수신자 SMTP 서버 주소를 찾는다. 주소를 얻은 후 해당 메일 서버로 이메일을 보낸다. 메일 서버 간 통신 프로토콜도 SMTP다.
3. 지메일 서버는 이메일을 저장하고 수신자인 밥이 읽어갈 수 있도록 한다.
4. 밥이 지메일에 로그인하면 지메일 클라이언트는 IMAP/POP 서버를 통해 새 이메일을 가져온다.

#### **저장소**

- 전통적 메일 서버는 이메일을 파일 시스템의 디렉터리에 저장한다.
- 사용자가 늘어나면서 더 안정적인 분산 데이터 저장소 계층이 필요했다.

<details>
<summary>Maildir</summary>

- 이메일 서버가 사용자에게 온 편지들을 HDD에 보관할 때 사용하는 **1메일 1파일 방식의 폴더형 저장 포맷**
  - 구형방식 - mbox
    - 모든 이메일을 단 하나의 거대한 텍스트 파일에 줄줄이 이어 붙여서 저장
      - 메일이 많은 데 유저가 동시에 편지를 지우면? ⇒ 파일이 깨져서 Lock이 필요 ⇒ 병목이 걸림
  - 현대적 방식 - Maildir
    - 메일 한 통을 각각의 독립된 개별 파일로 만들어서 저장
      - 편지 하나하나가 다른 파일이라 Lock을 걸 필요가 없다
      - 하나의 파일에 넣지 않아서 파일이 깨질 위험이 거의 없다
    - 구조
      - tmp : 메일서버가 편지 데이터를 한창 전송받고 있는 상태
      - new : 다운이 끝난 이메일 파일이며 아직 안읽은 상태
      - cur : new에 있는 파일이 클릭되는 순간 이동. 읽음, 답장함 등의 flag가 텍스트로 붙어서 이메일의 상태를 기억한다

</details>

### **분산 메일 서버**

- 현대적 사용 패턴을 지원하고 확장성과 안정성 문제를 해결한다.

#### **이메일 API**

- POST /v1/messages 엔드포인트: 수신자에게 메시지 전송
- GET /v1/folders 엔드포인트: 주어진 이메일 계정에 존재하는 모든 폴더 반환
- GET /v1/folders/{:folder_id}/messages 엔드포인트: 주어진 폴더 아래의 모든 메시지 반환
- GET /v1/messages/{:message_id} 엔드포인트: 주어진 특정 메시지에 대한 모든 정보 반환

### **이메일 전송 절차**

[🖼️ 원본 이미지: 이메일 전송 절차]

1. 사용자가 웹메일 환경에서 메일 작성 후 전송 버튼을 누른다.
2. 로드밸런서는 처리율 제한 한도를 넘지 않는 선에서 요청을 웹 서버로 전달한다.
3. 웹 서버는 다음 역할을 담당한다.
   - 기본적인 이메일 검증
   - 수신자 이메일 주소 도메인이 송신자 이메일 주소 도메인과 같은지 검사
   - 그러고 나서 저장소에 데이터를 분리를 하고 가벼운거만 외부 전송 큐로 직행
4. 메시지 큐
   - 4-a. 기본적인 검증에 실패한 이메일은 에러 큐에 보관
   - 4-b. 기본적인 검증을 통과한 이메일은 외부 전송 큐로 전달
5. 외부 전송 담당 SMTP 작업 프로세스는 외부 전송 큐에서 메시지를 꺼내어 이메일의 스팸 및 바이러스 감염 여부 확인
6. 검증 절차를 통과한 이메일은 저장소 계층 내의 `보낸 편지함`에 저장된다.
7. 외부 전송 담당 SMTP 작업 프로세스가 수신자의 메일 서버로 메일을 전송

- 큐에 메일이 너무 오래 있으면 아래방법 사용
  - 지수적 백오프
  - 더 많은 소비자 추가

### **이메일 수신 절차**

[🖼️ 원본 이미지: 이메일 수신 절차]

1. 이메일이 SMTP 로드밸런서에 도착한다.
2. 로드밸런서는 트래픽을 여러 SMTP 서버로 분산한다.
3. 이메일의 첨부 파일이 큐에 들어가기 너무 큰 경우 첨부 파일 저장소에 보관한다.
4. 이메일을 수신 이메일 큐에 넣는다.
5. 메일 처리 작업 프로세스는 스팸 메일을 걸러내고 바이러스를 차단하는 등의 다양한 역할을 한다.
6. 이메일을 메일 저장소, 캐시, 객체 저장소 등에 보관한다.
7. 수신자가 온라인 상태일 경우 이메일을 실시간 서버로 전달한다.
8. 실시간 서버는 수신자 클라이언트가 새 이메일을 실시간으로 받을 수 있도록 하는 웹소켓 서버다.
9. 오프라인 상태 사용자의 이메일은 저장소 계층에 보관한다.
10. 웹 서버는 새로운 이메일을 저장소 계층에서 가져와 클라이언트에 반환한다.

- 내 생각 왜 SMTP랑 메일 처리랑 하나로 안합칠까? 그리고 메일처리를 안하고 저장소에 넣으면 바이러스가 있는 데이터가 들어가는 거 아니야?
  - 일단 하나로 합치면 대규모 시스템이라면 하나하나가 오래 걸릴거다 메일 검사하는게 시간이 오래 걸리는 작업이라 일단 빨리 보내줘야 하는데 그래서 비동기 방식이 필요
  - 저장소에 처리 안된 데이터를 넣어도 괜찮다
    - 바이러스 코드는 실행만 안되면 되기 때문이다
  - 그래서 메일처리에서 문제가 되는 메일을 발견하면 저장소에 있는 데이터를 제거해버린다

## **상세 설계**

### **메타데이터 데이터베이스**

#### **이메일 메타데이터의 특성**

- 이메일의 헤더는 작고, 빈번히 이용된다.
- 사용 빈도가 낮다.
- 관련된 사용자만 이메일을 읽을 수 있어야 한다.
- 데이터의 신선도는 데이터 사용 패턴에 영향을 미친다.
- 데이터의 높은 안정성이 보장되어야 한다.

#### **올바른 데이터베이스의 선정**

- 관계형 데이터베이스: 이메일을 효율적으로 검색할 수 있음 + 데이터 크기가 작을 때 좋음. BLOB 사용해도 검색이 별로다(I/O작업이 너무 많이 발생) → 부적격
- 분산 객체 저장소: 백업 데이터를 보관하기에는 좋지만, 부가기능을 구현하기에는 좋지 않음
- NoSQL 데이터베이스: 내부 구현이 잘 알려져있지 않음. 카산드라 고려해도 좋지만 현직에서는 이메일 용도로 카산드라를 사용하지는 않는다
- 결론, 자체적인 시스템을 만들어 많이 사용함
  - 대신 아래 내용이 필수
    - 강력한 일관성, 디스크I/O최소화, 매우 높은 가용성, 증분백업(최근 시점 기준으로 변경된 부분만 저장하는 방식)

#### **데이터 모델**

- 파티션 키: 데이터를 여러 노드에 분산하는 구실
- 클러스터 키: 같은 파티션에 속한 데이터를 정렬하는 구실
- 사용되는 질의는 다음과 같다.
  - 특정 사용자의 모든 폴더 질의
  - 특정 폴더에 속한 모든 이메일 표시
  - 이메일 생성/삭제/수신
  - 읽은, 또는 읽지 않은 모든 메일

#### **일관성 문제**

- 장애가 발생하면 클라이언트는 다른 사본을 통해 주 사본이 복원될 때까지 동기화/갱신 작업을 완료할 수 없다.
- 데이터 일관성을 위해 가용성을 희생한다. CAP 원리를 말한다 근데 분할내성(P)은 무조건 적으로 가져가야하기 때문에 사실상 2가지 선택지다

### **이메일 전송 가능성**

- 보통 새로 생긴 서버는 평판이 없어서 인터넷에서 스팸으로 분류가 된다. 그래서 아래와 같은 것을 하면 평판을 늘릴 수 있다
- 전용 IP: 이메일을 보낼 때 전용 IP를 사용하는 것이 좋다.
- 범주화: 범주가 다른 이메일은 다른 IP 주소를 통해 보내는 것이 좋다.
- 발신인 평판: 새로운 이메일 서버의 IP 주소는 사용 빈도를 서서히 올리는 것이 좋다.
- 스팸 발송자의 신속한 차단: 스팸을 뿌리는 사용자를 신속히 차단한다.
- 피드백 처리: ISP 측에서의 피드백을 쉽게 받아 처리할 수 있는 경로를 만드는 것이 중요하다.
  - 불만 접수가 생기면 아래 반송이 생길 수 있다
    - 경성반송 : 수신인의 이메일이 달라서 ISP가 전달을 거부
    - 연성반송 : ISP 측 문제로 일시적으로 이메일 전송이 안된 경우
    - 불만신고 : 수신인이 스팸으로 박은 것
- 이메일 인증: ISP와 좋은 관계를 유지할 필요가 있다.

### **검색**

- 이메일 시스템의 검색 기능에서는 쓰기 연산이 읽기 연산보다 훨씬 많이 발생한다.

#### **방안1: ElasticSearch**

- 사용자는 검색 버튼을 누른 후 다음 결과가 수신될 때까지 기다린다. (동기 방식)
- ElasticSearch는 이메일 검색에 필요한 텍스트 기반 검색을 잘 지원한다.
- 주 이메일 저장소와 동기화를 맞추는 부분이 까다롭다.

#### **방법2: 맞춤형 검색 솔루션**

- 대규모 이메일 서비스 사업자는 보통 자기 제품에 고유한 요구사항을 만족시키기 위해 검색 엔진을 자체적으로 개발해 사용한다.

### **규모 확장성 및 가용성**

- 시스템의 대부분 컴포넌트는 수평적으로 규모 확장이 가능할 것으로 기대할 수 있다.
- 가용성을 향상시키기 위해 데이터를 여러 데이터센터에 다중화하는 것이 필요하다.
