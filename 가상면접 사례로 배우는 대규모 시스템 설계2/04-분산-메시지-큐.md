## 1. 왜 메시지 큐인가

| 이점 | 내용 |
|---|---|
| **결합도 완화** | 컴포넌트 사이 강결합을 느슨하게 |
| **규모 확장성 개선** | 트래픽에 맞춰 생산자·소비자를 따로 스케일링 |
| **가용성 개선** | 한쪽이 멈춰도 다른 쪽은 계속 동작 |
| **성능 개선** | 비동기 통신 가능 |

- 유명한 분산 메시지 큐: 아파치 카프카 · RocketMQ · RabbitMQ · 펄사 · ActiveMQ · ZeroMQ

| 구분 | 예 |
|---|---|
| **메시지 큐** | RocketMQ, ActiveMQ, RabbitMQ, ZeroMQ |
| **이벤트 스트리밍 플랫폼** | 카프카, 펄사 |

> 💡 둘이 지원하는 기능이 서로 수렴하면서 차이가 점점 희미해지고 있다. 이번 설계는 **보관·순서·반복 소비**를 지원하므로 스트리밍 플랫폼 쪽(카프카)에 가깝다.

## 2. 요구사항

### 2-1. 기능 요구사항
- 생산자는 메시지를 보내고, 소비자는 메시지를 받는다.
- 메시지는 **반복 수신**도, **단 한 번 수신**도 설정할 수 있어야 한다.
- 오래된 이력 데이터는 삭제될 수 있다. (보관 기간 **2주**)
- 메시지 크기는 **KB 수준**, 텍스트 메시지만.
- **생산된 순서대로** 소비자에게 전달.
- 전달 방식은 **최소 한 번 / 최대 한 번 / 정확히 한 번** 가운데 설정 가능.
- 생산자·소비자는 많을수록 좋다.

### 2-2. 비기능 요구사항
- **높은 대역폭 vs 낮은 전송 지연** 중 하나를 설정으로 고를 수 있어야 한다.
- **규모 확장성** — 메시지 양이 급증해도 처리 (분산 시스템).
- **지속성·내구성** — 데이터는 디스크에 보관하고 여러 노드에 복제.

### 2-3. 전통적 메시지 큐와 다른 점

| 항목 | 전통적 메시지 큐 | 이번 설계 |
|---|---|---|
| 메시지 보관 | 중요하게 다루지 않음. 전달될 동안만 **메모리**에 | **디스크**에 2주 보관 |
| 전달 순서 | 보존하지 않음 | 생산 순서대로 |

## 3. 개략적 설계

[🖼️ 원본 이미지: 메시지 큐의 핵심 컴포넌트 — 생산자 · 메시지 큐 · 소비자]

- **생산자**는 메시지를 큐에 **발행**하고, **소비자**는 큐를 **구독**해 메시지를 소비한다.
- 메시지 큐는 둘 사이 결합을 느슨하게 해 **독립적인 운영·확장**을 가능하게 한다.
- 클라이언트/서버 관점에서 생산자·소비자는 **클라이언트**, 메시지 큐는 **서버**이고 네트워크로 통신한다.

### 3-1. 메시지 모델

| 모델 | 동작 | 특징 |
|---|---|---|
| **일대일** | 큐의 메시지는 **오직 한 소비자**만 가져간다. 가져갔다고 알리면 큐에서 **삭제** | 전통적 큐의 모델. **데이터 보관 미지원** |
| **발행-구독** | 메시지를 **토픽**에 보내고 받는다. 토픽의 모든 메시지는 그 토픽을 구독한 **모든 소비자**에게 전달 | 한 메시지를 여러 곳이 받음 |

[🖼️ 원본 이미지: 일대일 모델]
[🖼️ 원본 이미지: 발행-구독 모델]

> 💡 이번 설계는 **2주 보관 지속성 계층**을 두어, 일대일 모델에서도 메시지를 **반복 소비**할 수 있게 한다.

### 3-2. 토픽 · 파티션 · 브로커

[🖼️ 원본 이미지: 파티션]

| 용어 | 뜻 |
|---|---|
| **토픽** | 메시지가 보관되는 이름 붙은 통 |
| **파티션** | 토픽이 서버 한 대로 감당이 안 될 때 쪼갠 조각 (= **샤딩**). 메시지를 파티션에 균등하게 분배 |
| **브로커** | 파티션을 유지하는 서버. 파티션을 브로커에 고르게 흩어 **규모 확장성** 달성 |
| **오프셋** | 파티션 안에서의 메시지 위치. 각 파티션은 **FIFO 큐**처럼 동작 |
| **메시지 키** | 같은 키 → **같은 파티션**. 키가 없으면 무작위 파티션 |

### 3-3. 소비자 그룹

[🖼️ 원본 이미지: 소비자 그룹]

- 그룹 안의 소비자는 **협력**해서 토픽을 소비한다. 한 그룹은 여러 토픽을 구독할 수 있고, **오프셋을 그룹별로 따로** 관리한다.
- 같은 그룹 소비자가 병렬로 읽으면 대역폭은 좋지만, **같은 파티션의 순서**가 깨질 수 있다.
  - 해결: **한 파티션은 그룹 안에서 오직 한 소비자만** 읽게 한다.
  - 이 제약 아래 모든 소비자를 한 그룹에 두면 → 결국 **일대일 모델**과 같아진다.

### 3-4. 개략적 설계안

[🖼️ 원본 이미지: 개략적 설계안]

| 영역 | 컴포넌트 | 역할 |
|---|---|---|
| 클라이언트 | **생산자** | 메시지를 특정 토픽으로 보냄 |
| | **소비자 그룹** | 토픽을 구독하고 메시지 소비 |
| 핵심 서비스 | **브로커** | 파티션 유지 (파티션 = 특정 토픽 메시지의 부분 집합) |
| 저장소 | **데이터 저장소** | 메시지를 파티션 단위로 보관 |
| | **상태 저장소** | 소비자 상태(소비자 쪽 **오프셋**) 보관 |
| | **메타데이터 저장소** | 토픽 설정·속성 보관 |
| 조정 서비스 | **서비스 탐색** | 어떤 브로커가 살아 있는지 |
| | **리더 선출** | 브로커 중 하나를 **컨트롤러**로 선출 (클러스터당 활성 컨트롤러 1개, 파티션 배치 책임). 보통 **주키퍼·etcd** 사용 |

## 4. 상세 설계 — 저장소와 메시지

상세 설계의 세 가지 방향:
1. **디스크 기반 자료 구조** 활용
2. 생산자→소비자까지 **수정되지 않는 메시지 자료 구조**
3. **일괄 처리 우선** 시스템

<details>
<summary>디스크 기반 자료구조 (참고: 회전 디스크 · B+Tree · LSM)</summary>

- **회전 디스크** — LP판 위 바늘처럼, 바늘이 가리키는 곳에서 읽고 쓴다. **탐색 시간(바늘 이동)**이 병목이라 **랜덤 I/O가 비효율**적이다. 이진 탐색처럼 여기저기 뛰면 성능이 크게 떨어진다. 바늘이 한 번 움직이면 디스크 최소 읽기 단위만큼 데이터를 퍼온다.
- **B+Tree** — B-Tree는 모든 노드에 데이터를 두지만, B+Tree는 **리프에만 실제 데이터**를 두고 브랜치 노드에는 위치 정보만 둬서 **차수↑ → 높이↓ → I/O↓**. 리프끼리 연결돼 있어 **범위 탐색**도 쉽다.
- **LSM** — 메모리의 **Memtable**에 추가 전용으로 쌓다가 꽉 차면 **SSTable**로 flush. 읽을 땐 Memtable → (블룸 필터로 거른) SSTable 순. SSTable이 많아지면 **병합(compaction)**.

| 병합 방식 | 방법 | 장점 | 단점 |
|---|---|---|---|
| 크기 기반 | 비슷한 크기 SSTable끼리 합침 | 쓰기 매우 빠름 | SSTable이 흩어져 검색 느림, 디스크 여유 공간 필요 |
| 레벨 기반 | 계층별로, 레벨이 차면 다음 레벨과 병합 | 레벨당 파일 하나만 찾으면 돼 읽기 빠름 | 정렬하느라 I/O 많음 |
| 시간 범위 기반 | 같은 시간대 SSTable끼리 묶음 | 시계열에 최적, 오래된 시간대 파일째 삭제 | 일반 CRUD 트랜잭션엔 부적합 |
| FIFO 압축 | 병합을 거의 안 하고 용량·보존기한 지나면 SSTable째 버림 | 디스크 I/O 오버헤드 없음 | 데이터 삭제됨, 공간 낭비 방치 |

</details>

### 4-1. 데이터 저장소

메시지 데이터의 접근 패턴: **읽기·쓰기 빈번 · 갱신/삭제 없음 · 대부분 순차 읽기/쓰기**.

| 선택지 | 방식 | 판단 |
|---|---|---|
| **데이터베이스** | RDB: 토픽별 테이블(행 1 = 메시지 1) / NoSQL: 토픽별 컬렉션(문서 1 = 메시지 1) | ❌ 대규모 읽기·쓰기를 동시에 감당하는 DB 설계가 어렵다 |
| **쓰기 우선 로그(WAL)** ✅ | 새 항목이 **추가되기만 하는 일반 파일** | 읽기·쓰기 모두 **순차 접근** → 디스크에 딱 맞음 |

- **로그 파일 줄 번호 = 오프셋**.
- 파일은 **세그먼트** 단위로 나눈다 (파티션 안의 조각).
  - 활성 세그먼트에만 쓰고, 한계에 도달하면 **비활성화 → 새 세그먼트 생성·활성화** (= **세그먼트 롤링**).
  - 비활성 세그먼트는 읽기에만 쓰인다.
- 회전 디스크 기반 저장장치는 **용량 대비 싸다**.

> 💡 **디스크 성능 유의사항** — 순차 접근을 적극 활용하면 디스크로도 **수백 MB/s** 읽기·쓰기가 나온다 (랜덤 접근은 느림). WAL은 **OS 디스크 캐시(페이지 캐시)**를 적극 활용해 가용 메모리 전부를 캐시로 쓴다.

### 4-2. 메시지 자료 구조

메시지 자료 구조는 **생산자 · 메시지 큐 · 소비자 사이의 계약**이다. 전달 도중 바뀌지 않아야 불필요한 복사가 없다.

| 필드 | 뜻 |
|---|---|
| **키** | 파티션을 정할 때 사용. 같은 키 → 같은 파티션, 없으면 무작위 |
| **값** | 메시지 내용(페이로드). 일반 텍스트 또는 압축된 이진 블록 |
| **토픽** | 메시지가 속한 토픽 이름 |
| **파티션** | 메시지가 속한 파티션 ID |
| **오프셋** | 파티션 안 위치. **토픽 + 파티션 + 오프셋**이면 메시지를 찾을 수 있다 |
| **타임스탬프** | 메시지가 저장된 시각 |
| **크기** | 메시지 크기 |
| **CRC** | 순환 중복 검사. 데이터 **무결성** 보장 |

<details>
<summary>대역폭 줄이는 법 (참고: 배치 · 종단 간 압축 · 제로 카피)</summary>

- 대역폭 = 데이터가 이동하는 고속도로의 폭. 대규모 시스템은 **인바운드보다 아웃바운드가 크다** (한 메시지를 여러 소비자가 읽으니까).
- **배치 처리** — 생산자가 모아서 보낸다.
- **End-to-End 압축** — 생산자가 압축해서 보내고 → 브로커는 압축 덩어리 **그대로** 세그먼트에 저장 → 소비자가 스스로 푼다.
- **Zero-Copy** — 세그먼트 파일을 네트워크로 내보낼 때

| 방식 | 경로 |
|---|---|
| 보통 | 디스크 → 커널 → 애플리케이션(RAM) → 커널 → 네트워크 카드 |
| 제로 카피 | 디스크 → 커널 → 네트워크 카드 |

</details>

### 4-3. 일괄 처리

생산자·소비자·메시지 큐 모두 **가급적 일괄 처리**한다. 이유:
- 여러 메시지를 **한 번의 네트워크 요청**으로 → 네트워크 왕복 비용↓
- 브로커가 여러 메시지를 한 번에 로그에 기록 → **더 큰 순차 쓰기** + OS 페이지 캐시에서 **더 큰 연속 공간** 점유 (건건이 쓰면 흩어지고, 배치는 효율적)
- 처리량을 더 올리려면 **파티션 수를 늘린다**.

> ⚖️ 일괄 처리 크기를 키우면 **대역폭↑ · 지연↑**. 요구사항의 "대역폭 vs 지연 선택"이 여기서 조절된다.

## 5. 상세 설계 — 생산자·소비자 흐름

### 5-1. 생산자 측 작업 흐름

[🖼️ 원본 이미지: 라우팅 계층]

**처음 안 (라우팅 계층 별도)**
1. 생산자가 메시지를 **라우팅 계층**으로 보낸다.
2. 라우팅 계층은 메타데이터 저장소의 **사본 분산 계획**을 읽어 캐시해 두고, 메시지를 해당 파티션(예: 파티션-1)의 **리더 사본**(예: 브로커-1)에 보낸다.
3. 리더가 메시지를 받고, **팔로워 사본**들은 리더에게서 데이터를 가져간다.
4. 충분한 수의 사본이 동기화되면 리더가 **커밋**(디스크 기록)한다. 카프카는 디스크 캐시(RAM)에 커밋하고 flush는 OS가 한 번에 처리한다.

- 복제하는 이유: **장애 내성(fault tolerance)**.
- 문제점: 라우팅 계층이라는 **노드가 하나 더** 생겨 오버헤드 · **배치 처리 없음**.

[🖼️ 원본 이미지: 생산자 측 버퍼 및 라우팅 (수정본)]

**수정 안 — 라우팅을 생산자 안으로 + 버퍼 도입**
- 네트워크 홉이 줄어 **전송 지연↓**.
- 생산자가 **어느 파티션에 보낼지 자기 로직**을 가질 수 있다.
- 메시지를 **버퍼 메모리**에 모았다가 일괄 전송 → **대역폭↑**.

### 5-2. 소비자 측 작업 흐름
- 소비자는 **특정 파티션의 오프셋**을 주고, 그 위치부터 이벤트를 **묶어서** 가져온다.

### 5-3. 푸시 vs 풀

| | 푸시 (브로커 → 소비자) | 풀 (소비자 ← 브로커) ✅ |
|---|---|---|
| 지연 | 받는 즉시 보내므로 **낮음** | 소비자가 가져갈 때까지 |
| 속도 결정 | **생산자**가 좌우 → 소비자가 느리면 **과부하**, 항상 그만큼 자원 준비 필요 | **소비자**가 결정 → 느리면 소비자를 늘리거나 따라잡을 때까지 기다리면 됨 |
| 일괄 처리 | 불리 | **적합** |
| 단점 | | 메시지가 없는데 계속 당기면 자원 낭비 → **롱 폴링**(없으면 일정 시간 대기)으로 완화 |

[🖼️ 원본 이미지: 풀 모델]

**풀 모델 흐름**
1. 그룹-1에 합류해 토픽-A를 구독하려는 새 소비자가 **그룹 이름을 해싱**해 접속할 브로커(**코디네이터**)를 찾는다. 같은 그룹 소비자는 같은 브로커로 간다.
2. 코디네이터가 소비자를 그룹에 넣고 **파티션-2를 할당**한다.
3. 소비자는 **마지막으로 소비한 오프셋 이후** 메시지를 가져온다.
4. 처리 후 **새 오프셋을 브로커에 커밋**한다.

### 5-4. 소비자 재조정
- **어떤 소비자가 어떤 파티션을 맡을지 다시 정하는** 과정. 소비자가 추가·이탈·장애로 바뀔 때 일어난다.
- **코디네이터** = 재조정을 위해 소비자들과 통신하는 브로커 노드.
  - **박동 신호(heartbeat)**가 끊기면 장애로 감지 → 재조정 시작 → 파티션 재배치.

## 6. 상세 설계 — 상태·메타데이터·복제

### 6-1. 상태 저장소 vs 메타데이터 저장소

| | 상태 저장소 | 메타데이터 저장소 |
|---|---|---|
| 담는 것 | 소비자↔파티션 배치 관계, 그룹별·파티션별 **마지막 소비 오프셋** | 토픽 설정·속성 (예: "'결제_로그' 토픽은 파티션 50개", "메시지 최대 1MB") |
| 접근 패턴 | 읽기·쓰기 **빈번**하지만 양은 적음, **갱신 잦고** 삭제 거의 없음, **무작위** 읽기·쓰기 | **자주 안 바뀌고** 양도 적음 |
| 요구 | **일관성** 중요 | **높은 일관성** |
| 적합한 것 | | **주키퍼** |

### 6-2. 주키퍼
- **계층적 키-값 저장소**를 제공하는, 분산 시스템의 필수 서비스.

| 용도 | 뜻 |
|---|---|
| 분산 설정 서비스 | 클러스터 전체가 공유할 '마스터 설정' 보관·전파 → **메타데이터 저장소** 역할 |
| 동기화 서비스 | 여러 서버가 동시에 같은 데이터를 고칠 때 **락**을 걸고 순서를 정함 |
| 이름 레지스트리 | 서버들의 IP·상태를 기록하는 '출석부' |

- 브로커 클러스터의 **리더(컨트롤러) 선출**을 돕는다.

### 6-3. 복제
- **높은 가용성**을 위한 방법.
- 생산자 → **리더에게만** 보냄 → 팔로워 사본은 리더에게서 새 메시지를 **계속 가져와 동기화** → 일정 개수 이상 동기화되면 리더가 생산자에게 응답.
- **사본 분산 계획** — 조정 서비스로 브로커 하나가 리더(컨트롤러)로 선출되면, 그 브로커가 사본 분산 계획을 만들어 **메타데이터 저장소**에 보관하고, 다른 브로커들은 그 계획대로 움직인다.

### 6-4. 사본 동기화 (ISR)
- **ISR(In-Sync Replicas)** = 리더와 동기화된 사본 집합. **성능과 영속성 사이의 타협점**이다.
- 리더는 항상 ISR에 속한다.
- 느린 사본까지 전부 기다리면, 사본 하나만 느려도 **파티션 전체가 느려지거나 멈춘다** → 그래서 "동기화된 것들"만 기다린다.

| 설정 | 생산자가 ACK를 받는 시점 | 특징 |
|---|---|---|
| **ACK=all** | **모든 ISR**이 받은 뒤 | 가장 안전, 가장 느림 |
| **ACK=1** | **리더가 저장**하면 바로 | 중간 |
| **ACK=0** | 기다리지 않음, **재시도도 없음** | 가장 빠름, 유실 가능 |

## 7. 규모 확장성 · 전달 방식 · 고급 기능

### 7-1. 규모 확장성

| 대상 | 확장 방법 |
|---|---|
| **생산자** | 그룹 조정에 가담할 필요가 없어 그냥 추가·삭제 |
| **소비자** | 그룹 내 추가·삭제·장애 → **재조정**이 처리 (확장성 + 결함 내성) |
| **브로커** | 노드 추가·삭제 시 **사본 재배치**. 이때 컨트롤러가 **설정보다 많은 사본을 한시적으로 허용** → 도중 데이터 손실 방지 |
| **파티션** | 수를 바꿔도 생산자·소비자 안정성엔 영향 없음. 늘리면 간단히 토픽 확장. 제거될 땐 재조정 필요 |

### 7-2. 메시지 전달 방식

| 방식 | 의미 | 설정 |
|---|---|---|
| **최대 한 번** | 소실돼도 다시 보내지 않음 (중복 없음, 유실 가능) | ACK=0 |
| **최소 한 번** | 중복은 있을 수 있지만 소실은 없음 | ACK=1, ACK=all |
| **정확히 한 번** | 중복도 소실도 없음. 같은 입력에 항상 같은 결과를 내지 않는(**멱등하지 않은**) 시스템과 연동할 때 특히 중요 | |

### 7-3. 고급 기능
- **메시지 필터링**
  1. 소비자가 다 받고 필요 없는 걸 버린다.
  2. 브로커에서 걸러 소비자는 원하는 것만 받는다.
  3. 메시지에 **태그 필드**가 있으면 브로커가 그걸로 필터링할 수 있다.
- **지연 전송 · 예약 전송**
  - 메시지를 바로 토픽에 넣지 않고 브로커 내부 **임시 저장소**에 두었다가 시간이 되면 토픽으로 옮긴다.
  - 예약 전송(지정 시각에 보내기)도 설계 철학은 같다.

## 🔁 셀프 체크
1. 메시지 저장소로 DB 대신 **WAL(추가 전용 로그)**을 고른 이유는?
2. 소비자 그룹에서 **"한 파티션은 그룹 안에서 한 소비자만"** 제약을 두는 이유와, 그 결과 모든 소비자를 한 그룹에 넣으면 어떤 모델이 되는가?
3. ACK=0 / ACK=1 / ACK=all 의 차이와, 각각 어떤 메시지 전달 방식에 대응하는가?

<details>
<summary>답</summary>

1. 메시지 데이터는 **갱신·삭제가 없고 읽기·쓰기가 대부분 순차적**이다. WAL은 새 항목을 끝에 추가하기만 하는 파일이라 읽기·쓰기 모두 **순차 접근**이 되고, 디스크로도 수백 MB/s가 나오며 OS 페이지 캐시도 잘 탄다. 로그 줄 번호를 그대로 **오프셋**으로 쓰고 세그먼트 롤링으로 관리하면 된다. DB로는 이런 대규모 읽기·쓰기 패턴을 감당하는 설계가 어렵다.
2. 같은 그룹 소비자가 한 파티션을 병렬로 읽으면 **파티션 내 순서**가 깨진다. 그래서 한 파티션은 그룹 내 한 소비자만 읽게 한다. 이 제약 아래 모든 소비자를 한 그룹에 넣으면 메시지 하나를 오직 한 소비자만 가져가므로 **일대일 모델**과 같아진다.
3. **ACK=0**은 확인을 기다리지 않고 재시도도 없어 **최대 한 번**(빠르지만 유실 가능). **ACK=1**은 리더 저장 후, **ACK=all**은 모든 ISR이 받은 후 응답하며 재전송이 가능해 **최소 한 번**(유실 없음, 중복 가능). ACK=all이 가장 안전하고 느리다.

- 메시지 큐와 이벤트 스트리밍 플랫폼 사이의 차이는 지원하는 기능이 서로 수렴하면서 희미해지고 있다.

  - **스트리밍 플랫폼** : 카프카, 펄사

**문제 이해 및 설계 범위 확정**

**기능 요구사항**
- 생산자는 메시지 큐에 메시지를 보낼 수 있어야 한다.
- 소비자는 메시지 큐를 통해 메시지를 수신할 수 있어야 한다.
- 메시지는 반복적으로 수신할 수도 있어야 하고, 단 한 번만 수신하도록 설정될 수도 있어야 한다.
- 오래된 이력 데이터는 삭제될 수 있다.
- 지속성은 2주 지속성 보관 보장 안함 
- 메시지 크기는 KB 수준이고 텍스트 메시지만 지원
- 메시지가 생산된 순서대로 소비자에게 전달할 수 있어야 한다.
- 메시지 전달 방식은 최소 한 번, 최대 한 번, 정확히 한 번 가운데 설정할 수 있어야 한다.
- 프로듀서 컨슈머는 많을 수록 좋다

**비기능 요구사항**
- 높은 대역폭과 낮은 전송 지연 가운데 하나를 설정으로 선택 가능하게 하는 기능
- 규모 확장성 : 메시지 양이 급증해도 처리 가능해야 한다. (분산 시스템)
- 지속성 및 내구성 : 데이터는 디스크에 지속적으로 보관되어야 하며, 여러 노드에 복제되어야 한다.

**전통적 메시지 큐와 다른 점**
- 전통적 메시지 큐
  - 메시지 보관 문제를 중요하게 다루지 않는다.
  - 메시지가 소비자에게 전달되기 충분한 기간 동안만 메모리에 보관한다.
  - 메시지 전달 순서를 보존하지 않는다.

**개략적 설계안 제시 및 동의 구하기**

[🖼️ 원본 이미지: 메시지 큐의 핵심 컴포넌트]

메시지 큐의 핵심 컴포넌트
- 생산자는 메시지를 메시지 큐에 발행
- 소비자는 큐를 구독하고 구독한 메시지를 소비
- 메시지 큐는 생산자와 소비자 사이의 결합을 느슨하게 하는 서비스로, 생산자와 소비자의 독립적인 운영 및 규모 확장을 가능하게 하는 역할 담당
- 생산자와 소비자는 모두 클라이언트/서버 모델 관점에서 보면 클라이언트고 서버 역할을 하는 것은 메시지 큐이며 이 클라이언트와 서버는 네트워크를 통해 통신

**메시지 모델**
- **일대일 모델**

  [🖼️ 원본 이미지: 일대일 모델]

  일대일 모델
  - 전통적인 메시지 큐에서 흔히 발견되는 모델이다.
  - 큐에 전송된 메시지는 오직 한 소비자만 가져갈 수 있다.
    - 어떤 소비자가 메시지를 가져갔다는 사실을 큐에 알리면 해당 메시지는 큐에서 삭제된다.
  - 데이터 보관을 지원하지 않는다.
    - 본 설계안은 메시지를 2주 동안은 보관할 수 있도록 하는 지속성 계층을 포함하며, 해당 계층을 통해 메시지가 반복적으로 소비될 수 있도록 한다.
- **발행-구독 모델**

  [🖼️ 원본 이미지: 발행-구독 모델]

  발행-구독 모델
  - 메시지를 보내고 받을 때는 토픽에 보내고 받게 된다.
  - 토픽에 전달된 모든 메시지는 해당 토픽을 구독하는 모든 소비자에게 전달된다.

**토픽, 파티션, 브로커**

메시지는 토픽에 보관된다.

[🖼️ 원본 이미지: 파티션]

파티션
- 토픽에 보관되는 데이터의 양이 커져서 서버 한 대로 감당하기 힘들어지면, 파티션(partion), 즉 샤딩(sharding) 기법을 활용할 수 있다.
- 토픽을 여러 파티션으로 분할하여 메시지를 모든 파티션에 균등하게 나눠 보낸다.
- 파티션은 메시지 큐 클러스터 내의 서버에 고르게 분산 배치한다.
- 파티션을 유지하는 서버는 보통 브로커(broker)라 부른다.
- 파티션을 브로커에 분산함으로써 높은 규모 확장성을 달성할 수 있다.
- 각 토픽 파티션은 FIFO 큐처럼 동작한다.
- 파티션 내에서의 메시지 위치는 오프셋(offset)이라고 한다.
- 메시지에 키를 붙일 수 있는데, 같은 키를 가진 모든 메시지는 같은 파티션으로 보내지고, 키가 없는 메시지는 무작위로 선택된 파티션으로 전송된다.

**소비자 그룹**

[🖼️ 원본 이미지: 소비자 그룹]

소비자 그룹
- 소비자 그룹 내 소비자는 토픽에서 메시지를 소비하기 위해 서로 협력한다.
- 하나의 소비자 그룹은 여러 토픽을 구독할 수 있고, 오프셋을 별도로 관리한다.
- 같은 그룹 내의 소비자는 메시지를 병렬로 소비할 수 있다.
- 데이터를 병렬로 읽으면 대역폭 측면에서는 좋지만 같은 파티션 안에 있는 메시지를 순서대로 소비할 수는 없다.
  - 어떤 파티션의 메시지는 한 그룹 안에서는 오직 한 소비자만 읽을 수 있도록 하면 해결할 수 있다.
  - 위 제약사항을 도입한 후 모든 소비자를 같은 소비자 그룹에 두면 같은 파티션의 메시지는 오직 한 소비자만 가져갈 수 있으므로 결국 일대일 모델에 수렴하게 된다.

**개략적 설계안**

[🖼️ 원본 이미지: 개략적 설계안]

개략적 설계안
- 클라이언트
  - `생산자`: 메시지를 특정 토픽으로 보낸다.
  - `소비자 그룹`: 토픽을 구독하고 메시지를 소비한다.
- 핵심 서비스 및 저장소
  - `브로커`: 파티션을 유지한다. 하나의 파티션은 특정 토픽에 대한 메시지의 부분 집합을 유지한다.
- 저장소
  - `데이터 저장소`: 메시지는 파티션 내 데이터 저장소에 보관된다.
  - `상태 저장소`: 소비자 상태는 이 저장소에 유지된다.(소비자쪽 오프셋을 기억하는 공간)
  - `메타데이터 저장소`: 토픽 설정, 토픽 속성 등은 이 저장소에 유지된다.
- 조정 서비스
  - `서비스 탐색`: 어떤 브로커가 살아있는지 알려준다.
  - `리더 선출`: 브로커 가운데 하나는 컨트롤러 역할을 담당해야 하며, 한 클러스터에는 반드시 활성 상태 컨트롤러가 하나 있어야 한다. 이 컨트롤러가 파티션 배치를 책임진다.
  - 아파치 주키퍼나 etcd가 보통 컨트롤러 선출을 담당하는 컴포넌트로 널리 이용된다.

**상세 설계**
- 디스크 기반 자료 구조를 활용한다.
- ▸ **디스크 기반 자료구조** (토글)
  - 회전 디스크 : LP판에 바늘 → 바늘이 향한 곳에서 데이터 읽/쓰
    - 탐색시간 병목 + I/O 의 비효율성
  - 이진 탐색 사용하면 성능 박살(바늘을 새로 움직여야 하니깐)
    - 바늘 움직이면 디스크가 읽는 최소 단위 만큼 데이터를 퍼오기
  - 대표 디스크 기반 자료구조 2가지
    - ▸ **B+Tree** (토글)

      B+Tree가 깊게 내려갈 수록 I/O가 늘어나는데<br>
      이걸 막기 위해서<br>
      기존 B-Tree는 모든 노드에 데이터를 넣어 두었다면<br>
      B+Tree는 가장 밑 리프 노드에만 실제 데이터를 넣어주도<br>
      그 사이 브랜치 노드에는 실데이터가 아닌 데이터의 위치를 넣어 두어 차수를 늘려서 탐색할 수 있는 높이를 줄여 I/O를 줄일 수 있고 가장 밑 리프 노드 끼리는 또 연결되어 있어서 옆으로도 탐색이 가능 즉 범위 탐색도 기존 B-Tree 대비 쉽다
    - ▸ **LSM** (토글)
      - 먼저 메모리 속 Memtable에 Append-only방식으로 쌓아 올리기
      - Memtable이 꽉차면 SSTable로 flush를 한다
      - 읽을 때 먼저 Memtable보고 없으면 블룸필터 써서 있을 거 같은 SSTable 파일들을 뒤지고 거기서 데이터를 가져온다 
      - 나중에 SSTable이 너무 많아지면 과거 데이터들을 새로운 SSTable로 병합을 한다 
        - 병합 방법 4가지
          - 크기기반
            - 비슷한 크기의 SSTable을 합쳐서 더 큰 SSTable로 병합
              - 장 : 쓰기 속도가 매우 빠르다
              - 단 : SSTable이 흩어져 있는 경우가 많아 검색이 느림 + 디스크의 여유공간이 필요
          - 레벨기반
            - SSTable을 여러 계층으로 나눠 각 레벨이 차면 다음 레벨과 병합하는 방식
              - 장 : 레벨 기준으로 파일 하나만 찾으면 되어서 속도가 빠름
              - 단 :  단 정렬하느라 I/O가 많이 발생해서 성능은 떨어짐
          - 시간범위기반
            - 데이터가 들어온 시간을 기준으로 버킷을 만들고 같은 시간대 SSTable끼리만 묶는 방식
              - 장 : 시계열 데이터 처리에 최적화<br>데이터 버릴 때도 가장 오래된 시간대 파일을 버릴 수 있다 
              - 단 : 일반적인 CRUD 트랜잭션엔 부적합
          - FIFO 압축
            - 물리적인 데이터 병합 과정 거의 포기 + 용량이나 보존기한이 지나면 FIFO 방식으로 SSTable자체를 버리는 방식
              - 디스크 I/O 오버헤드가 없지만 데이터가 삭제됨
              - 단 : 공간 낭비 방치 
- 생산자부터 소비자까지 전달되는 과정에서 데이터가 수정되지 않도록 하는 메시지 자료 구조를 설계하고 활용한다.
- 일괄 처리를 우선하는 시스템을 설계한다.

**데이터 저장소**
- 읽기/쓰기가 빈번하게 일어난다.
- 갱신/삭제 연산은 발생하지 않는다.
- 순차적인 읽기/쓰기가 대부분이다.

> **선택지1: 데이터베이스**

- `관계형 데이터베이스`: 토픽별로 테이블을 만든다. 행 하나 = 1개의 메시지
- `NoSQL 데이터베이스`: 토픽별로 컬렉션을 만든다. 문서 하나 = 1개의 메시지
- 데이터베이스로는 본 설계안이 필요로 하는 데이터 사용 패턴을 지원하기 어렵다.
  - 설계가 어려워서(대규모 읽기 쓰기 연산이 대규모로 발생하는 DB 설계)

> **선택지2: 쓰기 우선 로그(WAL)**

- `WAL(Write-Ahead Log)`은 새로운 항목이 추가되기만 하는 일반 파일이다.
- WAL에 대한 접근 패턴은 읽기/쓰기 전부 순차적이다.<br>(지속성 보장 메시지는 디스크에 WAL로 보관하기)
- 회전신 디스크 기반 저장장치는 비용이 싸다 용량대비
- 로그 파일 줄 번호 = 오프셋으로 사용 단위는 세그먼트로 
  - 세그먼트(파티션 속에 있는 것)
    - 메시지가 계속 들어오고 세그먼트 한계에 도달하면 비활성화한다<br>대신 새로운 세그먼트를 만들고 활성화하고 거기에 메시지를 넣는다<br>비활성화 된 거는 읽기할 때도 사용한다  <br>(이 과정 세그먼트 롤링)

**디스크 성능 관련 유의사항**
- 데이터 장기 보관에 대한 요구사항 때문에 디스크 드라이브를 활용하여 다량의 데이터를 보관한다.
- 순차적 데이터 접근 패턴을 적극 활용하는 디스크 기반 자료 구조를 사용하면, 수백 MB/sec 수준의 읽기/쓰기 성능을 달성할 수 있다.(단 랜덤으로 데이터 접근하면 느려진다)
- WAL도 OS가 제공하는 디스크 캐시 기능을 적극적으로 활용한다.<br>가용한 메모리 전부를 디스크 데이터 캐시 활용

**메시지 자료 구조**
- 메시지 자료 구조는 생산자, 메시지 큐, 그리고 소비자 사이의 계약이다.
- ▸ **대역폭** (토글)
  - 데이터가 이동하는 고속도로의 넓이
  - 대규모 시스템에서는 인바운드 대비 아웃바운드가 크다
    - 해결책
      - 배치처리 : 프로듀서가 배치처리를 한다
      - End-to-End 압축
        - 프로듀서 : 압축해서 데이터 쏘기
        - 브로커 : 압축된 덩어리 그대로 SSTable/세그먼트에 저장
        - 소비자 : 압축된 데이터 가져와서 스스로 압축을 푼다 
      - Zero-Copy 기술 
        - 세그먼트 파일을 네트워크로 내보내려면
          - 보통 : 디스크 ➡️ 커널 ➡️ 애플리케이션(RAM) ➡️ 커널 ➡️ 네트워크 카드
          - 제로카피 : 디스크 ➡️ 커널 ➡️ 네트워크 카드

**메시지 키**
- 메시지의 키는 파티션을 정할 때 사용된다.
- 키가 주어지지 않은 메시지의 파티션은 무작위로 결정된다.<br>(같은 메시지 키를 가지는 메시지는 같은 파티션에 들어감)

**메시지 값**
- 메시지 값은 메시지의 내용(페이로드)이다.
- 메시지 값은 일반 텍스트일수도, 압축된 이진 블록일수도 있다.

**메시지의 기타 필드**
- `토픽`: 메시지가 속한 토픽의 이름
- `파티션`: 메시지가 속한 파티션의 ID
- `오프셋`: 파티션 내 메시지의 위치, 메시지는 토픽, 파티션, 오프셋 3가지 정보를 알면 찾을 수 있다.
- `타임스탬프`: 메시지가 저장된 시각이다.
- `크기`: 메시지의 크기이다.
- `CRC`: 순환 중복 검사의 약자로, 주어진 데이터의 무결성을 보장하는 데 이용된다.

**일괄 처리**
- 일괄 처리는 본 설계안에서 광범위하게 사용된다.
- 생산자, 소비자, 메시지 큐는 메시지를 가급적 일괄 처리한다.
- 일괄 처리가 성능 개선에 중요한 이유는 다음과 같다.
  - 여러 메시지를 한 번의 네트워크 요청으로 전송할 수 있도록 하기 때문에 네트워크 왕복 비용을 줄일 수 있다.
  - 더 높은 디스크 접근 대역폭을 달성할 수 있다.<br>브로커가 여러 메시지를 한 번에 로그에 기록하면<br>더 큰 규모의 순차 쓰기 연산이 발생(한 번에 많은 데이터를 넣는다) <br>+ OS가 관리하는 디스크 캐시에서 더 큰 규모의 연속 된 공간을 점유<br>(카프카가 데이터를 받으면 OS RAM에 페이지 캐시를 한다<br>건건 : 데이터가 흩어짐, 배치 : 효율적인 공간 제공 )
- 처리량 up : 파티션 수 늘리기 

**생산자 측 작업 흐름**

[🖼️ 원본 이미지: 라우팅 계층]

라우팅 계층
1. 우선 생산자는 메시지를 라우팅 계층으로 보낸다.
2. 라우팅 계층은 메타데이터 저장소에서 사본 분산 계획을 읽어 자기 캐시에 보관한다.
    - 메시지가 도착 후 파티션-1의 리더 사본에 보낸다.
    - 예제에서 해당 사본은 브로커-1에 저장되어 있음을 알 수 있다.
3. 리더 사본이 메시지를 받고 해당 리더를 따르는 다른 사본은 해당 리더로부터 데이터를 받는다.
4. 충분한 수의 사본이 동기화되면 리더는 데이터를 디스크에 기록한다.<br>카프카의 경우는 디스크 캐시(RAM)에 커밋이 된다 flush는 OS가 알아서 한번에 처리
- 복제하는 이유 : Fault tolerance 때문에  

위 설계 문제점
- 라우팅 계층 도입 시 노드하나 추가 ⇒ 오버헤드 
- 배치처리 없음 

[🖼️ 원본 이미지: 생산자 측 버퍼 및 라우팅 (수정본)]

생산자 측 버퍼 및 라우팅 (수정본) - 라우팅 계층을 생산자 쪽으로 편입 + 버퍼 도입
- 네트워크를 거칠 필요가 줄어들어 전송 지연이 줄어든다.
- 생산자는 메시지를 어느 파티션에 보낼지 결정하는 자신만의 로직을 가질 수 있다.
- 전송할 메시지를 버퍼 메모리에 보관했다가 목적지로 일괄 전송하여 대역폭을 높일 수 있다.

**소비자 측 작업 흐름**

소비자는 특정 파티션의 오프셋을 주고 해당 위치에서부터 이벤트를 묶어 가져온다.

**푸시 vs 풀**

🤔 브로커가 데이터를 소비자에게 보낼 것인가, 소비자가 브로커에서 가져갈 것인가?

**푸시 모델**
- 낮은 지연: 브로커는 메시지를 받는 즉시 소비자에게 보낼 수 있다.
- 소비자가 메시지를 처리하는 속도가 생산자가 메시지를 만드는 속도보다 느리면, 소비자에게 큰 부하가 걸릴 수 있다.
- 생산자가 데이터 전송 속도를 좌우하므로, 소비자는 항상 그에 맞는 처리가 가능한 컴퓨팅 자원을 준비해두어야 한다.

**풀 모델**
- 메시지를 소비하는 속도는 소비자가 알아서 결정한다.
- 메시지 소비 속도가 생산 속도보다 느리면 소비자를 늘리거나 생산 속도를 따라잡을 때까지 기다려도 된다.
- 일괄 처리에 적합하다.
- 브로커에 메시지가 없어도 데이터를 끌어가려하면 컴퓨팅 자원 낭비로 이어진다.
  - 롱 폴링 지원: 당장 가져가 메시지가 없어도 일정 시간 기다리게 한다.

    [🖼️ 원본 이미지: 풀 모델]

풀 모델
1. 그룹-1에 합류하고 토픽-A를 구독하길 원하는 새로운 소비자가 있다. 그룹 이름을 해싱하여 접속할 브로커 노드를 찾는다.(같은 그룹의 소비자는 같은 브로커)
2. 코디네이터는 해당 소비자를 그룹에 참여시키고 파티션-2를 해당 소비자에 할당한다.
3. 소비자는 마지막으로 소비한 오프셋 이후 메시지를 가져온다.
4. 소비자는 메시지를 처리하고 새로운 오프셋을 브로커에 보낸다.

**소비자 재조정**
- 소비자 재조정은 어떤 소비자가 어떤 파티션을 책임지는지 다시 정하는 프로세스다.
  - 소비자 변경이 일어날 때 프로세스가 발생한다.
- 코디네이터는 소비자 재조정을 위해 소비자들과 통신하는 브로커 노드다.
  - 박동 신호가 사라지는 현상을 통해 소비자에게 발생한 장애를 감지할 수 있다.
  - 장애 감지 후 코디네이터는 재조정 프로세스를 시작하여 파티션을 재배치한다.

**상태 저장소**
- 다음과 같은 정보가 저장된다.
  - 소비자에 대한 파티션의 배치 관계
  - 각 소비자 그룹이 각 파티션에서 마지막으로 가져간 메시지의 오프셋
- 소비자 상태 정보 데이터가 이용되는 패턴은 다음과 같다.
  - 읽기/쓰기가 빈번하게 발생하지만 양은 많지 않다.
  - 데이터 갱신은 빈번하게 일어나지만 삭제되는 일은 거의 없다.
  - 읽기/쓰기 연산은 무작위적 패턴을 보인다.
  - 데이터의 일관성이 중요하다.

**메타데이터 저장소**
- 메타데이터 저장소에는 토픽 설정이나 속성 정보를 보관한다.
  - **예시:** "'결제_로그' 토픽은 파티션이 50개다."
  - **예시:** "이 토픽의 메시지 최대 크기는 1MB로 제한한다."
- 메타데이터는 자주 변경되지 않으며 양도 적다.
- 높은 일관성을 요구한다.
- 주키퍼가 적절하다.

**주키퍼**
- 계층적 키-값 저장소 기능을 제공하는, 분산 시스템에 필수적인 서비스이다.
- 보통 분산 설정 서비스, 동기화 서비스, 이름 레지스트리 등으로 이용된다.
  - 보통 분산 설정 서비스 : 클러스터 전체가 공유해야 하는 '마스터 설정'을 보관하고 전파
    - 메타데이터 저장소 역할
  - 동기화 서비스 : 여러 대의 서버가 동시에 같은 데이터를 수정하려 할 때, 충돌하지 않도록 락을 걸고 순서를 정해준다 
  - 이름 레지스트리 : 분산된 서버들의 IP 주소와 현재 상태를 기록하는 '출석부'
- 브로커 클러스터의 리더 선출 과정을 돕는다.

**복제**
- 높은 가용성을 보장하기 위해 많이 사용되는 방법이다.
- 생산자 → 리더에게만 보내기 
- → 다른 사본은 리더에게서 새 메시지를 지속적으로 가져와 동기화한다.
- → 일정 개수 넘으면 리더는 생산자에게 응답을 보냄 

사본 분산 계획
- 조정 서비스에서 브로커 노드 속 하나가 리더로 선출이 되면 <br>리더 브로커 노드가 사본 분산 계획을 만들고 메타 데이터 저장소에 보관<br>다른 모든 브로커가 해당 계획대로 움직이면 된다

**사본 동기화**
- ISR은 성능과 영속성 사이의 타협점이다.
- 리더는 항상 ISR 상태다.
- 어느 사본 하나라도 동기화를 신속하게 처리하지 못하게 되면 파티션 전부가 느려지거나 아예 못 쓰게 되는 일이 벌어지고 말 것이다.

**ACK=all**

생산자는 모든 ISR이 메시지를 수신한 뒤에 ACK 응답을 받는다.

**ACK=1**

리더가 메시지를 저장하고 나면 바로 ACK 응답을 받는다.

**ACK=0**

보낸 메시지에 대한 수신 확인 메시지를 기다리지 않고 계속 메시지를 전송하며 어떤 재시도도 하지 않는다.

**규모 확장성**
- 생산자
  - 그룹 단위의 조정에 가담할 필요가 없다.
  - 새로운 생산자를 추가/삭제할 수 있다.
- 소비자
  - 같은 소비자 그룹 내의 소비자가 새로 추가/삭제되거나 장애로 제거되어야 하는 경우 재조정 메커니즘이 맡아 처리한다.
  - 소비자 측의 규모 확장성과 결함 내성을 보장한다.
- 브로커
  - 브로커 노드가 추가/삭제될 때 사본을 재배치한다.
  - 브로커 컨트롤러로 하여금 한시적으로 시스템에 설정된 사본 수보다 많은 사본을 허용하도록 한다.<br>→ 도중에 발생할 수 있는 데이터 손실을 피할 수 있다 
- 파티션
  - 파티션 수의 조정은 생산자와 소비자의 안정성에는 영향을 끼치지 않는다.
  - 파티션을 늘리면 간단히 토픽의 규모를 늘릴 수 있다.
  - 파티션이 제거되는 시점이 오면 생산자 그룹은 재조정 작업을 개시해야 한다.

**메시지 전달 방식**
- **최대 한 번**: 메시지가 전달 과정에서 소실되더라도 다시 전달되는 일은 없다.(ACK = 0)
- **최소 한 번**: 같은 메시지가 한 번 이상 전달될 수는 있으나 메시지 소실은 발생하지 않는 전달 방식이다.(ACK = ALL, ACK = 1)
- **정확히 한 번**: 중복을 허용하지 않으며, 구현에 이용할 서비스나 제3자 제품이 같은 입력에 항상 같은 결과를 내 놓도록 구현되어 있지 않은 애플리케이션에 특히 중요하다.

**고급 기능**

**메시지 필터링**
1. 소비자가 일단 모든 메시지를 받은 다음 필요 없는 메시지는 버린다.
2. 브로커에서 메시지를 필터링하여 소비자는 원하는 메시지만 받을 수 있도록 한다.
3. 태그 필드가 있으면 브로커는 해당 필드를 활용해 메시지를 필터링할 수 있다.

**메시지의 지연 전송 및 예약 전송**
- 때로는 소비자에게 보낼 메시지를 일정 시간만큼 지연시켜야 하는 일이 있을 수 있다.
- 메시지는 토픽에 바로 저장하지 않고 브로커 내부의 임시 저장소에 넣어 두었다가 시간이 되면 토픽을 옮긴다.
- 메시지 예약 전송 기능은 지정된 시간에 소비자에게 메시지를 보낼 수 있도록 하는 기능으로, 전반적인 시스템 설계 철학은 메시지 지연 전송 시스템과 유사하다.
