# 3.6 서비스 공개

## 3.6.1 서비스를 사용해서 파드에 접속하기

> 🧩 **한 줄 요약** — 파드는 죽고 살 때마다 IP가 바뀐다. **서비스(Service)**는 여러 파드 앞에 붙는 **대표 고정 IP(+이름)** 로, 클라이언트는 이 주소로만 접속하면 알아서 파드로 연결된다.

### 1. 왜 서비스가 필요한가
- 파드가 죽고 재시작되면 그 IP는 **무조건 다른 번호로 바뀐다** → 프론트가 어디로 요청할지 혼란.
- **서비스** = 같은 기능을 하는 파드 그룹에 **공통 대표 IP**를 부여 → 하나의 서비스처럼 접속.
- IP뿐 아니라 **이름(서비스명)으로도** 접근 가능.

## 3.6.2 외부에 서비스 공개하기

> 🧩 **한 줄 요약** — 파드·서비스 IP는 클러스터 **내부 전용**. 외부에 열려면 **NodePort**(노드 포트 개방) → **LoadBalancer**(클라우드 LB 자동 생성) → **Ingress**(여러 서비스를 하나의 진입점으로) 순으로 발전한다.

### 1. NodePort
- 각 노드의 **고정 포트**를 클러스터 외부에 공개하고, 그 포트로 온 요청을 서비스가 파드로 분산(LB).
- **한계** : 노드가 여러 개면 "유저에게 어느 노드 IP를 알려주지?" 문제 + 노드 그룹 LB를 **개발자가 직접** 구성해야 함.

### 2. LoadBalancer
- 매니페스트에 `type: LoadBalancer` **한 줄**만 적으면 쿠버가 클라우드 LB(ELB 등)를 자동 생성·배선.
- 흐름 : **유저 → 클라우드 LB(살아있는 노드 탐색) → 노드 포트(NodePort) → 서비스 → 파드**.
- NodePort의 "어느 노드 IP를 알려주지?" 문제를 클라우드로 해결.

### 3. Ingress
- 서비스가 많으면 LoadBalancer도 서비스 수만큼 늘어난다 → 이를 **하나로 합친 것**.
- 외부 요청을 원하는 서비스로 라우팅해 바로 파드로 넘김 → **서비스마다 LB를 만들 필요가 없다**.

### 정리 — 세 방식 비교

| 방식 | 외부 공개 방법 | 특징 |
|---|---|---|
| **NodePort** | 노드의 포트를 개방 | 노드 여러 개면 LB 직접 구성 |
| **LoadBalancer** | 클라우드 LB 자동 생성 | `type: LoadBalancer` 한 줄 |
| **Ingress** | 통합 진입점 | 여러 서비스 경로 라우팅, LB 절약 |
