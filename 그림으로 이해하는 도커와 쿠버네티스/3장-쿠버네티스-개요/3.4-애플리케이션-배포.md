# 3.4 애플리케이션 배포

## 3.4.1 디플로이먼트

> 🧩 **한 줄 요약** — **디플로이먼트**는 "파드를 항상 N개 유지"를 담당하는 리소스(유지 대상은 노드가 아니라 파드 수). 스케일링·셀프 힐링·업데이트/롤백을 제공하고, 업데이트는 **단순**(전부 교체) vs **롤링**(점진 교체) 두 방식이 있다.

### 1. 디플로이먼트 = 파드 개수 유지
- 파드 그룹을 지정한 숫자만큼 유지한다. **유지 대상은 노드가 아니라 파드 수**다.

### 2. 3대 기능
- **파드 스케일링** : 매니페스트에서 파드 개수를 바꾸고 `kubectl apply`로 재선언하면 파드 수가 바뀐다.
- **셀프 힐링** : 가동 파드 수가 지정값보다 줄면(장애 등) 자동으로 새 파드를 실행해 복구한다.
- **업데이트 & 롤백** : 아래 두 방식 →

### 3. 업데이트 방식 — 단순 vs 롤링

| 방식 | 동작 | 특징 |
|---|---|---|
| **단순** (Recreate) | 현재 버전 파드를 **전부 삭제** → 새 버전 일괄 배포 | 다운타임 발생 |
| **롤링** (RollingUpdate) | 일부 파드는 가동 유지하며 **점진적으로 교체** | 무중단 |

> ➕ 노드 자체는 클라우드에서 파드 수에 따라 자동 추가하도록 설정할 수 있다 — **Cluster Autoscaler**, **Karpenter** 같은 도구를 붙여서.

## 3.4.2 스테이트풀셋

> 🧩 **한 줄 요약** — **스테이트풀셋**은 상태 유지가 필요한 앱을 위해 각 파드를 **인덱스·호스트명으로 구별**한다. 파드를 전부 똑같이 다루는 디플로이먼트와 달리, 파드마다 고유 이름·고유 볼륨을 주고 생성/삭제도 인덱스 순서대로 한다.

### 1. 왜 스테이트풀셋인가
- 컨테이너는 기본적으로 **무상태**다. 상태(데이터)를 유지해야 하는 앱을 위한 것이 스테이트풀셋.

### 2. 디플로이먼트 vs 스테이트풀셋

| 축 | 디플로이먼트 | 스테이트풀셋 |
|---|---|---|
| 파드 취급 | 전부 **동일하게** 핸들링 | 각 파드를 **구별**해서 핸들링 |
| 식별 | 구분 없음 | 파드마다 **인덱스 + 호스트명** 부여 |
| 통신 | IP 기반 | 헤드리스 + 내부 DNS로 **이름(주소)으로 통신** |
| 생성/삭제 | 순서 무관 | **인덱스 순서** |
| 볼륨 | 공유/임시 | 파드마다 **고유 볼륨**, 재기동해도 데이터 유지 |

- **헤드리스 서비스**와 조합하면 클러스터 내부 DNS에서 각 파드의 이름을 얻어, IP가 아닌 이름으로 독립·협력 통신이 가능하다.

### 3. 인덱스 순서 (스테이트풀셋에만 있음)
- **생성(스케일 아웃)** : `0번` 완료 → `1번` → `2번`
- **삭제(스케일 다운)** : 역순으로 `2번` → `1번` → `0번`
- 즉 **0번이 가장 먼저 시작, 가장 마지막에 종료**된다.

## 3.4.3 데몬셋

> 🧩 **한 줄 요약** — 디플로이먼트가 "클러스터 전체에 파드 N개"라면, **데몬셋**은 "**모든 노드마다 파드 1개**"다. 모니터링처럼 각 노드에 하나씩 떠 있어야 하는 앱에 쓴다.

### 1. 디플로이먼트 vs 데몬셋

| 축 | 디플로이먼트 | 데몬셋 |
|---|---|---|
| 배치 기준 | 클러스터에 파드 **N개** (노드 무관) | **노드마다 파드 1개** |
| 용도 | 일반 애플리케이션 | 노드에 종속된 앱 (모니터링 등) |

### 2. 특징
- 각 노드에 **데몬 프로세스처럼 1대씩** 배치 → **1노드 1파드**
- **롤링 업데이트** 지원
- 노드에 (데몬셋) 파드가 없으면 **자동으로 파드 추가** → 새 노드가 늘어도 알아서 배치

## 3.4.4 잡과 크론잡

> 🧩 **한 줄 요약** — **잡(Job)**은 "끝이 있는 작업"을 실행하고 완료되면 파드를 종료해 자원을 아낀다(성공 조건·재시도 설정). **크론잡(CronJob)**은 그 잡을 크론 형식 스케줄로 주기 실행한다.

### 1. 잡 (Job)
- **완료형(배치) 작업**용. 작업이 끝나면 파드를 종료해 노드(컴퓨터 자원)를 아낀다.
- **설정 항목** : 성공해야 하는 파드 수, 타임아웃, 실패 시 재실행 정책, 허용 실패 횟수 등
- **동작** : 설정대로 파드를 배포·실행 → 종료 상태 코드로 성공 여부 판단 → 필요 시 재실행

| 축 | 디플로이먼트·데몬셋 | 잡 |
|---|---|---|
| 파드 수명 | 계속 가동 (죽으면 재실행) | **작업 완료 시 종료** |

### 2. 크론잡 (CronJob)
- 잡을 **크론 형식 스케줄**로 주기 실행하는 기능.
- **크론** = 실행 시작 시점과 주기적 실행을 설정(스케줄링).

```bash
# ┌분 ┌시 ┌일 ┌월 ┌요일
  0   2   *   *   *      # 매일 02:00에 잡 실행
```

2. 디플로이먼트와 스테이트풀셋이 파드를 다루는 방식은 어떻게 다르며, 스테이트풀셋 파드는 왜 재기동 후에도 데이터를 유지하나?
3. 데몬셋은 파드를 어떤 기준으로 배치하나? 잡이 노드 자원을 아끼는 방식은?

**3.4.1 디플로이먼트**

- 파드 스케일링, 자동복구, 업테이트 등의 기능 존재
  - 파드 스케일링

  - 업데이트 및 롤백
    - 단순 : 현재 가동 중인 버전의 파드 모두 삭제 → 새로운 저번의 파드를 일괄 배포
    - 롤링 업데이트 : 일정개수 파드는 클러스터에서 가동 중인 상태 유지 + 파드 그룹을 점진적으로 업테이트 롤링하는 방식
- 노드는 클라우드 환경에서 파드 개수에 따라 알아서 추가하도록 설정
  - 'Cluster Autoscaler'나 'Karpenter' 같은 자동화 도구를 붙여서

**3.4.2 스테이트풀셋**
- 컨테이너는 무상태
- 위를 막기위한 스테이트풀 컨테이너도 있음
- 디플로이먼트와 스테에트풀 셋
  - 디플로이먼트
    - 파드 그룹을 동일하게 핸들링
  - 스테이트 풀 셋
    - 각 파드를 구별해서 핸들링
    - 각 파드에 인덱스랑 호스트 명을 부여 <br>(헤드리스 기능과 조합시 쿠버 클러스터 내부 DNS에서 각 파드에 대해 주소(이름)을 얻을 수 있어 독립적으로 혹은 협력적으로도 다룰 수 있다(IP가 아닌 이름으로 통신 가능))
    - 스케일링 파드 작성 삭제는 인덱스 순서 (스테이트 풀 셋에서만 )
      - 0번은 가장먼저 시작 가장 마지막에 종료(삭제)
      - e.g.
        - **생성 (스케일 아웃):** `0번` 파드 실행 완료 → `1번` 실행 → `2번` 실행
        - **삭제 (스케일 다운):** 역순으로 `2번` 파드 삭제 완료 → `1번` 삭제 → `0번` 삭제
    - 각 파드에는 고유의 볼륨 할당 가능
      - 파드 종료 후 같은 인덱스로 가동하면 할당되었던 데이터 상태 유지 가능

**3.4.3 데몬셋**
- 디플로이먼트 : 파드 그룹을 클러스터에서 N개가 가동한다라는 형태로 관리(특정 노드가 아님)
  - 모니터링 같이 노드랑 관계가 있는 애플리케이션은 각 노드에 데몬 프로세스 처럼 1대씩 있는 것이 좋음
  - 즉, 1노드 1파드이 데몬셋
  - 롤링 업데이트도 되고, 노드에 파드가 없으면 자동으로 파드 추가

**3.4.4 잡과 크론잡**
- 잡
  - 최소한 성공해야하는 파드개수, 타임아웃 시간, 실패 시 재실핼 정책, 허용가능 실패 횟수 등을 설정
  - 위 설정에 따라 파드 배포하고 실행하고 파드 종료 상태 코드를 보고 성공 여부를 판단하여 재실행등 처리
  - 즉, 작업이 끝나면 파드를 종료 시켜서 노드(컨퓨터자원)를 아낄 수 있도록 관리
- 크론잡
  - 크론 형식으로 실행시작과 주기적 실행 방법을 설정하는 기능
  - 크론 : 실행 시작과 주기적 실행 설정(스케줄링)
