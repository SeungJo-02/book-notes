# 3.5 설정 항목과 볼륨

## 3.5.1 컨피그맵과 시크릿을 활용한 애플리케이션 설정 관리

> 🧩 **한 줄 요약** — 앱 설정을 이미지에서 떼어내 따로 관리하는 것이 **컨피그맵**(일반 설정)과 **시크릿**(민감 정보). 둘 다 키-값이고, 컨테이너에 **환경 변수**나 **읽기 전용 파일**로 주입한다.

### 1. 왜 설정을 분리하나
- 설정을 코드·이미지에 박아두면 환경(개발/운영)이 바뀔 때마다 이미지를 다시 빌드해야 한다.
- 설정만 밖으로 빼서 독립 관리하면 같은 이미지를 여러 환경에서 그대로 쓸 수 있다.

### 2. 컨피그맵 vs 시크릿

| 축 | 컨피그맵 (ConfigMap) | 시크릿 (Secret) |
|---|---|---|
| 저장 대상 | 일반 설정 파일·설정용 환경 변수 | 보안 데이터(비밀번호·토큰 등) |
| 공통 | 키-값 · 환경 변수 주입 · 파일 마운트 | 좌동 |
| 특징 | — | 컨테이너 이미지에 포함하지 않음 |

### 3. 주입 방식
- **환경 변수**로 컨테이너에 넣기
- 컨테이너 파일시스템에 **읽기 전용 마운트** — 예: `application.yml`(스프링 부트 설정)을 컨피그맵으로 저장하면 파드 실행 시 컨테이너 안 `/config/application.yml`로 붙는다.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  application.yml: |          # 이 값이 /config/application.yml로 마운트됨
    server:
      port: 8080
```

## 3.5.2 볼륨을 사용한 스토리지 관리

> 🧩 **한 줄 요약** — **볼륨**은 컨테이너가 죽어도 데이터가 사라지지 않게 하는 추가 저장 공간. 파드 수명을 넘겨 영구 보존하는 **퍼시스턴트볼륨**과, 파드와 함께 사라지는 **임시 볼륨**으로 나뉜다.

### 1. 볼륨이란
- 컨테이너가 종료되면 내부 기록이 사라진다 → 데이터를 담아둘 **추가 저장 영역**이 볼륨.
- 저장 위치 : 메모리, 노드의 디렉터리 등.
- 관리 주체 : 쿠버가 직접 관리하거나, **외부 플러그인(CSI 등)**으로 관리.

> 💡 원본의 "CSI, GKE" 중 **CSI**(Container Storage Interface)가 외부 스토리지를 붙이는 표준 플러그인이다. GKE는 스토리지 드라이버가 아니라 구글의 관리형 쿠버 서비스다.

### 2. 두 종류

| 축 | 퍼시스턴트볼륨 (PV) | 임시 볼륨 |
|---|---|---|
| 수명 | 파드와 **독립**, 파드 수명 넘어 유지 | 파드와 **동일** |
| 재시작 시 | 데이터 유지 | 데이터 소실 |
| 자세히 | → 3.5.3 | → 3.5.4 |

## 3.5.3 퍼시스턴트볼륨

> 🧩 **한 줄 요약** — **PV**(퍼시스턴트볼륨)는 파드와 독립적으로 존재하는 실제 저장소. 개발자는 **PVC**(요청서)로 "이런 볼륨 주세요" 요청하고, 쿠버가 조건이 맞는 PV를 찾아 짝지어준다. **StorageClass**로 즉석 생성(동적 프로비저닝)도 된다.

### 1. PV와 PVC
- **PV** : 파드와 독립, 파드 수명을 넘어 유지되는 **실제 저장 공간(HDD)**. 매니페스트에 사양(크기·재사용 정책·마운트 옵션 등)을 작성한다.
- **PVC** (퍼시스턴트볼륨클레임) : 원하는 볼륨 조건을 적은 **요청서**. 파드 매니페스트에 PVC 이름 + 마운트 위치를 지정하면 볼륨을 쓸 수 있다.
- **매칭** : 쿠버가 PVC를 읽고 조건이 맞는 PV를 짝지어준다.

|  | PV | PVC |
|---|---|---|
| 정체 | 실제 저장소(매물) | 요청서(조건 명시) |
| 누가 | 관리자/스토리지가 제공 | 개발자가 파드에서 요청 |

### 2. 볼륨 생성 — StorageClass
- **정적** : 미리 만들어 둔 PV 중 조건 맞는 것을 연결.
- **동적 프로비저닝** : **StorageClass**가 PVC를 보고 조건에 맞는 PV를 즉석에서 생성해 연결.

## 3.5.4 임시 볼륨

> 🧩 **한 줄 요약** — 파드와 함께 사라지는 볼륨. **emptyDir**(노드에 빈 폴더 — 캐시·컨테이너 간 공유)과 **일반 임시 볼륨**(동적 프로비저닝으로 클라우드 디스크를 파드 수명만큼 빌림)이 있다. 볼륨 준비 방식은 **정적 vs 동적 프로비저닝**으로 갈린다.

### 1. 임시 볼륨이란
- 파드와 **수명이 같고**, 재시작 시 데이터가 사라지는 볼륨.

### 2. emptyDir
- 대표적 임시 볼륨. 파드가 뜬 **노드의 HDD**(또는 메모리)에 빈 폴더를 만든다. **PVC 과정 없음** — 쿠버가 파드를 띄우며 자동 생성.
- 용도(작고 가벼운 임시 데이터) : 사이드카 패턴 데이터 공유 · 초고속 인메모리 캐시 · 소규모 임시 작업장.

### 3. 일반 임시 볼륨
- **동적 프로비저닝**으로 파드와 같은 수명의 볼륨을 즉석 생성 (예: AWS EBS 등 외부 클라우드 디스크).
- 파드가 죽으면 만들어둔 디스크(PV·PVC)까지 **자동 폐기** ← 일반 PVC(파드가 죽어도 영구 보존)와 반대.
- 용도 : 대용량 임시 데이터 · SSD 필요 · 클라우드 전용 기능.

### 4. 정적 vs 동적 프로비저닝

| 축 | 정적 프로비저닝 | 동적 프로비저닝 |
|---|---|---|
| PV 준비 | 관리자가 **미리 수동 생성·등록** | 미리 안 만듦 |
| 볼륨 확보 | 기존 PV 중 조건 맞는 것 연결 | **StorageClass**가 요청 보고 즉석 생성 |
| 문제/특징 | 딱 맞는 PV 없으면 파드 **Pending**, 낭비·수고 | 필요할 때 자동 생성(자판기처럼) |

3. PV는 파드와 독립적으로 존재하는 실제 저장소, PVC는 원하는 볼륨 조건을 적어 제출하는 요청서. 정적 프로비저닝은 관리자가 딱 맞는 PV를 미리 안 만들어 두면 파드가 디스크를 못 얻고 영원히 Pending에 빠지며, 공간 낭비와 관리 수고가 크다.

      - 사용
        - 임시데이터인데 용량이 작고 가벼운 작업
          - 사이드카 패턴의 데이터 공유
          - 초고속 인메모리 캐시

  - 일반 임시 볼륨
    - 동적 프로비저닝 사용
    - 볼륨요청을 직접 기술 + 해당 파드와 동일한 수명을 가진 볼륨을 동적으로 작성할 수 있다

      - 저장위치

      - 생성방식
        - **동적 프로비저닝(PVC 자동 생성)** 방식<br>파드를 띄울 때 "나 임시로 쓸 거니까 AWS 클라우드에 100GB짜리 하드디스크 하나 당장 만들어줘!"라고 요청(PVC)
        - 차이
          - 일반적인 PVC는 파드가 죽어도 데이터가 영구 보존
          - 일반 임시 볼륨
            - 파드가 죽는 순간 쿠버네티스가 클라우드에 만들어둔 하드디스크(PV, PVC)까지 싹 다 알아서 폐기 처분
      - 사용
        - 임시데이터인데 대용량 작업
        - SSD 필요시
        - 클라우드 전용 보안/기능이 필요할 때
- 정적 프로비저닝
  - **동작 순서:**
    1. **관리자의 노가다:** 관리자가 AWS 콘솔에 들어가서 10GB짜리 하드디스크 1개, 50GB짜리 1개를 직접 마우스로 클릭해서 만듭니다. 그리고 쿠버네티스에 PV(매물)로 일일이 등록해 둡니다.
    2. **개발자의 요청:** 개발자가 "10GB짜리 디스크 필요해요!" 하고 PVC(요청서)를 제출합니다.
    3. **매칭:** 쿠버네티스가 미리 만들어둔 PV 목록을 뒤져서 10GB짜리 매물을 찾아 연결해 줍니다.
  - **치명적인 단점:** 만약 개발자가 "15GB가 필요해요!"라고 요청했는데, 관리자가 15GB짜리 PV를 미리 안 만들어 뒀다면? **파드는 디스크를 얻지 못하고 영원히 대기(Pending) 상태에 빠집니다.** 공간 낭비도 심하고 관리자가 너무 귀찮습니다.
- 동적 프로비저닝
  - 쿠버네티스에 `StorageClass`라는 '자동 발주기(자판기)' 하나만 딱 설치
  - **동작 순서:**
    1. **관리자의 자유:** 관리자는 PV(실제 디스크)를 단 한 개도 미리 만들어두지 않습니다.
    2. **개발자의 요청:** 개발자가 "나 AWS 최고급 SSD로 15GB짜리 만들어줘!"라고 PVC(요청서)에 `StorageClass` 이름을 적어서 제출합니다.
    3. **마법 같은 자동화:** 쿠버네티스의 `StorageClass`가 이 요청서를 보자마자 **AWS 클라우드에 API로 명령을 내려서 즉시 15GB짜리 실제 하드디스크(PV)를 새로 뚝딱 만들어내고** 파드에 연결해 줍니다.
