# 3.7 쿠버네티스의 파드와 CRI 컨테이너 런타임

## 3.7.1 kubelet으로 파드 관리

> 🧩 **한 줄 요약** — **kubelet**은 각 노드에 상주하는 쿠버의 "현장 관리자". 컨트롤 플레인의 명령을 받아 그 노드에서 파드를 실제로 띄우고, 잘 도는지 계속 지켜본다.

- 노드마다 하나씩 떠 있는 **에이전트(프로그램)** 다.
- API 서버가 "이 노드에 이 파드 띄워" 하면 **kubelet이 실제로 실행**한다.
- 파드 상태를 계속 **감시** → 죽으면 다시 살리고, 상태를 API 서버에 보고한다.

> 💡 비유 — 본사(컨트롤 플레인)의 지시를 받아 현장(노드)에서 일을 실행하고 감독하는 **현장 소장**.

## 3.7.2 CRI 런타임

> 🧩 **한 줄 요약** — **CRI**(Container Runtime Interface)는 kubelet과 "컨테이너를 실제로 실행하는 프로그램(런타임)" 사이의 **표준 콘센트**. 규격만 맞으면 어떤 런타임이든 갈아끼울 수 있다.

- kubelet은 컨테이너를 직접 실행하지 못해서 **런타임에게 시킨다.**
- **CRI** = kubelet과 런타임이 대화하는 **표준 규격(약속)** 이다.
- 덕분에 **containerd, CRI-O** 같은 런타임을 자유롭게 교체할 수 있다.
- 그래서 쿠버는 도커 직접 지원을 접고 containerd 등으로 넘어갔다.

> 💡 비유 — 표준 **콘센트 규격**. 규격만 맞으면 어느 회사 플러그(런타임)든 꽂힌다.

## 3.7.3 CNI 플러그인

> 🧩 **한 줄 요약** — **CNI**(Container Network Interface)는 파드에 IP를 붙이고 파드끼리 통신되게 만드는 **네트워크 표준**. 실제 연결은 Calico·Flannel 같은 **플러그인**이 담당한다.

- 파드가 뜨면 누군가 **IP를 주고** 다른 파드와 **연결**해줘야 한다 → 그 일을 하는 게 CNI 플러그인.
- **CNI** = 쿠버와 네트워크 플러그인 사이의 **표준 규격**이다.
- 플러그인 종류 : **Calico, Flannel, Cilium** 등 (원하는 걸 골라 설치).

> 💡 비유 — 새 컴퓨터(파드)에 랜선을 꽂고 IP를 배정해 주는 **네트워크 기사**.

## 3.7.4 kube-proxy

> 🧩 **한 줄 요약** — **kube-proxy**는 각 노드에서 "**서비스 주소로 온 요청을 실제 파드로 넘겨주는**" 교통 정리 담당. 여러 파드에 부하를 나눠준다.

- 파드는 죽고 살면서 **IP가 계속 바뀐다** → 고정된 **서비스(Service) 주소**가 필요하다.
- 서비스 주소로 온 요청을 **실제 파드 IP로 전달(라우팅)**하고 **로드밸런싱**한다.
- 노드마다 하나씩 돌면서 iptables/IPVS 규칙으로 처리한다.

> 💡 비유 — 대표 전화번호(서비스)로 온 전화를 실제 상담원(파드)에게 돌려주는 **전화 교환원**.

## 3.7.5 노드 컴포넌트의 관계

> 🧩 **한 줄 요약** — 한 노드 위에서 **kubelet · CRI 런타임 · CNI · kube-proxy**가 역할을 나눠 협력한다. kubelet이 지휘하고, 런타임은 컨테이너 실행, CNI는 네트워크 연결, kube-proxy는 서비스 라우팅을 맡는다.

### 파드 하나가 뜨는 순서
1. API 서버가 **kubelet**에게 "이 파드 띄워"라고 지시
2. kubelet이 **CRI 런타임**에게 컨테이너 실행을 요청
3. **CNI 플러그인**이 파드에 IP를 주고 네트워크에 연결
4. **kube-proxy**가 서비스로 온 요청을 그 파드로 라우팅

### 역할 정리

| 컴포넌트 | 역할 |
|---|---|
| **kubelet** | 노드의 파드 관리·감시 (지휘) |
| **CRI 런타임** | 컨테이너를 실제로 실행 |
| **CNI 플러그인** | 파드 네트워크(IP·통신) 담당 |
| **kube-proxy** | 서비스 → 파드 요청 라우팅 |
