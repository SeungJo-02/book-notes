# LESSON 35. 응용 계층에서 사용하는 로드 밸런서

> 📝 **Notion 원본**: https://app.notion.com/p/3c4d7d6851ff81baabafe8af8dbf8899

> 🧩 **한 줄 요약** — 로드 밸런서는 몰려드는 요청을 여러 서버에 나눠준다. **어느 계층까지 들여다보느냐** 에 따라 L4와 L7로 갈리는데, **L7은 L4가 보는 것(IP·포트)에 더해 URL·헤더·쿠키까지** 본다.

---

## 1. 무엇을 해결하는가

- 서버 한 대로 감당이 안 될 때 **여러 대에 요청을 나눠** 준다 → 처리량 확보.
- 한 대가 죽어도 나머지로 넘겨 **서비스가 멈추지 않게** 한다 → 가용성 확보.
- 이게 가능한 전제는 **HTTP가 Stateless** 라는 것(LESSON 31). 서버가 이전 요청을 기억하지 않으니 아무 서버에 보내도 된다.

---

## 2. L4와 L7

원본에 적은 *"응용 계층 LB는 전송 계층 LB 기능까지 포함"* 이 핵심이다. **L7은 L4의 상위 집합** 이다.

| 기준 | **L4 (전송 계층)** | **L7 (응용 계층)** |
|---|---|---|
| 판단 재료 | IP, 포트 | IP, 포트 + **URL, 헤더, 쿠키** |
| 분산 단위 | 연결 단위 | **서비스·요청 단위** |
| 속도 | 빠름 (내용을 안 봄) | 느림 (본문까지 해석) |
| 유연성 | 낮음 | 높음 |

- **L4** — 봉투의 주소만 보고 분류하는 우체국. 안을 열지 않으니 빠르다.
- **L7** — 봉투를 열어 내용을 읽고 담당 부서로 보내는 안내 데스크. 느린 대신 똑똑하다.

### 2-1. L7이라서 할 수 있는 일

- **경로 기반 라우팅** — `/api` 는 API 서버로, `/images` 는 이미지 서버로.
- **SSL 종료(SSL Termination)** — 암호를 LB에서 풀어 뒷단 서버의 부담을 덜어준다. 내용을 봐야 하므로 **L7에서만** 가능.
- **고정 세션(Sticky Session)** — 쿠키를 보고 **같은 사용자를 늘 같은 서버로** 보낸다.

> ⚠️ **L7이 항상 정답은 아니다.** 내용을 해석하는 만큼 지연과 자원 소모가 늘어난다. 단순히 트래픽만 나누면 되는 구간(예 : DB 앞단, 게임 서버)에서는 **L4가 더 낫다.** "더 많이 볼 수 있다 = 더 좋다"가 아니라, **볼 필요가 있을 때만** L7을 쓴다.

---

## 3. 나누는 기준 — 분산 알고리즘

| 방식 | 규칙 | 적합한 상황 |
|---|---|---|
| 라운드 로빈 | 순서대로 돌아가며 | 서버 성능이 같을 때 |
| 가중 라운드 로빈 | 성능 좋은 서버에 더 많이 | 서버 사양이 다를 때 |
| 최소 연결 | 연결 수가 가장 적은 서버로 | 요청마다 처리 시간이 들쭉날쭉할 때 |
| IP 해시 | 클라이언트 IP로 서버를 고정 | 같은 사용자를 같은 서버로 보낼 때 |

> 📎 LESSON 29(전송 계층 로드 밸런서)에서 정리한 라운드로빈·가중 라운드로빈·랜덤·해시가 그대로 이어진다. L7은 여기에 **URL·헤더·쿠키 기준** 이 더해지는 것.

---

## 4. 헬스 체크 — 죽은 서버를 빼는 장치

- LB는 뒷단 서버에 **주기적으로 신호를 보내** 살아 있는지 확인한다.
- 응답이 없으면 **분산 대상에서 제외** 하고, 다시 살아나면 자동으로 넣는다.
- 이게 없으면 로드 밸런서는 **죽은 서버에도 꼬박꼬박 요청을 보내** 일부 사용자만 에러를 겪게 된다.

<details>
<summary>⚠️ 고정 세션의 함정</summary>

- 쿠키로 사용자를 특정 서버에 묶으면, **그 서버가 죽는 순간 로그인도 함께 날아간다.**
- 또 특정 서버에만 사용자가 몰려 **부하가 고르게 분산되지 않는다.**
- 그래서 실무에서는 고정 세션 대신, 세션을 **Redis 같은 외부 저장소에 두어** 어느 서버가 받아도 처리되게 만드는 쪽을 선호한다.

</details>

## 5. 정리

| 개념 | 한 줄 정의 |
|---|---|
| L4 로드 밸런싱 | IP·포트만 보고 분산 — 빠름 |
| L7 로드 밸런싱 | URL·헤더·쿠키까지 보고 분산 — 유연함 |
| SSL 종료 | LB에서 암호를 풀어 뒷단 부담을 덜어줌 |
| 고정 세션 | 같은 사용자를 같은 서버로 고정 |
| 헬스 체크 | 죽은 서버를 분산 대상에서 제외 |

## 🔁 셀프 체크

1. `/api` 로 오는 요청만 다른 서버로 보내고 싶다. L4로 가능한가?
2. L7이 L4보다 항상 나은 선택인가?
3. 헬스 체크가 없으면 구체적으로 무슨 일이 벌어지는가?

<details>
<summary>답</summary>

1. **불가능하다.** 경로(`/api`)는 HTTP 메시지 안에 있어서 **L7이라야 읽을 수 있다.** L4는 IP와 포트까지만 본다.
2. **아니다.** 내용을 해석하는 만큼 느리고 자원을 더 쓴다. 내용을 볼 필요가 없다면 **L4가 더 빠르고 저렴하다.**
3. LB가 **죽은 서버에도 계속 요청을 보내**, 그 서버로 배정된 사용자만 에러를 겪는다. 전체 장애가 아니라 **일부만 실패** 해서 원인을 찾기도 어렵다.

</details>
