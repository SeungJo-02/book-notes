# LESSON 31. HTTP 프로토콜

> 📝 **Notion 원본**: https://app.notion.com/p/3c4d7d6851ff81ba8a50ef10e25eed5c

> 🧩 **한 줄 요약** — HTTP는 **요청 한 번 / 응답 한 번** 으로 끝나는 단순한 텍스트 규격이고, 그 메시지는 항상 **시작 라인 → 헤더 → 빈 줄 → 본문** 네 덩어리로 되어 있다. 버전의 역사는 곧 **"연결을 얼마나 아껴 쓰느냐"의 역사** 다.

---

## 1. 요청과 응답

- **요청(Request)** — 클라이언트가 URL로 "이거 주세요"라고 보냄
- **응답(Response)** — 서버가 데이터와 함께 결과를 돌려줌
- 기본 포트는 **80**, 암호화된 HTTPS는 **443**.

### 1-1. HTTP는 상태를 기억하지 않는다 (Stateless)

- 서버는 이전 요청을 **기억하지 않는다.** 요청 하나하나가 완전히 독립적이다.
- 그래서 로그인 상태를 유지하려면 **쿠키·세션·토큰** 을 매 요청에 실어 보내야 한다.
- 기억하지 않는 대신 서버를 얼마든지 늘릴 수 있다 — 이 성질이 **로드 밸런싱(LESSON 35)** 을 가능하게 만든다.

---

## 2. 메시지 구조

```
GET /index.html HTTP/1.1      ← 시작 라인
Host: www.example.com         ← 헤더
Connection: keep-alive
Accept-Language: ko-KR
                              ← 빈 줄 (헤더 끝 표시)
(본문 — GET에는 보통 없음)
```

> ✏️ **정정** — 원본에 `GET/ index.html / HTTP/1.1` 로 적었는데, 올바른 형식은 **`GET /index.html HTTP/1.1`** 이다. 세 요소를 **공백 하나** 로만 구분하며, 메서드 뒤나 경로 뒤에 `/` 를 덧붙이지 않는다.

- **빈 줄이 문법적으로 중요하다.** 서버는 이 빈 줄을 보고 "헤더 끝, 여기부터 본문"을 판단한다.
- 시작 라인은 요청이냐 응답이냐에 따라 이름이 다르다 — 요청은 **요청 라인(Request Line)**, 응답은 **상태 라인(Status Line)**.

### 2-1. 경로(Path)

- 형식은 `/경로/파일명.확장자` — 예 : `/docs/intro.html`
- 경로만 주고 파일명을 생략하면(`/docs/` 또는 `/`) 서버가 **미리 정해둔 기본 파일** 을 대신 돌려준다. 그게 보통 `index.html` 이다.

> ✏️ **정정** — 원본에는 `index.html` 을 "경로와 파일명이 없으면 **자동으로 생성되는** 파일"이라고 적었는데, 서버가 파일을 만들어내는 게 아니다. **이미 있는 파일 중에서 기본값으로 찾아 반환** 할 뿐이고, 그 파일이 없으면 403이나 404가 난다. 어떤 파일을 기본값으로 삼을지는 서버 설정에 달렸다 (Apache의 `DirectoryIndex`, Nginx의 `index` 지시어).

## 3. HTTP 메서드

| 메서드 | 용도 | 멱등성 |
|---|---|---|
| GET | 조회 | ⭕ (안전하기도 함) |
| POST | 생성 | ❌ |
| PUT | **전체** 갱신 | ⭕ |
| PATCH | **일부** 갱신 | ❌ (구현에 따라 다름) |
| DELETE | 삭제 | ⭕ |

- **멱등성(idempotent)** — 같은 요청을 여러 번 보내도 결과가 같은 성질.
- 이게 중요한 이유 : 응답을 못 받았을 때 **재시도해도 되는지** 가 여기서 갈린다. POST는 두 번 보내면 주문이 2건 생길 수 있어 재시도가 위험하다.

<details>
<summary>💡 PUT과 PATCH, 실무에서 어떻게 갈리나</summary>

- `PUT /users/1` 에 이름만 담아 보내면, 명세상 **나머지 필드는 비워진다.** 전체 교체이기 때문.
- 이름만 바꾸고 싶으면 `PATCH` 가 맞다.
- 실무에서는 이 구분을 지키지 않고 PUT을 부분 갱신처럼 쓰는 API도 많다 — 남의 API를 쓸 땐 문서를 확인해야 하는 지점.

</details>

## 4. 상태 코드

| 번호대 | 뜻 | 대표 예시 |
|---|---|---|
| 1XX | 정보 — 받았고 처리 중 | 100 Continue |
| 2XX | 성공 | 200 OK, 201 Created |
| 3XX | 리다이렉션 — 다른 곳에 있음 | 301 영구이동, 302 임시, 304 안 바뀜 |
| 4XX | **클라이언트** 잘못 | 400, 401 인증필요, 403 권한없음, 404 |
| 5XX | **서버** 잘못 | 500, 502 게이트웨이오류, 503 과부하 |

- 4XX와 5XX를 나누는 기준은 **"누가 고쳐야 하는가"** 다. 404는 클라이언트가 주소를 고쳐야 하고, 500은 서버 개발자가 코드를 고쳐야 한다.
- **304 Not Modified** 는 캐시의 핵심 — "네가 가진 게 최신이니 다시 안 보낸다"는 뜻이라 본문이 비어 있고, 그래서 빠르다.

## 5. 주요 헤더

| 헤더 | 의미 |
|---|---|
| `Host` | 접속하려는 서버의 도메인·포트 |
| `Connection` | 작업 후에도 연결을 유지할지 여부 |
| `Accept-Language` | 응답에 원하는 언어 |
| `Content-Type` | 본문의 형식 (`application/json` 등) |
| `Content-Length` | 본문의 바이트 길이 |

> 📌 **`Host` 헤더는 HTTP/1.1에서 필수가 됐다.** 서버 하나에 도메인 여러 개를 올리는 **가상 호스팅** 때문이다. IP는 같으므로, 이 헤더가 없으면 서버는 어느 사이트를 달라는 건지 구분할 수 없다.

## 6. 버전의 진화

| 버전 | 핵심 변화 | 해결한 문제 |
|---|---|---|
| 1.0 | 헤더·버전·상태 정보 도입 | — |
| 1.1 | **Keep-Alive**(연결 재사용), Host 필수 | 매번 연결을 새로 맺는 비용 |
| 2.0 | **바이너리 프레이밍**, 멀티플렉싱 | 요청이 순서대로 줄 서는 문제 |
| 3.0 | **QUIC**(UDP 기반) | TCP 자체의 지연·재연결 비용 |

> ✏️ **정정** — 원본에 1.1의 킵얼라이브를 "한 번 연결 시 **데이터 교환 때까지만** 유지 이후 연결 끊기"라고 적었는데, 이러면 1.0과 다를 게 없어진다.
> Keep-Alive의 핵심은 **하나의 연결로 여러 번의 요청·응답을 연달아 처리** 하는 것이다. HTML 하나 받고 끊는 게 아니라, 그 안의 이미지·CSS·JS까지 **같은 연결로** 받아온 뒤 끊는다.

- **1.1의 한계** — 연결은 재사용하지만 요청은 **보낸 순서대로** 처리된다. 앞의 응답이 느리면 뒤가 전부 밀리는데, 이를 **HOL 블로킹(Head-of-Line Blocking)** 이라 한다.
- **2.0의 멀티플렉싱** — 메시지를 바이너리 프레임으로 잘게 쪼개 **하나의 연결에 뒤섞어 보낸다.** 순서에 묶이지 않으니 HOL 블로킹이 풀린다. 원본의 "텍스트를 바이너리로 변환 후 분할 전송"이 정확히 이 얘기다.

## 7. 정리

| 개념 | 한 줄 정의 |
|---|---|
| 메시지 구조 | 시작 라인 → 헤더 → 빈 줄 → 본문 |
| Stateless | 서버가 이전 요청을 기억하지 않음 |
| 멱등성 | 여러 번 보내도 결과가 같음 → 재시도 가능 |
| Keep-Alive | 연결 하나로 여러 요청·응답 처리 |
| HOL 블로킹 | 앞 응답이 밀리면 뒤가 전부 대기 |

## 🔁 셀프 체크

1. HTTP 메시지에서 **빈 줄 한 줄** 은 무슨 역할을 하는가?
2. 결제 요청이 응답 없이 끊겼다. 그대로 재시도해도 되는가? POST와 PUT으로 나눠 답하라.
3. HTTP/1.1의 Keep-Alive는 "연결을 언제까지" 유지하는가?

<details>
<summary>답</summary>

1. **헤더의 끝** 을 알리는 구분자. 서버는 이 줄을 보고 여기부터가 본문이라고 판단한다.
2. **PUT은 멱등이라 재시도해도 안전** 하지만, **POST는 멱등이 아니라 결제가 2건 생길 수 있다.** 그래서 실무에서는 멱등키(Idempotency-Key)를 붙여 POST를 멱등하게 만든다.
3. 요청 하나가 아니라 **여러 요청·응답을 처리할 동안** 유지한다. 페이지 하나를 그리는 데 필요한 이미지·CSS까지 같은 연결로 받고 나서 끊는다.

</details>
