## 1. 출발 — URL 입력

- `http://www.google.com` 입력 → DNS로 IP를 얻고 → **TCP 3-way 핸드셰이크** 로 연결
- 포트 : `http` 는 **80번**, `https` 는 **443번**
- 경로를 생략하면 서버가 **기본 파일** 을 대신 돌려줌 → 보통 `index.html`
  - 실제 주소는 `http://www.google.com/index.html`
- 요청 라인 형식 : `GET /index.html HTTP/1.1`

> ✏️ **정정 2건**
> 1. 원본에 `http://www.google.com.index.html` 로 적었는데, 도메인과 경로는 **점이 아니라 슬래시(`/`)** 로 구분한다 → `http://www.google.com/index.html`
> 2. 원본에 `GET/ index.html HTTP/1.1` 로 적었는데, 올바른 형식은 **`GET /index.html HTTP/1.1`** — 메서드·경로·버전을 **공백 하나** 로만 구분한다

<details>
<summary>✏️ 정정 — "HTTP → HTTPS 자동 변환"은 자동이 아니다</summary>

- 원본에 "HTTP → HTTPS로 자동 변환(80 → 443)"이라고 적었는데, **프로토콜이 알아서 바꿔주는 기능은 없다.**
- 실제로는 둘 중 하나가 동작한 것 :
  - **서버의 301 리다이렉트** — 80번으로 온 요청에 "443으로 다시 오라"고 응답
  - **HSTS** — 서버가 한 번 알려주면, 그 뒤로는 **브라우저가 요청을 보내기도 전에** 스스로 https로 바꿈
- 차이가 중요한 이유 : 301 방식은 **첫 요청이 평문으로 한 번 나가서** 중간자 공격에 노출된다. HSTS는 그 첫 요청조차 막는다.

</details>

## 2. 송신자 관점 — 계층을 내려가며 헤더 붙이기

| 계층 | 붙는 헤더 | 담기는 정보 |
|---|---|---|
| 전송 | TCP 헤더 → **세그먼트** | 출발지 포트, 목적지 포트(80) |
| 네트워크 | IP 헤더 → **패킷** | 송신자 IP, 수신자 IP |
| 데이터 링크 | 이더넷 헤더 → **프레임** | 송신자 MAC(내 PC), 수신자 MAC(**라우터**) |
| 물리 | — | 비트 → 전기 신호로 변환해 송출 |

- 포트 방향 정리
  - 요청 : 내 IP `:임시포트` → 서버 IP `:80`
  - 응답 : 서버 IP `:80` → 내 IP `:임시포트`

| 범위 | 이름 | 용도 |
|---|---|---|
| 0 ~ 1023 | 잘 알려진 포트 | HTTP 80, HTTPS 443 등 서버가 사용 |
| 1024 ~ 49151 | 등록된 포트 | 특정 애플리케이션에 배정 |
| 49152 ~ 65535 | 동적·임시 포트 | 클라이언트가 **매 연결마다 임시로** 사용 |

- 클라이언트 출발지 포트를 **임시 포트** 라고 부르는 이유 : 연결이 끝나면 반납되고 다음엔 다른 번호가 배정됨
  - 실제 범위는 OS마다 다름 (리눅스는 32768~60999가 기본)

> 📌 **수신자 MAC이 서버가 아니라 라우터인 이유** — MAC 주소는 **같은 네트워크 안에서만** 의미가 있다. 구글 서버는 내 네트워크 밖에 있으므로 MAC을 알 수도, 쓸 수도 없다. 그래서 "일단 밖으로 나가는 문", 즉 **기본 게이트웨이(라우터)의 MAC** 을 목적지로 적는다.

## 3. 장비 관점 — 스위치와 라우터를 지나며

```mermaid
flowchart LR
    PC["내 PC"] --> SA["스위치 A"] --> RA["라우터 A"] --> RB["라우터 B"] --> SB["스위치 B"] --> WS["웹 서버"]
```

### 3-1. 스위치 A

- 프레임을 받아 **MAC 주소 테이블** 을 보고 해당 포트로 내보냄
- 스위치는 **2계층 장비** — IP는 보지 않고 MAC만 보고 전달

> ✏️ **정정** — 원본에 "스위치는 MAC 주소를 **알아내기** 위한 용도"라고 적었는데, 역할이 조금 다르다.
> - 상대의 MAC 주소를 **알아내는 것** 은 **ARP** 프로토콜이다. "이 IP를 쓰는 사람 MAC 좀 알려줘"를 네트워크에 브로드캐스트해서 받아낸다.
> - **스위치** 는 이미 정해진 MAC 주소를 보고 **어느 포트로 내보낼지 결정(포워딩)** 하는 장비다. 학습한 MAC-포트 대응을 테이블로 갖고 있다.

### 3-2. 라우터 A — 여기서 주소가 바뀐다

1. 이더넷 헤더의 수신자 MAC이 자신과 같으면 → **이더넷 헤더를 벗김**
2. IP 헤더의 수신자 IP를 보고 **라우팅 테이블** 에서 다음 경로를 찾음
3. **NAT 수행** : 송신자 IP를 **사설 IP → 라우터의 공인 IP** 로 변경
4. 이더넷 헤더를 **새로 붙임**
   - 송신자 MAC = 라우터 A / 수신자 MAC = **다음 홉(라우터 B)**

> ✏️ **가장 중요한 정정** — 원본 마지막 줄에 "라우터를 만나면 **MAC 주소와 IP 주소를 바꿔 줘야 한다**"고 적었는데, 이건 절반만 맞다.
> - **MAC 주소는 홉마다 반드시 바뀐다.** 구간을 하나 건널 때마다 "바로 옆 장비"가 달라지기 때문.
> - **IP 주소는 원칙적으로 바뀌지 않는다.** 출발지와 목적지를 끝까지 유지해야 응답이 돌아올 수 있다.
> - IP가 바뀌는 것은 **NAT를 수행하는 경계 라우터에서만** 일어나는 예외다. 중간의 인터넷 라우터들은 IP를 그대로 두고 전달만 한다.
> - 한 줄로 : **MAC은 구간용(매번 교체), IP는 종단용(끝까지 유지), NAT만 예외.**

<details>
<summary>💡 NAT — 원본이 설명한 그 동작의 이름</summary>

원본의 "송신자 IP를 자신의 공인 IP로 변경", "그래서 라우터는 공인이랑 사설 IP를 가지고 있다"가 정확히 **NAT(Network Address Translation)** 다.

- **왜 필요한가** : IPv4 주소가 부족해서, 집·회사 안에서는 **사설 IP** (`192.168.x.x`, `10.x.x.x`)를 쓰고 밖으로 나갈 때만 **공인 IP 하나** 로 바꿔 쓴다.
- **어떻게 돌아오나** : 라우터가 **`사설IP:포트` ↔ `공인IP:포트`** 대응표를 기억해뒀다가, 응답이 오면 원래 기기로 되돌려준다. 포트까지 함께 변환하므로 정확히는 **NAPT(PAT)**.
- **부수 효과** : 밖에서 안으로 먼저 연결할 수 없어 **방화벽 역할** 도 하지만, 반대로 외부에서 접속시키려면 **포트 포워딩** 을 따로 걸어야 한다.

</details>

### 3-3. 라우터 B → 스위치 B → 웹 서버

- 라우터 B도 같은 절차 : 이더넷 헤더 확인·제거 → 라우팅 → **목적지 NAT** → 이더넷 헤더 재부착
  - 송신자 MAC = 라우터 B / 수신자 MAC = **웹 서버**
- 스위치 B가 MAC을 보고 웹 서버 포트로 전달 → 전기 신호로 도착

## 4. 수신자 관점 — 계층을 올라가며 헤더 벗기기

| 계층 | 확인하는 것 | 동작 |
|---|---|---|
| 물리 → 데이터 링크 | 수신자 MAC이 나인가 | 맞으면 이더넷 헤더 제거 |
| → 네트워크 | 수신자 IP가 나인가 | 맞으면 IP 헤더 제거 |
| → 전송 | 목적지 포트(80) | 해당 프로세스로 넘기고 TCP 헤더 제거 |
| → 응용 | HTTP 요청만 남음 | 웹 서버가 요청에 맞는 응답 생성 |

- 각 계층은 **자기 주소가 맞는지 확인 → 맞으면 자기 헤더만 벗김** → 이 반복이 역캡슐화

## 5. 정리

| 개념 | 한 줄 정의 |
|---|---|
| MAC vs IP | MAC은 **구간마다 교체**, IP는 **끝까지 유지** |
| ARP | IP로 상대의 MAC 주소를 알아내는 프로토콜 |
| NAT | 사설 IP ↔ 공인 IP 변환. **IP가 바뀌는 유일한 경우** |
| 기본 게이트웨이 | 네트워크 밖으로 나갈 때 첫 목적지 MAC |
| 임시 포트 | 클라이언트가 연결마다 임시로 쓰는 출발지 포트 |

<details>
<summary>답</summary>

1. MAC 주소는 **같은 네트워크 안에서만** 유효하다. 구글 서버는 내 네트워크 밖이라 MAC을 알 수도 쓸 수도 없으므로, 밖으로 나가는 문인 **기본 게이트웨이(라우터)의 MAC** 을 적는다.
2. **MAC은 홉마다 바뀌고 IP는 유지된다.** IP가 바뀌는 건 **NAT를 수행하는 경계 라우터** 에서뿐이고, 중간 라우터들은 IP를 그대로 두고 전달만 한다.
3. **NAT** 때문이다. 내부에서는 사설 IP를 쓰다가 밖으로 나갈 때 공인 IP로 바꿔야 하므로, 라우터가 양쪽 주소를 모두 가지고 경계에서 변환한다.

</details>

[장비관점]

- 웹서버에 데이터를 요청하기 위해서는 먼저 스위치 A를 거침
- 스위치는 MAC주소를 알아내기 위한 용도
- 근데 스위치도 웹 서버의 MAC주소를 모르니까 라우터 MAC을 수신자 MAC으로 변경
- 그리고 물리계층에서 이걸 전기신호로 바꿔서 라우터에게 전달

- 라우터가 데이터 링크의 수신자 MAC 주소를 자신의 것과 비교한 뒤 같으면 이더넷 헤더를 벗김
- 라우터가 라우팅 테이블에서 수신자의 IP 주소확인
  - 송신자 IP를 자신의 공인IP 주소로 변경
  - 그래서 라우터는 공인이랑 사설 IP를 가지고 있다
  - 핵심
    - 송신자의 MAC주소를 라우터 A 자신의 MAC주소로 변경
    - 수신자의 MAC 주소를 라우터 B의 MAC 주소로 변경
  - 이렇게 변경이 되면 다시 데이터 링크로 보냄 이때 이더넷 헤더를 다시 붙임
    - 그리고 라우터B로 전달
    - 즉 이더넷헤더의 MAC주소는 각각 다른 라우터의 주소가 됨
  - 그리고 라우터 B로 오면
    - 데이터 링크층에서 MAC 주소가 같으면 이더넷 헤더를 분리→ 네트워크 계층으로 보냄
    - 네트워크 계층에서는 수신자 IP 주소가 자신의 라우팅 테이블에 있는 지 확인
    - 문제는 송신자의 IP 주소가 라우터 B가 아니니까 문제가 생김
    - 그래서 헤더를 내부통신 할 수 있도록 라우터 B IP 주소로 변경
    - 그리고 데이터링크 계층에서 다시 이더넷 헤더를 결합 MAC 주소 변경
    - 송신자의 MAC 주소는 라우터 B의 주소로 변경 수신자의 MAC 주소는 웹서버 주소로 변경
    - 그리고 스위치 B로 전달 스위치 B는 다시 데이터 링크 계층에서 이더넷 헤더를 다시 결합
    - 그리고 전기신호를 거쳐서 웹서버에 전달
  - 정리
    - 송신자랑 수신자 사이 라우터를 중간에 만나게 되면 MAC주소와 IP주소를 바꿔 줘야한다

[수신자 관점]

- → 전송 계층
  - TCP 포트 번호 확인하고 TCP 헤더 분리
- → 응용 계층
  - 요청만 남아 있으니까 웹서버는 데이터에 맞는 걸 보여줌
